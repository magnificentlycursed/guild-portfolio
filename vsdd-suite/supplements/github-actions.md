# GitHub Actions Supplement

GitHub Actions is the suite's default CI/CD platform for projects hosted on [GitHub](https://github.com). Workflows live in `.github/workflows/*.yml` at the repository root; the per-project CI configuration (build / test / lint / security-scan / supply-chain-audit) lives in one workflow file per project so a failure isolates to the project that introduced it. This supplement covers GitHub Actions as a CI/CD platform: workflow shape, action SHA-pinning, secrets handling, permissions discipline, cost discipline, PR-template integration, and merge-gating completion checklists. The canonical reference is [the GitHub Actions documentation](https://docs.github.com/en/actions); this supplement does not restate the workflow syntax — it documents the dimensions to review when GitHub Actions is the chosen CI/CD platform. What this supplement is NOT: a tutorial on writing workflows, a guide to choosing GitHub Actions vs alternatives (GitLab CI, CircleCI, Jenkins — those are Solution Architect concerns at project scaffold time), or a substitute for the host-language supplement that owns the build/test commands ([Rust](rust.md), [Python](python.md), [JavaScript/TypeScript](javascript-typescript.md)).

**Authored:** [Review 86](../suite-development/review-log/2026-05-21-suite-review.md) (2026-05-21) — the portfolio's three Rust projects (`issue-tracker-cli`, `bookmark-cli-manual`, `bookmark-manager`) each ship a per-project GitHub Actions workflow, and there was no language-level supplement for GitHub Actions to apply during domain reviews. This supplement closes that gap. Companion artifact: [`.github/PULL_REQUEST_TEMPLATE.md`](../../.github/PULL_REQUEST_TEMPLATE.md) (the merge-gating PR template that references the canonical manual-test files instead of duplicating their content) + [`.github/workflows/pr-checklist.yml`](../../.github/workflows/pr-checklist.yml) (the workflow that gates merge on completion-checklist closure).

**Multi-domain authoring note:** the sections below were drafted with the relevant role-domain perspectives — Platform Engineer (PRIMARY — workflow shape, jobs/steps decomposition, runner selection, matrix builds, caching, artifact handling, reusable workflows, concurrency control, triggers + path filters), Security (action SHA-pinning, `permissions:` block discipline, secret handling, `pull_request_target` trap, third-party action vetting, Dependabot/Renovate for action updates, `GITHUB_TOKEN` scope), AI Engineer (CI cost discipline at scale — runner-minute budget, cache hit rate, matrix-shape token-economy analogue, re-run strategy), Technical Writer (workflow YAML readability, named-step discipline, run-output clarity, status-check labels matching the work they do), Documentation Reviewer (clone-and-follow fidelity for users replicating CI locally via [act](https://github.com/nektos/act) or [actionlint](https://github.com/rhysd/actionlint); workflow file as cold-readable documentation), Solution Owner (which CI behaviors are spec-promised vs incidental; required-vs-optional check declarations at branch-protection layer; scope discipline against CI-feature-creep), Quality Engineer (test discipline at CI — Red Gate-style failing-tests-actually-fail-the-build; coverage threshold enforcement), Performance Engineer (runner-time budget per workflow; cache effectiveness; long-compile-job mitigation). The supplement is forward-looking against the 2026 GitHub Actions ecosystem ([GHA runner image v3+](https://github.com/actions/runner-images); [actions/checkout@v4](https://github.com/actions/checkout) SHA-pinned; [Dependabot](https://github.com/dependabot) for action-version monitoring; [actionlint](https://github.com/rhysd/actionlint) as the dominant YAML+shell linter; [pull_request_target] caveats well-documented in CVE history).

**Scope of this supplement:** any `.github/workflows/*.yml` file in the repo, any composite or reusable action declaration (`.github/actions/*/action.yml`), and the merge-gate disciplines that GHA workflows enforce ([`.github/PULL_REQUEST_TEMPLATE.md`](../../.github/PULL_REQUEST_TEMPLATE.md), branch-protection required-check declarations, the per-PR completion-checklist verification at [`.github/workflows/pr-checklist.yml`](../../.github/workflows/pr-checklist.yml)). Out of scope: GitHub Actions Marketplace publishing (the suite consumes actions; it doesn't publish them); self-hosted runners (the portfolio's projects use GitHub-hosted runners only); enterprise GitHub Actions features (organization secrets, environment protection rules — applicable only at scale beyond the portfolio's reach).

## Baseline standards

- **Workflows live at `.github/workflows/*.yml`** — One workflow file per project (`bookmark-cli-manual.yml`, `issue-tracker-cli.yml`, etc.) so a failure isolates to the project that introduced it. A monorepo of unrelated projects sharing a single `ci.yml` is a finding — the failure-isolation discipline applies even at the portfolio level.
- **YAML syntax: UTF-8, LF line endings, no BOM, 2-space indent** — Per the [YAML supplement](yaml.md) baseline. Enforce via `.gitattributes` (`*.yml text eol=lf`).
- **One trailing newline at EOF** — POSIX text file convention; many YAML parsers tolerate missing trailing newline but the diff hygiene matters.
- **Triggers declared explicitly** — Each workflow's `on:` block names the triggers (`push`, `pull_request`, `schedule`, `workflow_dispatch`). A workflow with `on: [push, pull_request]` shorthand is acceptable for simple cases; complex cases use the long form with `branches:` / `paths:` filters per the next standard.
- **Path filters for per-project workflows** — A workflow scoped to one project under a monorepo uses `paths:` filters so unrelated changes don't trigger it. Example: `paths: ['vsdd-suite-reference-examples/bookmark-cli-manual/**', '.github/workflows/bookmark-cli-manual.yml']`. A workflow that runs on every push regardless of which directory changed wastes runner minutes + adds noise to status checks; that's a finding.
- **Action SHA-pinning at the version-tag tier** — Third-party actions (anything not in the `actions/` namespace) are pinned by full SHA, not by `@v1` / `@main` / `@master`. Tagged releases can be force-pushed; SHAs cannot. The pattern: `uses: dtolnay/rust-toolchain@3c5f7ea28cd621ae0bf5283f0e981fb97b8a7af9  # master at 2026-05-04`. The trailing comment names the human-readable version the SHA corresponds to so the pin is auditable. First-party actions (`actions/checkout@v4`) MAY use the version tag, but SHA-pin is the more conservative default.
- **`permissions:` block declared explicitly per workflow or per job** — The `GITHUB_TOKEN` defaults to overly-broad permissions; declare `permissions:` at the workflow or job level to limit to what's actually needed. A workflow that only runs `cargo test` needs `contents: read` and nothing else. A workflow that has no `permissions:` block inherits org defaults — that's a finding.
- **Secrets via `secrets.*` context, never echoed** — Secrets (API tokens, GitHub tokens with elevated scope, signing keys) are accessed via `${{ secrets.MY_SECRET }}` and are masked in runner output by GHA. Code that `echo "$MY_SECRET"`, prints the secret to a build artifact, or commits it back to the repo is a finding — even if the run output appears masked, the secret may leak through downstream logs or rerun-from-cache flows.
- **`pull_request_target` only when authorized** — `on: pull_request_target` runs with the BASE branch's secrets + write permissions, even when the PR is from a fork. This is the [most common GitHub Actions privilege-escalation vector](https://securitylab.github.com/research/github-actions-preventing-pwn-requests/). Use `pull_request` (which runs without secrets, in the PR's context) by default; use `pull_request_target` only with explicit operator sign-off + a corresponding `paths:` or `if:` filter limiting the trigger to changes that cannot smuggle malicious code.

## Platform Engineering

PRIMARY DOMAIN for GitHub Actions review — workflows are the operational deployment surface for every project.

- **One workflow per project under a monorepo** — Per the baseline. Name the workflow file after the project (`bookmark-cli-manual.yml`), set `name:` at the top of the workflow to a human-readable label, and scope triggers via `paths:` filters so unrelated changes don't fire the workflow.
- **Job decomposition: fmt / clippy / test / deny / audit as separate jobs** — A monolithic job that runs every check sequentially is harder to interpret when one fails (the failure mode collapses all downstream checks). Decomposing into named jobs (`fmt`, `clippy`, `test`, `deny`, `audit`) means a clippy failure shows as a single red check without obscuring whether tests would have passed. The cost is some duplication of `checkout` + `toolchain install` steps; the Rust-cache action and prompt-cache-equivalent (Swatinem/rust-cache) mitigate the cost. Per [Platform Engineer R1 F1](../../vsdd-suite-reference-examples/bookmark-cli-manual/vsdd-suite/review-log/2026-05-20-platform-engineer.md).
- **`runs-on:` declared explicitly per job** — `ubuntu-latest` is the canonical default for the portfolio's projects (the projects don't depend on macOS- or Windows-specific behavior at Layer 1; matrix-expand to those platforms is a Layer-2+ concern). Avoid `ubuntu-22.04` / `ubuntu-24.04` literal-version pins unless the project requires a specific image; `ubuntu-latest` rolls forward with the GitHub Actions team's testing.
- **Caching strategy declared explicitly** — Compilation-heavy languages (Rust, TypeScript, Java) benefit substantially from build-artifact caching. Use the language-canonical cache action: `Swatinem/rust-cache@<sha>` for Rust; `actions/setup-node@<sha>` with `cache: 'npm'` for Node.js; `actions/setup-python@<sha>` with `cache: 'pip'` for Python. The cache key includes the lockfile hash so a dependency change invalidates the cache; that's the discipline that prevents stale-cache-poisoning regressions.
- **Matrix builds when cross-platform / cross-version matters** — Use `strategy.matrix` to fan out a job across `os: [ubuntu-latest, macos-latest, windows-latest]` or `rust: [stable, beta, msrv]`. The matrix is cost: N jobs run in parallel; runner minutes multiply by N. Only use matrices when the cross-product is load-bearing — Layer 1 of a Unix-only CLI doesn't need a Windows matrix; a library intended for cross-platform use does.
- **Concurrency control for redundant runs** — A push of three commits in quick succession triggers three workflow runs; the first two are typically obsolete by the time they complete. Use `concurrency: { group: ..., cancel-in-progress: true }` at the workflow level to cancel obsolete runs. Pattern: `concurrency: { group: 'ci-${{ github.ref }}', cancel-in-progress: true }`. Save runner minutes + reduce status-check noise.
- **Reusable workflows / composite actions for shared shape** — If three project workflows have the same checkout + toolchain-install + cache shape, factor it into a composite action at `.github/actions/setup-rust/action.yml` and `uses: ./.github/actions/setup-rust` from each project workflow. The DRY benefit pays for itself once 3+ projects share the shape. For 1-2 projects, inline is fine.
- **Artifact upload for build outputs that need cross-job access** — Use `actions/upload-artifact@<sha>` + `actions/download-artifact@<sha>` to pass build outputs between jobs in the same workflow. Artifacts expire by default (90 days); explicit `retention-days: 30` shortens the window for non-load-bearing artifacts. Don't use artifacts as long-term storage — that's what releases are for.
- **MSRV / toolchain pinning consistent across `Cargo.toml`, `rust-toolchain.toml`, and the workflow** — For Rust projects: `Cargo.toml` declares `rust-version = "X.Y"` (the MSRV; consumer-visible); `rust-toolchain.toml` declares `channel = "X.Y"` (the contributor-visible toolchain); the workflow declares `toolchain: X.Y` in each `dtolnay/rust-toolchain` invocation (the CI-visible toolchain). All three should match (or the workflow toolchain may be newer if the project tests against multiple). A mismatch is a finding. Per the PR #38 fix for dtolnay/rust-toolchain's `rust-toolchain.toml` auto-discovery only working at repo root, not in subdirectory projects.

## Security

- **Action SHA-pinning, not version-tag** — Per the baseline. The pattern + the rationale matter equally — a reviewer should be able to look at any `uses:` line and answer "what version is this?" via the trailing comment, not by clicking through to GitHub. Named failure mode: `uses: actions/checkout@v4` is acceptable for first-party actions (GitHub's own); `uses: thirdparty/some-action@v1` is NOT acceptable — version tags can be force-pushed, SHAs cannot.
- **`permissions:` block at the most-restrictive granularity** — The default for workflows that don't declare `permissions:` is org-default-permissive (often `contents: write` + `pull-requests: write` + `issues: write` + others). Declare `permissions: { contents: read }` at the workflow level for read-only workflows (build/test/lint). Per-job `permissions:` overrides for jobs that need elevated scope (e.g., a job that posts a PR comment needs `pull-requests: write`).
- **Never echo secrets, never write to artifacts that could be public** — Build logs are visible to anyone with read access on the repo. A `echo "$MY_TOKEN"` to debug a failing job leaks the token, even if GHA masks it in the live log view — the masking can fail on string transformations (base64-encoded secrets, secret fragments substring-printed). Use `if: failure()` debug steps that read structured state, not secrets.
- **`pull_request_target` audit** — Every `pull_request_target` trigger requires (a) explicit operator sign-off in the workflow comments naming the security rationale, (b) a `paths:` or `if:` filter limiting the trigger to changes that can't introduce code execution, and (c) avoidance of `actions/checkout` against the PR's HEAD (which would let a fork PR run its own code with BASE secrets). A workflow that has `on: pull_request_target` AND `actions/checkout` against `github.event.pull_request.head.ref` is the canonical pwn-request shape — that's a finding regardless of intent.
- **Third-party action vetting** — Before adding a third-party action, audit its source: who maintains it; what permissions does it request; does its source repo show recent activity; does it have a Dependabot-managed dependency tree; is it SHA-pinned itself. A one-off third-party action by an inactive maintainer is a supply-chain risk; reach for first-party or well-maintained-community alternatives first.
- **Dependabot / Renovate for action version monitoring** — Configure `.github/dependabot.yml` to monitor GitHub Actions for security updates: `package-ecosystem: github-actions; directory: /; schedule: { interval: weekly }`. Dependabot opens PRs when an action has a newer SHA; the operator reviews + merges. Without monitoring, actions stagnate at SHAs with known CVEs.
- **`GITHUB_TOKEN` scope minimization at branch-protection level** — Branch protection rules can restrict which workflows can run + which permissions they have via `repository.settings.actions.workflow_permissions`. The recommended baseline: set the default workflow permissions to `contents: read` at the repository level; require explicit per-workflow `permissions:` blocks for any elevated need.

## AI Engineer

GitHub Actions runner-minute cost discipline is the CI analogue to the AI Engineer's token-economy discipline for cold-session adversarial review. The same per-finding-cost lens applies: a workflow that burns 30 runner-minutes per merge to surface defects a `pre-commit run --all-files` invocation would catch in 30 seconds is over-investment; a workflow that takes 90 seconds and misses regressions caught by `cargo clippy --all-targets -- -D warnings` is under-investment.

- **Runner-minute budget per merge** — Cap the per-merge runner-minute consumption at a calibrated band: ≤ 5 minutes for a Layer-1 single-Rust-CLI (the bookmark-cli-manual band); ≤ 10 minutes for a Layer-2+ multi-binary or matrix-built project; ≤ 30 minutes for a full production project with cross-platform matrix + integration tests + security scans + audit. A workflow that drifts outside its band triggers a pre-merge AI Engineer evaluation (per [`primers/3-review-session.md`](../primers/3-review-session.md) § Pre-cycle methodology check, extended to CI).
- **Cache hit rate as the runner-minute multiplier** — A 30-second `cargo build` from a warm cache vs a 3-minute cold compile is a 6x runner-minute swing. Effective caching (per Platform Engineer above) is the highest-leverage cost optimization. Audit cache hit rate periodically: the [Swatinem/rust-cache](https://github.com/Swatinem/rust-cache) action reports cache-hit/cache-miss in its step output; a per-merge cache miss is operative if the lockfile changed, but a per-merge cache miss when the lockfile didn't change is a misconfiguration finding.
- **Re-run strategy: re-run failed only, not re-run all** — The "Re-run all jobs" button in the GitHub Actions UI re-runs every job including those that passed; "Re-run failed jobs" re-runs only the failures. For a transient flake in one job, "Re-run failed jobs" preserves the cost discipline. Re-running all jobs to "be sure" is the over-investment pattern at the operator-action layer.
- **Matrix-shape token-economy analogue** — A 3x3 OS-by-version matrix runs 9 jobs in parallel. Each matrix combination consumes runner minutes; the discipline is to use matrices only when the cross-product carries information. A matrix that tests `ubuntu-latest x stable` and `ubuntu-latest x msrv` (2 jobs) captures most of the value of `(ubuntu, macos, windows) x (stable, beta, msrv)` (9 jobs) at 22% of the runner-minute cost.
- **Concurrency-cancel for obsolete runs** — Per Platform Engineer above. Cancel-in-progress for the same branch is a pure runner-minute saver — a push that supersedes the prior push's commit cancels the prior workflow + starts fresh.
- **CI cost-tally in the audit trail at capstone+ intent** — Per the [Cost-tally discipline](../suite-development/suite-development.md#per-review-entry-preamble-under-each--review-n--yyyy-mm-dd-hhmmz), multi-agent IAR cycle-closing entries include a `**Cost-tally:**` field naming agent-spawns + token consumption. The CI-analogue for capstone+ projects: each major workflow change (new job added; matrix expanded; new dependency installed) names the runner-minute delta in the audit trail. A workflow change that doubles runner minutes without naming the rationale is a finding.

## Technical Writer

- **Workflow `name:` matches the work the workflow does** — The workflow's `name:` is what appears in the GitHub Actions UI + status checks. A workflow named "CI" that runs only `cargo audit` is misleading; name it "Security audit" so a reader scanning the status checks understands what each check covers. The same applies to job + step names: `name: Format check` is clearer than `name: Step 3` or unset (defaults to the command).
- **Step `name:` for every non-trivial step** — Single-command steps with self-evident commands (e.g., `run: cargo fmt --check`) may omit `name:`. Multi-command steps + composite-action invocations + setup steps need a `name:`. The reader scanning a failed workflow's step list shouldn't have to read each `run:` block to understand what failed.
- **Comments on non-obvious choices** — A `concurrency: { group: 'ci-${{ github.ref }}', cancel-in-progress: true }` block + a one-line comment explaining the policy ("cancel obsolete runs from supersession pushes") makes the workflow cold-readable. A bare concurrency block is a forward-reference for the reader who hasn't memorized GHA's concurrency semantics.
- **Status-check labels match what they actually check** — A required-check named "Build" that actually runs build + lint + test conflates three concerns. Decompose into separate jobs (per Platform Engineer above) so each status check label names one check.
- **No magic numbers in the workflow** — A `timeout-minutes: 17` is a magic number; what's significant about 17? Either name the timeout meaningfully (`timeout-minutes: 10  # cap at 2x observed median to catch hangs`) or use the GHA default (360 minutes = 6 hours; the implicit-default-trap for runner-hour overruns).
- **The workflow file is documentation, not just configuration** — A new contributor reading the workflow should be able to understand both *what* the CI does AND *why* it does what it does. Magic numbers, unnamed steps, undocumented action invocations, and uncommented complex `if:` conditions all degrade the workflow as documentation.

## Documentation Reviewer

- **Workflow names match the badge labels in the README** — If `README.md` shows a `[![CI](https://github.com/.../ci.yml/badge.svg)](https://github.com/.../actions)` badge, the workflow file should be named `ci.yml` and have `name: CI` at the top. A README badge that points at a workflow whose actual name has changed (post-rename) becomes a 404; a Doc Reviewer Dim 4 (cross-reference resolution) finding.
- **Clone-and-follow fidelity: can a user replicate CI locally?** — The workflow's commands should be runnable locally (modulo runner-specific paths). A `run: ./scripts/special-build-script.sh` that exists only in CI runners (not committed to the repo) breaks the local-reproducibility test. Use [act](https://github.com/nektos/act) to test workflow execution locally; document the limitation when GHA-specific features (`secrets.*`, `services.*`, runner-installed tooling) prevent full local reproduction.
- **Status-check declarations align with branch-protection requirements** — The required status checks declared in the repo's branch protection rules should match the workflow's job names exactly (no `ci/build` vs `Build` mismatches that cause silent permissive-merge after a rename). A renamed job whose old name is still in the branch protection rules effectively disables that check — silent failure mode worth Dim-1 (clone-and-follow) attention.
- **Workflow file as cold-readable documentation** — The Documentation Reviewer cold-reader test applies: a contributor who has never read the workflow before should be able to follow it top-to-bottom and answer "what does this CI do?" + "what's gated on success?". Implicit-knowledge audit: terms like "MSRV", "lockfile", "cargo-deny" should be cross-referenced (link to the language supplement or the project's `Cargo.toml` for context) or expanded inline on first use.

## Solution Owner

- **CI behaviors are spec-promised when DESIGN.md / CHANGELOG / TODO.md names them** — `bookmark-cli-manual`'s [`DESIGN.md`](../../vsdd-suite-reference-examples/bookmark-cli-manual/DESIGN.md) § Constraints names "Rust 1.78+ MSRV"; the CI workflow's `toolchain: 1.95` in `dtolnay/rust-toolchain` is the enforcement. A CI workflow that runs `cargo audit` because the project's CHANGELOG promised "supply-chain audit at every merge" is spec-promised; a workflow that runs `cargo audit` because "it's a good idea" is incidental. The SO reviewer audits which CI behaviors are tied to spec promises + which are incidental.
- **Required vs optional checks declared in branch protection** — Branch protection rules name which checks block merge. A check that's run but not required is informational; required checks gate merge. The discipline: required checks correspond to spec-promised CI behaviors; informational checks are everything else. A workflow change that adds a new check without operator-decided required-vs-optional classification is a finding.
- **Scope discipline against CI-feature-creep** — A new third-party tool is added to CI ("we should also run X"); the cost is runner minutes + dependency surface + status-check noise; the benefit is one more layer of automated review. SO scope discipline asks: does the project's DESIGN.md or layer plan name this check? If no, the addition is scope creep — defer to a layer that names the discipline OR don't add it.
- **PR template + merge-gate completion checklist** — The repo's [`.github/PULL_REQUEST_TEMPLATE.md`](../../.github/PULL_REQUEST_TEMPLATE.md) is a SO-owned artifact. The completion checklist gates merge by convention; the [`.github/workflows/pr-checklist.yml`](../../.github/workflows/pr-checklist.yml) workflow gates merge mechanically. The PR template's checklist content corresponds to the SO scope-promised PR readiness criteria + the project's layer-gate criteria; the workflow's check ensures no unchecked boxes survive merge. A PR template that duplicates the `manual-tests/` folder content is a Documentation Reviewer Dim 4 finding (per the Review 84 retirement-of-redundant-navigation-surfaces precedent applied to PR template content).
- **PR draft findings resolve before PR finalization** — Spot-check items in the PR draft body ("[ ] grep -rn returns clean") are concrete verification tasks; they belong in the completion checklist, not as informal-prose checkboxes. The SO discipline: the PR draft's checklist names the verifiable conditions; each is executed; each is marked complete with evidence linked from the audit trail (commit SHA, log line, manual-test step closure); the merge-gate workflow blocks merge until every box is checked.

## Quality Engineer

- **Red Gate at CI: failing tests actually fail the build** — A workflow that runs `cargo test || true` swallows test failures and lets the build pass; the test discipline is broken. Verify: every test job's exit-non-zero must fail the workflow. Named failure mode: `continue-on-error: true` on a test step (allows the job to continue but doesn't fail the workflow); use sparingly + only for non-test informational steps.
- **Coverage threshold enforcement, when declared** — If DESIGN.md names a coverage threshold (e.g., "100% statement coverage on the storage module"), the CI workflow enforces it via the coverage tool's threshold flag (`cargo llvm-cov --fail-under-lines 100`); a soft-fail coverage report that's informational only doesn't enforce the threshold. A threshold declared in DESIGN.md but not enforced in CI is a QE finding routed to Phase 2a (test discipline).
- **Test reporting: structured output for failure triage** — `cargo test` produces JSON via `--message-format json`; the workflow can attach the JSON as an artifact + parse it for the structured failure list in a follow-up step. The discipline: a failed test job should produce enough output that a contributor reading only the workflow log can identify which test failed + why, without needing to re-run locally. Per the AI Engineer Dim 11 audit-trail machine-readability principle applied to CI artifacts.

## Performance Engineer

- **Workflow execution-time budget** — Each workflow should declare an execution-time budget (in a comment near `on:` or `name:`); a workflow that drifts past its budget is a finding. Bookmark-cli-manual's budget: ≤ 5 minutes per merge. Issue-tracker-cli's budget: ≤ 5 minutes per merge.
- **Cache effectiveness audit** — Periodically (per layer-gate close), check the cache hit rate for the cache-using actions. A consistent cache miss when the lockfile didn't change is a misconfiguration finding (often: the cache key includes a time-varying input).
- **Long-compile-job mitigation** — Rust compile times are the largest per-merge cost for Rust projects. Mitigations: incremental compilation via Swatinem/rust-cache; `--release` only when release-specific behavior is being tested (otherwise debug-mode tests run faster); parallelism via `cargo test -j N` matched to runner CPU count. Per [Performance Engineer R1 F7](../../vsdd-suite-reference-examples/bookmark-cli-manual/vsdd-suite/review-log/2026-05-20-performance-engineer.md) cost-discipline pattern.

## PR template + merge-gate integration

The [`.github/PULL_REQUEST_TEMPLATE.md`](../../.github/PULL_REQUEST_TEMPLATE.md) is part of the GitHub Actions surface — it's the human-authored side of the PR-validation discipline; the workflow-gated checks are the mechanical side. The pair (template + workflow) implements the merge-gate completion checklist.

- **Template references canonical manual-test files, NEVER duplicates their content** — `manual-tests/layer-N.md` and `manual-tests/install-verification.md` are the canonical manual-test contracts per [Review 74 manual-test split convention](../suite-development/review-log/2026-05-20-suite-review.md#review-74--2026-05-20-1230z). The PR template's test plan references them (`[ ] Manual test plan for layer N executed (see manual-tests/layer-N.md); attach the closure note`); it does NOT re-list the test steps. Duplication is a Documentation Reviewer Dim 4 finding + a maintenance-cost drag (the manual-test plan changes; the PR template's copy drifts).
- **PR draft spot-checks → completion-checklist items, NOT informal-prose checkboxes** — A PR draft's `## Test plan` section that says "[ ] Spot-check: grep returns clean" is naming a verification task; the task belongs in the completion checklist where it's gated by the merge workflow. The discipline: every verifiable condition in the PR description is a completion-checklist item; every item has a verification step (a command, a manual-test reference, a CI status); every item is ticked with evidence linked from the audit trail before merge.
- **Completion checklist gates merge mechanically via `pr-checklist.yml` workflow** — The workflow at [`.github/workflows/pr-checklist.yml`](../../.github/workflows/pr-checklist.yml) parses the PR body on every `pull_request` event, identifies the `## Completion checklist` section, fails the run if any `- [ ]` items remain unchecked. Branch protection rules require the `PR completion checklist` status check to pass before merge. The pair (workflow + branch-protection rule) closes the operator-side compliance gap — the operator can't merge a PR with unchecked completion-checklist items even by mistake.
- **The template's checklist matches the suite's layer-gate criteria + the project's DESIGN.md scope** — A learning-exercise project's completion checklist is shorter than a capstone project's. The template ships a generic baseline; per-project layer-gate criteria override or extend it. Per the [SO domain](../domains/role/SOLUTION-OWNER-REVIEW.md) scope discipline, the per-project extension is the SO's authoring responsibility.

## Anti-patterns

- **"Action @v1 is fine"** — Version-tag pinning instead of SHA-pinning. Tag force-pushes are a known supply-chain risk. Always SHA-pin third-party actions; first-party (`actions/`) actions MAY use version tags but SHA-pin is the conservative default.
- **"Inherit org-default permissions"** — Missing `permissions:` block. Inherits whatever the org-default is (often overly permissive). Declare `permissions:` explicitly at workflow or job level.
- **"`pull_request_target` runs PR code with secrets"** — `on: pull_request_target` + `actions/checkout` of PR HEAD is the canonical pwn-request shape. Don't.
- **"Re-run all jobs to be sure"** — Re-running all jobs (including passed) wastes runner minutes when only one job flaked. Use "Re-run failed jobs" instead.
- **"The workflow is just configuration; comments aren't needed"** — A workflow with no `name:` fields, no comments, and magic-number timeouts is unreadable cold. Treat the workflow as documentation; comment non-obvious choices; name every non-trivial step.
- **"The PR template's test plan is exhaustive"** — A PR template that duplicates the `manual-tests/` folder content drifts from the canonical source. The template references; it doesn't duplicate.
- **"Required status checks updated whenever a job is renamed"** — Branch protection's required-check list uses string-match on job names; a renamed job whose old name is still in the required-check list silently disables the check. After any job rename, audit the branch protection rules.
- **"`if: failure()` debug step that prints `env`"** — A debug step that dumps environment variables on failure leaks secrets if any secret was exposed via `env:` in a prior step. Use structured debug output that names what state to check, not what state to print.
- **"Cache key includes timestamps"** — A cache key with a time-varying input (`${{ github.run_id }}`, `${{ now() }}`) busts the cache on every run, defeating the purpose. Cache keys should be deterministic against the inputs they're caching for.
- **"30+ minute workflow"** — Without a declared time budget + a corresponding `timeout-minutes:` cap, workflows can run for the GHA default of 360 minutes when they hang. Declare a budget; cap timeouts; alert on overruns.
- **"PR draft findings ignored at merge"** — Spot-check items in a PR draft ("[ ] grep returns clean") that are never executed before merge. The completion-checklist + merge-gate workflow closes this gap; the discipline is to use them.

## Three-audience lens

GitHub Actions workflows + the PR template + the merge-gate completion checklist serve all three audiences per the [Three-audience design principle](../suite-development/suite-development.md#three-audience-design-principle-review-80-finding-3):

- **Suite developers** (contributors extending the suite's CI patterns) read the workflows to understand which CI behaviors the suite teaches as canonical + how to extend them for new projects. The supplement teaches the pattern; the per-project workflows demonstrate it.
- **Suite users** (project teams applying VSDD with GitHub Actions) read the workflows to understand which CI checks gate their merges + what each check enforces. The PR template's completion checklist names the human-side discipline; the workflow's checks name the mechanical side.
- **AI agents** (parallel cold-session reviewers + main-session orchestrators) read the workflows to understand which build/test/lint commands the project commits to + which CI state evidence the project's audit trail can reference. The workflow file's structured shape (jobs, steps, status checks) is the machine-readable surface.

The companion review dimensions per audience map cleanly to the workflow surface: SO scopes which CI behaviors are spec-promised (suite-developer audience); Documentation Reviewer audits clone-and-follow fidelity of the workflow YAML (suite-user audience); AI Engineer audits the runner-minute cost-discipline per merge (AI-agent audience equivalent — the cost-budget is the same shape as the per-finding token cost); TW audits the workflow YAML for cold-reader readability (cross-audience).
