# YAML Language Supplement

YAML is the suite's standard configuration language: the suite's own [`.pre-commit-config.yaml`](../hooks/) wires every hook gate; future CI workflow files (GitHub Actions, GitLab CI), container manifests (`docker-compose.yaml`, Kubernetes manifests), and per-tool config files (`mkdocs.yml`, `.yamllint`, `pyproject.toml`'s YAML siblings) all share the same syntax and the same failure modes. This supplement covers YAML as a config language for VSDD projects: schema design, validation, security posture, tooling, and operational discipline. The canonical reference is [the YAML 1.2 spec](https://yaml.org/spec/1.2.2/); this supplement does not restate the grammar — it documents the dimensions to apply when YAML is the chosen format. What this supplement is NOT: a tutorial on writing YAML, a guide to choosing YAML vs JSON vs TOML at architecture time (that's a [Solution Architect](../domains/role/SOLUTION-ARCHITECT-REVIEW.md) concern handled at project scaffold), or a substitute for the host-language supplement that owns the parser code ([Python](python.md), [Rust](rust.md), [JavaScript/TypeScript](javascript-typescript.md), [Bash](bash.md)).

**Authored:** Review 80 (2026-05-20) — companion to the [JSON supplement](json.md) (authored the same review). The suite uses YAML pervasively for the pre-commit hook configuration but had no language-level review dimensions for it. This supplement closes that gap. The companion artifact is the dimension set itself: when a domain review encounters YAML-defined artifacts, the reviewer applies the relevant section below in addition to the standard domain dimensions.

**Multi-domain authoring note:** the sections below were drafted with the relevant role-domain perspectives — [Platform Engineer](../domains/role/PLATFORM-ENGINEER-REVIEW.md) (PRIMARY — pre-commit configs, CI workflows, container manifests, tool-version pinning), [Quality Engineer](../domains/role/QUALITY-ENGINEER-REVIEW.md) (lint + schema validation, dry-run before merge), [Security](../domains/role/SECURITY-REVIEW.md) (`yaml.safe_load`, billion-laughs DoS, secret scanning), [Solution Architect](../domains/role/SOLUTION-ARCHITECT-REVIEW.md) (config schema design, layered config, anchor/alias tradeoffs), [Data Engineer](../domains/role/DATA-ENGINEER-REVIEW.md) (Airflow / dbt / Kubernetes manifests, schema evolution), [Technical Writer](../domains/role/TECHNICAL-WRITER-REVIEW.md) (self-documenting keys, comment discipline), [Localization](../domains/role/LOCALIZATION-REVIEW.md) (Rails-i18n-style translation files, plural-key conventions). The supplement is forward-looking against the 2026 YAML ecosystem ([YAML 1.2.2](https://yaml.org/spec/1.2.2/) as the canonical spec; [yamllint](https://yamllint.readthedocs.io/) for style + schema; [yamale](https://github.com/23andMe/Yamale) and [JSON Schema via check-jsonschema](https://github.com/python-jsonschema/check-jsonschema) for validation; [PyYAML](https://pyyaml.org/) 6.0+ as the most common Python parser).

**Scope of this supplement:** any `.yaml` or `.yml` file in the repo, any YAML payload produced or consumed by project code, and any YAML-dialect configuration declared by tools the suite uses. Out of scope: JSON (see [json.md](json.md)), TOML, INI, XML — adjacent configuration formats each warrant their own supplement if the suite ever ships substantial artifacts in them.

## Baseline standards

- **[YAML 1.2.2](https://yaml.org/spec/1.2.2/) as the canonical spec.** YAML 1.1 (still the default for many older parsers, including PyYAML through 5.x) has incompatible boolean parsing — `yes`, `no`, `on`, `off`, `y`, `n` are all booleans in 1.1, plain strings in 1.2. The 1.1 → 1.2 difference is the source of an entire class of silent config bugs (see Anti-patterns below). New projects MUST target 1.2; legacy projects that depend on a 1.1 parser SHOULD document the dependency explicitly.
- **2-space indentation, never tabs.** YAML's indentation is semantically significant. Tabs are forbidden by the spec for indentation (YAML 1.2 §6.1) — most parsers reject them outright; some accept them as content. 2 spaces is the de facto community convention (matched by [Prettier](https://prettier.io/), [yamllint](https://yamllint.readthedocs.io/) defaults, and every major YAML-emitting tool). 4-space indent is acceptable for the project but uncommon; mixing 2 and 4 within one document is a finding.
- **UTF-8 encoding, no BOM.** YAML 1.2 §5.2 specifies UTF-8 / UTF-16 / UTF-32 encodings; UTF-8 is the universal default. A leading UTF-8 BOM is technically permitted by the spec but many tools (kubectl, GitHub Actions, pre-commit) reject it. Save files as UTF-8 without BOM. Detector: `file file.yaml` reports `UTF-8 Unicode text` (clean) vs `UTF-8 Unicode (with BOM) text` (defect).
- **LF line endings.** Unix line endings (`\n`) only. CRLF (`\r\n`) renders identically to most viewers but produces noise in diffs and breaks some YAML parsers' multi-line string handling. Enforce via `.gitattributes` (`*.yaml text eol=lf`, `*.yml text eol=lf`) and the pre-commit `end-of-file-fixer` hook.
- **One trailing newline.** Like all text files, YAML ends with a single trailing newline. POSIX defines a text file as ending in `\n`; some YAML parsers warn on missing trailing newline; many emit-then-parse round-trip tools normalize to include one.
- **No trailing whitespace.** Trailing whitespace at end of lines is invisible noise; some block-scalar styles (`|`, `>`) interact with trailing whitespace in ways that are easy to get wrong. Strip via pre-commit `trailing-whitespace` hook.
- **Quoting policy — plain scalars by default.** YAML allows three string forms: plain (`foo: bar`), single-quoted (`foo: 'bar'`), double-quoted (`foo: "bar"`). The policy: prefer plain scalars when the value contains no special characters AND isn't one of YAML's "magic" strings (booleans, nulls, numbers). Single-quote when the value contains characters that would otherwise be interpreted (leading `*`, `&`, `!`, `|`, `>`, `%`, `@`, `` ` ``, `#`; trailing `:`; embedded `: `). Double-quote when the value needs escape sequences (`\n`, `\t`, `é`). The wrong choice (e.g., double-quoting a value with a `\` in it that wasn't meant as an escape) silently changes meaning.
- **Explicit `null` instead of empty values.** YAML maps an empty scalar to `null` by default — `foo:` is identical to `foo: null` is identical to `foo: ~`. The empty form is ambiguous to readers (was this intentional or unfinished?); explicit `null` documents the intent. Style preference: write `null` (more readable than `~`).
- **Document marker `---` only when multi-document.** A single-document YAML file does not require the leading `---` marker. Some style guides recommend it for explicitness; the suite convention is to omit `---` in single-document files and require it as a separator in multi-document files (e.g., Kubernetes manifests bundling Deployment + Service + ConfigMap). Mixing styles within a project is a finding.
- **`.yaml` vs `.yml` — pick one.** Both extensions are universally accepted. `.yaml` is the spec-recommended form (per [yaml.org](https://yaml.org/faq.html)); `.yml` is the Windows-legacy 3-char-extension form, common in older tools. The suite convention: `.yaml` for new files; preserve `.yml` only when an external tool (Docker Compose's `docker-compose.yml`, GitHub Actions' `.github/workflows/*.yml`) demands it.

## Platform Engineer

PRIMARY DOMAIN for YAML review — pre-commit hooks, CI workflows, and container manifests are the load-bearing YAML artifacts.

- **Pre-commit configuration discipline.** Is `.pre-commit-config.yaml` present and wired into CI? Are hook `rev:` fields pinned to specific tags or SHAs (`rev: v5.0.0`) rather than floating refs (`rev: main`, `rev: HEAD`)? A floating `rev:` means each contributor's environment installs whatever's current on the upstream's default branch — silent drift between local and CI. The pre-commit framework's [autoupdate](https://pre-commit.com/#pre-commit-autoupdate) command refreshes pins explicitly; floating refs sidestep the review step. The suite's own [`.pre-commit-config.yaml`](../hooks/) is the worked example — every `rev:` is a concrete version tag.
- **CI workflow YAML pinning.** In [GitHub Actions](https://docs.github.com/en/actions) workflow files, are `uses:` references pinned to specific tags or commit SHAs (`uses: actions/checkout@v4` or `uses: actions/checkout@a5ac7e51b41094c92402da3b24376905380afc29`) rather than floating branches (`uses: actions/checkout@main`)? Floating refs are a supply-chain attack vector: an upstream compromise propagates to every consumer the next time the workflow runs. The SHA-pinned form is the strongest defense (immutable); the tag-pinned form is a workable middle ground (tags can be moved but the practice is rare and noticed).
- **Workflow-trigger schema correctness.** GitHub Actions' `on:` key is the workflow trigger; YAML 1.1 parsers can mis-interpret bare `on:` as a boolean `True` rather than the string key `"on"`. Workarounds: quote the key (`"on":`) for paranoid robustness, or trust that GitHub's parser is YAML-1.2 compliant (it is, in 2026). This trap recurs in other contexts (`yes:`, `no:` as keys) — see Anti-patterns.
- **Container manifest review.** For `docker-compose.yaml` and Kubernetes manifests, review the manifest's `image:` references for tag discipline (`image: postgres:16.2` good; `image: postgres:latest` bad — non-reproducible). Review resource limits (`cpu:`, `memory:`) for presence — manifests without limits can OOM the host. Review volume mounts for accidental host-path exposure. Review `privileged: true` and `securityContext:` for least-privilege violations. The YAML structure encodes operational decisions that the platform engineer is the right reviewer for.
- **Tool-version pinning in tool-config YAML.** When a YAML config file pins tool versions (e.g., `.tool-versions` for asdf, `.nvmrc` for Node, `python-version:` in workflow inputs), is the pinned version specific (`3.12.4`) rather than implicit (`3.12`, `latest`)? Same discipline as elsewhere in the suite — floating versions mean "the build broke and we don't know what changed."
- **Multi-environment config — `dev` / `staging` / `prod` consistency.** When the project has per-environment YAML configs (`config.dev.yaml`, `config.prod.yaml`), is the schema identical across them? A key present in `config.dev.yaml` but absent from `config.prod.yaml` is a deployment-time surprise. The standard pattern: a `config.base.yaml` with shared defaults, per-environment override files that ONLY set values that differ. Validate every environment's merged config against the same schema.
- **`.editorconfig` for YAML conventions.** Is `.editorconfig` in the repo with rules for `.yaml` / `.yml` files (`indent_style = space`, `indent_size = 2`, `end_of_line = lf`, `charset = utf-8`, `insert_final_newline = true`, `trim_trailing_whitespace = true`)? Editors honor `.editorconfig` automatically; the alternative is convention drift across contributors.
- **CI tool versions pinned.** `yamllint`, `prettier`, `check-jsonschema`, `yamale` versions pinned in CI workflow files. A floating tool version means "the build broke and we don't know what changed." Same discipline as other languages' tooling.

## Quality Engineer

- **[yamllint](https://yamllint.readthedocs.io/) as the style + structural gate.** Is `yamllint` run as a pre-commit hook AND in CI? `yamllint` catches the bulk of YAML style issues: indentation inconsistencies, trailing whitespace, line-length excesses, unsafe boolean values, duplicate keys, anchor/alias errors. Treat yamllint warnings as build failures (`yamllint --strict` is the recommended mode). The `.yamllint` config file documents the project's chosen ruleset.
- **Schema validation with [yamale](https://github.com/23andMe/Yamale) or [check-jsonschema](https://github.com/python-jsonschema/check-jsonschema).** Is every project-owned YAML document validated against a schema before use? `yamale` uses a YAML-shaped schema dialect (concise, readable); `check-jsonschema` validates YAML against a JSON Schema (re-uses the broader [JSON Schema](https://json-schema.org/) tooling ecosystem — see [json.md](json.md)). The choice is project-level; the discipline is mandatory for any YAML that crosses a trust boundary or that consumer code accesses by key path.
- **CI-config dry-run before merge.** For CI workflow YAML and container manifest YAML, is there a dry-run gate that catches schema errors before the workflow runs? Examples: [`actionlint`](https://github.com/rhysd/actionlint) for GitHub Actions workflow YAML (catches expression-syntax errors, missing-action errors, type mismatches in `inputs:`); `kubectl apply --dry-run=client -f manifest.yaml` for Kubernetes manifests; `docker compose config` for Compose files. A workflow YAML that's only validated by GitHub Actions itself fails on the PR — a workflow YAML validated by `actionlint` in pre-commit fails before the PR opens.
- **Schema-document tests.** The schema itself is testable. Author positive examples (documents that MUST validate) and negative examples (documents that MUST fail validation with named error paths) and run them in CI. A schema authored without negative tests over-permits silently — it's "correct" for the example documents and accepts garbage for everything else.
- **Round-trip serialization tests.** For every parse/emit pair the project owns, is there a test that loads a known document, re-emits it, and asserts equality (modulo whitespace, comment placement, and quoting style)? YAML's parse-emit cycle is famously lossy (comments are typically discarded; quoting styles are reformatted; anchor/alias relationships may flatten). Tests should assert on the canonical-normalized form, not byte-equality.
- **Coverage of multi-document files.** For YAML files containing multiple documents (`---` separators), tests should exercise each document, not just the first. Named failure mode: a Kubernetes manifest with Deployment + Service + ConfigMap where the consumer test only validates the Deployment block.

## Security

- **`yaml.load` is RCE on untrusted input — use `yaml.safe_load`.** [PyYAML](https://pyyaml.org/)'s `yaml.load(data)` (without a Loader argument, or with `Loader=Loader`) instantiates arbitrary Python objects, including ones that execute code on instantiation. This is functionally identical to `pickle.load` on untrusted input — remote code execution. PyYAML 6.0+ requires an explicit Loader argument to `yaml.load`, mitigating the worst form of the trap, but legacy code in the wild still uses the unsafe form. The rule: `yaml.safe_load(data)` for any data that crosses a trust boundary; reserve `yaml.load(data, Loader=FullLoader)` for trusted-source-only data and document the trust assumption inline. Named worked attack: a YAML file containing `!!python/object/apply:os.system ["rm -rf ~"]` — `yaml.load` executes the `os.system` call during deserialization.
- **Billion-laughs DoS via YAML anchors.** YAML's anchor (`&`) and alias (`*`) mechanism allows one node to reference another, enabling reuse. A malicious document chains aliases to produce exponential expansion: `a: &a [1, 1]; b: &b [*a, *a]; c: &c [*b, *b]; ...` — each level doubles the size. A document under 1 KB can expand to gigabytes when parsed. Defense: use parsers with anchor-expansion limits (PyYAML's `safe_load` is the default-safe path for Python; `yaml.CSafeLoader` if available is faster + still safe); cap input bytes before parsing; reject documents whose anchor count exceeds a sensible threshold.
- **Secret scanning in YAML configs.** YAML config files are a common accidental commit-point for secrets (API keys, database URLs, JWT signing keys). Are pre-commit hooks scanning YAML for secret patterns ([detect-secrets](https://github.com/Yelp/detect-secrets), [gitleaks](https://github.com/gitleaks/gitleaks), [trufflehog](https://github.com/trufflesecurity/trufflehog))? Named pattern: a `config.yaml` with `database_url: postgres://user:hunter2@host/db` committed and pushed before review. The pre-commit gate catches this BEFORE the secret hits the remote.
- **Secrets out-of-band — never in committed YAML.** Even with secret-scanning gates, the discipline is: secrets live in environment variables, a secrets manager (AWS Secrets Manager, GCP Secret Manager, HashiCorp Vault), or `.env` files (gitignored). The YAML config references the secret by name (`database_url: ${DATABASE_URL}`) and the runtime resolves it. The committed YAML never contains the secret value.
- **Environment-variable substitution discipline.** When the YAML uses `${VAR}` substitution, is the substitution done by a single well-known mechanism (Docker Compose, kubectl with `envsubst`, the application's own loader) rather than multiple competing ones? Mixed mechanisms (some `${VAR}` interpreted by Docker Compose, others by the application) produce surprising results when one mechanism's substitution rules differ from another's.
- **Untrusted YAML — size limit.** Cap the bytes accepted at the trust boundary. A 10-MB YAML config is suspicious for most application use cases; a 10-GB one is an attack. The cap applies BEFORE parsing — never let an unbounded parse run on attacker-controlled bytes.
- **`!!python/...` and other type tags.** YAML's type-tag mechanism (`!!`) allows documents to declare types beyond the core (string, int, float, bool, null, list, map). Some libraries (PyYAML, libyaml-binding) support language-specific tags (`!!python/object`, `!!python/tuple`) that instantiate arbitrary types — the RCE surface above. The safe-loader paths reject these tags by default. Any project-specific type tag (`!Vault`, `!Include`) is a custom parser surface — review the parser code for the same RCE risks.

## Solution Architect

- **Config schema design upfront.** Before writing the first YAML config, sketch the schema: what are the top-level keys, what are their types, what are the nested shapes, what's optional vs required? A YAML document authored ad-hoc and consumed by code that drifts to match it is a maintenance debt that compounds. Express the schema in JSON Schema or yamale schema syntax — the act of writing the schema surfaces design questions the prose can hide.
- **Layered config — defaults + env-specific overrides + secrets-out-of-band.** The standard pattern for application configuration: a `defaults.yaml` (committed, hardcoded sensible defaults) + a per-environment override file (`dev.yaml`, `prod.yaml`, committed) + an environment-variable layer for secrets (not committed) + a CLI-flag override layer (highest precedence, runtime-only). The layering documents the precedence; a flat single-file config conflates all four concerns. Schema validation should validate the merged result, not each layer independently.
- **Environment-variable substitution patterns.** Three common patterns: (a) `${VAR}` interpolated at config-load time by the application (most flexible; the loader resolves); (b) `${VAR:-default}` Bash-style with fallback values (Docker Compose convention); (c) `!ENV ${VAR}` custom type tag (requires a project-specific loader). Pick one per project; document it in the schema README. Mixed conventions in one project are a finding.
- **YAML anchor + alias use vs. duplication tradeoffs.** Anchors (`&name`) + aliases (`*name`) let one block reference another, reducing duplication. The tradeoff: anchors help when the reused block is genuinely shared (changes propagate); anchors hurt when the reused block is "accidentally similar" (one site needs to diverge and the anchor blocks the change). Heuristic: use anchors for true shared configuration (a database connection block referenced by multiple service definitions); avoid anchors for similar-looking-but-independently-evolving config blocks. Aggressive anchor use also degrades readability — a reader following `*db_config` has to scroll back to find the definition.
- **Nesting depth limit.** Keep nesting to 4 levels or fewer. A 7-level-deep YAML document is unreadable, painful to address by path (`a.b.c.d.e.f.g`), and indicates schema-design failure. When the data wants more depth, the schema wants a redesign — usually splitting deeply-nested structure into separate documents or flattening to a record-per-entity model.
- **Reference vs. embedding (same as JSON).** When the same sub-document appears in multiple places, prefer reference-by-ID over duplication. YAML anchors are one mechanism; explicit ID-based references (a top-level `databases:` map keyed by name, referenced from services as `database: postgres-main`) are another. The reference form keeps consistency by construction.
- **Schema versioning strategy.** Three patterns: (a) a top-level `version: "1.0.0"` field, consumers branch on version; (b) the schema file's URL embedded as a comment header (`# schema: https://example.com/schema/v1.json`); (c) implicit versioning by filename or location. Pattern (a) is the most common for persisted config files; pattern (b) leverages JSON Schema's `$schema` convention via comment for YAML.
- **Backward-compatible evolution.** Adding an optional key with a sensible default is backward-compatible. Renaming a key, changing a key's type, or making an optional key required is breaking. Document breaking changes in CHANGELOG and increment the schema version. Named failure mode: a key renamed from `databaseUrl` to `database_url` "to match the new convention" breaks every consumer that didn't update simultaneously.

## Data Engineer

- **YAML for data pipeline configs.** YAML is the dominant config format for data pipeline tools: [Apache Airflow](https://airflow.apache.org/) (YAML-defined DAGs via the Airflow CLI's serialization layer), [dbt](https://www.getdbt.com/) (`dbt_project.yml`, model `schema.yml` files), [Dagster](https://dagster.io/) (`dagster.yaml`, asset definitions). Kubernetes manifests are also YAML-defined data infrastructure when the pipeline runs on Kubernetes. The Data Engineer reviewer applies the YAML supplement when the pipeline's config files are in scope.
- **Schema evolution in long-lived configs.** Data pipeline YAML configs (especially dbt's `schema.yml` files documenting table/column metadata) evolve continuously as the underlying data evolves. Schema-evolution patterns from [json.md](json.md) apply identically: optional keys with defaults are backward-compatible; renames are breaking; the CHANGELOG and a per-file schema version document the evolution. Named pattern: a dbt `schema.yml` that adds a new column documentation entry is additive; one that renames an existing column entry (without renaming the underlying database column) is documentation drift.
- **Kubernetes manifest schema discipline.** Kubernetes manifests are versioned by `apiVersion:` — `apps/v1`, `networking.k8s.io/v1`, etc. A manifest using a deprecated apiVersion (e.g., `extensions/v1beta1` for Ingress) fails on cluster upgrade. Periodic review against [the Kubernetes deprecation guide](https://kubernetes.io/docs/reference/using-api/deprecation-guide/) is the data engineer's responsibility for projects that ship Kubernetes manifests.
- **Per-tool YAML dialect awareness.** Tools layer dialects on top of base YAML: GitHub Actions adds `${{ }}` expression syntax (NOT base YAML); Helm adds Go-template syntax (`{{ .Values.x }}`); Ansible adds Jinja2 (`{{ var }}`). The base YAML parser doesn't understand these dialects — they're interpreted by the tool AFTER YAML parsing. The implication: yamllint can validate the YAML structure but can't validate the dialect-specific content; the tool-specific linter is the right gate (actionlint for Actions, `helm lint` for Helm, `ansible-lint` for Ansible).
- **CSV / JSON / YAML format choice by workload.** YAML for human-edited configuration (Airflow connection definitions, dbt project config). JSON for machine-to-machine data interchange (API payloads). CSV / [JSON Lines](https://jsonlines.org/) / [Parquet](https://parquet.apache.org/) for tabular data at scale. A 10-MB YAML data file is the wrong format — YAML's parsing cost and verbosity are wrong for tabular data; switch to Parquet (analytical) or JSONL (streaming).
- **Don't store data in YAML — store config in YAML.** The boundary: YAML files describe HOW the pipeline runs (config), not WHAT the pipeline processes (data). A YAML file with 10,000 rows of user records is config-format misuse; the data belongs in a database or columnar file. The line is fuzzy at small scales (a 50-row lookup table in YAML is fine) but firm at large scales.

## Technical Writer

- **YAML keys self-document the config.** Without comments, key names carry the entire weight of self-description. `connection_timeout_seconds` is better than `timeout`; `max_concurrent_workers` is better than `workers`; `retry_on_5xx_responses` is better than `retry`. The terseness savings (a few bytes per key) are negligible compared to the readability cost. Repeated keys compress well — YAML's verbosity is a gzip's win.
- **Comments are first-class — use them.** Unlike JSON, YAML has native comment support (`# comment`). Use them. The standard pattern: a header comment block at the top of the file describing the file's purpose and schema location; per-section comments explaining the WHY of non-obvious decisions; per-key comments for values whose meaning isn't carried by the key name alone. The anti-pattern: comments that restate the key (`# the timeout in seconds` next to `timeout_seconds: 30` adds nothing).
- **Comments explain WHY, not WHAT.** The key already says WHAT. The comment is the place for WHY this value, this decision, this tradeoff. `# Lower than the upstream default of 60 because we observed long-tail timeouts blocking the worker pool` is useful; `# the timeout` is not.
- **Key ordering matters for readability.** YAML preserves key order in most parsers (PyYAML 6.0+, ruamel.yaml). Group related keys; place high-level keys (`name`, `version`, `description`) before low-level keys (`internals`, `debug`); place required keys before optional ones. The reader scans top-to-bottom; ordering for the reader's benefit is a small effort with a large payoff.
- **Schema documentation lives next to the schema.** Companion documentation patterns: a sibling Markdown file (`schema.md` next to `schema.yaml`); a `description:` field in the JSON Schema or yamale schema (rendered by schema-doc generators); inline `# ` comments in an annotated example file. The anti-pattern: an undocumented YAML config and a wiki page that drifts out of sync.
- **README integration for project-level YAML.** Project READMEs SHOULD reference the YAML files the user is expected to author or edit (config files, manifest files, workflow files) with a one-line description of each and a link to its schema. A repo with five undocumented `.yaml` files at the root is a tour-of-discovery for new contributors.
- **Inline-reference navigability.** Per [TW Dim 13](../domains/role/TECHNICAL-WRITER-REVIEW.md), prose references in the YAML's comments to other suite artifacts (Review N, G-ID, domain names, file paths) follow [the anchor-link convention](../suite-development/suite-development.md#anchor-link-convention-for-cross-references-review-79-finding-3). YAML comments are forward-facing prose just like Markdown body text.

## Localization

- **YAML translation file conventions.** YAML is the dominant format for [Rails i18n](https://guides.rubyonrails.org/i18n.html) (Ruby on Rails) and several other server-side i18n frameworks. The convention: one file per locale (`en.yml`, `fr.yml`, `ja.yml`), top-level key is the locale code, nested namespaces map to dot-paths (`en.users.profile.title`). The schema is per-framework but the YAML shape is consistent across frameworks that adopt the Rails convention.
- **Namespacing.** Translation keys SHOULD be hierarchical (namespaced by feature: `auth.signup.button`, `settings.profile.title`) and stable across translations. Avoid embedding the source-language text in the key — `welcome_message_for_logged_in_users` is fine; `welcome_back_friend` ages poorly when the marketing tone shifts. The hierarchy serves as a discovery index: a translator opens `settings:` and sees every settings-page string in one place.
- **Pluralization key conventions.** Rails i18n's pluralization uses CLDR plural forms — `zero`, `one`, `two`, `few`, `many`, `other` — under a single key:
  ```yaml
  en:
    items:
      one: "1 item"
      other: "%{count} items"
  ru:
    items:
      one: "%{count} элемент"
      few: "%{count} элемента"
      many: "%{count} элементов"
      other: "%{count} элемента"
  ```
  Languages have non-binary plural forms (Russian: three forms; Arabic: six; Polish: three). Hardcoded `if count == 1` English plural logic breaks every non-English locale. The framework's plural-form API is the standard tool.
- **Locale-key consistency across files.** Every locale file MUST share the same key structure — a key present in `en.yml` but absent from `fr.yml` is an untranslated string. Use a sync tool (e.g., `i18n-tasks` for Rails) to detect missing keys, surplus keys, and orphan keys.
- **UTF-8 mandatory for i18n.** Every i18n YAML file is UTF-8. Latin-1 / Windows-1252 / Shift-JIS / EUC-KR are all defects in 2026. The file's encoding is asserted by the editor's save dialog, the repo's `.gitattributes`, and the `.editorconfig`; the parser typically assumes UTF-8 by default.
- **Interpolation marker consistency.** Rails uses `%{name}` for variable interpolation; other frameworks use `{{name}}`, `{name}`, or `${name}`. The framework's chosen marker MUST be used uniformly across all locale files in the project. Mixed markers in one project are a finding (the framework's interpolator will silently fail on the wrong marker).

## Tooling

The standard toolchain for YAML across the suite. Pre-commit hooks and CI gates configure these tools; this section is the inventory.

- **[yamllint](https://yamllint.readthedocs.io/)** — Style + structural linter. `yamllint --strict file.yaml` in CI; `yamllint -d "{extends: default, rules: {line-length: {max: 120}}}" file.yaml` for inline rule overrides. The `.yamllint` config file documents the project's chosen ruleset. The de facto YAML linter; first tool to wire into any project shipping YAML.
- **[Prettier](https://prettier.io/) with YAML support** — Opinionated formatter. `prettier --check '**/*.yaml' '**/*.yml'` in CI; `prettier --write '**/*.yaml' '**/*.yml'` as developer-side autofix. The standard for cross-language repos that want one formatter for `.json` + `.md` + `.yaml`. Prettier's YAML support is competent but opinionated — it may conflict with project-specific yamllint rules; pick one tool as authoritative.
- **[yamale](https://github.com/23andMe/Yamale)** — Schema validator using a YAML-shaped schema dialect. Concise schema syntax, readable, designed for YAML-native workflows. `yamale -s schema.yaml file.yaml`.
- **[check-jsonschema](https://github.com/python-jsonschema/check-jsonschema)** — Validate YAML files against JSON Schema. Reuses the broader JSON Schema tooling ecosystem (see [json.md](json.md)); useful when the project already uses JSON Schema for JSON validation and wants one schema language across YAML + JSON.
- **[actionlint](https://github.com/rhysd/actionlint)** — GitHub Actions workflow YAML linter. Catches expression-syntax errors, missing-action errors, type mismatches in `inputs:`. The right tool to run pre-commit for `.github/workflows/*.yml`.
- **[pre-commit-hooks](https://github.com/pre-commit/pre-commit-hooks)** — The pre-commit framework's stock hooks include `check-yaml` (syntax validation via PyYAML's safe_load), `end-of-file-fixer`, `trailing-whitespace`, `mixed-line-ending`. The minimal YAML gate.
- **[PyYAML](https://pyyaml.org/) / [ruamel.yaml](https://yaml.readthedocs.io/)** — The two dominant Python YAML libraries. PyYAML is older, faster (with libyaml C extension), lossy on round-trip (drops comments, reformats quoting). ruamel.yaml is newer, preserves comments and structure on round-trip, slightly slower. Choice by workload: PyYAML for read-only parsing; ruamel.yaml for edit-and-rewrite tooling.

**Pre-commit hook examples.** Add to `.pre-commit-config.yaml`:

```yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: check-yaml          # syntax validation via safe_load
      - id: end-of-file-fixer
      - id: trailing-whitespace
      - id: mixed-line-ending
        args: [--fix=lf]
  - repo: https://github.com/adrienverge/yamllint
    rev: v1.35.1
    hooks:
      - id: yamllint
        args: [--strict]
  - repo: https://github.com/python-jsonschema/check-jsonschema
    rev: 0.29.4
    hooks:
      - id: check-github-workflows  # validates .github/workflows/*.yml
      - id: check-github-actions    # validates action.yml composite actions
```

For schema-aware validation of project-owned YAML, add a project-local hook that runs `yamale` or `check-jsonschema` against the project's schemas.

## Anti-patterns

The named anti-patterns that recur in YAML review. Each is a finding when encountered; the fix is documented inline.

- **Tabs for indentation.** YAML 1.2 §6.1 forbids tabs for indentation. Some parsers reject outright; some accept and produce confusing errors elsewhere. Editor settings that expand tabs to spaces on save are the standard prevention; yamllint's `indentation:` rule is the gate.
- **Unquoted version numbers parsed as floats.** `version: 3.9` parses as the float `3.9`, NOT the string `"3.9"`. The float-vs-string ambiguity bites Docker Compose users (Compose file versions), Python `pyproject.toml` siblings, and anywhere a version-like string is unquoted. Fix: quote version strings explicitly (`version: "3.9"`). Worked example: `version: 3.10` parses as the float `3.1` (trailing zero dropped), changing the meaning silently.
- **Unquoted keys/values parsed as YAML 1.1 booleans.** Under YAML 1.1 parsers, `yes`, `no`, `on`, `off`, `y`, `n`, `Yes`, `No`, `On`, `Off`, `Y`, `N`, `TRUE`, `FALSE`, `True`, `False` all parse as booleans. The classic trap: GitHub Actions' `on:` key — a YAML 1.1 parser would interpret `on:` as the boolean `True:` key. GitHub's parser is YAML 1.2-compliant in 2026 (booleans are only `true` / `false`), but the trap recurs in other tools. Defense: quote known-ambiguous values (`country: "NO"` for Norway's country code, not the boolean `false`); set yamllint's `truthy:` rule to flag the 1.1 forms.
- **Over-use of anchors that hurt readability.** Anchors (`&`) + aliases (`*`) reduce duplication but force readers to scroll back to the anchor definition. A YAML document with 20 anchors becomes a graph the reader has to traverse mentally. Fix: use anchors sparingly; prefer explicit reference-by-ID for clarity; reserve anchors for truly-shared configuration that benefits from automatic propagation.
- **Deeply-nested structures (> 4 levels).** A 7-level-deep document is unreadable and indicates schema-design failure. Fix: promote inner objects to top-level maps keyed by ID, flatten with key paths (`services.web.database.url` as a single top-level key in a flat-config style), or split into multiple documents.
- **Comments that explain WHAT instead of WHY.** `# the timeout in seconds` next to `timeout_seconds: 30` adds nothing. Fix: write comments that document the rationale, the tradeoff, or the constraint that forced the value — the information NOT carried by the key name.
- **Secrets committed in YAML.** `database_url: postgres://user:hunter2@host/db` in a committed config file. Fix: move the secret to an environment variable or secrets manager; reference by name in the YAML (`database_url: ${DATABASE_URL}`); add a pre-commit secret-scanning hook to catch the next attempt.
- **Not pinning tool versions in config.** `uses: actions/checkout@main` in a GitHub Actions workflow — floating ref. `uses: actions/checkout@v4` good (tag pin); `uses: actions/checkout@a5ac7e51b41094c92402da3b24376905380afc29` better (SHA pin). Fix: replace floating refs with tag or SHA pins; configure [Dependabot](https://docs.github.com/en/code-security/dependabot) or [Renovate](https://docs.renovatebot.com/) to keep the pins current.
- **`yaml.load` on untrusted input.** Python `yaml.load(data)` without an explicit safe loader is RCE on attacker-controlled YAML. Fix: switch to `yaml.safe_load(data)` everywhere user-supplied YAML is parsed; reserve full `yaml.load` for trusted-source-only data with the trust assumption documented inline.
- **Mixed `.yaml` / `.yml` extensions in one project.** Both extensions work, but mixing creates pre-commit hook regex headaches (`files: \.ya?ml$` works but obscures intent) and looks unintentional. Fix: pick one extension; rename outliers; document the choice. Exception: external tools that demand a specific name (`docker-compose.yml`, `.github/workflows/*.yml`) are preserved as-is.
- **Duplicate keys in one mapping.** `{a: 1, a: 2}` is permitted by YAML's parser but the resolved value is parser-defined (most take the last; some take the first). Fix: yamllint's `key-duplicates:` rule catches this; never emit duplicates; normalize at parse time if input has them.
- **Quoting style drift within one file.** `key1: 'value'`, `key2: "value"`, `key3: value` mixed without rationale. Fix: apply the quoting policy uniformly (plain by default; single-quote when special chars; double-quote when escapes needed); a formatter (Prettier, yamllint with `quoted-strings:`) enforces consistency.
