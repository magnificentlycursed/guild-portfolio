# Python Language Supplement

These dimensions supplement the standard IAR domain reviews for Python projects. During each domain review, apply the relevant section below in addition to the standard dimensions for that domain.

**Authored:** Review 76 (2026-05-20) — surfaced when a human reviewer questioned why the suite's own Python hooks ended in `.sh`. The supplement consolidates the Python-specific concerns that should have governed those hooks since they were authored. The companion artifact rename (`.sh` → `.py` for Python hooks; preserve `.sh` for actually-bash scripts) is the worked example the supplement teaches.

**Multi-domain authoring note:** the sections below were drafted with the relevant role-domain perspectives in mind — QE (testing tooling), Security + Red Team (Python's exploit-prone APIs), SE + SA (idiomatic Python and module structure), PE (packaging + dependency management evolved rapidly through 2024–2026 with uv replacing pip+venv for many flows), DE (typed data validation has consolidated around pydantic + msgspec), TW + Doc Reviewer (Python docs have a docstring-vs-Sphinx-vs-mkdocs choice with real tradeoffs). The supplement is forward-looking against the 2026 Python ecosystem (Python 3.11+; ruff replacing flake8/isort/pyupgrade; uv as the recommended package manager).

## Quality Engineering

- **Test framework** — Is `pytest` the runner? `unittest` is acceptable but `pytest` is the suite's recommended default for new projects. Are fixtures used over setUp/tearDown boilerplate? Is `conftest.py` used for shared fixtures across multiple test files?
- **Property-based testing with `hypothesis`** — For pure functions, validation logic, and any path where exhaustive enumeration is intractable, are property-based tests via `hypothesis` used? Named patterns: `@given(st.text())` for input-shape generalization; `@given(st.integers(min_value=..., max_value=...))` for numeric ranges; stateful testing via `RuleBasedStateMachine` for stateful systems. A pure function with only example-based tests is testing what the author thought to write; property-based tests catch what the author didn't think of. Coordinate with QE Dim 2 (Test falsifiability).
- **Mutation testing with `mutmut`** — For pure functions and validation logic, run `mutmut run` and confirm the surviving-mutations count is zero on in-scope modules. Install: `pip install mutmut`. Common invocation: `mutmut run --paths-to-mutate src/<module>.py` to scope to a specific module. A surviving mutation means a test passes against a deliberately-wrong implementation — a defect in the test surface, not the implementation. Mutation classes that recur in Python specifically: boundary off-by-one (`<` ↔ `<=`); conjunction flips (`and` ↔ `or`); negation flips (`not x` ↔ `x`); default-argument mutations; comparison-operator polarity (`==` ↔ `!=`). Surviving mutations are findings whose fix is either (a) a new test asserting the boundary the mutation crossed, or (b) a tightened assertion on an existing test.
- **Coverage thresholds with `coverage.py`** — Line coverage should be at minimum 80%. Public API coverage should be 100% — every exported function, class method, and module-level callable must have at least one test exercising it. Install: `pip install coverage` or use `pytest-cov`. Invocation: `pytest --cov=src --cov-report=term-missing --cov-fail-under=80`. Branch coverage (`coverage run --branch`) is the stronger check — it catches untested else-branches that line coverage marks green when the if-branch alone is hit.
- **Doctest discipline** — If docstrings contain `>>>` examples, are they runnable via `pytest --doctest-modules` (or `python -m doctest module.py`)? A doctest that doesn't actually run is misleading documentation — the example shows behavior the implementation no longer exhibits. Doctests should be enabled in the CI test run if they exist in source.
- **Type checking as test surface (`mypy --strict`)** — Is `mypy` (or `pyright`) run in CI with `--strict`? Type errors are tests for invariants the runtime can't check. A project that uses type hints decoratively (annotations present but never checked) gets none of the type-system's value. Named failure modes: `Any` used where a specific type would constrain; missing `-> None` on functions that return implicitly; `Optional[X]` declared but `None` paths untested; protocol/abc abstractions defined but not enforced.
- **Test isolation** — Are tests isolated from each other? Named failure modes: tests that depend on prior test execution (`test_a` must run before `test_b`); tests that mutate global state without restoring it; tests that share filesystem state without `tmp_path` fixtures; tests that share network state without mocking. Pytest's `-p no:randomly` should NOT be set in CI — random test ordering catches isolation failures.

## Security

- **Input validation at trust boundaries** — Every function that accepts data from outside the process (CLI args, file contents, HTTP requests, env vars, subprocess output) must validate the input shape and value range before use. Named failure modes: `int(user_input)` without try/except for `ValueError`; `json.loads(user_data)` without schema validation against the loaded structure; `open(user_path)` without path-traversal validation. Trust-boundary validators should be centralized so the same input class is validated identically across the codebase.
- **`eval`, `exec`, `compile`, `__import__` discipline** — Are these dynamic-code APIs used? Each call site must be justified — if any user input reaches `eval`/`exec` it is a critical security defect (arbitrary code execution). Named worked examples of unsafe patterns: `eval(user_supplied_formula)` for a calculator app (use `ast.literal_eval` or a real parser); `getattr(obj, user_supplied_name)` without allowlist validation (lets a caller access any attribute including dunders).
- **`pickle` as RCE vector** — `pickle.load` and `pickle.loads` execute arbitrary code defined by the pickle bytes. A pickle file from an untrusted source is equivalent to remote code execution. Named failure modes: caching system state via pickle for "convenience"; deserializing user-uploaded pickle files; using pickle for IPC where one side is untrusted. The rule: pickle ONLY for data your process produced and stored, never for data crossing a trust boundary. For untrusted serialization use JSON, msgpack, or msgspec.
- **`yaml.load` vs `yaml.safe_load`** — `yaml.load(data)` (without a Loader argument, or with `Loader=Loader`) instantiates arbitrary Python objects and is equivalent to `pickle.load` on untrusted input — RCE. Use `yaml.safe_load(data)` for any data that crosses a trust boundary. PyYAML 6.0+ removed the unsafe default but legacy code in the wild still uses the unsafe form.
- **`subprocess` shell-injection** — Are `subprocess.run(cmd, shell=True)` or `subprocess.Popen(cmd, shell=True)` used? With `shell=True`, a string command is parsed by the shell, making any user-controlled component an injection vector. The safe form: pass a list to `subprocess.run([prog, arg1, arg2])` with `shell=False` (the default). Named worked example: `subprocess.run(f"convert {user_filename} out.png", shell=True)` lets the user inject `; rm -rf ~`; the safe form `subprocess.run(["convert", user_filename, "out.png"])` passes `user_filename` as a single argv element.
- **SQL injection in raw queries** — Are SQL queries constructed via f-strings or `%` formatting with user input interpolated? Named worked example: `cursor.execute(f"SELECT * FROM users WHERE name = '{name}'")` — injection-vulnerable. The safe form: `cursor.execute("SELECT * FROM users WHERE name = ?", (name,))` (parameterized query). Same rule for ORMs — never compose query strings from user input; use the ORM's parameterized API.
- **Secrets discipline** — Are API keys, tokens, database URLs, or credentials hardcoded in source? Are they read from environment variables or a `.env` file (via `python-dotenv` or `pydantic-settings`)? Is `.env` in `.gitignore`? Are pre-commit hooks scanning for secret patterns (e.g., `detect-secrets`)?
- **Dependency vulnerability scanning** — Is `pip-audit` (or `safety`) run against the lock file (`requirements.txt`, `poetry.lock`, `uv.lock`)? Are CVE advisories acknowledged? `pip-audit` is the modern PyPA-endorsed tool; `safety` is a viable alternative; both should be run in CI.
- **AST-level security scanning with `bandit`** — Is `bandit -r src/` run in CI? Bandit catches the named exploit patterns above (eval/exec, pickle, yaml.load, shell=True, weak crypto) at the AST level. Suppressions (`# nosec`) require a comment explaining why the flagged pattern is safe in context.
- **Error-message escape** — Per Security Dim 9 (G-125), Python error messages that interpolate user input via f-strings or `format` can leak control characters or Trojan-Source (Cf class) characters. Sanitize user-derived values in error paths: a wrapper function that calls `repr()` or applies a `control-char escape` is the standard defense. Detector: grep for `raise X(f"...{user_var}...")` patterns and confirm each wraps `user_var` with a sanitizer.

## Software Engineering

- **Type hints with `mypy --strict`** — Are all function signatures annotated? Are module-level constants annotated where their type is non-obvious? Is `from __future__ import annotations` used (allows forward references and PEP 604 union syntax `X | None` on Python 3.7+)? Type hints without `mypy --strict` enforcement are decorative — they document intent but don't catch violations. The recommendation: type hints + `mypy --strict` in CI is the baseline; missing either is a finding for projects with reviewer attention.
- **Dataclass / pydantic / msgspec choice** — For value types: `@dataclass(frozen=True)` for simple immutable records; `pydantic.BaseModel` for runtime-validated models (slower, full validation, JSON-friendly); `msgspec.Struct` for high-performance validated serialization (fastest, less ecosystem maturity). The choice depends on workload: API boundaries → pydantic; internal value types → dataclass; high-throughput serialization → msgspec. A project that uses all three for the same concern without rationale is a finding.
- **Context manager discipline** — Are resources (files, locks, network connections, database transactions) acquired and released via `with` blocks? Named failure modes: `f = open(path)` without a matching `f.close()` and no `with`; `conn.cursor()` without `with conn`. The `contextlib` module provides `@contextmanager` for authoring custom context managers. Async equivalents: `async with`, `contextlib.asynccontextmanager`.
- **Exception type discipline** — Are `except:` (bare except) and `except Exception:` used? Bare `except:` catches `KeyboardInterrupt` and `SystemExit` — almost always wrong. `except Exception:` is acceptable at outer boundaries (top-level CLI handler, request handler) but suspect in inner code (probably masking a specific exception the caller should handle). Custom exception hierarchies (`class MyError(Exception)`) should be defined at module boundaries; raising raw `ValueError` or `RuntimeError` for domain errors is weaker than naming the domain-specific exception.
- **`pathlib.Path` over `os.path`** — For new code, is `pathlib.Path` used? Named failure modes: `os.path.join(a, b)` instead of `Path(a) / b`; `os.path.exists(p)` instead of `Path(p).exists()`; manual string-concatenation of paths. The `pathlib` API is platform-portable, type-safe (paths are objects, not strings), and chainable. The os.path module is acceptable for backward compatibility with existing code but not for new code.
- **f-strings as the format default** — Are f-strings (`f"{x}"`) used for string interpolation in new code? `"%s" % x` and `"{}".format(x)` are older patterns; f-strings are clearer, faster, and don't have the `%`-format gotchas (e.g., `"%s" % obj` invokes `__str__`, which can be expensive). For logging specifically, use `logger.info("message %s", value)` (the logger does the formatting lazily) — f-strings in logger calls evaluate even if the log level is suppressed.
- **Generator / iterator patterns** — For collections that don't need full materialization, are generators (`yield`) and iterators used? Named failure modes: `[x for x in data]` materializing the full list when a generator suffices; `list(map(f, data))` when a streaming form would work; reading a large file via `f.read().splitlines()` when `for line in f:` streams. Generators have a real performance + memory benefit for large data; list comprehensions are the right shape for small in-memory data.
- **Logging vs print** — Is `logging` used for diagnostic output? `print()` to stdout in library code is a finding (the library shouldn't own the user's stdout); `print()` to stdout in CLI code is acceptable for user-facing output (results, prompts); diagnostic output ("connecting to..."; "retrying..."; "computed result is...") belongs in `logging` with explicit levels.
- **Ruff format compliance** — Is `ruff format` (or `black`) run as a pre-commit hook? `ruff` is the modern fast formatter+linter that replaces `black` + `flake8` + `isort` + `pyupgrade` in one tool. Invocation: `ruff format src/ tests/` (formatting); `ruff check src/ tests/` (linting). A project without an enforced formatter accumulates whitespace/quote/import-order drift that masks substantive diffs.

## Platform Engineering

- **Package manager — `uv` (recommended for 2026)** — Is `uv` (the Astral.sh package manager) used for environment + dependency management? `uv` is 10–100x faster than `pip + venv` and consolidates the lockfile + venv + install workflow. Invocation: `uv venv` (create env), `uv pip install -r requirements.txt` (install), `uv lock` (lockfile generation). For backward-compat, `pip + venv` is still acceptable; `poetry` is an older option that's been largely superseded by `uv`.
- **`pyproject.toml` as canonical configuration** — Is `pyproject.toml` the single source of truth for project metadata (name, version, deps), build configuration (`[build-system]`), and tool configuration (`[tool.ruff]`, `[tool.mypy]`, `[tool.pytest.ini_options]`)? Named failure modes: project using `setup.py` for metadata (deprecated for new projects since PEP 517/518); tool configuration scattered across `setup.cfg`, `pytest.ini`, `mypy.ini`, `.flake8`; a `requirements.txt` file that's the actual source of truth while `pyproject.toml` only lists "minimum versions." For new projects, `pyproject.toml` is canonical; legacy `setup.py` is acceptable in legacy projects.
- **Lockfile committed** — For applications (not libraries), is the lockfile (`uv.lock`, `poetry.lock`, or pinned `requirements.txt`) committed to version control? A `requirements.txt` with only top-level packages and no version pins is not a lockfile — `pip install -r` against it produces different environments on different days. The standard: lockfile committed; CI installs from the lockfile; developers regenerate the lockfile via explicit commands when adding deps.
- **CI test matrix** — Is the test suite run against the Python versions the project supports? A library that supports Python 3.10+ should run CI against 3.10, 3.11, 3.12, 3.13. A binary application can pin to one version. Named failure modes: CI runs only on 3.12 but the README claims "supports 3.10+"; CI matrix lists multiple Pythons but the workflow file actually only installs one.
- **Pre-commit framework integration** — Is the `pre-commit` framework used to wire `ruff format`, `ruff check`, `mypy`, and project-specific hooks? Named failure modes: pre-commit configured but only locally (CI doesn't re-run); pre-commit hooks installed but not pinned by `rev:` (drift between contributors); CI duplicates pre-commit logic with different versions of the tools (silent drift between local and CI).
- **CI tool versions pinned** — Is `python-version`, `uv-version`, `ruff-version` pinned in CI? A floating tool version means "the build broke and we don't know what changed."
- **Distribution — `pipx` for CLI tools** — For Python projects that ship as installable CLIs, do the docs reference `pipx install <pkg>` rather than `pip install <pkg>`? `pipx` installs in an isolated venv so the user's global Python isn't polluted. For libraries (consumed by other Python code), `pip` is correct.
- **Docker image strategy** — If the project ships a Docker image: is the base image specific (`python:3.12-slim`) rather than implicit (`python:3.12`)? Is a multi-stage build used to separate build deps from runtime? Are non-root users used (`USER nobody` or similar)? Is the image size monitored?

## Data Engineering

- **`pydantic.BaseModel` for boundary validation** — At every trust boundary (HTTP request body, CLI arg parsing, file deserialization), is `pydantic.BaseModel` used to validate the shape and value ranges of incoming data? Named failure modes: `json.loads(request.body)` without subsequent validation against a schema; CLI arg accepted as `str` and parsed to `int` later (the validation happens far from the boundary); a `from_dict` classmethod that doesn't validate ranges. Pydantic v2's performance is competitive with msgspec for typical workloads; v1 was significantly slower and is no longer supported.
- **`msgspec.Struct` for high-performance serialization** — When pydantic's per-validation overhead is the bottleneck (high-throughput servers, batch data processing), is `msgspec` used? Named tradeoff: msgspec is faster and lower-memory but has fewer ecosystem integrations; pydantic is slower but has FastAPI / Django / SQLModel / pydantic-settings integrations.
- **Schema evolution with optional fields + defaults** — When adding a field to a serialized type, is the new field declared `Optional[T] | None` with a default? Loading old data should not fail; serializing new data with the new field should succeed. Named failure modes: required new field that breaks deserialization of old persisted state; default value that is a mutable singleton (`def __init__(self, x: list = [])` — Python evaluates the default once at function-def time, sharing the list across all calls).
- **Asymmetric trust boundary (create vs. load) — G-126** — Validation at create time and validation at load time must be symmetric. Named failure modes: a pydantic model that rejects empty strings on `__init__` but a `from_json` path that doesn't go through `__init__`; a dataclass with a `__post_init__` validator that doesn't fire on `dataclass.replace()`. The detector pattern: enumerate every persisted type, locate the create-side validator AND the load-side validator, confirm both apply the same constraint set.
- **Validation strictness symmetry (input vs. output) — G-152** — If input validation rejects a byte/value class, output rendering should not silently normalize it (or input validation should permit it). Named failure modes: a model that rejects `\r` on create but a JSON serializer that auto-normalizes line endings; a CSV reader that accepts BOM but a writer that strips it. Detector: for every `validate_*`/`parse_*` function, find every render/format function touching the same field and confirm constraint sets match.
- **SQLAlchemy + Alembic for migrations** — If the project uses a relational database, is SQLAlchemy 2.x used with Alembic for schema migrations? Named failure modes: schema changes applied via raw SQL without an Alembic revision; Alembic revisions present but never applied in CI tests; downgrade paths absent (one-way migrations are operational hazards). For SQLite-only projects, raw schema management is acceptable if migration tests exist.
- **CSV / JSON / Parquet roundtripping** — If the project reads and writes structured data, are roundtrip tests present? A reader that accepts data the writer can't produce, or a writer that produces data the reader can't load, is a silent schema-drift defect. The roundtrip test: write a value via the project's writer, read it back via the project's reader, assert equality.

## Red Team

- **`pickle.loads` on attacker-controlled data** — Find every `pickle.load` and `pickle.loads` call site and trace the data lineage. If any path allows attacker-controlled bytes to reach pickle, that's remote code execution. Named worked attack: poison a cache file the application reads on startup; serialize a class with a `__reduce__` method that returns `(subprocess.call, (['rm', '-rf', '~/'],))`; the deserialization triggers the command.
- **`yaml.load` on attacker-controlled data** — Same shape as pickle. `yaml.load(open(path))` with `path` user-controlled or `path` pointing at user-writable data is RCE. The safe form is `yaml.safe_load`.
- **`eval` / `exec` on user input** — Trace every `eval()` and `exec()` to the input source. If user-controllable data reaches either, code injection. Named attack: a `--filter` CLI flag passed to `eval()` for "expressivity" lets the attacker pass `__import__('os').system('...')`.
- **Format-string injection in `format`/`%`** — Python's `str.format` exposes attributes via `{x.__class__}` patterns. If `user_input.format(**context)` runs with a user-controlled format string, the user can dereference object attributes the developer didn't expect to be accessible. The safe form: never let user input become the format string itself; user input is the VALUE being formatted, not the template.
- **`subprocess` with `shell=True`** — Every `subprocess.run(..., shell=True)` is a candidate shell-injection point. If any element of the command string is user-derived, injection. Trace each `shell=True` and confirm either (a) no user input reaches the command, or (b) all user-derived components are shell-escaped via `shlex.quote`.
- **Path traversal in file APIs** — `open(user_path)`, `Path(user_path).read_text()`, `shutil.copy(src, user_dst)` — any user-supplied path is a traversal candidate. Named attack: a profile-picture upload accepts a filename, writes to `Path(uploads_dir) / user_filename`; `user_filename = "../../../../etc/passwd"` escapes the intended directory.
- **`tarfile.extractall` / `zipfile.extractall` path traversal** — Both libraries can extract archive entries to absolute paths or `..`-traversal paths by default. Python 3.12+ added `filter=` parameters to tarfile (`data` filter is the safe default for untrusted archives); older code patterns are vulnerable. Audit every `extractall` and confirm a path-validation filter is applied.
- **XXE in lxml / xml.etree** — XML external entity attacks: an XML document declares an entity that references a system file (`<!ENTITY xxe SYSTEM "file:///etc/passwd">`) or an external URL. `xml.etree.ElementTree` is safe by default in 3.7+; `lxml` requires explicit `XMLParser(resolve_entities=False)`. `xmlrpc` and SOAP libraries have historically been XXE-vulnerable.
- **PyPI typosquatting** — Check `pyproject.toml` / `requirements.txt` for dependencies that look like they could be typo-typed names of popular packages (`requets` vs `requests`; `pythn-dateutil` vs `python-dateutil`). Recent dependencies pinned to a "first known good" version with no publication history are suspect — verify the author and check PyPI for prior versions before trusting.
- **`pip install` from arbitrary sources** — `pip install -r requirements.txt` where the file contains `--index-url https://my-private-index/` or `git+https://...` lines pulls code from non-PyPI sources. Each such source is a trust boundary the project owner must own.

## Performance Engineer

- **`cProfile` for the first-pass hotspot survey** — For any non-trivial Python performance work, `cProfile` is the standard first measurement. Invocation: `python -m cProfile -o profile.out -s cumulative my_script.py`. The output identifies cumulative time per function — the natural first thing to look at. Performance claims without `cProfile` (or equivalent) are speculation.
- **`py-spy` / `scalene` for sampling profilers** — For long-running processes or production-like workloads, sampling profilers (`py-spy`, `scalene`) avoid `cProfile`'s deterministic overhead. `py-spy record -o profile.svg --pid <pid>` attaches to a running process and produces a flamegraph. `scalene` additionally profiles memory allocation and GPU usage.
- **GIL implications: threading vs. multiprocessing** — Are CPU-bound operations using `threading.Thread`? The GIL serializes Python bytecode execution across threads; CPU-bound thread-parallelism does nothing in CPython. For CPU work, use `multiprocessing.Pool` or `concurrent.futures.ProcessPoolExecutor`. For I/O work, threading is fine (the GIL is released during I/O syscalls). Named failure mode: `ThreadPoolExecutor` used for a CPU-bound numeric workload that completes in approximately serial time. Python 3.13's free-threaded build is opt-in and not yet default; treat threading as GIL-bound unless the project explicitly enables `--disable-gil`.
- **`async`/`await` task overhead** — Are CPU-bound operations called inside async functions without `asyncio.to_thread` / `loop.run_in_executor`? A blocking call inside an async event loop starves every other task on the loop. Named failure mode: `time.sleep(5)` inside an async function (use `await asyncio.sleep(5)`); a synchronous `requests.get` call inside an async handler (use `httpx.AsyncClient`).
- **Memory profiling with `memray` / `fil`** — For memory-bound workloads, `memray run --output mem.bin script.py` followed by `memray flamegraph mem.bin` produces an allocation flamegraph. Named failure modes: per-iteration `list.append` for millions of items where a generator suffices; `pandas.DataFrame` materialized when `polars` streaming would work; pickle-roundtrip on a large object that has a memory-equivalent in-memory representation.
- **Allocation patterns** — Does the hot path allocate inside a loop? Named failure modes: `f"{x}"` in a tight loop (creates a new string each iteration); `list.append` repeatedly when the size is knowable (`list = [0] * n` and assign by index); `dict.update` with many small dicts instead of one big build.
- **NumPy / Polars vectorization** — For numerical / tabular workloads, are operations vectorized (NumPy / Pandas / Polars) rather than Python-loop-iterated? A 1000-element numpy operation is 10–100x faster than the equivalent Python loop. Polars is the modern Pandas alternative with better performance characteristics for large data; for new projects with substantial tabular workloads, evaluate Polars first.

## Solution Architect

- **`src/` layout vs. flat layout** — Is the project's source code under `src/<package_name>/` or directly in `<package_name>/` at the repo root? `src/` layout prevents the "import from project root" antipattern where tests accidentally pick up unbuilt source; the package being importable requires an actual install (`pip install -e .` or `uv pip install -e .`). For libraries, `src/` is recommended; for applications it's still preferred but less critical.
- **`__init__.py` discipline** — Are `__init__.py` files used to define the package's public API surface (`from .module import PublicClass, public_fn`)? Are deep imports (`from package.internal.utils import _private_helper`) treated as a boundary violation? An `__init__.py` that exports everything reachable via `from X import *` ambiguates the public surface.
- **Circular imports** — Are circular imports present? Named failure mode: module A imports from module B; module B imports from module A; both work at runtime through import-order luck, then break when the import order changes. The standard fix: extract the shared type/protocol into a third module both depend on, OR use `TYPE_CHECKING` guards for type-hint-only references (`if TYPE_CHECKING: from .b import B`).
- **Type-stub vs. inline annotations** — Are types declared inline (the modern Python pattern) or in `.pyi` stub files (the legacy pattern, useful for third-party libraries that lack types)? For new code, inline; stubs are only for legacy code or vendored third-party.
- **Sync/async boundary** — Is the sync/async boundary clear at module level, or does the project mix `def` and `async def` for the same conceptual operation? Named failure modes: a library that provides `client.get(url)` AND `client.aget(url)` for sync/async forms — both must be tested and both can drift; the alternative pattern (`asyncio.run(client.aget(url))` for sync callers) is leaner. For libraries: pick one, document the other-form-via-asyncio-run pattern.
- **Module structure scales with project size** — For a 200-line project, one module is correct. For a 2000-line project, multiple modules organized by domain concern (`auth.py`, `storage.py`, `api.py`). For a 20000-line project, sub-packages organized by bounded context. A 200-line project split into 8 modules is over-engineering; a 2000-line project in one module is under-engineering.
- **Purity boundary explicit (per SA Dim 12)** — Are pure functions (no I/O, no global state mutation, deterministic) separated from effectful functions? Named pattern: `core.py` for pure logic, `io.py` for filesystem/network/database calls, the public API in `__init__.py` composes them. The purity boundary should be testable — pure-core tests run without I/O; effectful-shell tests use fixtures or mocks.

## Technical Writer

- **Docstring format consistency** — Are docstrings in Google style (`Args:` / `Returns:` / `Raises:` blocks), NumPy style, or reST style? The choice is a project-level decision; mixing styles within a project is a finding. Google style is the most common in modern Python; NumPy style is common in scientific Python; reST is the Sphinx-native format.
- **Type hints as docs** — Are types declared via annotations rather than in docstring prose? `def f(x: int) -> str:` is documentation; `def f(x):` with a `"""x: int"""` docstring is duplicated information that drifts. Type hints visible in `help()` output and at runtime via `__annotations__` are the canonical signature.
- **Public API documentation completeness** — Are all `pub` (public — names not starting with `_`) module-level functions, classes, methods, and constants documented? The test: `python -c "help(my_module)"` should produce a useful overview. Items with no docstring appear as `name(args)` with no description, which is documentation absence not minimal documentation.
- **Sphinx vs mkdocs choice** — For projects that need a documentation website: Sphinx (reST or MyST markdown; long-standing Python ecosystem default; tight integration with autodoc) or mkdocs-material (markdown-first; faster setup; mkdocstrings for autodoc). Both are valid; the project chooses based on existing convention (a library with multiple existing Sphinx-using siblings should use Sphinx; a new tool with no precedent can use mkdocs-material).
- **README → PyPI rendering** — If the package is published to PyPI, is `README.md` rendered correctly on the PyPI page? Named failure modes: links that work in the GitHub repo but break on PyPI (different base URL); badges that reference branch-specific files; relative paths to source files that PyPI's rendering can't resolve. The check: build the wheel locally, inspect the `long_description` field, paste into a markdown previewer that emulates PyPI's renderer.
- **`__doc__` vs class/method docstrings** — Module-level `__doc__` (the first string in a `.py` file, before imports) is the module's docstring. Class-level and method-level docstrings document their respective scopes. A module with no top-level docstring is missing the entry point a reader uses to orient.

## Documentation Reviewer

(Active when Technical Writer is active — paired per the forthcoming Documentation Reviewer domain registration. This section is forward-link only; the domain prompt at `vsdd-suite/domains/role/DOCUMENTATION-REVIEWER-REVIEW.md` lands in a subsequent Review. Until that domain registers, the section here documents the cold-reader Python-doc dimensions for whoever runs the pair-validation in advance of formal domain registration.)

- **Install-from-PyPI cold-reader test** — Can a reader who lands on the PyPI page (not the GitHub repo) install and use the package? Named failure modes: README references files in the GitHub repo with relative paths that PyPI's rendering can't resolve; install instructions assume the reader has the repo cloned; usage examples reference test fixtures not shipped in the wheel.
- **`help()` discoverability** — After install, does `python -c "import pkg; help(pkg)"` produce useful overview output? `help(pkg.func)` produce useful function-level docs? `dir(pkg)` produce a clean public API surface (no `_private` names leaking into the public list)? The standard: a user who installs the package and runs `help()` should be able to use it without consulting external docs for basic operations.
- **`--help` output executability** — For CLI projects, does `<cmd> --help` output enumerate every subcommand and flag the docs claim to support? Are usage examples in `--help` consistent with the README? A flag mentioned in the README but absent from `--help` is documentation rot; a flag in `--help` but undocumented in the README is undocumented surface.
- **Tutorial-followability** — If the project has a tutorial or quickstart, can a reader execute it verbatim from a fresh venv? Named failure modes: tutorial assumes prior `pip install <some-other-tool>`; tutorial copy-pastes code that depends on undocumented module-level state; tutorial uses a Python version that the project's CI doesn't actually test.
- **API reference vs tutorial separation** — Are API reference docs (one entry per public function) and tutorial docs (one walkthrough per use case) clearly separated, or is everything jammed into a single "documentation" page that's neither? A reader looking up `func(x)` shouldn't have to scroll through a 5-page tutorial; a reader learning the library shouldn't have to read 200 API entries.
- **Migration notes for breaking changes** — When the project releases a breaking change, is there a migration note documenting the change, the old behavior, the new behavior, and the migration path? CHANGELOG entries naming "BREAKING:" should cross-reference a migration note for non-trivial changes.

## Localization

- **`gettext` / `Babel` integration** — If the project supports multiple languages: are user-visible strings wrapped in `_("...")` (gettext) or equivalent? Are `.po` / `.pot` files maintained per locale? Is the message-extraction step (`pybabel extract`, `xgettext`) part of CI or a documented contributor step?
- **Locale-sensitive operations** — Are operations that have locale-specific behavior (date formatting, number formatting, string comparison, case folding) using locale-aware APIs (`locale.strftime`, `babel.dates.format_datetime`, `unicodedata.normalize`) rather than locale-naive ones? Named failure mode: `date.isoformat()` produces machine-readable output, not user-readable — using it for a user-facing display is a locale-agnostic-when-it-shouldn't-be failure.
- **UTF-8 mandatory in 2026** — Is the project explicitly UTF-8 on file I/O (`open(path, encoding="utf-8")`)? Python's default encoding on Windows historically was the system code page; defaulting causes mojibake. PEP 686 (Python 3.15+, default UTF-8) is forward-looking but new code should be explicit today.
- **Plural forms** — Are pluralized messages handled via the localization framework's plural-form API rather than `if count == 1: "1 item" else f"{count} items"`? Many languages have non-binary plural forms (Russian has three, Arabic has six); hardcoded English plural logic breaks them.

## Three-audience lens

The Python supplement covers Python-specific dimensions across 10+ domain perspectives. Per the [Three-audience design principle](../suite-development/suite-development.md#three-audience-design-principle-review-80-finding-3) ([Review 92 Finding 2](../suite-development/review-log/2026-05-24-suite-review.md#review-92--2026-05-24-0419z) cascade-applied for per-language supplements with broad domain-perspective coverage):

- **Suite developers** (contributors extending Python-specific dimensions) read this supplement to understand which Python idioms / failure modes the methodology teaches as canonical + how to extend per-domain sections when Python ecosystem changes (new release features; new packaging tools; new typing constructs; PEP adoption). Each per-domain section under `## <Domain>` is the extension surface; new dimensions land in the relevant per-domain section with the canonical Python authority cited + the named failure mode named.
- **Suite users** (project teams applying VSDD to a Python project) read this supplement alongside the domain prompt when running each domain's IAR cycle. The per-domain sections (`## Software Engineering`, `## Quality Engineering`, `## Security`, etc.) are the Python-specific add-ons to the corresponding domain's standard dimensions. When authoring a per-domain review-log entry, declare via the `**Supplements applied:**` preamble field (per [Review 91 Finding 2](../suite-development/review-log/2026-05-23-suite-review.md#r91-f2)) which section(s) of this supplement informed the round.
- **AI agents** (parallel cold-session reviewers + main-session orchestrators) read this supplement as the Python-specific failure-mode catalog. Per-domain sections are H2-anchored; agent grep idiom for SE Python-specific failure modes: `awk '/^## Software Engineering/,/^## /' vsdd-suite/supplements/python.md` returns the section's full content. Each named failure mode (bold-key-value form `- **<failure class>** — <description>`) is a substantive defect-class to assess; absent named-failure-mode coverage in a per-domain section is itself a methodology gap.

The companion review dimensions per audience map: SO scopes which Python idioms are spec-promised (suite-developer); Documentation Reviewer audits the supplement's clone-and-follow fidelity (suite-user); AI Engineer audits the supplement's per-domain coverage + cite-verify discipline at finding-authoring time (agent); TW audits the supplement's prose for cold-reader readability across all per-domain sections (cross-audience).
