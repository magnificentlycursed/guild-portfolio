# TOML Language Supplement

TOML is the suite's default configuration language for projects that need a human-authored, declaratively-parsed, comment-friendly format. The two [Rust](https://www.rust-lang.org/) projects in the portfolio ([`issue-tracker-cli/`](../../issue-tracker-cli/) and [`bookmark-cli-manual/`](../../bookmark-cli-manual/)) carry `Cargo.toml` for package metadata, dependency declarations, feature flags, and `[profile.*]` build tuning; any [Python](https://www.python.org/) project that adopts formal packaging will carry `pyproject.toml` per [PEP 621](https://peps.python.org/pep-0621/); third-party tools commonly read configuration from project-local TOML (`deny.toml` for [cargo-deny](https://github.com/EmbarkStudios/cargo-deny); `rust-toolchain.toml`; `.taplo.toml`; tool-specific tables in `pyproject.toml`). This supplement covers TOML as a language: schema design, validation, security, performance, and operational discipline. The canonical reference is [the TOML 1.0 spec](https://toml.io/en/v1.0.0); this supplement does not restate the grammar, it documents the dimensions to review when TOML is the chosen format. What this supplement is NOT: a tutorial on writing TOML, a guide to choosing TOML vs JSON/YAML at architecture time (that's a Solution Architect concern handled at project scaffold), or a substitute for the host-language supplement that owns the parser code ([Rust](rust.md), [Python](python.md)).

**Authored:** Review 81 (2026-05-20) — the portfolio's Rust projects rely on `Cargo.toml` for the load-bearing supply-chain surface (dependency pinning, license declaration, profile-tuned release builds), and there was no language-level review dimension set for TOML to apply during domain reviews. This supplement closes that gap. The companion artifact is the dimension set itself: when a domain review encounters TOML-defined artifacts, the reviewer applies the relevant section below in addition to the standard domain dimensions.

**Multi-domain authoring note:** the sections below were drafted with the relevant role-domain perspectives — PE (PRIMARY — `Cargo.toml` dependency management, semver constraints, feature flags, workspace configuration, `[profile.release]` optimization), SE (package metadata fields; `pyproject.toml` PEP 621 metadata; dependency-group declarations), SA (schema design, declarative vs imperative, workspace layout for multi-package projects, build-vs-runtime dependency separation), Security (untrusted-TOML parser hardening, version-pin discipline, [cargo-deny](https://github.com/EmbarkStudios/cargo-deny) / [cargo-audit](https://github.com/RustSec/rustsec/tree/main/cargo-audit) supply-chain checks), QE ([taplo](https://taplo.tamasfe.dev/) linting and formatting; schema validation), PerfE (`Cargo` profile tuning — `opt-level`, `lto`, `codegen-units`, `panic`; profile inheritance; PGO config), TW (comment-friendliness; key ordering for readability; section grouping that mirrors logical organization). The supplement is forward-looking against the 2026 TOML ecosystem ([TOML 1.0](https://toml.io/en/v1.0.0) as the stable grammar; [taplo](https://taplo.tamasfe.dev/) as the dominant linter+formatter; [PEP 621](https://peps.python.org/pep-0621/) as the canonical Python-project-metadata standard; [cargo workspaces](https://doc.rust-lang.org/cargo/reference/workspaces.html) with `workspace = true` inheritance for multi-package repos).

**Scope of this supplement:** any `.toml` file in the repo, any TOML payload produced or consumed by project code, and any tool config embedded in a TOML table (e.g., `[tool.ruff]` in `pyproject.toml`). Out of scope: JSON, YAML, XML — adjacent serialization formats covered by their own supplements ([JSON](json.md) exists; YAML and XML supplements would warrant separate authoring if the suite ever ships substantial artifacts in those formats).

## Baseline standards

- **[TOML 1.0](https://toml.io/en/v1.0.0) strict compliance** — `.toml` files MUST parse under a strict TOML 1.0 parser. The grammar is intentionally narrow — single-document, no aliases, no merge keys, no `!Construct` tags — which makes parser exploits rarer than [YAML](https://yaml.org/) and the spec less interpretation-prone than [JSON](https://www.rfc-editor.org/rfc/rfc8259) (which has dialects). A `.toml` file that requires TOML 0.5 extensions or a vendor-specific dialect is a finding — the extension is a contract with consumer code, not a hint.
- **UTF-8 encoding mandatory** — TOML 1.0 §1 requires UTF-8 encoding. A BOM is permitted (TOML 1.0 §1.1) but discouraged; many tools strip or silently mishandle it. Save files as UTF-8 without BOM. Detector: `file file.toml` reports `UTF-8 Unicode text` (clean) vs `UTF-8 Unicode (with BOM) text` (defect).
- **LF line endings** — Unix line endings (`LF`, `\n`) only. CRLF (`\r\n`) is parser-tolerated but produces noise in diffs and breaks line-counting tools that count `\n`. Enforce via `.gitattributes` (`*.toml text eol=lf`) and the [pre-commit-hooks](https://github.com/pre-commit/pre-commit-hooks)' `end-of-file-fixer` hook.
- **One trailing newline** — Like all text files, TOML files end with a single trailing newline. POSIX defines a text file as ending in `\n`; tools that read the last line break on files lacking it.
- **Flat key-value pairs at top; tables grouped with `[section]`** — Pre-table key-value pairs at the file head belong to the implicit root table; subsequent pairs belong to the most-recent `[section]` header. The convention: top-level metadata first (e.g., in `Cargo.toml`, the `[package]` table with `name`, `version`, `edition`), then logical groupings via named tables, then dotted-key flattening only for terse leaf configuration. A file that interleaves root-level keys with `[section]`-scoped keys is a finding — the resulting parse depends on reader interpretation of which `[section]` is "current."
- **Arrays-of-tables with `[[section]]`** — When a collection of homogeneous tables is needed (e.g., `[[bin]]` in `Cargo.toml` declaring multiple binaries; `[[tool.poetry.source]]` declaring multiple Python package indices), use `[[section]]` array-of-tables syntax rather than inline arrays of inline tables. The double-bracket form is more readable for the multi-line case; the inline form is acceptable only for trivial single-line records.
- **Consistent quoting — basic strings double-quoted, literal strings single-quoted when escapes unwanted** — TOML provides four string types: basic (`"..."`, supports `\n` and other escapes), multi-line basic (`"""..."""`), literal (`'...'`, no escape processing — what you see is what you get), and multi-line literal (`'''...'''`). The convention: double-quoted basic strings as default; single-quoted literal strings when the value contains backslashes that should be taken verbatim (Windows paths, regex patterns, raw escape characters). A file that uses literal strings for every value (to "avoid thinking about quoting") obscures intent — the choice carries meaning.
- **Sentence-case section comments** — Where a `[section]` table benefits from prose explanation, attach a `#`-prefixed comment block immediately above the section header. TOML's comment support is one of its principal advantages over JSON; use it.

## Platform Engineering

PRIMARY DOMAIN for TOML review — `Cargo.toml` is the load-bearing artifact for every Rust project's build, dependency, and release configuration.

- **Dependency declarations with semver constraints** — In `[dependencies]` (and `[dev-dependencies]`, `[build-dependencies]`), are versions declared with explicit semver constraints (`"1.2.3"`, `"^1.2"`, `">= 1.2, < 2.0"`) rather than the wildcard `"*"`? `serde = "1"` is the canonical caret-equivalent form ([cargo](https://doc.rust-lang.org/cargo/) treats it as `^1.0.0`). Wildcard `"*"` is rejected by `crates.io` for published crates but is permitted in local workspaces — accidentally using it is a finding (see Anti-patterns).
- **Lockfile commitment** — For binary crates and applications, is `Cargo.lock` committed to version control? Libraries should exclude it; binaries should include it for reproducible builds. The `Cargo.toml` declares ranges; the lockfile pins exact versions per resolution.
- **Feature flag discipline** — Are `[features]` declarations grouped under a single table with the `default = [...]` line first, then named feature flags, each with documentation? Named failure modes: feature flags that enable seemingly-unrelated dependency optional-features (`my-feature = ["serde/derive", "tokio/full"]` without comment explaining the coupling); features that are mutually exclusive but lack runtime validation; `default = ["all-features"]` defeating the point of having opt-in features. Each non-trivial feature should carry a comment naming its purpose.
- **Workspace configuration** — For multi-package repos, is `[workspace]` declared at the root `Cargo.toml`, with `members = [...]` listing the sub-packages and `resolver = "2"` (or `"3"` once stabilized) declared explicitly? Workspace-level dependency unification via `[workspace.dependencies]` + `dep = { workspace = true }` in member crates is the modern pattern — it ensures one version per dep across the workspace and one place to update.
- **`[profile.release]` optimization settings** — Are release-build profile settings declared explicitly rather than inheriting cargo defaults? Common tuning: `opt-level = 3` (the cargo default for release — declare for clarity), `lto = "fat"` or `"thin"` (link-time optimization; `"fat"` is strongest but slowest to compile), `codegen-units = 1` (single codegen unit enables maximum cross-function inlining at the cost of compile parallelism), `panic = "abort"` (smaller binary; no unwinding — incompatible with `catch_unwind`-based tests), `strip = "symbols"` (strip debug symbols from the release binary). Each setting carries a tradeoff — declare the chosen value and a one-line rationale.
- **`[profile.dev]` discipline** — Conversely, dev-build settings should NOT inherit release-tuned values. Named failure mode: `[profile.dev] opt-level = 3` slows dev compilation by 5–20x with no actionable benefit (debugger steps become opaque; iterate-edit-recompile loops slow to minutes). Dev profile is for fast iteration; release profile is for shipped binaries.
- **`rust-toolchain.toml` for toolchain pinning** — Is the Rust toolchain version pinned via a `rust-toolchain.toml` file (or the legacy `rust-toolchain` plain-text file) so all contributors and CI use the same `rustc` + `cargo` + component set? Named pattern: `[toolchain] channel = "1.78.0"`, `components = ["rustfmt", "clippy"]`, `profile = "minimal"`. Without a pin, contributors run different toolchains and silently produce different lockfile-resolution outcomes or different clippy warning sets.
- **`[build-dependencies]` separation** — Dependencies needed only by `build.rs` scripts (codegen, schema generation, native-library binding setup) belong in `[build-dependencies]`, not `[dependencies]`. Mixing them inflates the runtime dependency graph and obscures which deps are actually shipped in the final binary.

## Software Engineering

- **`[package]` metadata completeness** — Are the canonical `[package]` fields present and accurate: `name`, `version`, `edition`, `license` (SPDX identifier), `description`, `repository`, `readme`, `keywords`, `categories`, `authors` (or absence justified — modern crates often omit authors in favor of `repository`-derived attribution)? A `Cargo.toml` missing `license` or `description` cannot be published to `crates.io`; one missing `repository` is harder for downstream consumers to navigate.
- **`pyproject.toml` PEP 621 metadata** — For Python projects, is project metadata declared under `[project]` per [PEP 621](https://peps.python.org/pep-0621/) — `name`, `version` (or `dynamic = ["version"]` if generated), `description`, `readme`, `requires-python`, `license`, `authors`, `dependencies`, `optional-dependencies`? Tool-specific tables go under `[tool.<toolname>]` (`[tool.ruff]`, `[tool.mypy]`, `[tool.pytest.ini_options]`). Named failure modes: project metadata split between legacy `setup.py` AND `pyproject.toml` (one is the actual source of truth and the other drifts); `[project] dependencies` empty while a `requirements.txt` carries the real list; `version` hardcoded in two places (`pyproject.toml` + `__init__.py` `__version__`).
- **Dependency-group declarations** — For Python projects, are development-only dependencies declared under `[project.optional-dependencies]` (e.g., `dev = [...]`, `test = [...]`, `docs = [...]`) or — using PEP 735 dependency groups — under `[dependency-groups]`? The dev/test/runtime separation lets a deployer install only runtime deps. A `pyproject.toml` that lumps test deps into the runtime `dependencies` list is a finding.
- **`edition` declared explicitly** — Rust crates should declare `edition = "2021"` (or later) in `[package]` rather than relying on the implicit pre-2018 default. The edition controls language-feature availability and idiom defaults; missing-edition crates use the 2015 edition silently.
- **`workspace = true` for shared metadata** — In workspace member crates, fields that should match the workspace root (e.g., `version`, `edition`, `rust-version`, `license`, `repository`, `authors`) should be declared as `version.workspace = true` and inherited from `[workspace.package]` at the root. Manually duplicating these fields across member crates accumulates drift.
- **Dotted-key form for nested single-leaf config** — TOML's dotted-key form (`tool.ruff.line-length = 100`) is equivalent to a nested table (`[tool.ruff]` followed by `line-length = 100`) and is the readable form when the table has only one or two keys. For multi-key configuration, prefer the explicit `[section]` form — chains of dotted keys become hard to read once each section has more than ~3 fields.
- **Comment block for each `[section]` table's purpose** — Each non-obvious `[section]` should carry a one-to-three-line comment block above its header naming its purpose. `[package]` and `[dependencies]` don't need comments (well-known); `[profile.release-with-debug]` (a custom profile) does. The reviewer trying to understand a multi-table TOML file shouldn't have to read the consuming tool's docs to learn what each section is for.
- **No trailing whitespace** — TOML parsers are whitespace-tolerant on lines, but trailing spaces produce noisy diffs and break some text-processing tools. Enforce via the `trailing-whitespace` pre-commit hook.

## Solution Architect

- **Declarative over imperative — TOML preferred when the format permits** — TOML is a declarative configuration language. When the configuration question is "what should the system do?" rather than "how should the system compute its config?", TOML is the right choice. Named pattern: a `Cargo.toml` declares dependencies and profile tuning; a `build.rs` declares procedural build steps. Conflating them — putting computation in TOML via a custom DSL embedded in string values — is the anti-pattern. If logic is needed, push it to the consuming language; keep the TOML declarative.
- **Schema design for project-local configs** — When the project introduces a new TOML configuration file (a custom `myproject.toml`, not a tool's well-known config), is the schema sketched before the first file is written? What are the top-level tables, what are the required vs optional keys, what's the cardinality of arrays-of-tables? A TOML config authored ad-hoc and consumed by code that drifts to match it is the same maintenance debt as ad-hoc [JSON](json.md) — TOML's grammar doesn't enforce a schema, the project's discipline does.
- **Workspace layout for multi-package projects** — For Rust workspaces, is the layout one of the standard shapes: (a) flat workspace (members at the same level, e.g., `crates/foo/`, `crates/bar/`); (b) library-with-binary (`Cargo.toml` declares both `[lib]` and `[[bin]]`; one crate, two outputs); (c) hierarchical workspace (root + nested `crates/`)? Mixing patterns within one repo is a finding — pick one and document the rationale. Named failure mode: a workspace whose member crates are siblings of the root `Cargo.toml` AND nested under `crates/` AND also referenced as path dependencies — the dependency graph is ambiguous and pre-cargo-resolver-2 misresolves it.
- **Build-vs-runtime dependency separation** — In `Cargo.toml`, are dependencies correctly partitioned between `[dependencies]` (linked into the binary), `[dev-dependencies]` (for tests and benchmarks), and `[build-dependencies]` (for `build.rs`)? In `pyproject.toml`, the equivalent split is `dependencies` vs `optional-dependencies` (or dependency groups). Mixing partitions inflates the runtime closure and obscures supply-chain reasoning.
- **Profile inheritance and naming** — `[profile.*]` declarations support inheritance via `inherits = "release"` (or `"dev"`); custom profiles (e.g., `[profile.release-with-debug]`) should inherit from the closest cargo built-in profile and override only the fields that differ. Named anti-pattern: a custom profile that copies every field from `[profile.release]` rather than inheriting — when cargo's defaults change in a future toolchain, the custom profile silently diverges.
- **One source of truth per concern** — Workspace-level concerns (shared dependencies, shared metadata, shared lint configuration via `[workspace.lints]`) live at the workspace root with member crates opting in via `workspace = true`. Member-specific concerns live in the member crate's `Cargo.toml`. A workspace where each member redeclares the same dependency version is fragile to update; a workspace where members override the workspace dependency with no comment is harder to reason about than uniform inheritance.

## Security

- **TOML parser hardening** — TOML's strict spec makes parser exploits rarer than [YAML](https://yaml.org/) (which has document-construction-from-arbitrary-types via tags) or pickle-like formats. There is no `!Construct` analog; no aliases or merge keys; no comment-as-code escape. The remaining concern: resource exhaustion via deeply-nested tables, very long strings, very large integer literals, or arrays-of-tables with millions of entries. For untrusted-source TOML, parse with a known-maintained library ([toml-rs](https://docs.rs/toml/) for Rust; the standard library's `tomllib` for Python 3.11+; [toml](https://pypi.org/project/toml/) for legacy Python) and set size limits at the I/O layer (read at most N bytes) before handing bytes to the parser.
- **Pinned dependency versions in `Cargo.toml`** — Are dependencies in `[dependencies]` pinned with caret constraints (`"1.2.3"` → `^1.2.3` → matches `1.x.y` for `x >= 2` or `x == 2, y >= 3`) rather than wildcards (`"*"`) or unpinned tilde forms with overly-loose constraints? `Cargo.lock` records the exact resolved version, but the `Cargo.toml` constraint controls which versions cargo considers during update — looser constraints widen the supply-chain attack surface for `cargo update` runs. The combination of constrained `Cargo.toml` + committed `Cargo.lock` is the standard discipline.
- **[cargo-deny](https://github.com/EmbarkStudios/cargo-deny) configured** — Is `cargo deny check` configured with a `deny.toml`? A complete `deny.toml` configures four sections: `[advisories]` (CVE policy via [RustSec](https://rustsec.org/) advisory DB), `[licenses]` (allowed/denied SPDX identifiers), `[bans]` (duplicate-version policy, denied crates), `[sources]` (allowed registries and git sources). Missing or incomplete `deny.toml` is a finding. Coordinate with the [Rust supplement](rust.md) Platform Engineering section.
- **[cargo-audit](https://github.com/RustSec/rustsec/tree/main/cargo-audit) in CI** — Is `cargo audit` run against `Cargo.lock` in CI? `cargo audit` scans for known CVEs in the resolved dependency graph; new advisories published after the lockfile was generated will trigger findings on the next CI run. `cargo deny` subsumes most `cargo audit` functionality via `[advisories]` but `cargo audit` alone is acceptable for projects not yet running `cargo deny`.
- **Path dependencies and git dependencies as trust boundaries** — A `Cargo.toml` entry like `mylib = { path = "../mylib" }` or `mylib = { git = "https://github.com/somewhere/mylib.git" }` adds a trust boundary: the local path or remote repository is now a code-execution surface. Each such entry should be justified — for workspaces the path entry is normal; for external git deps the URL owner is a trust dependency that should be documented.
- **`build.rs` discipline** — A crate with a `build.rs` script runs that script (arbitrary Rust code) on every `cargo build`. Pulling a crate with a malicious `build.rs` from `crates.io` is remote code execution at build time. The defense is supply-chain review at dependency-add time (verify the crate author, check publication history) plus `cargo deny`'s `[bans]` section to block known-malicious crates.
- **No secrets in TOML committed to version control** — Are API keys, tokens, database URLs, or credentials present in committed TOML files? `Cargo.toml` and `pyproject.toml` are public per their commit-to-repo convention; embedding secrets in them is equivalent to publishing those secrets. Use environment variables, `.env` files (gitignored), or a secrets manager — never plain values in committed TOML. Detector: scan for high-entropy strings via `detect-secrets` or `gitleaks` in pre-commit.

## Quality Engineering

- **[taplo](https://taplo.tamasfe.dev/) for linting and formatting** — Is `taplo lint *.toml` and `taplo fmt --check *.toml` run as a pre-commit hook AND in CI? [taplo](https://taplo.tamasfe.dev/) is the canonical TOML linter+formatter (analogous to `cargo fmt` for Rust or `ruff format` for Python). Treat lint warnings as build failures; treat format violations as commit-blockers. A project without an enforced TOML formatter accumulates whitespace, quoting, and key-order drift that masks substantive diffs.
- **Schema validation against `taplo.toml` schema** — taplo supports schema validation against the [taplo schema catalog](https://taplo.tamasfe.dev/configuration/) (which includes `Cargo.toml`, `pyproject.toml`, `rust-toolchain.toml`, and others). Configure `taplo.toml` (or `.taplo.toml`) at the repo root to declare which schemas apply to which files; taplo will then validate during `taplo lint`. Named pattern: `[schema] path = ".cargo/Cargo.toml"` mapped to the canonical Cargo schema URL.
- **`cargo verify-project`** — `cargo verify-project --frozen` parses `Cargo.toml` and reports any structural issues without requiring a network connection or a rebuild. A quick CI gate to confirm the manifest is well-formed before running the slower `cargo check` / `cargo test`.
- **Round-trip parse/serialize test** — For project code that reads and writes TOML, is there a test that loads a known document, re-serializes it, and asserts equality (modulo whitespace and key order)? Named failure mode: a reader that accepts `key = "value"` but a writer that emits `key = 'value'` (literal-string form) — the reader-writer cycle isn't a fixed point. The [toml-rs](https://docs.rs/toml/) crate's `serde` integration preserves shape on round-trip; ad-hoc string-build serialization frequently doesn't.
- **Positive and negative parse examples** — When the project owns a TOML schema, are positive (must-parse) and negative (must-fail-with-named-error) example documents present in `tests/`? A schema authored without negative tests over-permits silently — it accepts the example documents and accepts garbage for everything else.
- **Pre-commit hook for `check-toml`** — The [pre-commit-hooks](https://github.com/pre-commit/pre-commit-hooks) repo provides `check-toml` which runs Python's `tomllib` parser on every staged `.toml` file. This catches structural errors at commit time, before they reach CI. Standard pre-commit entry:

  ```yaml
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: check-toml
  ```

## Performance Engineer

- **`[profile.release]` `opt-level` tuning** — Is `opt-level = 3` declared explicitly (the cargo default for release builds) or has the project chosen a different value (`"s"` for size-optimized, `"z"` for aggressive size optimization, `2` for slightly faster compiles at minor runtime cost)? The choice is workload-dependent — a CLI tool where startup time matters favors smaller binaries; a numeric-throughput service favors `opt-level = 3`. Declare the chosen value rather than inheriting silently.
- **`lto` configuration tradeoff** — Link-time optimization (`lto = "thin"`, `"fat"`, or `false`) controls cross-crate inlining. `"fat"` LTO produces the smallest, fastest binary at the cost of 2–10x release compile time; `"thin"` LTO produces most of the benefit at modest compile cost; `false` (the default) skips LTO entirely. For CLI tools and binaries where users run the release artifact thousands of times, `"thin"` or `"fat"` LTO is the right tradeoff; for libraries (whose consumers control LTO at their own build time), library `Cargo.toml` should not force LTO on consumers.
- **`codegen-units = 1` tradeoff** — Setting `codegen-units = 1` in `[profile.release]` disables parallel codegen, which allows the optimizer to see the entire crate as one unit (more inlining opportunities, smaller binaries). The cost: release builds become serial (single-CPU-core bound). For a CI release-build pipeline running on many cores, this is a significant compile-time slowdown; for the final shipped artifact, the runtime gain is typically 5–15%.
- **`panic = "abort"` for binary size and predictability** — `panic = "abort"` in `[profile.release]` swaps the panic-handler from "unwind the stack and run drop handlers" to "abort the process immediately." This removes the unwinding machinery from the binary (smaller size) and avoids a class of subtle bugs where partial cleanup leaves the process in an inconsistent state. Tradeoff: `catch_unwind` tests and FFI consumers expecting unwinding are incompatible — verify before enabling.
- **Profile-guided optimization (PGO) config** — For workloads where runtime profiles can be collected, PGO is configured via `RUSTFLAGS="-Cprofile-generate=..."` (instrument), then a representative workload run, then `RUSTFLAGS="-Cprofile-use=..."` (rebuild with the profile). PGO is not declared in `Cargo.toml` directly but the workflow can be encoded via cargo aliases in `.cargo/config.toml`. For projects with hot-path performance requirements, PGO yields 5–25% throughput improvement at significant operational cost — adopt only when the workload justifies it.
- **Cargo's incremental compilation in dev profile** — `[profile.dev] incremental = true` is the cargo default; explicit declaration is for clarity. Disabling incremental in dev (`incremental = false`) trades dev compile-time for binary stability — useful in CI to avoid cache-poisoning bugs, hostile to a developer iteration loop. Don't conflate the two contexts in one profile.

## Technical Writer

- **TOML's comment support is a documentation surface** — Unlike [JSON](json.md), TOML supports `#` line comments anywhere. Use them: each non-obvious `[section]` table benefits from a one-to-three-line comment above its header naming its purpose; non-obvious key values benefit from a trailing or above-line comment naming the rationale ("# `lto = thin` chosen over `fat` because release compile time is the bottleneck"); each feature flag in `[features]` should carry a comment describing what it enables. The discipline parallels source-code commenting: comments name the why; the value names the what.
- **Key ordering by readability** — TOML does not require alphabetical key order; the convention is logical ordering (most-important first, related-keys grouped). In `[package]`: `name`, `version`, `edition`, `description`, `license`, `repository` is a more readable order than alphabetical (`description`, `edition`, `license`, `name`, `repository`, `version`). [taplo](https://taplo.tamasfe.dev/) supports key-order rules but does not enforce alphabetical by default; project-level convention drives the choice.
- **Section grouping that mirrors logical organization** — In `Cargo.toml`, the conventional section order is: `[package]`, `[lib]` (if any), `[[bin]]` (if any), `[features]`, `[dependencies]`, `[dev-dependencies]`, `[build-dependencies]`, `[profile.*]`, `[workspace]` (root only). Deviation is acceptable when a project-specific narrative calls for it, but the convention exists because readers expect it; surprises cost reader attention.
- **Schema documentation via `# Schema:` comments at file top** — For project-local custom TOML configs (not well-known tools), a brief schema description at the top of the file is the analog of a module-level docstring. Name the file's purpose, the top-level tables, and any required keys. Readers landing on the file should not have to read the consuming code to learn its shape.
- **Linkable references in comments** — Where a TOML file's behavior is governed by an external standard ([PEP 621](https://peps.python.org/pep-0621/), [SemVer 2.0](https://semver.org/), [the cargo manifest reference](https://doc.rust-lang.org/cargo/reference/manifest.html)), include the URL in a header comment. Maintainers updating the file should not have to guess which spec governs.
- **Whitespace-tolerance favors human authoring** — TOML's parser is whitespace-tolerant: blank lines between sections, indentation inside sections (optional, not required), and trailing whitespace after values are all permitted. Use the whitespace for visual organization. A `Cargo.toml` with `[package]` and `[dependencies]` jammed together on consecutive lines reads as one block; the same file with a blank line between them reads as two sections.

## Tooling

- **[taplo](https://taplo.tamasfe.dev/)** — Linter + formatter. Install via `cargo install taplo-cli --locked` (Rust) or `npm install -g @taplo/cli` (Node). Invocation: `taplo lint *.toml` (lint), `taplo fmt --check *.toml` (format check), `taplo fmt *.toml` (format in place). Configure via a `taplo.toml` (or `.taplo.toml`) at the repo root for repo-wide rules and schema mappings.
- **[cargo-deny](https://github.com/EmbarkStudios/cargo-deny)** — Supply-chain policy enforcement for Rust workspaces. Install via `cargo install cargo-deny --locked`. Invocation: `cargo deny check` (runs all four policy classes — advisories, licenses, bans, sources). Configure via `deny.toml` at the workspace root; see the [cargo-deny book](https://embarkstudios.github.io/cargo-deny/) for the full schema.
- **[cargo-audit](https://github.com/RustSec/rustsec/tree/main/cargo-audit)** — Single-purpose CVE scanner against the [RustSec](https://rustsec.org/) advisory DB. Install via `cargo install cargo-audit --locked`. Invocation: `cargo audit` (scans `Cargo.lock` against the advisory DB). Faster than `cargo deny` for the CVE-only case; both can coexist.
- **[pre-commit-hooks](https://github.com/pre-commit/pre-commit-hooks)' `check-toml`** — Parser-level TOML validation at commit time. Configured via `.pre-commit-config.yaml`:

  ```yaml
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: check-toml
      - id: end-of-file-fixer
      - id: trailing-whitespace
  ```

  Coordinate with the suite's existing `.pre-commit-config.yaml` shape — these hooks join the existing entries without disturbing project-specific local hooks.
- **Editor integration** — [taplo](https://taplo.tamasfe.dev/) ships a VS Code extension and a language-server (`taplo lsp stdio`) that provides on-keystroke schema-aware autocompletion, hover docs, and inline lint warnings. For projects with multi-author contribution, editor integration catches the same issues as the pre-commit hook earlier in the workflow.

## Anti-patterns

- **Wildcard dependency versions in `Cargo.toml` (`"*"`)** — `serde = "*"` matches every version of serde from 0.0.1 forward; the lockfile resolution becomes a roll of the dice. `crates.io` rejects published crates with wildcard deps; local crates can declare them, but doing so is a finding. Fix: declare a caret constraint matching the version family actually tested (`serde = "1"` for serde 1.x).
- **Duplicating shared metadata across workspace members** — In a multi-member workspace, manually redeclaring `version`, `license`, `repository`, `edition`, `rust-version` in each member crate accumulates drift — one member updates to `edition = "2024"` and the others stay on `"2021"` silently. Fix: declare in `[workspace.package]` at the root and reference via `field.workspace = true` in each member.
- **Flat top-level keys when a section would group better** — A `pyproject.toml` with `ruff-line-length = 100` and `ruff-target-version = "py312"` and `mypy-strict = true` at the root flattens what should be `[tool.ruff]` and `[tool.mypy]` tables. Fix: group related keys under named tables; the dotted-key form is fine for one-or-two-key groups, but more than two leaf keys is the threshold for explicit `[section]`.
- **Tabs inside string values** — TOML permits tab characters inside basic strings (silently) but most editors render them as variable-width and many text-processing tools normalize them. The result: a value that looks right in one editor and is silently wrong in another. Fix: use `\t` escape in basic strings, or literal strings with explicit tabs only when the consumer requires them.
- **Comments on commit-required lines that cargo rewrites** — Tools like cargo (specifically `cargo add` and `cargo update`) rewrite `Cargo.toml` to update dependency declarations. Inline comments on dependency lines (`serde = "1" # provides Serialize/Deserialize`) survive most cargo operations but can be lost on aggressive rewrites. Defense: put rationale comments ABOVE the line, not after the value, so cargo's value-rewrite preserves the comment block.
- **`[profile.dev]` with release-tuned optimizations** — Setting `opt-level = 3` or `lto = "fat"` in `[profile.dev]` slows dev compile times by 5–20x with no actionable benefit (the dev profile exists for fast iteration; the release profile exists for shipped binaries). Fix: keep dev profile defaults; if some debug-time runtime-perf is needed, define a custom profile (`[profile.bench-dev]` inheriting from dev) rather than corrupting `[profile.dev]`.
- **Mixing top-level keys with `[section]`-scoped keys** — TOML's section-membership rule is "the most-recent `[section]` header owns all subsequent keys until the next header." Interleaving root-table keys with section keys (a root key declared AFTER a `[section]` header) is an error in TOML 1.0 (the parser rejects it). The older TOML 0.5 was more permissive; legacy files may still exhibit the pattern and break under a strict parser. Fix: declare all root-table keys before the first `[section]` header.
- **Hand-rolled TOML parsing in string-manipulation code** — A project that needs to read TOML values and uses `grep` + `sed` instead of a real parser will silently mishandle multi-line strings, dotted keys, escape sequences, and comments. Fix: use a real TOML library — Python 3.11+'s standard-library `tomllib`, [toml-rs](https://docs.rs/toml/) for Rust, or [yj](https://github.com/sclevine/yj) (the cross-format converter) for shell pipelines.

## Maintenance

- **Update when TOML 1.0 spec evolves** — The [TOML 1.0](https://toml.io/en/v1.0.0) spec is stable; a TOML 1.1 (or later) revision would add features. Revisit this supplement when a new spec revision lands and update the baseline-standards section.
- **Update when [taplo](https://taplo.tamasfe.dev/) ships new defaults** — taplo's default formatter rules and lint rules occasionally change. Pin the taplo version in pre-commit (`rev: <version>` for the taplo pre-commit repo, or pin via `cargo install taplo-cli --version X.Y.Z`) and update intentionally rather than tracking floating versions.
- **Update when cargo profile semantics evolve** — Cargo's `[profile.*]` schema gains new keys (`split-debuginfo`, `debug-assertions`, `incremental`, `strip` were all added post-1.0). When a new key becomes a recommended default, update the Performance Engineer section.
- **Update when [PEP 621](https://peps.python.org/pep-0621/) or [PEP 735](https://peps.python.org/pep-0735/) evolves** — Python packaging standards continue to evolve through the PEP process. New PEPs that affect `pyproject.toml` schema (e.g., PEP 735's dependency groups) warrant a Software Engineering section update.
- **Update when cargo workspace inheritance gains capabilities** — `[workspace.dependencies]` and `[workspace.package]` were added relatively recently; future cargo versions may extend the inheritance machinery (e.g., to `[workspace.profile.*]` or `[workspace.lints]`). Update the Platform Engineering and Solution Architect sections when new inheritance surfaces stabilize.
- **Update when [cargo-deny](https://github.com/EmbarkStudios/cargo-deny) or [cargo-audit](https://github.com/RustSec/rustsec/tree/main/cargo-audit) ship new default policies** — Supply-chain tooling evolves with the threat landscape. When new advisory classes or new policy categories become available, update the Security section.
- **Forward link to crosslink contract** — If the suite's [crosslink](https://github.com/forecast-bio/crosslink) integration ever consumes TOML directly (e.g., a `crosslink swarm review` invocation that reads a `crosslink.toml` config), update [crosslink-contract.md](../crosslink-contract.md) and cross-reference here.
