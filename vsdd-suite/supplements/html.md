# HTML Language Supplement

These dimensions supplement the standard IAR domain reviews for projects whose content is delivered as HTML. HTML is the content language of browser-app projects — the document structure that CSS styles and JavaScript animates. During each domain review, apply the relevant section below in addition to the standard dimensions for that domain. This supplement is not an HTML tutorial; it assumes baseline HTML5 familiarity (elements, attributes, the document tree) and applies adversarial pressure to the dimensions where HTML choices materially affect accessibility, security, performance, and maintainability. For the broader browser-app interface concerns that span HTML + CSS + JS together (rendering safety, CSP, responsive design, focus management at the interface level), see the companion interface-type supplement [`browser-app.md`](browser-app.md); this supplement is HTML-specific and goes deeper on the document-structure dimensions browser-app.md treats in passing.

**Multi-domain authoring note:** the sections below were drafted with the relevant role-domain perspectives in mind — [Accessibility](../domains/role/ACCESSIBILITY-REVIEW.md) as the primary domain (HTML is the substrate accessibility is built on; WCAG 2.1 AA conformance starts with semantic markup), [UX](../domains/role/UX-REVIEW.md) (semantic structure mirrors information architecture; form ergonomics), [Security](../domains/role/SECURITY-REVIEW.md) and [Red Team](../domains/role/RED-TEAM-REVIEW.md) (HTML is the XSS surface; rendering boundaries determine whether user content executes), [Quality Engineer](../domains/role/QUALITY-ENGINEER-REVIEW.md) (validation tooling: [html-validate](https://html-validate.org/), [W3C validator](https://validator.w3.org/), [axe-core](https://github.com/dequelabs/axe-core)), [Performance Engineer](../domains/role/PERFORMANCE-ENGINEER-REVIEW.md) (resource hints, lazy loading, render-blocking resources), [Solution Architect](../domains/role/SOLUTION-ARCHITECT-REVIEW.md) (the structure/presentation/behavior separation that progressive enhancement depends on), [Platform Engineer](../domains/role/PLATFORM-ENGINEER-REVIEW.md) (build-pipeline minification, transfer encoding, cache headers), [Technical Writer](../domains/role/TECHNICAL-WRITER-REVIEW.md) (meta description, `<title>` quality, JSON-LD structured data), and [Localization](../domains/role/LOCALIZATION-REVIEW.md) (`lang`, `dir`, bidirectional text). The supplement is forward-looking against the 2026 HTML ecosystem (HTML Living Standard; widely-deployed `loading="lazy"`, `inert`, dialog element, popover API; ARIA 1.2).

**Scope of this supplement:** any project that delivers an HTML document to a browser — single-page apps, multi-page sites, server-rendered pages, static sites. Email HTML is out of scope (the rendering surface there is materially different — table-based layouts, no JS, restricted CSS — and warrants a separate supplement if the suite ever ships an HTML-email artifact). The recommendation: write HTML5 against the [HTML Living Standard](https://html.spec.whatwg.org/) and assume modern browser support (Chrome / Firefox / Safari current and one prior major version) unless DESIGN.md explicitly widens the support matrix.

## Baseline standards

These are the floor for every HTML document in a VSDD project. A document missing any of them is a finding regardless of which domain review is active.

- **HTML5 doctype** — Does every HTML document start with `<!DOCTYPE html>`? The doctype triggers standards mode; without it, browsers fall back to quirks mode which silently breaks layout and selector behavior in ways no test catches. Quirks-mode rendering is the kind of cross-browser difference that looks like a UX bug but is actually a missing doctype.
- **Semantic HTML elements over generic containers** — Is the document structured with `<nav>`, `<main>`, `<article>`, `<section>`, `<aside>`, `<header>`, `<footer>`, `<figure>`, `<figcaption>` where appropriate, rather than `<div>` everywhere? Semantic elements carry implicit ARIA roles, navigability for assistive technology, and document structure that machine readers (search engines, screen readers, reader-mode) can interpret. A page whose entire structure is `<div>` is technically valid HTML and functionally inaccessible.
- **ARIA only where semantic HTML doesn't suffice** — Is ARIA (`role`, `aria-*`) used to fill gaps the native element set leaves, not to relabel elements that already have correct semantics? `<button role="button">` is redundant; `<div role="button">` is a finding (the correct fix is to use a `<button>`). The first rule of ARIA per [WAI-ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/) is "don't use ARIA when a native element exists." Incorrect ARIA is worse than no ARIA — it misinforms assistive technology.
- **UTF-8 charset declared as the first child of `<head>`** — Is `<meta charset="utf-8">` the first element in `<head>`, before any other meta tags or content? The HTML parser scans the first ~1024 bytes for the charset declaration; a charset declared after a `<title>` containing non-ASCII characters can be parsed wrong. UTF-8 is the only acceptable encoding for new projects.
- **Viewport meta tag for responsive layouts** — Does the document include `<meta name="viewport" content="width=device-width, initial-scale=1">`? Without it, mobile browsers render at a desktop-width virtual viewport and scale down, producing tiny text. Avoid `user-scalable=no` and `maximum-scale=1` — they prevent users from zooming, which is a WCAG 1.4.4 (Resize Text) failure.
- **`lang` attribute on the root element** — Is `<html lang="en">` (or the appropriate locale code) set? Screen readers use `lang` to choose pronunciation rules; translation tools use it to detect source language; search engines use it to rank results by locale. A document with no `lang` is rendered with the user-agent default, which is wrong for non-English content and ambiguous for English.
- **`<title>` present and meaningful** — Every document has a `<title>` element in `<head>`; the title is unique per page, describes the page's purpose, and is the primary signal screen readers announce on page load and that browser tabs / search results display. A title of "Untitled" or the framework default is a finding.

## Accessibility

[Accessibility](../domains/role/ACCESSIBILITY-REVIEW.md) is the primary domain for HTML — the document structure determines what assistive technology can see, navigate, and operate. WCAG 2.1 Level AA is the floor for VSDD projects.

- **WCAG 2.1 AA conformance** — Is the document tested against [WCAG 2.1 Level AA](https://www.w3.org/WAI/WCAG21/quickref/?currentsidebar=%23col_customize&levels=aaa) success criteria? Named tools: [axe-core](https://github.com/dequelabs/axe-core) (automated scan; ~30–40% of WCAG failures), [Lighthouse](https://developers.google.com/web/tools/lighthouse) (accessibility audit + performance), [Pa11y](https://pa11y.org/) (CI-friendly accessibility CLI), [WAVE](https://wave.webaim.org/) (browser extension for manual review). Automated scanning is the floor; manual keyboard + screen-reader testing is required.
- **Landmark roles via semantic elements** — Does the document expose landmark regions for screen-reader navigation: `<header>` (banner), `<nav>` (navigation), `<main>` (main), `<aside>` (complementary), `<footer>` (contentinfo)? Screen readers offer landmark-navigation shortcuts; a page with no landmarks forces users to traverse linearly. Exactly one `<main>` per page; multiple `<nav>` regions need `aria-label` to distinguish them ("Primary navigation" vs "Footer navigation").
- **Heading hierarchy** — Does the heading structure (`<h1>` through `<h6>`) form a logical outline without skipped levels? `<h1>` is the page's primary heading (one per page); `<h2>` for top-level sections; `<h3>` for subsections nested under `<h2>`. Skipping from `<h2>` to `<h4>` is a WCAG 1.3.1 failure — assistive technology relies on the hierarchy to build a navigable outline.
- **Alt text on every `<img>`** — Every `<img>` element has an `alt` attribute. The attribute is required even when the image is decorative — in that case `alt=""` (empty string) tells assistive technology to skip it; missing `alt` causes screen readers to announce the file name as a fallback, which is always worse. Alt text describes the image's purpose in the document, not its appearance — for a logo that links to home, `alt="MySite home"` is correct; `alt="logo"` is not.
- **Form labels programmatically associated** — Every form control (`<input>`, `<select>`, `<textarea>`) has a programmatically associated label via `<label for="id">` matching `<input id="id">`, or `aria-labelledby`, or wrapping the input inside a `<label>`. Placeholder text is not a label — placeholders disappear on focus and have insufficient contrast. A form with placeholder-only labels is a WCAG 1.3.1 + 3.3.2 failure.
- **Required and error states programmatic** — Required fields use `required` (HTML attribute) AND/OR `aria-required="true"` (for assistive technology where `required` is insufficient). Error states use `aria-invalid="true"` on the field and `aria-describedby` pointing to the error-message element's ID — visual red borders alone are a WCAG 1.4.1 (Use of Color) failure.
- **Focus management** — Does focus land in the right place after every DOM change? After a modal opens, focus moves to the modal (first focusable element or the dialog itself with `tabindex="-1"`); after a modal closes, focus returns to the element that triggered it. The `<dialog>` element handles this natively via `showModal()`; custom-modal implementations must hand-roll the focus management. Test by opening every modal/dialog with a keyboard and pressing Tab — focus must stay within and Escape must close + restore.
- **Keyboard operability** — Every interactive element is reachable and operable with Tab, Shift+Tab, Enter, Space, arrow keys, and Escape as appropriate. Tab order follows visual reading order — a `tabindex` greater than 0 reorders tab flow and is almost always a finding (use the document order instead). `tabindex="-1"` removes the element from tab flow but keeps it programmatically focusable (correct for modal-container focus targets); `tabindex="0"` adds a non-interactive element to tab flow (correct only when paired with appropriate ARIA role and keyboard handlers).
- **Color contrast** — Text contrast meets WCAG AA: 4.5:1 for normal text, 3:1 for large text (18pt+ or 14pt+ bold) and UI component boundaries. The contrast is a property of foreground + background as rendered, including hover and focus states. Test with a tool that calculates from rendered colors — visual judgment is unreliable. HTML's contribution: the element's role (text vs UI component vs decorative) determines which threshold applies.
- **Skip link as first interactive element** — Does the document include a skip-navigation link as the first focusable element (`<a href="#main">Skip to main content</a>`)? Keyboard users otherwise tab through the entire navigation on every page load. The skip link can be visually hidden but must become visible on focus.
- **Language changes within a document** — When a passage uses a different language from the document's `lang`, is that passage wrapped in an element with the inline `lang` attribute (`<span lang="fr">bonjour</span>`)? Screen readers switch pronunciation rules at the boundary; without the attribute they mispronounce.

## UX

[UX](../domains/role/UX-REVIEW.md) treats HTML structure as the substrate of information architecture — the document outline should mirror the user's mental model.

- **Semantic structure mirrors information architecture** — Does the document outline (the heading + landmark structure) match the information architecture DESIGN.md specifies? A page whose visual hierarchy is "Title → Section → Subsection" but whose HTML is `<div><div><div>` has lost the structure for assistive technology and search engines, and is implicitly inviting CSS-only visual hierarchy that breaks when CSS fails.
- **Form-field grouping with `<fieldset>` and `<legend>`** — Are related form fields grouped inside `<fieldset>` with a `<legend>` describing the group? Radio-button groups and checkbox groups need this — the group's purpose ("Shipping address" vs "Billing address") is announced once at the group boundary rather than repeated per-control. The legend is the only correct way to label a group of controls; `<label>` is for individual controls.
- **Error-state markup colocated with the field** — When a field has a validation error, the error message is in the DOM near the field, associated via `aria-describedby`, and announced via an `aria-live="polite"` region (or `role="alert"` for critical errors). A toast notification at the page corner that doesn't move focus and isn't programmatically associated with the failed field is a UX + accessibility failure — sighted-mouse users miss it because it's outside their visual focus; keyboard / screen-reader users miss it because there's no programmatic connection.
- **Loading and async-state markup** — When content is loading or an async operation is in progress, does the DOM expose the state? `<output aria-live="polite">Loading...</output>` for status updates; `aria-busy="true"` on the container during the operation; `role="status"` for non-critical confirmation messages. A spinner with no programmatic state is invisible to assistive technology.
- **Native dialog over custom modal** — Use the [`<dialog>` element with `showModal()`](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/dialog) for modal dialogs in 2026 — it handles focus trap, backdrop, Escape-to-close, and the `inert` semantics natively. Custom `<div role="dialog">` implementations re-implement what the platform provides for free and are the canonical source of focus-trap bugs.
- **Inputs typed for the data** — Does every `<input>` use the most specific `type` attribute available? `type="email"`, `type="tel"`, `type="url"`, `type="number"`, `type="date"`, `type="search"`. Mobile browsers show appropriate keyboards; desktop browsers offer appropriate validation; password managers and autofill detect intent. `type="text"` for an email field loses all of that.

## Security

[Security](../domains/role/SECURITY-REVIEW.md) treats HTML as the XSS surface. Every place where user-controlled data reaches the DOM is a potential injection point.

- **Never `innerHTML` with untrusted strings** — `element.innerHTML = userString` parses the string as HTML and executes any scripts, event handlers, or `javascript:` URIs it contains. The safe form: `element.textContent = userString` (treats the string as text); for structured HTML output, build a `DocumentFragment` and append elements with their attributes set via `.setAttribute()` or DOM properties. This is the primary XSS surface for JavaScript that touches the DOM. Coordinate with [browser-app.md](browser-app.md) § Security (Rendering safety) and the [JavaScript / TypeScript supplement](javascript-typescript.md) § Security.
- **Sanitize on input OR escape on output (pick one consistently)** — Either the data is sanitized at the trust boundary (rejected or normalized before storage) OR it is escaped at every render site (treated as untrusted text at output). Mixing the two strategies — sanitizing some paths and escaping others — leaves gaps. The output-escape strategy is more robust: untrusted data is treated as untrusted at every render site, so a new render site automatically inherits the protection. For sanitization use [DOMPurify](https://github.com/cure53/DOMPurify) for HTML allow-listing — never hand-rolled regex.
- **Content Security Policy headers** — Is a [CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/CSP) present, delivered as an HTTP `Content-Security-Policy` header (preferred) or `<meta http-equiv="Content-Security-Policy">` (acceptable, with limitations — the header form supports more directives)? A baseline CSP: `default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'`. Avoid `'unsafe-inline'` and `'unsafe-eval'` in `script-src` — they neutralize the policy's XSS defense. For inline scripts that are necessary, use a CSP nonce or hash.
- **`rel="noopener noreferrer"` on every `target="_blank"` link** — A link with `target="_blank"` opens a new window that, in older browsers without [the 2021 change to default behavior](https://developer.chrome.com/blog/target-blank/), can access the originating window via `window.opener` and navigate it to a phishing page. The defense: `rel="noopener noreferrer"` on every external link with `target="_blank"`. Modern browsers default to `noopener` for `target="_blank"`, but the explicit declaration is the safe form and protects users on older browsers.
- **`<iframe sandbox>` for embedded third-party content** — Every `<iframe>` loading content from a different origin uses the `sandbox` attribute to restrict what the embedded document can do. Start with `sandbox=""` (everything restricted) and add capabilities (`allow-scripts`, `allow-same-origin`, `allow-forms`) only as required. An unsandboxed third-party iframe can navigate the parent, run scripts, read storage — every capability of a same-origin script.
- **Never `javascript:` URIs in `href` or `src`** — `<a href="javascript:doThing()">` and `<iframe src="javascript:...">` execute arbitrary code. The safe form: attach an event listener via JavaScript (`button.addEventListener('click', handler)`). For any URL attribute (`href`, `src`, `action`, `formaction`, `cite`, `poster`) where the value comes from user input, validate the protocol is `https:`, `http:`, or `mailto:` before placing the value in the attribute. Coordinate with [browser-app.md](browser-app.md) § Security (URL injection).
- **Subresource Integrity (SRI) on third-party scripts** — Every `<script src>` and `<link rel="stylesheet">` loaded from a third-party origin uses the `integrity` attribute with a SHA-384 hash. Without SRI, a compromised CDN serves arbitrary code with the privileges of your origin. Modern build tooling generates the hashes automatically.
- **`autocomplete` on sensitive fields** — Password fields use `autocomplete="current-password"` or `autocomplete="new-password"` (the latter for registration); credit-card fields use `autocomplete="cc-number"`; one-time-code fields use `autocomplete="one-time-code"`. The browser's password manager and autofill rely on these signals to fill correctly and securely. `autocomplete="off"` on a password field does not prevent password manager use in modern browsers; it does prevent autofill in form fields where autofill is desirable.

## Quality Engineer

[Quality Engineer](../domains/role/QUALITY-ENGINEER-REVIEW.md) treats HTML validation and accessibility automated scanning as quality gates.

- **HTML validation in CI** — Is HTML validated against the [HTML Living Standard](https://html.spec.whatwg.org/) via [html-validate](https://html-validate.org/) (CI-friendly, configurable, integrates with build tooling) or the [W3C Markup Validation Service](https://validator.w3.org/) (canonical reference, web UI + API)? Invalid HTML is a class of defect that browsers paper over via the parser's error-recovery rules — the recovery is browser-specific, which is the source of "works in Chrome, broken in Safari" bugs that are actually invalid markup interpreted differently. Treat validation as a gate, not advisory.
- **Accessibility automated tests via axe-core** — Is [axe-core](https://github.com/dequelabs/axe-core) (or `axe-playwright` / `axe-cli`) run in the test suite and configured to fail on violations? Coordinate with [browser-app.md](browser-app.md) § Quality Engineering (Accessibility automated scanning). Automated scanning catches ~30–40% of WCAG failures; treat it as the floor, not the ceiling — manual keyboard + screen-reader testing covers the rest.
- **Semantic-correctness tests** — Beyond validation, are there tests asserting the document structure DESIGN.md specifies? Named patterns: "the page has exactly one `<main>` landmark"; "every form input has an associated label"; "the heading outline has no skipped levels"; "every `<img>` has an `alt` attribute". These assertions belong in the integration test layer where the rendered DOM is queryable.
- **Visual regression tests** — For documents whose rendered visual appearance matters, is there a visual-regression test (Playwright screenshots, [Percy](https://percy.io/), [Chromatic](https://www.chromatic.com/)) that catches unintended layout changes? A semantic-correctness test catches structural changes; visual-regression tests catch CSS-applied changes that the HTML test layer cannot see.
- **Multi-browser test coverage** — Is the test suite run against Chrome, Firefox, and Safari (or a documented subset with rationale)? HTML parsing differs across engines on edge cases (malformed markup, exotic Unicode, novel features) — single-engine testing misses the differences. Playwright's multi-engine support is the standard pattern.
- **Pre-commit validation hook** — Is HTML validation wired into the pre-commit hook chain so invalid markup never enters the repository? Pattern: `html-validate src/**/*.html` as a `pre-commit` framework hook. CI duplicates the check as a backstop for direct-to-main commits (which should be blocked by branch protection — see [PE](../domains/role/PLATFORM-ENGINEER-REVIEW.md)).

## Performance Engineer

[Performance Engineer](../domains/role/PERFORMANCE-ENGINEER-REVIEW.md) treats HTML as the document the browser must parse, render, and paint before the user sees content. Every byte of HTML is on the critical path.

- **Lazy-loading images via `loading="lazy"`** — Every `<img>` and `<iframe>` below the fold uses `loading="lazy"` so the browser defers loading until the element is near the viewport. For above-the-fold images use `loading="eager"` (the default — make it explicit for clarity). For LCP (Largest Contentful Paint) images use `fetchpriority="high"` to signal the browser to prioritize the network request.
- **Resource hints — `preload`, `prefetch`, `preconnect`, `dns-prefetch`** — Are critical resources hinted to the browser? `<link rel="preload" as="script" href="critical.js">` for resources the page will need immediately; `<link rel="prefetch" href="next-page.html">` for resources likely needed on next navigation; `<link rel="preconnect" href="https://api.example.com">` to establish TLS / TCP connections early; `<link rel="dns-prefetch" href="//cdn.example.com">` for DNS-only hints. Each hint costs network resources — use them deliberately for measured-bottleneck resources, not speculatively for everything.
- **Deferred and async scripts** — Scripts that aren't required for initial render use `defer` (executes after HTML parsing, in document order — the default for most scripts) or `async` (executes as soon as it loads, out of order — for scripts with no document dependency). Inline `<script>` and `<script src>` without `defer`/`async` block HTML parsing — render-blocking scripts in `<head>` are the most common cause of slow time-to-interactive.
- **Render-blocking resources audit** — Run [Lighthouse](https://developers.google.com/web/tools/lighthouse) and examine the "Eliminate render-blocking resources" audit. The render-blocking set is the resources the browser must download and parse before painting; minimizing it is the primary lever for first paint. Named techniques: inline critical CSS in `<head>`, defer non-critical CSS via `<link rel="preload" as="style" onload="this.rel='stylesheet'">`, move scripts to the end of `<body>` or use `defer`, eliminate font-loading FOIT via `font-display: swap` in CSS.
- **`<picture>` and `srcset` for responsive images** — Are large images served at multiple resolutions via `<picture>` (for art direction across viewport sizes) or `srcset` + `sizes` (for resolution-density variants)? A single 4K image served to a 320px mobile viewport wastes bandwidth and degrades LCP. Modern build tooling (Vite, Next.js, [Astro](https://astro.build/) image components) generates the variants automatically.
- **`<img>` width and height attributes** — Every `<img>` declares `width` and `height` attributes matching the image's intrinsic aspect ratio. The browser uses them to reserve layout space before the image loads, preventing Cumulative Layout Shift (CLS). An image with no dimensions causes content reflow when it loads, which is a poor UX and a [Core Web Vitals](https://web.dev/articles/vitals) failure.
- **Avoid unnecessary DOM depth and node count** — Documents with many thousands of DOM nodes incur measurable layout and paint costs. Named anti-pattern: rendering a 10,000-row table without virtualization (every row is layout-cost on every reflow); deeply-nested `<div>` containers where flatter structure would suffice. The Lighthouse "Avoid an excessive DOM size" audit flags the threshold; the project's own performance budget defines the acceptable ceiling.

## Solution Architect

[Solution Architect](../domains/role/SOLUTION-ARCHITECT-REVIEW.md) treats HTML as the structural layer of the three-layer separation that defines a browser-app.

- **Separation of structure (HTML) / presentation (CSS) / behavior (JS)** — Are the three concerns separated by file, or are they entangled? Named anti-patterns: inline `style="..."` attributes (presentation in HTML); `onclick="doThing()"` inline event handlers (behavior in HTML); CSS that depends on JS-injected classes for layout (presentation depends on behavior). The separation isn't dogmatic — there are valid cases for inline critical CSS (performance) and inline event handlers (legacy compatibility) — but each violation needs explicit rationale, not casual convenience.
- **Progressive enhancement** — Does the document deliver its core content and primary functionality before JavaScript runs? A page that renders blank until JS executes is broken for slow networks, JS-disabled environments, and assistive technology that loads content before JS. The architectural test: disable JavaScript, reload the page — what works? For a content site, all content should be visible; for an app, at least the navigation and a meaningful explanation should render. SPAs that fail this test owe DESIGN.md an explicit accepted-deviation rationale.
- **Graceful degradation** — When a feature is unavailable (the network is offline, an API call fails, a feature uses a browser API the current browser lacks), does the document degrade gracefully or break? Named patterns: `<noscript>` fallback content for critical features that require JS; `@supports` CSS feature queries to provide fallback styling; capability detection via `if ('IntersectionObserver' in window)` rather than user-agent sniffing.
- **Custom elements for component boundaries** — For documents with reusable component structure, are [custom elements](https://developer.mozilla.org/en-US/docs/Web/API/Web_components) (Web Components) used to define encapsulated component boundaries? `<my-card><h2>Title</h2></my-card>` provides the same architectural benefit as a framework component while remaining standards-based and framework-agnostic. The pattern is appropriate for component libraries that outlive specific framework choices.
- **Server-rendered vs client-rendered HTML** — Is the HTML structure delivered by the server (SSR) or generated client-side after JS executes (CSR)? The choice has architectural consequences for first paint, SEO, accessibility-on-slow-networks, and the complexity of the build pipeline. DESIGN.md should document the choice and the rationale.

## Platform Engineer

[Platform Engineer](../domains/role/PLATFORM-ENGINEER-REVIEW.md) treats HTML as a build-pipeline artifact subject to minification, compression, and caching.

- **Minification in build output** — Is HTML minified in production builds (whitespace collapsed, comments stripped, optional tags removed)? Named tools: [html-minifier-terser](https://github.com/terser/html-minifier-terser), the HTML minification step in build frameworks ([Vite](https://vitejs.dev/), [Next.js](https://nextjs.org/), [Astro](https://astro.build/)). Minification is on by default in most modern build tools — verify the production build actually produces minified output. Source HTML in version control stays human-readable.
- **Gzip / Brotli content encoding** — Does the server deliver HTML with `Content-Encoding: br` (Brotli, preferred — ~20% smaller than gzip for HTML) or `Content-Encoding: gzip` (broader compatibility)? Most CDNs (Cloudflare, Fastly, CloudFront) negotiate compression automatically; verify the response headers show the encoding for HTML responses.
- **Cache headers tuned for content stability** — Are cache headers set appropriately for each HTML response? Long-lived cache (`Cache-Control: public, max-age=31536000, immutable`) for fingerprinted asset URLs; short-lived cache (`Cache-Control: public, max-age=0, must-revalidate`) for HTML entry points that should always check for updates. A static-site entry point cached for a year cannot be invalidated for users who don't clear cache.
- **Service worker offline strategy** — For PWA / offline-capable projects, does the service worker cache HTML appropriately? Stale-while-revalidate is the common pattern for HTML; cache-first risks serving stale content; network-first defeats the offline use case. The strategy choice is DESIGN.md-visible.
- **Build-pipeline pre-commit hooks** — Are pre-commit hooks running [Prettier](https://prettier.io/) (HTML formatting), [html-validate](https://html-validate.org/) (validation), and project-specific HTML checks (no `<script>` outside designated paths, no `style="..."` attributes, etc.)? Hook the discipline at the commit boundary so invalid or non-conforming markup never lands.

## Technical Writer

[Technical Writer](../domains/role/TECHNICAL-WRITER-REVIEW.md) treats HTML as the documentation surface for the page's purpose, embedded for both human readers and machine consumers.

- **`<meta name="description">` per page** — Every page has a `<meta name="description" content="...">` that summarizes the page's content in 150–160 characters. Search engines display the description in result snippets; social-media sharing tools use it as a fallback when [Open Graph](https://ogp.me/) tags are absent; assistive technology and reader-mode tools surface it for context. A missing description leaves the search engine to infer one from page content, which is rarely as good.
- **`<title>` quality and uniqueness** — Is each page's `<title>` specific to the page's purpose and unique within the site? Pattern: "Page Purpose | Site Name" (e.g., "Sign In | Bookmark Manager"). The title is the primary signal in browser tabs, browser history, search results, and screen-reader page-load announcements. A site where every page has the same title is unnavigable in browser history.
- **Open Graph and Twitter Card metadata** — Are social-sharing metadata tags present for pages that are shared? `<meta property="og:title">`, `<meta property="og:description">`, `<meta property="og:image">`, `<meta property="og:type">` for [Open Graph](https://ogp.me/); the `twitter:*` equivalents for X / Twitter. Pages without OG metadata produce unattractive shares (no image, generic title) which suppresses sharing.
- **Structured data via JSON-LD** — Where content has machine-readable structure (articles, products, events, organizations, FAQs), is [Schema.org](https://schema.org/) markup present as JSON-LD in `<script type="application/ld+json">`? Google Search uses structured data for rich-result eligibility; voice assistants and aggregators use it as a content source. JSON-LD is the preferred syntax (microdata and RDFa are older alternatives); validate with the [Schema.org validator](https://validator.schema.org/) or [Google's Rich Results Test](https://search.google.com/test/rich-results).
- **Canonical URL when content has multiple paths** — Is `<link rel="canonical" href="https://example.com/canonical-path">` present when a piece of content is reachable at multiple URLs (with/without trailing slash, with/without query parameters, mobile/desktop variants)? Canonical URLs prevent search-engine duplicate-content penalties and consolidate signals to the canonical version.
- **Inline comments in source HTML** — Does source HTML carry comments (`<!-- ... -->`) explaining non-obvious structure or decisions? Same standard as inline code comments: explain *why*, not *what*. `<!-- Skip link for keyboard users; visually hidden by .visually-hidden CSS -->` is documentation; `<!-- div -->` is noise. Minification strips comments from production output; source-tree comments are for maintainers.

## Localization

[Localization](../domains/role/LOCALIZATION-REVIEW.md) treats HTML's locale-handling attributes as the primary signal for assistive technology, search engines, and translation tooling.

- **`lang` attribute on the root element** — Is `<html lang="en">` (or the appropriate IETF [BCP 47](https://www.rfc-editor.org/rfc/bcp/bcp47.txt) language tag) set on the root element? See § Baseline standards. The attribute carries to every descendant; inline `lang` attributes override locally for passages in a different language.
- **`dir` attribute for bidirectional text** — For documents in right-to-left languages (Arabic, Hebrew, Persian, Urdu), is `<html dir="rtl">` set? CSS logical properties (`margin-inline-start`, `padding-inline-end`, `text-align: start`) respect the direction; directional CSS (`margin-left`, `text-align: left`) does not. The directional attribute change cascades to layout, scrollbar position, and form-control alignment — RTL is a design-time concern, not an afterthought CSS class.
- **Locale-aware content via `hreflang`** — When the same content exists in multiple locales, are alternate-language pages declared via `<link rel="alternate" hreflang="es" href="...">`? Search engines use `hreflang` to serve the appropriate locale variant to users. Self-referential `hreflang` (the page declaring its own language) and an `x-default` fallback are recommended.
- **Translation-key extraction from HTML templates** — If the build pipeline extracts user-visible strings from HTML for translation, are the strings marked with the framework's i18n attribute (e.g., `data-i18n="key"`, `i18n` in Angular, `<Trans>` in [react-i18next](https://react.i18next.com/))? Hardcoded strings in HTML are invisible to extraction tooling and become English-only in shipped builds. Coordinate with the [JavaScript / TypeScript supplement](javascript-typescript.md) § Localization.
- **Translatable attribute values** — Are user-visible attribute values (`title`, `alt`, `placeholder`, `aria-label`, `value` on submit buttons) extracted for translation, not just text content? A `<button value="Submit">` with no extraction wrapper ships the English literal regardless of locale. The extraction tooling must understand which attributes carry user-visible strings.
- **`<time>` element with `datetime` attribute** — Are dates and times wrapped in `<time datetime="2026-05-20T14:30Z">May 20, 2026</time>`? The `datetime` attribute carries the machine-readable ISO 8601 form; the element content can be locale-formatted prose. Assistive technology and translation tools use the structured form; CSS / JS can rewrite the visible form per locale without losing the machine signal.

## Tooling

Concrete tools the supplement names. Each is a known-good choice as of 2026; the project picks per its existing convention.

- **[html-validate](https://html-validate.org/)** — CI-friendly HTML validator with configurable rule sets; the recommended default for VSDD projects that need validation as a quality gate.
- **[W3C Markup Validation Service](https://validator.w3.org/)** — Canonical reference validator; useful for spot-checks and pre-deployment audits where html-validate's rule set may differ from the spec.
- **[Prettier](https://prettier.io/)** — Opinionated formatter with HTML support; runs as a pre-commit hook to enforce consistent whitespace, attribute order, and quote style.
- **[axe-core](https://github.com/dequelabs/axe-core)** — Accessibility testing engine; integrates with Playwright, Cypress, Jest, and CI; the recommended default for automated WCAG scanning.
- **[Lighthouse](https://developers.google.com/web/tools/lighthouse)** — Performance + accessibility + SEO + best-practices audit; runs in Chrome DevTools and via CLI; the recommended default for performance budgeting.
- **[Pa11y](https://pa11y.org/)** — CI-friendly accessibility CLI; alternative to axe-cli for projects that prefer its rule presentation.
- **[DOMPurify](https://github.com/cure53/DOMPurify)** — HTML sanitizer for the cases where untrusted HTML must be rendered (rich-text comments, user-supplied markdown that's been rendered to HTML); never hand-roll sanitization.
- **[html-minifier-terser](https://github.com/terser/html-minifier-terser)** — Build-pipeline HTML minifier; usually integrated via the build framework rather than invoked directly.

**Pre-commit hook patterns:** the standard chain for HTML in a VSDD project: (1) Prettier on every staged `.html` file (formatting); (2) html-validate on every staged `.html` file (validation); (3) project-specific HTML checks (no inline styles, no inline event handlers, no `target="_blank"` without `rel="noopener"`); (4) on CI re-run all three plus axe-core against the built output as a regression gate. The pre-commit framework configuration lives in `.pre-commit-config.yaml`; see the [Platform Engineering supplement on pre-commit framework integration](../domains/role/PLATFORM-ENGINEER-REVIEW.md).

## Anti-patterns

Concrete bad patterns. Each is a finding when encountered in source HTML.

- **`<div>` or `<span>` as button / link replacement** — `<div onclick="...">Click me</div>` is not keyboard-accessible (no Tab focus, no Enter activation), is invisible to assistive technology as an interactive element, and is the canonical accessibility failure. The fix is always `<button>` (for in-page actions) or `<a href="...">` (for navigation). If the visual styling needs to differ from native button defaults, style the `<button>` — don't rebuild the button from a `<div>`.
- **Inline `style="..."` attributes** — Inline styles entangle presentation with structure, can't be overridden by stylesheets without `!important` (which compounds the problem), bypass CSS variables and design tokens, and accumulate as drift. The narrow exception: inline `style` for one-off dynamic positioning where the value is computed at runtime and isn't reusable. For everything else: a class in the stylesheet.
- **Tables for layout** — `<table>` is for tabular data — rows and columns of related values. Using tables for page layout (the 2005 pattern) confuses assistive technology (which announces the table structure) and ignores the CSS layout primitives (Flexbox, Grid) that solve layout correctly. Modern HTML's only correct use of `<table>` is data; layout uses `<main>`, `<section>`, `<div>`, plus CSS.
- **Missing `alt` on `<img>`** — Every `<img>` needs `alt`. Decorative images get `alt=""` (empty); content images get descriptive text; missing `alt` causes screen readers to announce the file name. There is no acceptable reason to omit the attribute.
- **Missing `<label>` on form controls** — Every `<input>`, `<select>`, `<textarea>` needs an associated label. Placeholder text is not a label. `aria-label` on the control is acceptable but a visible `<label>` is better — it's also a touch target, which improves mobile UX.
- **Skipped heading levels** — Jumping from `<h2>` to `<h4>` (skipping `<h3>`) breaks the document outline. The heading hierarchy is for structure, not visual styling — to change a heading's appearance, use CSS, not a wrong-level heading element.
- **`target="_blank"` without `rel="noopener"`** — A finding per § Security. Modern browsers default to `noopener` but the explicit declaration is the safe form across the browser support matrix.
- **`javascript:` URIs in `href` or `src`** — A finding per § Security. Always an XSS vector; always replace with an event listener.
- **Empty `<a href="#">` for JavaScript-only actions** — A link with `href="#"` is not a link — clicking it navigates to the top of the page and updates URL history. Use `<button type="button">` for in-page actions; `<a>` is for navigation only. The `href="#"` pattern usually indicates the developer reached for `<a>` because it was easier to style than `<button>` (which is solved by styling the button) or that they need a clickable element that isn't a navigation (which is the definition of a button).
- **`autoplay` on `<audio>` and `<video>`** — Autoplaying media (especially with sound) is a usability and accessibility failure — it interferes with assistive technology, surprises users, and consumes bandwidth without consent. Modern browsers block autoplay-with-sound by default; relying on the block is fragile. Don't autoplay unless DESIGN.md explicitly justifies it (e.g., a video-first product where autoplay is the core interaction model).
- **`<br>` for spacing** — `<br>` is a line break within text content (a poem, an address). Using `<br><br>` for visual spacing between paragraphs is structurally wrong (use `<p>` for paragraphs) and fragile (CSS margins are the correct lever).
- **`<i>` and `<b>` for semantic emphasis** — `<i>` and `<b>` are presentational (italic / bold visual appearance); `<em>` and `<strong>` are semantic (emphasis / strong emphasis). For text that *means* emphasis (a stressed word in prose), use `<em>`; for text that *looks* italic (a book title, a foreign word), `<i>` is acceptable but `<cite>` (book title) or `<i lang="fr">` (foreign word) is better.

## Maintenance

When to update this supplement:

- **HTML Living Standard change** — When the [HTML Living Standard](https://html.spec.whatwg.org/) adds an element, attribute, or pattern this supplement should recommend (or deprecates one this supplement currently recommends). The standard is versionless — changes are continuous; revisit the supplement quarterly against the spec's changelog.
- **WCAG version revision** — WCAG 2.2 is current as of 2024 with WCAG 3.0 in draft. When 3.0 stabilizes or the project's compliance target shifts, the Accessibility section needs revision.
- **ARIA version revision** — [WAI-ARIA](https://www.w3.org/TR/wai-aria-1.2/) 1.2 is current; future versions may shift role and attribute recommendations.
- **Browser support matrix change** — When [Baseline](https://web.dev/baseline) widely-available features change (a new feature becomes widely available, or a feature's support cliff retires), the Performance Engineer and Solution Architect sections may need to update their recommendations (lazy loading, `<dialog>`, popover API).
- **Tooling churn** — When a tool this supplement names is superseded (e.g., a successor to html-validate emerges) or abandoned, update the Tooling section and the cross-references.
- **Project-application learnings** — When a VSDD project surfaces an HTML defect class this supplement doesn't cover, add the dimension. The supplement is a living artifact; the standard for adding a dimension is: it has surfaced as a real finding in a project review, it generalizes to other projects, and it has a concrete detector or test pattern.
