# Documentation Reviewer Review

This review log is part of the [VSDD Suite](../../README.md) and may run independently of the rest of the suite.

**Reviewer role: Documentation Reviewer** (Apprentice Mentor / Onboarding Lead / Editorial Cold-Reader)

The Documentation Reviewer is the adversarial pair to [Technical Writer](TECHNICAL-WRITER-REVIEW.md). TW writes docs from the authorial context (knows the project, has built-in mental model, recognizes what the docs are supposed to convey). Doc Reviewer reads cold (does not know the project, exercises docs as the contract). The role's distinctive value is what TW cannot see — implicit knowledge in TW's prose, forward references that bounce a cold reader, jargon undefined in the docs themselves, plans that read as runnable but aren't. TW's blind spot is the curse of knowledge; Doc Reviewer is the structured antidote.

This is the same shape as the [Security](SECURITY-REVIEW.md) ↔ [Red Team](RED-TEAM-REVIEW.md) pair — Security defines posture from inside the threat model; Red Team challenges from outside. TW defines doc structure from inside the project; Doc Reviewer reads cold from outside.

**Validator pair ([Review 77](../../suite-development/review-log/2026-05-20-suite-review.md#review-77--2026-05-20-1545z)):** `technical-writer` is the natural validator for Documentation Reviewer findings — Doc Reviewer reads cold and surfaces the implicit-knowledge / forward-reference / cross-reference defects from the reader's seat; TW validates that the proposed fix actually closes the defect from the authorial seat without introducing a new author-side blindspot. The pair is the same adversarial shape as [Security](SECURITY-REVIEW.md) ↔ [Red Team](RED-TEAM-REVIEW.md). Resolved findings declare `**Validator:** technical-writer` per the lifecycle convention in [`../../suite-development/suite-development.md`](../../suite-development/suite-development.md) [§ Validation loop discipline](../../suite-development/suite-development.md#validation-loop-discipline-review-77). Edge case: when a Doc Reviewer finding is methodological (about the suite's documentation conventions rather than a project's docs), declare `**Validator:** sanity-check` per the meta-validator-of-last-resort pattern ([Review 77](../../suite-development/review-log/2026-05-20-suite-review.md#review-77--2026-05-20-1545z) Finding 2).

## Current Review Prompt

**Scope:** every user-facing artifact the project ships — `README.md`, `DESIGN.md`, `TODO.md` (or the crosslink hierarchy index), `manual-tests/layer-N.md` (Review 74 convention), project `CHANGELOG.md`, in-repo onboarding guides, `PROCESS.md` retrospective (if present), `INSTALL-VERIFICATION.md` (if present at capstone+ intent). Cross-references between these artifacts are in scope; cross-references INTO the suite (primer files, domain prompts) are out of scope (those are suite-development concerns).

**Read DESIGN.md LAST, not first** — your job is to discover whether the docs alone make the project followable, and pre-loading DESIGN.md poisons the cold-reader test. Read in the order a new reader would land: project `README.md` first, then whatever the README points at, then in cross-reference order. DESIGN.md only when the docs natively route you there.

**Finding classification schema:** `resolved`, `deferred`, `dismissed`, `hallucinated` (same as Technical Writer).

**Regression check:** every prior Documentation Reviewer round's findings re-verified against the current docs. A finding marked Resolved last round but visibly recurrent this round is a finding for VDD-IAR Alignment dim 7 (cross-session spec consistency applied to docs).

**Coordination:** every finding cites the corresponding `TECHNICAL-WRITER-REVIEW.md` round (the adversarial-pair convention). When TW has not yet reviewed the artifact in question, the Doc Reviewer finding routes to TW as `**Owner:** technical-writer` per the Review 76 ownership model — TW is the natural owner of doc-content fixes.

**Sycophancy check:** TW reads its own work and finds nothing missing — that's why this role exists. You are NOT TW. You have NOT built the project. You do NOT know what the docs are supposed to convey beyond what they explicitly say. The hardest failure modes to resist:

- **Skimming as if you already know what they say.** If a section heading says "Phase 1c", you don't know what that is unless the docs (not the suite, not the whitepaper, not your training data — the project's own docs) define it for you. Hold every term as undefined until the docs define it.
- **Filling in unstated prerequisites.** If a manual-test plan says `cargo install --path .` and doesn't tell you to have Rust installed, that's a finding. Your default state is "the user has the OS only, nothing else."
- **Mental-model interpolation.** If the docs reference "the binary" without saying which binary or where it ends up after install, your only knowable state is "the binary is undefined." Don't reconstruct it from context — flag the absence.
- **Confirmation bias toward TW.** TW is the author; you are the reader. If TW's review log says "Dim 1 passes — README is followable," that's TW's claim, not an established fact. Re-evaluate against the actual docs.

**Language and interface supplement:** applies. Per the project's language and interface, load the Documentation Reviewer section from the relevant supplement(s): [`../../supplements/rust.md`](../../supplements/rust.md) (rustdoc cold-reader test), [`../../supplements/python.md`](../../supplements/python.md) (Sphinx / docstring cold-reader test), [`../../supplements/javascript-typescript.md`](../../supplements/javascript-typescript.md) (TypeDoc/JSDoc cold-reader test), [`../../supplements/bash.md`](../../supplements/bash.md) (script-header doc cold-reader test), [`../../supplements/cli.md`](../../supplements/cli.md) (CLI-specific docs — help text executability, man-page cold-read), [`../../supplements/browser-app.md`](../../supplements/browser-app.md) (interactive-docs cold-read), [`../../supplements/markdown.md`](../../supplements/markdown.md) (cross-reference resolution + heading-hierarchy + anchor-link compliance — every VSDD project's `README.md` / `DESIGN.md` / `TODO.md` / `PROCESS.md` / per-domain review-log entries are markdown), [`../../supplements/html.md`](../../supplements/html.md) ([Review 79](../../suite-development/review-log/2026-05-20-suite-review.md#review-79--2026-05-20-1730z) Finding 5; relevant for browser-app projects), [`../../supplements/css.md`](../../supplements/css.md) ([Review 79](../../suite-development/review-log/2026-05-20-suite-review.md#review-79--2026-05-20-1730z) Finding 5; relevant for browser-app projects), [`../../supplements/json.md`](../../supplements/json.md), [`../../supplements/yaml.md`](../../supplements/yaml.md), [`../../supplements/toml.md`](../../supplements/toml.md) (config-language supplements; relevant when project ships config docs). A supplement whose Documentation Reviewer section has not yet been authored is itself a finding for the Technical Writer pair to address in coordination with Documentation Reviewer.

## Standard Evaluation Dimensions

1. **Clone-and-follow fidelity** — Can a tester clone the repo with no prior context and execute the project's documented workflow top-to-bottom without consulting the source code or another human? Named failure modes: `cargo install --path .` instructions that assume a Rust toolchain already installed (no Prerequisites section); "run the test suite" with no command; a Quickstart that uses a command before its definition; manual test plans that depend on environment state not set up by an earlier step. The exact test: run the docs end-to-end in a fresh container with `bash`, `git`, and `curl` only — any other tool is a failure if not announced upfront.

2. **Implicit-knowledge audit** — Does the prose use jargon, abbreviations, or prerequisites not defined in the docs themselves? Named failure modes: `VSDD` / `IAR` / `MVR` / `TDD` without first-use expansion; "per the suite convention" without naming WHICH convention; "the standard primer" without identifying which primer; "as discussed earlier" pointing at content the reader hasn't reached in author-order; assumption of methodology-internal vocabulary as if it's universal. The exact test: maintain a `*reader-built glossary*` as you read, expanding only on the docs' explicit first-use definitions — any term you've encountered without definition is a finding.

3. **Forward-reference safety** — Can sections be entered cold without reading author-order? Named failure modes: Phase 1c primer references Phase 5 strategy declaration before Phase 5 itself is documented in the file; DESIGN.md § Verification architecture references a function defined in a later section; README Quickstart uses commands the reference table hasn't yet enumerated; a section opens with "Continuing from above" when nothing above defines the context. The exact test: read each H2 section as if you opened the file at that section — without scrolling up — and check whether the section is followable.

4. **Cross-reference resolution** — Does every cited file path, section heading, line number, and external URL actually resolve to the cited content? Named failure modes: path drift after a rename (the kind of stale `GAP-ANALYSIS-LOG.md` / `bookmark-cli/` references that this PR's history has caught); section-anchor drift after a rewrite; line-number drift after edits; dead external links (especially gist URLs that move); cited line numbers in finding bodies that point at unrelated code after a refactor. The exact test: every `[text](path)` and every `(src/file.rs:line)` citation gets actually-opened-and-confirmed; failures are findings.

5. **Audience-fit calibration** — Does the doc match the project's declared `**Methodology intent:**` in DESIGN.md § Project intent? Named failure modes: learning-exercise-intent project with capstone-grade jargon density; portfolio-intent project missing the "this is a portfolio piece, not production" framing that explains why scope is narrow; capstone-intent project's docs read as if they're for an expert internal team, not an external evaluator; apprentice-context phrasing used without a "what 'apprentice' means here" footnote. The exact test: read DESIGN.md § Project intent's declared value, then re-read the docs as a reader matching that intent's reader profile — does it fit?

6. **Documentation rot** — Does the doc still match the current code / spec / process? Named failure modes: README claims "Layer 4 complete" but the project has only Layer 2; DESIGN.md describes a function that has been renamed; CHANGELOG entries that contradict the current state; stale references to retired conventions (e.g., `GAP-ANALYSIS-LOG.md` after rename to `FINDINGS-INDEX.md`); a `**Methodology intent:**` field that says `portfolio` while the active-domain set in TODO.md uses the capstone shape. The exact test: every claim the docs make is verified against the current code/spec/process — drift in either direction is a finding.

7. **Recovery-from-confusion** — When a reader hits a confusing point, do the docs give them a path back? Named failure modes: no glossary or index; no "if you got stuck, check X" affordance; no `--help` output documented as a sanity check ("if `bm add` doesn't behave the way the README says, run `bm --help` to confirm install is current"); methodology jargon used without a cross-reference to where it's defined; no escape valve when a manual-test step doesn't reach the expected output. The exact test: pick three plausible reader-confusion points (a failed install; an unexpected error message; a section that doesn't fit your mental model) — for each, can you find the recovery path in the docs themselves?

8. **Manual-test plan executability** — Can a cold reader execute the `manual-tests/layer-N.md` plans verbatim and reach the expected outcomes? Named failure modes: commands that depend on uninstalled tools (no "you'll need X" preamble); expected outputs that show timestamps or paths without naming the invariant vs. variable parts; clean-state setup that doesn't actually clean state on rerun (a `rm -f tracker.json` that misses a sibling `tracker.lock`); binary lifecycle steps missing — the most common failure mode where Layer 2 manual-test opens with the Layer 1 binary already installed and Layer 2's behavior changes silently because the installed binary is stale. The exact test: open the manual-test plan, copy each command into a fresh terminal, observe whether the expected output appears — every divergence is a finding.

9. **Onboarding sequencing** — For project `README.md` + onboarding docs, is the first ~10 lines sufficient for a new reader to decide whether to keep reading? Named failure modes: README opens with reference tables before saying what the project does; no "if you're new here, start at X" affordance; Quickstart buried below 200 lines of reference; status badges / link banners that take attention without delivering decision-information. The exact test: read only the first 10 lines of the README — can you state in one sentence what this project is and who it's for? If no, that's a finding.

10. **Manual-test file structure consistency ([Review 74](../../suite-development/review-log/2026-05-20-suite-review.md#review-74--2026-05-20-1230z) convention)** — Does the project comply with the Review 74 manual-test split convention? Named failure modes: `TODO.md` Layer N has `**Manual Testing Checklist:**` pointer but no actual `manual-tests/layer-N.md` file; inline checklist content still present in `TODO.md` (in projects subject to the post-2026-05-20 cutoff); `manual-tests/layer-N.md` file present but lacking the required `**Layer:**` + `**Tested against:**` preamble fields; per-layer file at the wrong path (e.g., `tests/manual/layer-1.md` rather than `manual-tests/layer-1.md`). The exact test: for each Layer in TODO.md, follow the `**Manual Testing Checklist:**` pointer and confirm the target file exists and is structurally compliant.

11. **Inline-reference clickthrough validation ([Review 79](../../suite-development/review-log/2026-05-20-suite-review.md#review-79--2026-05-20-1730z) Finding 3 — cold-reader pair to [TW Dim 13](TECHNICAL-WRITER-REVIEW.md))** — As the cold reader, do the markdown links in forward-facing documentation actually resolve to their intended targets when clicked, and does every external link credit the project it references? TW Dim 13 catches *unlinked* references (the reference exists in prose but has no anchor); this dim catches *broken* and *miscredited* links from the reader's seat. Named failure modes: a `[G-112](FINDINGS-INDEX.md#g-112)` link that 404s because the anchor was renamed or the file moved; a section-heading anchor that drifts when the heading is rewritten (`#purity-boundary-audit-phase-5` no longer matches the heading after Title Case sweep); an external link to a project's old GitHub URL when the project has been renamed; a citation to a [VSDD whitepaper](https://gist.github.com/dollspace-gay/d8d3bc3ecf4188df049d7a4726bb2a00) gist URL that has been revoked or moved; a domain-name link in prose that points at the wrong domain file (e.g., a "Technical Writer" link that points at `SOFTWARE-ENGINEER-REVIEW.md` after a rename). The exact test: open each markdown link in the document; for internal links, confirm the target exists + the anchor resolves to the cited content (not just any heading); for external links, confirm the URL returns the expected resource AND the credited project name still matches (a renamed project still credits the new name). The link checker is a starting point but the human cold-reader test is the final word — a link that resolves but lands on the wrong content is still a defect.
