# AI Engineer Review

This review log is part of the [VSDD Suite](../../README.md) and may run independently of the rest of the suite.

**Reviewer role: AI Engineer** (Agent Operations Engineer / Token Economist / Methodology Cost Auditor)

The AI Engineer is the cost-and-quality discipline applied to how AI agents are used to drive the IAR cycle. The methodology says cold-session-per-domain is the gold standard; the AI Engineer asks whether that gold-standard is being executed with the discipline that preserves its value, at a cost calibrated to the project's intent tier. Where Performance Engineer measures cost-per-operation in the shipped artifact (latency, throughput, resource use), the AI Engineer measures cost-per-finding in the review pipeline (tokens, agent count, rate-limit consumption, prompt-cache hit rate, model selection appropriateness).

This domain emerged from the operator-surfaced observation during PR [#38](https://github.com/magnificentlycursed/guild-portfolio/pull/38) Round 2 dispatch — "Cold-session verification runs seem very token expensive. It may be time to revisit the AI Engineer domain role to determine what about them is expensive and how to realize the cold session benefits without immediately hitting daily session limits." The PR #38 cycle vindicated the framing: 10 parallel cold-session agents burned ~1.2M tokens per round; one agent hit Anthropic's daily limit mid-execution; the cluster-batching workaround cut agent count ~60% while preserving adversarial-pair separation. Codifying the cost discipline keeps the gold-standard achievable at scale.

**Validator pair:** No canonical role-domain pair. AI Engineer findings declare `**Validator:** sanity-check` per the meta-validator-of-last-resort pattern ([Review 77](../../suite-development/review-log/2026-05-20-suite-review.md#review-77--2026-05-20-1545z) Finding 2). The Dim concerns (token economy, prompt-cache discipline, model selection, rate-limit strategy, cluster-batching shape) span the whole methodology rather than mapping to a single peer-domain's adversarial lens; sanity-check applies methodology + supplement criteria to validate the proposed fix.

**Activation criteria:** Active by default at **capstone** and **production** intent tiers — these tiers exercise the full extended-domain set and run multi-round IAR cycles whose cost compounds. Active at **portfolio** intent when the project uses parallel cold-session adversarial review (the suite's gold-standard pattern), otherwise extended-pool with operator opt-in. Active at **learning-exercise** intent only when the apprentice is explicitly studying AI-agent-usage discipline (rare; most learning-exercise projects sidestep this complexity by serial review).

## Current Review Prompt

**Scope:** the IAR cycle's AI-agent-usage patterns as evidenced in the project's review-log + audit-trail artifacts. Specifically: the cold-session agent spawn shape (one agent per domain vs. cluster batching); the prompt design (per-agent context load, supplement-list size, cold-session framing); the model selection (Opus / Sonnet / Haiku per task class); the rate-limit headroom evidence (did any agent hit a daily limit mid-cycle); the prompt-cache discipline (was the 5-minute Anthropic cache hit between sequential agent steps); the Phase 4 routing as scope-reducer (did Round 2 re-scan or did it route prior-round findings); the cluster-batching shape (adversarial-pair separation preserved); the project memory + auto-memory cost (did context grow past the cache window). Cross-references INTO the suite (primer files, domain prompts, supplements) are out of scope — those are suite-development concerns. The shipped software artifact itself is out of scope — that's the role/meta domains' surface.

**Read DESIGN.md and the project source LAST, not first** — your job is to evaluate the AI-agent-usage shape, and pre-loading the project's spec / source poisons the cost-discipline test by pulling you into artifact-evaluation mode. Read in this order: project `README.md` (intent tier + active-domain set); `vsdd-suite/review-log/` (the per-domain review-log files — the AI-agent-usage record); the suite-side `vsdd-suite/suite-development/review-log/` Review N entries that orchestrated the cycle (the spawn shape, the cluster decisions, the operator-directive corrections); `vsdd-suite/CHANGELOG.md` (the cost-vs-value claims). DESIGN.md / source only when the AI-agent-usage record natively routes you there.

**Finding classification schema:** `Resolved`, `Deferred`, `Dismissed`, `Hallucinated` (same as Software Engineer / Documentation Reviewer / Performance Engineer / Platform Engineer).

**Regression check:** every prior AI Engineer round's findings re-verified against the current cycle. A finding marked Resolved last round but visibly recurrent this round is a finding for VDD-IAR Alignment dim 7 (cross-session methodology consistency applied to AI-agent-usage discipline).

**Coordination:** AI Engineer findings about the artifact's operational cost (e.g., the deployed binary's per-request token consumption in an LLM-using application) route to Performance Engineer per the cost-discipline shared surface — AI Engineer's surface is the *review pipeline's* cost, not the *artifact's* cost. AI Engineer findings about the methodology (the suite's own conventions) route to VDD-IAR Alignment or to suite-development discussion per [G-89](../../suite-development/FINDINGS-INDEX.md#g-89) forward-only narrative-preservation discipline.

**Error-event ownership boundary ([Review 87](../../suite-development/review-log/2026-05-21-suite-review.md#review-87--2026-05-21-1230z) Finding 6):** Per the per-error-class owner table codified in Review 87, AI Engineer owns a specific subset of tool/prompt error events: (1) **AI-inline-execution tool/command errors** — bash commands, `gh` invocations, sub-agent spawns, LLM tool calls, markdown parsers used by the AI inline to execute a prompt; (2) **process-enforcement scripts and hooks** — merge-gate workflows like [`pr-checklist.yml`](../../../.github/workflows/pr-checklist.yml); (3) **early-detection scripts and hooks** — pre-commit hooks that catch authoring violations (`check-suite-review-preamble.py`, `check-project-review-discipline.py`, `check-changelog-currency`, `check-crosslink-references.py`, `check-anonymization.sh`, `check-external-review-anonymization.py`, `check-suite-internal-terminology.py`), audit-trail discipline hooks, the anchor-link sweep script's discipline checks. AI Engineer does NOT own: artifact-CI/CD pipelines that build/test/lint the project artifact (Platform Engineer owns); artifact-domain tool errors (`cargo test` failure → Quality Engineer; `cargo clippy` failure → Software Engineer; etc., per existing Dim coverage). The boundary is **meta-tooling-of-methodology** (AI Engineer) vs **artifact-shipping-tools** (Platform Engineer + per-artifact-domain). See [Review 87 Finding 6](../../suite-development/review-log/2026-05-21-suite-review.md#review-87--2026-05-21-1230z) for the per-error-class owner table.

**Sycophancy check:** the operator running the IAR cycle is the same person reading this review — the temptation is to validate the choices already made (every cluster shape, every model selection, every spawn decision) because they shipped and the cycle reached its target state. You are NOT the operator. You have NOT made those decisions. Hold every choice as an open question until the cost evidence in the review-log + audit-trail justifies it. The hardest failure modes to resist:

- **Outcome bias toward shipped state.** A cycle that reached MVR at the chosen cost is not automatically calibrated correctly — the over-investment failure mode ([G-150](../../suite-development/FINDINGS-INDEX.md#g-150)) feels like quality because more findings surface, but tokens spent on Round 4 cold-sessions that produce only Hallucinated or sweep-discipline-gap findings are tokens that could have funded Round 1 on the next project.
- **Sunk-cost defense of the spawn shape.** "10 parallel agents" or "4 clusters" is an architecture choice, not a methodology requirement. If the cost evidence shows a 2-agent or 6-agent shape would have produced comparable adversarial coverage, that's a finding regardless of how many cycles the current shape has been run.
- **Anthropic-API-internal vocabulary as universal.** Terms like "prompt cache", "rate limit", "Opus vs. Sonnet vs. Haiku" are vendor-internal. If the project's audit trail doesn't define them in context, the review still uses them — but flag missing context-loads as Dim-2 findings against the audit trail's own readability.
- **Confirmation bias toward operator framing.** The operator's directive declared the cluster-batching workaround. That makes it the methodology's working solution; it does not make it the methodology's right solution. Re-evaluate whether a different shape (serial single-agent? 2-cluster wider-context? fan-out-to-sub-agents pattern?) would have served better.

**Language and interface supplement:** applies. Per the project's language, interface, and AI-agent runtime, load the AI Engineer section from the relevant supplement(s) when authored: [`../../supplements/markdown.md`](../../supplements/markdown.md) (every review-log + audit-trail artifact is markdown — heading shape + finding-header structure + cross-reference cost are AI Engineer concerns about machine-readable parsability of the audit trail per the [Review 80](../../suite-development/review-log/2026-05-20-suite-review.md#review-80--2026-05-20-1830z) Finding 3 Agent-API surface). Other supplements (Rust, Python, JS/TS, CLI, browser-app) become AI Engineer surfaces when the project uses AI agents AT RUNTIME (e.g., an LLM-powered CLI tool that bills tokens per user interaction); for those, AI Engineer findings about runtime agent usage coordinate with Performance Engineer per the cost-discipline shared surface.

## Standard Evaluation Dimensions

1. **Session isolation discipline** — Did each adversarial cold-session run in a genuinely cold context, or did agent-handoff leak prior-round state across the session boundary? Named failure modes: spawning Round 2 agents with the Round 1 review-log file already loaded in context (defeats the regression-check independence); reusing a single agent's conversation across multiple domains (loses the per-domain framing); routing the operator's main-session summary into the cold-session agent's spawn prompt (poisons the cold-reader test). The exact test: each cold-session spawn prompt's context-load list is reviewed — every loaded file is justified as cold-context required, and every prior-cycle review-log file is justified as a regression-check input that the agent will treat as adversary's prior claim, not as established fact.

2. **Token economy per finding** — What is the per-finding token cost of this cycle, and is it calibrated to the project's intent tier? Named failure modes: 200k+ tokens per finding (over-investment signal — the agent is spending more on context than the finding's defect-detection value justifies); under 5k tokens per finding (under-investment signal — the agent's context-load is too thin to surface dimensional findings; the round produces only surface-level defects); cost asymmetry across domains (one domain costs 10x another with no defect-density difference to justify the gap). The exact test: tally total agent token consumption across the round; divide by substantive (non-Hallucinated, non-Dismissed) finding count; compare against intent-tier expected band — learning-exercise ≤ 50k/finding; portfolio 50k–150k/finding; capstone 100k–300k/finding; production 200k–500k/finding (these bands are first-pass estimates; refine per project evidence).

3. **Anthropic prompt-cache discipline** — Does the spawn shape make use of the 5-minute prompt cache, or does each agent re-load the same context from cold? Named failure modes: sequential agent spawns more than 5 minutes apart (cache expires; each agent pays full context-load cost); parallel spawns whose context-loads diverge by trivial amounts (cache-busting on per-agent prompt-suffix differences that could be promoted to per-step variables); 10+ agents spawning serially with full re-load each time (the worst case — 10x the cache-eligible cost). The exact test: trace the spawn timeline + per-agent context-load shape; identify cache-eligible reuse opportunities; quantify the cache-miss cost as a percentage of total round cost.

4. **Sub-agent delegation patterns** — When the main session delegates work, is the delegation prompt self-contained and outcome-scoped, or does the sub-agent require multi-turn clarification? Named failure modes: sub-agent prompts that pass `Read the conversation summary and continue` (sub-agent has no context — wastes 30%+ of first turn re-discovering state); sub-agent prompts with no explicit success-criteria or report-shape (sub-agent over-explains or under-explains); main session running work inline that should have been delegated (context bloat in main session; main exhausts cache faster). The exact test: every delegated sub-agent's spawn prompt is reviewed for completeness; the sub-agent's first-turn behavior is checked for context-discovery overhead; the report-shape requested vs. delivered is compared.

5. **Rate-limit strategy + graceful degradation** — Did any agent hit a rate-limit mid-cycle, and was the cycle architected to degrade gracefully if one did? Named failure modes: 10 parallel agents spawned simultaneously at the start of a high-traffic Anthropic load window (compound rate-limit risk); no fallback plan when one agent fails to complete (the round is incomplete without a retry shape); rate-limit-hit agents respawned without restart-from-checkpoint discipline (the respawn pays full context-load cost again). The exact test: review the cycle's rate-limit-event log (if any); confirm the cycle had a documented retry shape; verify retries are cache-warmed rather than cold.

6. **Model selection per task class** — Was each agent spawned with the appropriate model (Opus 4.7 for highest-complexity adversarial review; Sonnet 4.6 for mid-complexity domain reviews; Haiku 4.5 for mechanical sweep or audit-trail-only tasks)? Named failure modes: Opus for every agent regardless of task complexity (over-investment — Sonnet would have produced comparable findings on mechanical-discipline domains like Doc Reviewer's clickthrough-validation pass); Haiku for a complex adversarial-review domain (under-investment — model under-resolves the Dim-N defects); no model declaration in the spawn prompt (default-model behavior is opaque). The exact test: tabulate per-agent model + task-class + finding-density; check for model/task mismatches; confirm the model-selection rationale appears in the audit trail.

7. **Cluster-batching with adversarial-pair separation** — When cluster batching is used to reduce agent count, is adversarial-pair separation preserved? Named failure modes: Security + Red Team in one cluster (destroys independent adversarial pressure); Technical Writer + Documentation Reviewer in one cluster (destroys cold-reader-vs-author dynamic); cluster shape that puts more than 3 domains in one agent (per-domain dimensional analysis dilutes below useful resolution); cluster files preserved with letter-coded names (`Cluster A/B/C/D`) post-execution (TW Dim 12 naming-discipline slip per the codified [feedback memory on avoiding lettering](https://github.com/magnificentlycursed/guild-portfolio)). The exact test: review the cluster manifest; verify each canonical adversarial pair (Security ↔ Red Team; TW ↔ Doc Reviewer) has its halves on different agents; confirm intermediate cluster files were consolidated + deleted at round-close.

8. **Phase 4 routing as Round-2+ scope-reducer** — Did Round 2+ cycles route the prior round's findings rather than re-scan the whole project? Named failure modes: Round 2 agents spawned with the same scope as Round 1 (no scope-reduction; doubles the cost of the cycle without proportional defect-detection gain — Round 2's value is in the regression-check + the new-defects-introduced-by-the-fix, not in re-finding what Round 1 already found); Round 2 prompts that omit the Round 1 finding list (agent re-discovers the prior round); Round 3 prompts that omit both Round 1 + Round 2 (cumulative re-scan cost). The exact test: each round's spawn-prompt scope statement is reviewed; the prior-round-finding-list is confirmed present in the context-load; the spawn prompt's "evaluate the prior round's resolution + surface NEW findings" framing is verified.

9. **Cold-session-budget declaration per project intent tier** — Does the project's `DESIGN.md` (or session-orchestration record) declare an explicit cold-session budget — number of rounds, max agents per round, model-tier ceiling — calibrated to the intent tier? Named failure modes: capstone-intent project running Round 7 cold-session verification without a stopping rule (compounding cost without a bright-line termination signal); production-intent project capped at Round 2 (under-investment relative to the intent's MVR-strict gate); learning-exercise project running 10 parallel agents per round (over-investment relative to the apprentice-bar). The exact test: locate the cold-session-budget declaration in the project's audit trail; verify it matches the intent tier's recommended band; check actual execution against the declared budget.

10. **Memory-leakage between sessions** — Do cold sessions stay genuinely cold, or do they inherit project-memory / auto-memory state that the methodology assumes they don't? Named failure modes: cold-session agent spawned with auto-memory files preloaded (the agent reads operator feedback memories before reading the artifact — biases adversarial framing); cold-session agent spawned in the same conversation thread as the main session (cross-turn state leakage); user-injected `# system-reminder` lines from the main session reaching the cold-session agent (the agent reads operator preferences as project facts). The exact test: review the cold-session agent's spawn-prompt + context-load list; confirm no memory file or main-session reminder reaches the cold context; verify the agent's prose treats every project-fact as undefined until the project's own artifacts define it.

11. **Audit-trail machine-readability cost** — Does the round's audit-trail (review-log + findings-index) parse cleanly under the [Review 80](../../suite-development/review-log/2026-05-20-suite-review.md#review-80--2026-05-20-1830z) Finding 3 Agent-API surface contract, so that future agents reading prior rounds don't pay re-parsing cost? Named failure modes: finding headers that drift from the canonical pattern (forces regex-extension across future agents); per-Finding anchor IDs missing (forces agent to construct anchors from headings); classification sub-section headings outside the domain's classification universe (forces agent to read full-text rather than grep classification); cluster-file-as-canonical (agent has to consolidate to per-session before grep). The exact test: run the round's review-log files through the suite's per-domain-discipline hook + the suite-review preamble hook; confirm clean pass; spot-check 3 finding-anchor links + 3 classification-section greps for clean machine-parsability.

12. **Operator-directive correction cost** — When the operator corrects a methodology slip mid-cycle (cluster naming, adversarial-pair co-location, filename violation), what is the rework cost — tokens spent on the wrong shape + tokens spent on consolidation + tokens spent on the corrected shape? Named failure modes: corrections deferred to next round (compounds cost across rounds); corrections applied inline but the prior shape's artifacts left in the audit trail (creates G-89 narrative-preservation noise distinguishable from genuine forward-only history); operator-directives that surface late in the cycle (the discipline lives in the methodology authoring; if the operator has to surface the discipline mid-cycle, the methodology authoring missed a Dim). The exact test: list every operator-directive correction in the cycle; quantify the rework cost; check whether the corrected discipline is now codified in the suite (so future cycles don't repeat the slip).

13. **Pre-cycle methodology check** — Before the cycle starts, does the operator + AI Engineer review-pair confirm the spawn shape against the project's intent tier + active-domain set + prior-cycle cost evidence? Named failure modes: cycle spawned without a budget declaration (open-ended; risks rate-limit hit + over-investment); cycle spawned with the same shape as the prior cycle without checking whether the prior cycle's cost was calibrated correctly (sunk-cost continuity); cycle spawned mid-Anthropic-load-window with no rate-limit headroom check. The exact test: each cycle has a pre-spawn declaration in the suite-side review-log naming the chosen shape + budget + rate-limit headroom + model selection; the AI Engineer round in the cycle close-out validates whether the pre-spawn declaration tracked actual cost.

14. **Tool / plan / execution-method identification** ([Review 90](../../suite-development/review-log/2026-05-23-suite-review.md#review-90--2026-05-23-1200z) Finding 2; PR [#45](https://github.com/magnificentlycursed/guild-portfolio/pull/45)) — Before any cost estimate, optimization recommendation, or methodology finding is generated, has the AI tool + plan tier + execution method been determined via verifiable means OR explicit operator prompt? Named failure modes: dollar cost figures quoted as if measured when the operator is on a subscription plan (Claude Max, ChatGPT Plus / Pro, Cursor Pro) and marginal per-spawn cost is $0 within plan limits — the would-be-API-cost framing is acceptable as a comparator but must not be presented as the operator's actual cost; rate-limit recommendations assuming Anthropic API pay-per-token when the operator is on Claude Max + the recommendations should track 5-hour-rolling-window utilization not token-budget; sub-agent delegation cost framed as token billing when the orchestrator's own context cost is excluded; optimization advice that assumes Cursor + Aider + Claude API direct + claude-code CLI all behave identically when they each have distinct rate-limit + cache + tool-cost surfaces. The exact test: every cost-tally + every cost-recommendation declares the AI tool (e.g., "claude-code CLI v0.X"), the plan tier (e.g., "Claude Max", "ChatGPT Plus", "Claude API direct pay-per-token"), and the execution method (e.g., "inline main session", "sub-agent worktree-isolated cluster spawn", "background `run_in_background` task"). Verifiable detection: process inspection (`ps aux | grep -E 'claude\\|cursor\\|aider'`); env var inspection (`env | grep -i 'anthropic\\|claude\\|openai'`); git config (operator's commit-message style); CLI feature detection (does `/cost` exist? does `gh` know the operator's GitHub handle?). If verifiable detection is ambiguous OR finds zero signal, prompt the user before generating a cost-relevant finding. The named per-tool supplements (e.g., [`supplements/claude-code-cli.md`](../../supplements/claude-code-cli.md)) provide the per-tool specifics; this Dim is the gating check that surfaces which supplement applies.

## Three-audience lens for this domain

AI Engineer is the **primary domain for the AI-agent audience** of the three-audience design principle ([Review 80](../../suite-development/review-log/2026-05-20-suite-review.md#review-80--2026-05-20-1830z) Finding 3; renamed in [Review 84](../../suite-development/review-log/2026-05-21-suite-review.md#review-84--2026-05-21-1100z) Finding 4 — see [`suite-development.md`](../../suite-development/suite-development.md#three-audience-design-principle-review-80-finding-3) § Three-audience design principle). Dim 11 (audit-trail machine-readability cost) is the direct application of the agent-audience lens to the prior round's audit trail; Dim 1 (session isolation), Dim 4 (sub-agent delegation), and Dim 8 (Phase 4 routing) operate on the agent-as-author side. Suite developers extending this domain + suite users running it against their project still consume the findings as the other two audiences, but the dim authoring is calibrated to the agent's reading + writing seat. Findings raised under this domain commit the suite to the Agent-API surface contract documented in [`suite-development.md`](../../suite-development/suite-development.md#agent-api-surface-review-80-finding-3) § Agent-API surface.

Review entries are logged in per-session files at `vsdd-suite/review-log/YYYY-MM-DD-ai-engineer.md` inside the project being reviewed; the project's `vsdd-suite/FINDINGS-INDEX.md` aggregates cross-cutting findings. The optional per-domain index at `vsdd-suite/AI-ENGINEER-REVIEW.md` activates when the project opts in via the scaffold script's `--with-per-domain-indexes` flag. See [`vsdd-suite/suite-development/suite-development.md`](../../suite-development/suite-development.md) [§ Governing standard for project-level review logs](../../suite-development/suite-development.md#governing-standard-for-project-level-review-logs).
