# Sanity Check Review

This review log is part of the [VSDD Suite](../../README.md) and may run independently of the rest of the suite.

[Sanity Check](SANITY-CHECK-REVIEW.md) is a **meta domain** serving two purposes:

1. **Primary — validator of last resort:** the natural cross-domain validator for findings owned by domains whose work has no obvious adversarial pair. Replaces `**Validator:** *self*` for the cases where self-validation would otherwise be the only option (PE shift-left mechanizations; SA architecture-doctrine findings without a Raised-to-SO routing; QE test-discipline meta findings; [Portfolio Assessment](PORTFOLIO-ASSESSMENT-REVIEW.md) introspective dimensions). Per Review 77's lifecycle convention, Sanity Check provides a structured meta-validation surface so the validation-loop discipline doesn't degrade into "I'll just self-validate" friction.

2. **Secondary — rubber-ducking surface:** a dedicated session type for the developer working through a problem whose solution emerges in the act of articulation. The session takes DESIGN.md + the relevant architecture (per the [Solution Architect](../role/SOLUTION-ARCHITECT-REVIEW.md)'s worked output) + the developer's prose articulation of the problem as input, and applies structured listening — surfacing inconsistencies, hidden assumptions, and coherence gaps that the developer's in-context view misses. The "duck" is structured; the rubber is the developer's own articulation pressure.

Sanity Check is a meta domain (parallel to [VDD-IAR Alignment](VDD-IAR-ALIGNMENT-REVIEW.md) and Portfolio Assessment) — no reviewer-role persona by design. The role's distinctive value is structural: it's the meta-validator that closes the otherwise-self-validated cases.

## Current Review Prompt

**Scope:** for validator-of-last-resort sessions, the artifact under review is the originally-raising domain's finding + its resolution + the relevant DESIGN.md sections + the architectural context (SA output / SA dimensions applied to the change). For rubber-ducking sessions, the artifact is the developer's prose articulation + DESIGN.md + the project's architectural state.

**Read DESIGN.md FIRST** — Sanity Check is the meta-domain that holds the spec contract against every other domain's local view. Without DESIGN.md context, the session reduces to opinion exchange.

**Finding classification schema:** `resolved`, `dismissed`, `hallucinated` (matches the meta-domain pattern from VDD-IAR Alignment — process findings are binary; no `deferred` because Sanity Check findings are typically either real-and-actionable or hallucinated). For rubber-ducking sessions specifically, the session may close with no findings at all if the articulation reached its own insight — the rubber-duck session's value was the articulation, not the discovery of a defect.

**Regression check:** every prior Sanity Check round's findings re-verified against the current state. A finding marked Resolved last round but visibly recurrent this round is itself a finding for VDD-IAR Alignment dim 7 applied at the meta-level.

**Coordination:** when a Sanity Check finding requires action by another domain, route via the `**Owner:**` field per Review 77 lifecycle convention. Sanity Check findings rarely produce code changes directly — they typically route to the originating domain (the one whose work was being sanity-checked) with `**Owner:** <originating-domain>` and the session's discovery as the finding body. A Sanity Check session that produces findings owned by Sanity Check itself usually means the rubber-ducking surfaced a process gap; route via VDD-IAR Alignment.

**Sycophancy check:** the dominant failure mode for a Sanity Check session is **agreement with the developer's articulation**. The developer arrived at the session with a model already formed; the rubber-duck surface that reflects the model back warm and uncritically has provided zero value. The hardest discipline to maintain:

- **Refuse to validate articulations that contradict DESIGN.md.** When the developer says "I'm going to add X" and DESIGN.md says X is out of scope, the answer is not "that sounds reasonable" — it's "DESIGN.md § Y says this is out of scope; before X lands, the spec needs the Raised-to-SO routing."
- **Refuse to validate fixes that don't address the original concern.** When invoked as validator-of-last-resort for a finding that would otherwise be `*self*`, the discipline is: read the original finding, read the resolution, ask "does this fix the thing that was reported?" If the answer is "the fix is in a different area than the finding indicated," that's a re-open, not a validation.
- **Surface hidden assumptions explicitly.** When the developer says "of course the user is...", "obviously the database always...", "we don't need to worry about...", treat each phrase as a hidden invariant the spec should explicitly own. Implicit invariants are findings; they typically route Raised-to-SO.
- **End rubber-duck sessions with explicit closure.** A rubber-duck session that ends "we'll figure that out later" or "let me think about it more" without a recorded next step is itself a finding for VDD-IAR Alignment — the unresolved articulation will silently drift. Acceptable closures: (a) the developer reached an insight (record it); (b) the developer did NOT reach an insight (record the unresolved question explicitly + name the next session's purpose).

**Language and interface supplement:** Not applicable. Sanity Check operates against DESIGN.md + architecture + prose articulation; the language-specific dimensions belong in the originating-domain's review, not at the meta-validation level.

**Validator pair (Review 77):** `vdd-iar-alignment` is the natural validator for Sanity Check findings — VDD-IAR Alignment confirms the meta-process discipline doesn't conflict with the project's declared intent. Sanity Check rarely raises its own findings (its work is validating others' findings), so this pair is the fallback for the rare case. When Sanity Check itself produces a finding owned by a different domain (the typical case — Sanity Check surfaces a gap in DOMAIN X's resolution), the Validator on that re-opened finding is DOMAIN X (the originating domain re-cold-reviews against the Sanity Check feedback).

## Standard Evaluation Dimensions

1. **Coherence with DESIGN.md** — Does the change / problem articulation cohere with the project's declared spec? A change that "makes sense" in isolation but contradicts a DESIGN.md invariant is a finding. The check: read DESIGN.md § Behavioral contracts, § Verification architecture, § Edge cases, and § Project intent in full; for each section, ask whether the current articulation respects or violates the section's statements. Named failure modes: a fix that introduces a behavior DESIGN.md doesn't name (unspecified behavior); a fix that changes a behavior DESIGN.md DOES name (spec violation routed to Raised-to-SO); a rubber-duck articulation whose mental model differs from DESIGN.md without acknowledging the divergence.

2. **Coherence with architecture** — Does the change / problem articulation cohere with the project's architectural choices (per the Solution Architect's worked output)? E.g., a fix that adds an effectful function to the pure core is a purity-boundary violation (SA Dim 12); a rubber-duck articulation that proposes a new dependency unmentioned in DESIGN.md's verification architecture is a finding. The check: identify the architectural commitments DESIGN.md and prior SA reviews have made; for each, ask whether the current articulation respects or violates the commitment.

3. **Internal consistency of articulation** — When the developer articulates a problem or proposed change in prose, does the articulation contain internal contradictions? Named failure modes: "the function should reject empty input AND accept any string"; "we need to support concurrent writes BUT preserve the single-writer invariant"; "DESIGN.md says X, but obviously what we mean is Y" (the divergence between explicit and implicit spec). Surfacing the contradiction is the rubber-duck value.

4. **Hidden assumption surfacing** — Phrases like "of course the user is single", "obviously the DB is always available", "we don't need to worry about empty input" name invariants the spec should explicitly own. The check: for each "of course / obviously / clearly" in the articulation, ask: is this invariant in DESIGN.md? If yes, the developer is just reciting; carry on. If no, the implicit invariant is a finding — typically routes Raised-to-SO with the proposed DESIGN.md addition.

5. **Validator-of-last-resort discipline** — When Sanity Check is invoked as the Validator for a finding that would otherwise be `*self*`, the session is structured differently from rubber-ducking: read the original finding (what was reported), read the resolution (what was changed), read DESIGN.md context (what the spec says about the affected area), then ask three questions: (a) does the fix address the reported concern? (b) does the fix introduce new defects in the affected area? (c) does the fix change anything in DESIGN.md's covered behaviors that the spec doesn't already permit? Yes-to-(a), No-to-(b), No-to-(c) → validate. Otherwise re-open the finding with the gap surfaced as a Sanity Check finding owned by the originating domain. Named anti-pattern: rubber-stamping a self-validated finding because the originating domain is the "expert" — Sanity Check's job is to catch what the originating domain missed by being too close to the problem.

6. **Rubber-duck closure honesty** — Every Sanity Check session ends with explicit closure recorded in the per-session log. Closure shapes: (a) **insight-reached** — the developer's articulation produced a concrete next step; record the insight and the step; (b) **insight-not-reached** — the articulation did not converge; record the unresolved question explicitly and name the next session's purpose (could be another Sanity Check session, OR a Raised-to-SO routing, OR a cold-context cold-review by the originating domain). A session that ends with no recorded closure is a finding for VDD-IAR Alignment dim 7 — the unresolved articulation will silently drift; the next reader of the log won't know whether the session resolved or evaporated.

7. **Spec-drift detection at meta level** — Across rubber-duck sessions, does a pattern emerge of the developer's mental model diverging from DESIGN.md without DESIGN.md updates? A single articulation that diverges is a finding; three consecutive sessions diverging in the same way is a spec-drift signal that Sanity Check escalates to Raised-to-SO with the proposed DESIGN.md reconciliation. The check is across-session, not within-session — read the prior Sanity Check session entries when opening a new session and look for the divergence pattern.

8. **Meta-discipline integrity** — Sanity Check is itself subject to the suite's discipline. A Sanity Check session that produces 5 findings all marked Resolved-in-session without any cross-domain validation is itself suspect — the meta-domain is supposed to catch what other domains miss, not generate its own resolved findings unilaterally. The check: review your own session's findings, and for each, name the originating domain whose work was being checked. If 5 findings all originate from rubber-ducking with no anchor in another domain's work, the session was likely an unstructured-conversation rather than a Sanity Check; flag the session-type-drift as a finding.

Findings from this domain serve all three audiences of the methodology (suite developers + suite users + AI agents) — see [`suite-development.md`](../../suite-development/suite-development.md#three-audience-design-principle-review-80-finding-3) § Three-audience design principle ([Review 80](../../suite-development/review-log/2026-05-20-suite-review.md#review-80--2026-05-20-1830z) Finding 3; renamed in [Review 84](../../suite-development/review-log/2026-05-21-suite-review.md#review-84--2026-05-21-1100z) Finding 4).

The optional per-domain index at `vsdd-suite/SANITY-CHECK-REVIEW.md` activates when the project opts in via the scaffold script's `--with-per-domain-indexes` flag.
