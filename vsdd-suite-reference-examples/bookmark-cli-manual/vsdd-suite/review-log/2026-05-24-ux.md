**Finding 1 — Top-level `bm --help` examples section omits `bm export` and `bm import`; the canonical `bm export | bm import` round-trip is undiscoverable from help text (Dim 1)**

**Owner:** ux
**Status:** raised
**Blocked by:** *(none)*

The `long_about` attribute at [`src/main.rs:35-54`](../../src/main.rs) was added at Layer 1 Round 1 to close [UX Review 1 Finding 4](2026-05-20-ux.md#r1-f4) (top-level `bm --help` missing usage examples). The fix added examples for five subcommands and two global flags. Layer 3 added `bm export` and `bm import` as new subcommands, but the `long_about` examples section was not updated.

**Evidence.** The current examples block (lines 41-48):

```
Examples:
  bm add https://example.com           # capture a URL with current UTC timestamp
  bm list                                # print bookmarks, newest-first
  bm tag https://example.com rust        # attach a label to all matching bookmarks
  bm list --tag rust                     # filter list by tag
  bm list --tag rust --tag go            # OR-semantics across repeated --tag
  bm --help                              # show this help text
  bm --version                           # show version
```

`bm export` and `bm import` are absent. clap WILL enumerate `export` and `import` in the subcommand list visible under `bm --help`'s `Commands:` section (auto-generated from the `Cmd` enum), but the canonical pipe composition `bm export | bm import` — the primary new use case at Layer 3, described in [`DESIGN.md`](../../DESIGN.md) § `bm export` (Layer 3) § Pipeline-script-ability — is nowhere in the help text. A user who sees `export` and `import` in the subcommand list and wants to understand how they compose must drill down to `bm export --help` + `bm import --help` separately; neither per-subcommand help cross-references the other.

**Discoverability gap.** The [CLI supplement § UX Dim 1](../../../../vsdd-suite/supplements/cli.md) asks: *"Does the top-level help include a usage example?"* The top-level help has examples for six operations but not for the Layer 3 additions. The export+import composition is the most novel behavior at Layer 3 (backup; cross-machine sync; store-to-store migration per DESIGN.md) and is the one most in need of an example — users unfamiliar with the pipe idiom won't infer `bm export | bm import` from reading the subcommand names alone.

**Proposed fix.** Add two examples to the `long_about` examples block:

```
  bm export                              # emit all bookmarks as JSON to stdout
  bm export | bm import                  # round-trip: backup or cross-machine sync
```

The `bm import` case is covered by the pipe example; a standalone `bm import` example is less valuable (import with no pipe source is an error or requires a here-doc). The `--max-stdin-bytes` flag need not appear in the top-level examples (it is an operator override; `bm import --help` already describes it).

**Sycophancy-compensation check.** A warm-context reviewer would say "clap's Commands section lists `export` and `import`; the user can drill to per-subcommand help for detail." The cold-pass push-back: the Layer 2 review cycle (Review 5 Finding 3, Resolved in Review 6) established precisely this discipline — that per-subcommand help-text richness matters at the layer where new commands land. The same discipline applies at the top-level examples for the pipe composition that is not visible at any single subcommand's help surface.

**Classification:** Deferred — fix is a two-line `long_about` update at [`src/main.rs:48`](../../src/main.rs) (insert before the `bm --help` example line); requires a `software-engineer` code change. No spec amendment. Routes to Phase 4 feedback integration for the next Layer 3 fix-cycle.

**Finding 2 — Size-cap error emits raw byte count without unit label; remediation hint (`--max-stdin-bytes`) absent from the error message (Dim 8)**

**Owner:** ux
**Status:** raised
**Blocked by:** *(none)*

**Evidence.** [`src/main.rs:435-437`](../../src/main.rs):

```rust
if bytes.len() > max_stdin_bytes {
    eprintln!("Error: stdin exceeded maximum byte limit of {max_stdin_bytes}.");
    return ExitCode::from(1);
}
```

When `max_stdin_bytes` is the default (10 MB = 10,485,760 bytes), the emitted error is:

```
Error: stdin exceeded maximum byte limit of 10485760.
```

Two UX defects:

1. **No unit label.** The raw integer `10485760` communicates nothing to a user who has not memorized that the default cap is 10 MB. The user cannot tell whether the limit is bytes, kilobytes, or megabytes without looking up the source or running `bm import --help`. The spec at [`DESIGN.md`](../../DESIGN.md) § `bm import` (Layer 3) says `Error: stdin exceeded maximum byte limit of <N>.` — using `<N>` as a placeholder that the implementation fills with the raw integer. The spec does not prescribe a unit suffix, but the spec is the floor, not the ceiling.

2. **No remediation hint.** The error message does not tell the user how to fix the problem. The [`--max-stdin-bytes <N>`](../../src/main.rs#L167-168) flag is the operator override, but its existence is not surfaced in the error. The precedent for remediation hints is [UX Review 1 Finding 5](2026-05-20-ux.md#r1-f5) (Resolved): storage-error messages now emit "Hint: check that the storage file at `<path>` ..." lines. The size-cap error follows the same UX pattern — the user has a knob to turn, but the error doesn't name it.

**Behavior consequence.** A user who pipes a large JSON export into `bm import` and hits the cap sees the raw-integer error, has no hint that a flag exists to override it, and must either find the README or run `bm import --help` to learn about `--max-stdin-bytes`. The flag is documented clearly in `bm import --help` (lines 164-168 — `--max-stdin-bytes <MAX_STDIN_BYTES> Maximum stdin byte count accepted. Defaults to 10 MB...`), but requiring an extra help-text lookup after an error is the UX friction the remediation-hint pattern was designed to eliminate.

**Comparison with prior precedent.** [UX R1 F5](2026-05-20-ux.md#r1-f5) was resolved by adding `Hint:` lines to `emit_storage_error`. The size-cap path is analogous: the user has hit a limit, the tool knows the override mechanism, and a one-line hint closes the discoverability gap without changing the spec-contracted error message line.

**Proposed fix.** Two changes:

1. Change the error message to include a human-readable byte representation alongside the raw count, or use a formatted string. The simplest improvement: format as `10 MiB` when the value is the default, or use a `format_bytes` helper. Alternatively, emit the value in human units only: `Error: stdin exceeded the 10 MB input-size cap.` — trades exactness for readability.

2. Add a remediation hint line: `Hint: use --max-stdin-bytes <N> to raise the limit for legitimately-larger imports (e.g., --max-stdin-bytes 104857600 for 100 MB).`

The hint references the actual flag name and gives a concrete example value — the same specificity pattern the R1 F5 remediation hints established.

**Sycophancy-compensation check.** The spec at DESIGN.md § `bm import` (Layer 3) names the error string as `Error: stdin exceeded maximum byte limit of <N>.` — a potential Raised-to-SO candidate if the SO considers the literal error string spec-contracted. However, the spec uses `<N>` as a placeholder, not a literal; the implementation already interpolates `{max_stdin_bytes}` into the placeholder position. A remediation hint is an additional stderr line (parallel to the `Hint:` lines in `emit_storage_error`) that does not alter the spec-contracted first line; no SO amendment needed. The unit-label improvement to `<N>` itself (e.g., `10485760 bytes` or `10 MB`) would change the string and would require the spec to acknowledge human-readable units — but the test at [`tests/bookmarks.rs`](../../tests/bookmarks.rs) AC 27 asserts on `code(1)` and stderr content starting with `Error: stdin exceeded`; the specific number format is not fully-pinned in the test, leaving room for the implementation to improve without breaking the integration test.

**Classification:** Deferred — two-part fix (unit representation + remediation hint) at [`src/main.rs:436`](../../src/main.rs); `software-engineer` code change. No spec amendment required for the hint line; unit-format change warrants SO review if the error string is considered spec-literal. Routes to Phase 4 feedback integration for the next Layer 3 fix-cycle.
