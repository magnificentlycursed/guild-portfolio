<a id="r5-f9"></a>

**Finding 9 — Downgrade-corruption hazard documented at `DESIGN.md:258` does NOT enable a new attacker primitive; the silent-data-loss asymmetry is operator-discipline-mitigated and the attacker advantage is null (Dim 9)**

**Owner:** red-team
**Status:** validated
**Blocked by:** *(none)*
**Validator:** security

The user-prompt specifically asks: *"the new threat-model paragraph + downgrade-corruption hazard paragraph — are there new attack surfaces they introduce or fail to address? E.g., the downgrade hazard makes silent data loss possible; can an attacker exploit this asymmetry?"*

Red Team-domain answer: **No exploitable attacker primitive.** Reasoning:

**Attack-class enumeration against the downgrade-hazard surface.** The asymmetry is: Layer 2 binary reads Layer 1 files cleanly (`#[serde(default)]`); Layer 1 binary reads Layer 2 files cleanly (serde_json ignores unknown fields) AND on next save silently drops the `tags` field. Question — what can an attacker do with this asymmetry?

1. **Attacker forces a downgrade.** Attacker needs to substitute the user's `bm` binary with a Layer 1 binary. This requires:
   - Write access to `~/.cargo/bin/bm` (or equivalent). On a single-user system, this requires the user's UID; on a shared system, this requires root or a UID-share. Both are out-of-scope per the Layer 1 R1 F1 accepted-risk framing.
   - OR: attacker controls `$PATH` to point at an attacker-supplied `bm` binary. Same out-of-scope shape — env-var ambient-authority per Layer 1 R1 F1.
   The attacker who can substitute the user's binary already has the worst-case primitive (they can run arbitrary code as the user); the downgrade-corruption is a secondary symptom of a primary compromise, not a separable attack class. **No new primitive.**

2. **Attacker exploits a legitimate downgrade.** If the user voluntarily downgrades (e.g., reverts to an older release; rolls back a system upgrade), the silent tag-loss is documented as a "deliberate forward-only migration choice" with operator-discipline mitigation. The attacker cannot induce the user to downgrade without already having the substitution primitive above; the attacker advantage in the legitimate-downgrade case is null because the attacker is not present.

3. **Attacker uses the asymmetry to mask tag-injection.** Scenario: attacker has Layer 1 R1 F1 env-var-redirection capability; user runs `bm tag <url> phishing` on the legitimate Layer 2 binary against the attacker-redirected store file; attacker then forces user to downgrade (somehow — see point 1 above); user's next `bm add` against the Layer 1 binary silently drops the `phishing` tag. **Attacker outcome:** the malicious tag-injection is *erased*, which is the OPPOSITE of the attacker's goal (the attacker wants the tag injection to persist as a misleading trust signal — RT R4 F6). The downgrade asymmetry HELPS the user in this scenario; it does NOT help the attacker. **Attacker primitive: negative.**

4. **Attacker uses the asymmetry to defeat user audit.** Scenario: user uses tags as a personal-audit signal (per RT R4 F6's framing — "I tagged this `verified` after auditing it"). Attacker injects tags via the file-write primitive. User downgrades (voluntarily, e.g., reverts a system upgrade). Next `bm add` silently drops the tags — including the user's own legitimate tags AND the attacker's injected tags. **Attacker outcome:** the attacker's injection is erased alongside legitimate data; net attacker advantage is zero. The user experiences data loss but not in an attacker-controlled direction.

5. **Attacker uses the asymmetry to DoS the user's tag-organization.** Scenario: attacker has the env-var-redirection capability; attacker pre-stages a Layer 2 file at the redirected location with N years of fabricated tag history; user downgrades (somehow); next save silently drops everything. This is a DoS shape — but the attacker can already DoS by deleting or corrupting the file directly via the same write primitive. **No new primitive; the downgrade-asymmetry is a slower path to a worse outcome the attacker can already achieve faster.**

The downgrade-corruption hazard is correctly characterized in the DESIGN.md paragraph as a **deliberate forward-only-migration choice** that affects the *user-discipline* surface (don't downgrade against a Layer 2 store without backup), not the *attacker-capability* surface. The attacker cannot exploit the silent-data-loss asymmetry to gain capability they don't already have.

**Adversarial probe (chained vulnerability between the downgrade hazard and other in-scope threats).** The Round 1 RT R4 finding-set named three in-scope adversary classes: co-tenant FS-read, $BOOKMARK_CLI_DB env-var redirection, adversary-supplied URL/tag content. Can the downgrade hazard chain with any of these?

- **Co-tenant FS-read.** Read-only access cannot induce downgrade or trigger save; the asymmetry only manifests on write. No chain.
- **$BOOKMARK_CLI_DB env-var redirection.** The attacker can pre-stage any file format at the redirected path. The Layer 2 binary will tolerate Layer 1 format (via `#[serde(default)]`) and Layer 2 format (canonically) and any extra-fields format (per serde_json's default behavior). The pre-stage attack works against the env-var redirection regardless of which format the attacker uses; the downgrade asymmetry adds no leverage. **No chain.**
- **Adversary-supplied URL/tag content.** This is the storage-content-injection class; the attack works through the existing render-time `display_safe` and threat-model-named accepted-risks. The downgrade hazard affects what survives a save cycle, not what reaches a render. **No chain.**

**Conclusion.** The downgrade-corruption hazard does NOT introduce a new attack surface and does NOT chain with any existing in-scope adversary class. The paragraph correctly identifies the asymmetry as an operator-discipline concern; the user-prompt's explicit question ("can an attacker exploit this asymmetry?") is answered: no. The paragraph's audit-trail framing is sound from the Red Team's lens.

**Classification:** Resolved (Dim 9) — affirmative-coherence finding; the downgrade-hazard documentation is Red-Team-coherent at first cold-session pass. No attacker primitive surfaces.

**Finding 10 — Threat-model paragraph at DESIGN.md:241 names tag-injection-as-trust-signal but does NOT name the new render-side amplification class the Layer 3 `--show-tags` flag would activate (Dim 9)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*
**Validator:** security

Adjacent-defect probe against the new threat-model bullet at [`DESIGN.md:241`](../../DESIGN.md). The paragraph documents tag-injection-as-trust-signal — an attacker who can write the storage file can fabricate tags that mislead the user when they `bm list --tag verified`. The paragraph names the storage-side primitive correctly. **What it does NOT name** is the corresponding render-side amplification class:

The Round 1 RT R4 F3 finding (still Raised-to-SO; carry-forward) names that a future `bm list --show-tags` flag (out-of-scope at Layer 2 per DESIGN.md line 70) would activate the tag-rendering path. RT R4 F3's framing is forward-readiness: when `--show-tags` lands, the implementer must remember to wrap tag content in `display_safe`. The Round 1 RT R4 F6 framing for tag-injection-as-trust-signal is the storage-side primitive: attacker fabricates tags via file-write.

The two findings combine into an unnamed chained-vulnerability class: an attacker with file-write capability + a future `--show-tags` flag without the `display_safe` wrap = a path-to-terminal-escape primitive against an attacker-controlled value class (tag content) that the spec has explicitly accepted as raw at storage. The current DESIGN.md amendment names the storage-side accepted-risk but not the chained class.

Why this is a NEW Round 2 finding rather than a re-iteration of RT R4 F3 + F6: the chained shape — *storage-side injection × future-flag-render-path = terminal-escape-against-accepted-raw-storage* — is a Dim 9 chained-vulnerability framing that neither Round 1 finding made explicit. RT R4 F3 framed the future `--show-tags` concern as a forward-readiness UX-confusion concern (bidi attack at export; OSC 8 masquerade); RT R4 F6 framed the tag-injection-as-trust-signal concern as a UX-confusion concern. Their combination is a terminal-injection-via-stored-tag concern: the attacker's storage-write injects an ANSI escape sequence into a tag value (e.g., `"tags": ["[2J[H"]`), then waits for the user to enable a future `--show-tags` flag, then the user sees a screen-clear primitive in their terminal.

The current amendment text addresses the trust-signal concern but does NOT mark the rendering-amplification chained class. A future Red Team Round (or a future SE landing `--show-tags`) reading the threat-model bullet sees the storage primitive but not the chained class.

**Proposed DESIGN.md amendment:** Add to the end of the existing [`DESIGN.md:241`](../../DESIGN.md) bullet:

> "**Forward-readiness chained class:** if a future Layer 3 `--show-tags` flag activates the tag-rendering path (out-of-scope at Layer 2 per § Scope), the storage-time tag-injection primitive combines with the render path to produce a terminal-escape-via-stored-tag class. The `display_safe` discipline at render time (per [Red Team Review 1 Round 3 Finding 3](vsdd-suite/review-log/2026-05-20-red-team.md#r3-f3)) MUST be applied at the rendering boundary of any tag-printing flag — see Layer 2 Round 1 Red Team F3 forward-readiness flag."

**Classification:** Raised to SO (Dim 9) — chained-vulnerability framing not addressed by the existing amendment text; needs explicit naming.
