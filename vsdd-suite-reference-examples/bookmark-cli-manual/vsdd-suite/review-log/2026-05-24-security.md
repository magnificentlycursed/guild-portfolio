<a id="r1-f1"></a>**Finding 1 — `display_safe` at the `bm export` serialization boundary breaks the spec's `bm export | bm import` byte-preservation claim for pathological URLs (Dim 2, Dim 1)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*

[DESIGN.md line 106](../../DESIGN.md) (§ `bm export` (Layer 3)) makes the following claim:

> "**Phase 2b implementation verification:** the implementation must confirm `display_safe`-wrapped strings remain JSON-valid (terminal escape sequences serialize as JSON-valid `` sequences so the round-trip `bm export | bm import` preserves the underlying bytes)."

The implementation at [`src/lib.rs:687-705`](../../src/lib.rs) escapes control / format characters via:

```rust
let _ = write!(out, "\\u{{{:04x}}}", c as u32);
```

— a **Rust-format escape** producing the 8-character literal sequence `\u{001b}` (backslash, `u`, open-brace, hex digits, close-brace). serde_json then serializes that 8-char string as the JSON literal `"\\u{001b}"`. JSON's actual `\uXXXX` escape (without braces) is what would round-trip the source byte; the Rust-style `\u{...}` form is NOT a JSON escape — JSON parsers (including serde_json's deserializer at `bm import` time) treat it as 8 literal characters.

**Concrete byte-trace of the round-trip:**

1. Source store: `{"url": "https://evil.example/[31mfrobnicate", ...}` (URL field contains 1-byte ESC + literal text).
2. `bm export` calls `display_safe(bm.url())` → `"https://evil.example/\u{001b}[31mfrobnicate"` (the ESC byte is replaced by 8 literal chars `\u{001b}`; total URL length grows by 7).
3. serde_json serializes the resulting string as `"https://evil.example/\\u{001b}[31mfrobnicate"` (the backslash is JSON-escaped to `\\`).
4. `bm import` deserializes that JSON string → URL field is the 8-char-extended literal `"https://evil.example/\u{001b}[31mfrobnicate"` (NOT the original 1-char-ESC form).
5. Destination store contains a URL field that is NOT byte-equal to the source.

The existing test [`tests_export_import_round_trip`](../../tests/bookmarks.rs#L1602) uses URLs without control chars (`https://item-0.example`, etc.), so it passes — the round-trip violation is **not test-covered**. The existing test [`tests_export_applies_display_safe_to_pathological_url`](../../tests/bookmarks.rs#L1236) asserts (a) no raw ESC in output, (b) output is JSON-valid, and (c) the URL field contains no raw ESC — it does NOT assert the byte-preservation round-trip. Both tests pass while the spec claim is silently violated.

**Why this is a Security finding, not a pure data-integrity finding:**

1. **Spec-violation on a security-relevant claim.** The spec at line 106 explicitly invokes round-trip byte-preservation as the verification target for the `display_safe`-at-export design choice. Security domain Dim 2 (persistence-data validation) covers any boundary where validated-vs-stored data shape drifts from spec; the export-import round trip IS a persistence boundary.
2. **"Store raw, sanitize at render" architectural-discipline violation.** [RT R1 F3 / RT R4 F3 carry-forward](2026-05-21-red-team.md#r4-f3) was closed at PR #46 with the framing "Layer 3 export path will render tag labels + URLs to stdout for downstream pipeline consumption; the existing `display_safe` sanitizer must apply at every Layer 3 export boundary that emits to a terminal-renderable surface." The implementation took the broader interpretation (sanitize the strings the serializer sees) rather than the narrower one (sanitize at the byte-emission boundary only, e.g., wrap stdout in a sanitizing Writer). The broader form is the one that violates the round-trip claim. RT R4 F3's amendment text matters: "the stored JSON is NOT sanitized" — the AMENDMENT closed at PR #46 says the **stored** JSON is unsanitized; the implementation in fact sanitizes the **exported** JSON's string values, producing a destination store with sanitized-escape-literals (not raw escape bytes) when re-imported. The destination store is therefore stored-sanitized — opposite to the spec's stated architectural choice.
3. **Defense-in-depth gain is real but spec-incoherent.** A reviewer could argue the implementation's behavior (sanitize-at-export-then-store-sanitized) is *more* defensive than the spec (store-raw, sanitize-at-render) because the destination store no longer carries live ESC bytes that a subsequent `bm list` would need to re-sanitize. That argument is valid as a design preference but it is not the design the spec describes; the spec needs to either match the implementation OR the implementation needs to change to match the spec.

**Reproducer (conceptual; sandbox forbids executing the binary in this session):**

```sh
# Source store with pathological URL containing a raw ESC byte:
printf '{"bookmarks":[{"url":"https://evil.example/\x1b[31mfrobnicate","timestamp":"2026-05-24T01:00:00Z","tags":[]}]}' > /tmp/src.json

# Export then import to a fresh destination:
BOOKMARK_CLI_DB=/tmp/src.json bm export | BOOKMARK_CLI_DB=/tmp/dst.json bm import

# Compare URL field bytes:
python3 -c "import json; print(repr(json.load(open('/tmp/src.json'))['bookmarks'][0]['url']))"
# Expected output (per spec line 106): 'https://evil.example/\x1b[31mfrobnicate'
python3 -c "import json; print(repr(json.load(open('/tmp/dst.json'))['bookmarks'][0]['url']))"
# Observed (per code analysis): 'https://evil.example/\\u{001b}[31mfrobnicate'
# Source URL is 33 bytes; destination URL is 40 bytes — NOT byte-preserving.
```

The reproducer was NOT run in-session because the sandbox forbids invoking the built binary; the byte-trace above is from code analysis of `display_safe` at [`src/lib.rs:687-705`](../../src/lib.rs) + the JSON serialization path. Red Team validation should run the binary directly to confirm the byte-divergence.

**Proposed disposition (two paths, SO adjudicates):**

- **Path A — spec amendment:** Amend [DESIGN.md line 106](../../DESIGN.md) to reflect the implementation's actual behavior: "`display_safe` wraps the URL + tag-label strings at the per-bookmark serialization step; this is the canonical sanitization-at-render-equivalent boundary per the RT R4 F3 carry-forward discipline. The round-trip `bm export | bm import` preserves bookmark records for URLs / tags that contain no `is_control()` or `is_format_char` bytes; for URLs / tags that DO contain such bytes, the round-trip stores the escaped literal form at the destination — the operator's terminal is safe regardless of which renderer the destination feeds, but byte-equality to the source store is NOT preserved." Amend the test [`tests_export_import_round_trip`](../../tests/bookmarks.rs#L1602) to include a pathological-URL case asserting the escape-literal preservation (not raw-byte preservation).

- **Path B — code change to match spec:** Move `display_safe` from the per-string-value-at-serialize boundary into the stdout-write boundary — wrap stdout in a `display_safe`-applying Writer at the `print!("{json}")` call site in `run_export` ([`src/main.rs:414`](../../src/main.rs)). The stored JSON string values become byte-equal to the source; the rendered stdout bytes are still escape-clean for terminal consumers. The round-trip `bm export | bm import` preserves source bytes because the import-side parser sees the JSON-escape-form (``) which deserializes to the original ESC byte. The trade-off: complexity moves from `export_json` (pure) to `run_export` (effectful); the existing test asserting no-raw-ESC-in-stdout passes either way; a new test asserting source-byte preservation across the round-trip is added.

**Recommended path (Security perspective):** Path A. Path A names the implementation's existing defense-in-depth gain explicitly; Path B re-introduces live ESC bytes into the destination store that a subsequent `bm list` must re-sanitize (correctness depends on the render-time `display_safe` discipline holding). The cost-asymmetry favors Path A: a 2-sentence spec amendment + one test assertion vs. a Writer-wrapping refactor whose correctness depends on a future maintainer not forgetting the wrap. Path A also closes RT R4 F3's "stored JSON is NOT sanitized" amendment language (which became inaccurate when the implementation diverged from it).

**Classification:** Raised to SO. The defect is at the DESIGN.md / implementation interface; only the Solution Owner has DESIGN.md change authority per the Security domain prompt. The risk-owner-pending-fix attribution is solution-owner; Security routes the decision and re-validates whichever path SO chooses.

<a id="r1-f2"></a>**Finding 2 — Tag-injection-as-trust-signal threat class extends to stdin-fed `bm import` but DESIGN.md § Threat model addition does not name the extension (Dim 1, Dim 8)**

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*

The Layer 2 threat-model paragraph at [DESIGN.md:301](../../DESIGN.md) names the **tag-injection-as-trust-signal** class:

> "an adversary with write access to the storage file (the same vector as Adversary-controlled `$BOOKMARK_CLI_DB` above) can fabricate tags like `["verified", "approved"]` on user-trusted bookmarks, creating a misleading trust-signal that the user might interpret as their own past-tagging."

The Layer 2 mitigation: mode 0600 + symlink-rejection prevent write access to the storage file; the attacker class is bounded by "the attacker already has more leverage than tag injection — they can also rewrite URLs, fabricate entire bookmark records, or replace the whole file." Documented as **accepted risk** because the write-access precondition already grants strictly greater leverage.

The Layer 3 spec's threat-model addition at [DESIGN.md:130](../../DESIGN.md) extends the threat model for the stdin attack surface, but covers only TWO dimensions:

> "Existing defenses apply: serde_json default 128-level recursion limit defends against JSON depth-bomb [...]; display_safe applies at the rendering boundary if imported bookmarks are subsequently rendered via `bm list`. New defenses for the stdin attack surface: **(a)** the 10 MB input-size cap above [...]; **(b)** import-from-attacker-controlled-stdin per the Layer 1 threat-model framing on adversary-supplied URL contents — same disposition: store the bytes as-given; defer rendering safety to the `display_safe` discipline at output time."

**The gap:** Layer 3 `bm import` introduces a NEW vector for tag injection that the Layer 2 paragraph's "write-access precondition grants strictly greater leverage" argument does NOT cover. An attacker who can supply the import payload (vector: user pipes attacker-published JSON via `curl ... | bm import`; clipboard-paste tool; wrapper script) gets the tag-injection primitive WITHOUT first needing write access to the storage file. The attacker's leverage is bounded only by what `import_json` will accept — which is any well-formed JSON with valid `url` + `timestamp` + `tags` fields. The attacker can fabricate tags like `["verified", "approved", "reviewed-by-user"]` on bookmarks they construct (or on bookmarks they prepend to legitimate exported payloads).

**Why this is NOT subsumed by the Layer 2 disposition:**

- Layer 2: attacker needs write access → already has greater leverage (can rewrite URLs, etc.) → tag-injection is a strict subset of an already-accepted-risk class.
- Layer 3: attacker needs only the ability to publish content the user pipes in → does NOT have arbitrary-file-write leverage on the user's account → tag-injection is the PRIMARY attack primitive available to this attacker class, not a secondary consequence.

The "store the bytes as-given; defer rendering safety to display_safe at output time" disposition in DESIGN.md line 130 addresses the **rendering** dimension (which `bm list` would sanitize anyway) but does NOT address the **trust-signal** dimension (the user querying `bm list --tag verified` will see attacker-fabricated bookmarks alongside legitimately-self-tagged ones with no distinguishing signal). The user's own audit trail (the tags they remember adding) is no longer authoritative once an attacker-supplied import has run.

**Concrete attack scenario (conceptual; reproducer left to Red Team validation):**

1. Attacker publishes `https://attacker.example/cool-rust-bookmarks.json` containing legitimate-looking bookmarks (real URLs, plausible timestamps) **tagged with `["verified", "approved", "reviewed"]` and other user-trust-signal labels**.
2. User runs `curl https://attacker.example/cool-rust-bookmarks.json | bm import` thinking they're importing a curated bookmark collection.
3. Destination store now contains attacker bookmarks with attacker-controlled tag labels.
4. User later runs `bm list --tag verified` expecting to see THEIR OWN past-verified bookmarks; attacker bookmarks surface alongside genuine ones with no distinguishing signal. The user clicks one. (`bm list` rendering doesn't open URLs but the user's downstream workflow — copy URL → paste in browser — is where the harm materializes.)

The attack succeeds without compromising the user's account, without writing to the storage file directly, without bypassing the mode-0600 control, and without bypassing the symlink-rejection. The Layer 2 mitigation chain is intact and does not foreclose this attack.

**Proposed disposition:**

- **Path A — spec amendment (Raised to SO):** Extend [DESIGN.md:130](../../DESIGN.md) to name the tag-injection class explicitly for the stdin vector. Proposed amendment text: *"**Tag-injection-as-trust-signal via stdin** (Layer 3 extension of the Layer 2 Adversary-supplied URL contents threat). The Layer 2 disposition documented at line 301 was that the write-access-precondition attacker has strictly greater leverage; the Layer 3 stdin attacker does NOT have that precondition, so tag-injection becomes the primary attack primitive for the stdin attacker class. Disposition: store the bytes as-given (consistent with the Layer 1 URL-content disposition); document this surface as an **accepted risk for the operator** who chooses to pipe attacker-supplied JSON through `bm import`. The mitigation the operator applies is workflow-level (verify the source of imported payloads; do not pipe untrusted curl-fetched JSON). The application does not validate that tag-labels are operator-authored vs. import-supplied — operators who need that distinction should maintain separate stores per import-source."*
- **Path B — code change:** Prefix imported tags with a provenance marker (e.g., `imported:verified` instead of `verified`) so the user can distinguish self-authored from import-supplied tags. This is a substantive UX / data-model change that affects the round-trip invariant; out of scope for a Security finding to mandate. Mentioned for completeness.
- **Path C — accepted risk:** Classify as **Accepted risk** per the Security four-class universe, with the **operator** named as the risk owner (the user piping attacker-supplied JSON accepts the trust-signal-fabrication surface).

**Recommended path (Security perspective):** Path A + Path C combined — amend the spec to name the surface, then classify the surface as Accepted risk with the operator as the risk owner. The spec amendment is the audit-trail closure; the classification is the disposition.

**Classification:** Raised to SO. The amendment is documentation-level (proposed text supplied above); the eventual disposition path is **Accepted risk** with the **operator** named as the substantive risk owner — but the spec amendment must land first so the audit trail names the surface before the disposition is recorded. Re-classification to Accepted risk in Round 2 once the spec amendment lands.

<a id="r1-f3"></a>**Finding 3 — Layer 3 spec does not extend the confidential data classification posture to stdin-supplied tag bytes (Dim 8)**

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*

[DESIGN.md § Storage data classification](../../DESIGN.md) (lines 314–322) names the `tags` field as confidential-class data per the Layer 2 R4 F1 / R5 F1 spec amendment:

> "The per-bookmark `tags: Vec<String>` field is also **confidential**-class — what someone tags their reading with is at least as sensitive as the URLs themselves [...] The mode-0600 + symlink-rejection mitigations established for URLs apply uniformly to the `tags` field — the on-disk file is one confidential-class artifact; there is no per-field permission split."

The Layer 3 spec extension at [DESIGN.md:130](../../DESIGN.md) (threat-model addition for stdin-fed input) is silent on the **provenance** of tag bytes that enter the store via `bm import`. The data-classification posture says "tags = confidential" but does not name that **import-supplied tags become confidential-class data at the destination store as soon as the import write completes**, nor that **the operator who pipes attacker-supplied tags into their store has authorized that data to be classified at the destination's confidentiality tier**. This is a Dim 8 audit-trail completeness gap — the same shape as R4 F1's gap on the `tags` field itself (the on-disk control was uniform; the spec-level classification statement was incomplete).

The gap matters for two reasons:

1. **Forward-readiness for a future "remove imported tags" or "purge by provenance" operation.** If a future Layer 4 adds a `bm purge --imported-tag <label>` operation to recover from a malicious-import event, the spec needs an authoritative statement of what "imported tag" means and how the destination's data-classification posture applies to mixed-provenance data. The current spec has no such statement.
2. **Confidentiality-aware reasoning for cross-store imports.** A user who exports from a *personal* store (containing personal-confidential tags) and imports into a *shared-machine* store inherits the confidentiality tier of the source's tags into the destination. The spec's silent treatment means the user has no spec-anchored basis to reason about whether the cross-store import maintains the confidentiality posture.

**Proposed disposition:** Raised to SO for a spec amendment. Suggested text (3 sentences for § Storage data classification or § Threat model):

> **Imported-tag classification (Layer 3).** Tags entering the store via `bm import` inherit the *confidential* classification tier of the destination store regardless of the source's classification posture. The destination's mode-0600 + symlink-rejection mitigations apply uniformly to imported bytes at write time. An operator who pipes attacker-supplied JSON through `bm import` has authorized those bytes to be classified at the destination's confidentiality tier; cross-store imports that move bytes between stores of different confidentiality tiers are the operator's responsibility to validate.

**Classification:** Raised to SO. The amendment is documentation-only (no code change); the on-disk control is already uniform.

<a id="r1-f4"></a>**Finding 4 — `serde_json::from_str` 128-level recursion limit on `bm import` re-evaluation: protection still holds at Layer 3 but the disposition basis shifts from "no attacker write access" to "default-limit-plus-cap-bounded" (Dim 2)**

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*

[Security Review 1 Finding 6](2026-05-20-security.md#r1-f6) (verified at R2 F7 / R3 F7) classified the serde_json depth-bomb concern as **Hallucinated** on two grounds: (a) the attacker model does not grant write access to the storage file; (b) serde_json's default 128-level recursion limit produces a graceful parse error rather than a stack overflow. R1 F6's own prose named the re-activation trigger explicitly:

> "If a future layer adds an `bm import` command that reads JSON from stdin or an untrusted URL, this dimension re-activates and is no longer hallucinated; flag for re-evaluation at Layer 3 (per [`DESIGN.md`](../../DESIGN.md) § Scope and non-goals "`bm import` — read bookmarks from stdin" deferred to Layer 3)."

**The trigger has fired.** Layer 3 `bm import` consumes attacker-supplied JSON from stdin. Leg (a) of the Hallucination determination is no longer applicable — the attacker DOES have a write surface (write to stdin, not directly to the file, but the import-then-save flow ultimately writes the attacker-influenced bytes to the destination).

<a id="r1-f5"></a>**Finding 5 — `--max-stdin-bytes <N>` flag is an operator-controlled write-cap override; an operator who sets `N = usize::MAX` effectively defeats the size cap (Dim 1)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*

[`src/main.rs:167-168`](../../src/main.rs) declares the `--max-stdin-bytes` flag:

```rust
#[arg(long = "max-stdin-bytes", default_value_t = MAX_STDIN_BYTES_DEFAULT)]
max_stdin_bytes: usize,
```

[`src/main.rs:424-427`](../../src/main.rs) reads stdin with the cap applied:

```rust
let mut bytes = Vec::new();
let cap_plus_one = u64::try_from(max_stdin_bytes)
    .unwrap_or(u64::MAX)
    .saturating_add(1);
if let Err(e) = std::io::stdin().take(cap_plus_one).read_to_end(&mut bytes) {
```

The `saturating_add(1)` on `u64::MAX` yields `u64::MAX`; `Read::take(u64::MAX)` is effectively unbounded; the subsequent `bytes.len() > max_stdin_bytes` check where `max_stdin_bytes == usize::MAX` is "len > usize::MAX" which is impossible for any in-memory `Vec<u8>`. The size-cap protection is therefore **defeasible by the operator** via `bm import --max-stdin-bytes <large-value>` — at large enough values the cap is effectively absent and the import flow is bounded only by available memory.

**Why this is Accepted risk, not Open:**

The pattern matches the Layer 1 R1 F4 / R2 F5 / R3 F5 `$BOOKMARK_CLI_DB` ambient-authority disposition exactly: the operator controls their own shell; the operator's shell is the access boundary; the operator who explicitly disables a protection has authorized the surface that protection covered. The 10 MB default is the design-time floor; the `--max-stdin-bytes` flag is the explicit operator escape hatch. DESIGN.md line 128 already names this:

> "Default cap: 10 MB (matches the project's existing scale ceiling of 10,000 bookmarks at ~1 KB each). Operator override via `--max-stdin-bytes <N>` flag."

The spec explicitly enables the override; the finding is the audit-trail acknowledgment that the override semantics include the all-bets-off case. The threat model's existing ambient-authority disposition covers this — Security raises it as **Accepted risk** so the audit trail names the surface explicitly rather than absorbing it silently into the operator's responsibility.

**Adjacent observation (not a separate finding):** the `usize::MAX` corner case is platform-dependent (32-bit vs. 64-bit). On a 32-bit platform `usize::MAX` is 4 GiB, which is reachable via `Vec<u8>` allocation if the process address space allows. On 64-bit `usize::MAX` is unreachable because no realistic stdin stream contains 16 EiB. The platform-dependent corner case does not change the disposition.

**Classification:** Accepted risk. **Risk owner:** solution-owner (per the env-var ambient-authority precedent — operator controls their own shell and own flags). The cost of a defensive cap on `--max-stdin-bytes` (e.g., reject values > 100 MB) is the operator who has a legitimate 200 MB import has to chunk their workflow; the benefit is a small additional safety margin for operators who fat-finger a large value. The Layer 3 spec chose the operator-trust path; Security preserves the choice with the risk-owner named.

<a id="r1-f6"></a>**Finding 6 — `String::from_utf8(bytes)` at the stdin-cap boundary creates a UTF-8-split-byte information-leakage oracle when the cap falls mid-multi-byte-sequence**

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*

A reviewer's first instinct on seeing [`src/main.rs:443-449`](../../src/main.rs) might be: when stdin is exactly cap-bytes long and the cap-th byte happens to fall in the middle of a multi-byte UTF-8 sequence, `String::from_utf8(bytes)` fails with `FromUtf8Error` and the implementation routes through:

**Specific demonstration of why the concern does not apply (per Phase 3 primer's hallucinated-finding discipline):**

1. **The attacker already knows the cap.** The cap is named in two places the attacker can read directly: (a) DESIGN.md line 128 publishes "Default cap: 10 MB"; (b) the error message at `bm import` rejection time emits `Error: stdin exceeded maximum byte limit of <N>.` ([`src/main.rs:436`](../../src/main.rs)) which echoes the operator's `--max-stdin-bytes` value verbatim. 3. **The UTF-8 boundary failure mode is a graceful exit-1, not a process abort.** The implementation handles the failure with the spec-contracted error message; no stack corruption, no memory disclosure, no use-after-free. The failure mode is the same as any other malformed-input error.

The finding does not represent a control gap because the "information" the oracle would leak (the cap value) is freely advertised, and the failure mode is graceful by design. The concern is structurally adjacent to a real oracle class (UTF-8 boundary timing in network protocols) but the specific application context — operator-set, freely-published cap — eliminates the secrecy precondition for the oracle to be useful.

**Classification:** Hallucinated. **Owner:** solution-owner

**Blocked by:** *(none)*

The architectural correction sub-decision at commit [`bfc0713`](https://github.com/magnificentlycursed/guild-portfolio/commit/bfc0713) removed `display_safe` from `export_json` entirely (rather than the routed Path C of switching its emit format). **The gap:** the trade-off acknowledgment is a one-sentence pointer toward "consumers should apply display_safe" but does NOT name **(a)** the cross-organizational-seam structure of the deferred control (the `bm` author ships one rendering boundary; arbitrary consumers control the second — they may not exist yet, may not be co-evolved with the `bm` versioning cycle, may not even be aware that `bm export` output requires sanitization), **(b)** the concrete attacker who exploits the gap (an attacker who can publish JSON the user pipes through `curl ... | bm import` cannot just be the import-time attacker; the SAME payload re-exported by the destination operator + piped to a DIFFERENT consumer is the cross-cut surface), or **(c)** the structurally-honest framing that "consumers must apply display_safe" is **an obligation the spec places on the consumer** without a mechanism to verify the consumer received the obligation or implemented it correctly.

**Why this is a Security finding, not a documentation finding:**

1. **Sanitize-at-render architectural discipline is half-honored.** The Layer 1 / Layer 2 disposition (per [DESIGN.md line 308](../../DESIGN.md)) said "URLs can carry terminal-escape sequences; mitigation is `display_safe` at every render boundary." `bm list` honors this — every URL render path wraps with `display_safe`. `bm export` post-correction does NOT honor it at the export boundary AND does not include any pipeline-consumer-side enforcement. The consumer-side gap is a real one-sided trust-boundary handoff.
2. **The curated format-char vectors that DO survive export are the same vectors named in [`is_format_char` at src/lib.rs:824](../../src/lib.rs).** The function's curated set covers U+202E (RLO bidi spoof — Trojan-Source), U+200B-200F (zero-width spaces + LRM/RLM), U+FEFF (BOM), U+E0020-E007F (tag-character supplementary plane), U+202A-202E (explicit bidi formatting), etc. — every one of these vectors carries a documented spoofing attack class. A URL like `https://example.com/[U+202E]xelf-loader.exe.pdf` survives `bm export` JSON output as raw bytes; a downstream consumer printing the parsed url field renders the URL with the bidi flip applied — the operator sees `gdp.exe.redoal-flxe/moc.elpmaxe//:sptth` or similar, which they may mis-identify as a PDF link. The Trojan-Source attack class is well-known (CVE-2021-42574 at the source-code level; analogous at the URL-rendering level).
3. **The "consumers should apply display_safe" pointer is unverifiable.** Unlike the Layer 2 tag-injection-as-trust-signal accepted-risk (where the operator's responsibility is `workflow-level: verify the source of imported payloads`), the consumer-side render obligation cannot be enforced by the spec OR validated by the operator. A spec that places an obligation on an unidentified third party without a verification mechanism has placed the obligation nowhere.

**Concrete attack scenario (conceptual; reproducer left to Red Team validation):**

1. Attacker publishes `https://attacker.example/bookmarks.json` containing legitimate-looking bookmarks with one URL containing `U+202E` between the legitimate path and a malicious extension: `{"url": "https://example.com/file[U+202E]gpj.gnp.bookmarks", ...}` (the `bm import` active-tag-mitigation does NOT cover URLs).
2. User runs `curl ... | bm import` and accepts the import.
3. User later runs `bm export | jq '.bookmarks[].url' | xargs -I{} echo {}` (a common-shape "list bookmark URLs without timestamps" workflow). `jq -r` strips the JSON quoting; `xargs ... echo` renders the URL raw to the terminal.
4. The terminal applies the bidi flip; the user sees a PNG that is actually a JPG-named-as-PDF that is actually a `.bookmarks`-extension binary. The user clicks/opens. (`bm` doesn't open URLs but the rendered display determines what the user copies + pastes elsewhere.)

The attack works because `bm export` output passes through a JSON-aware pipe (jq) that strips quoting + into a JSON-unaware renderer (`echo` to terminal) that does NOT apply `display_safe`. The architectural-correction trade-off documented at [DESIGN.md:106](../../DESIGN.md) names this trade-off in one sentence but does NOT name (a) the threat-actor (cross-organizational-seam consumer), (b) the canonical-shape attack scenario, or (c) the operator's mitigation handle (workflow-level discipline like jq's `--ascii-output` flag, or a `bm export --display-safe` opt-in flag).

**Proposed disposition (two paths, SO adjudicates):**

- **Path A — spec amendment (lowest cost, names the surface):** Amend [DESIGN.md § `bm export` (Layer 3)](../../DESIGN.md) to add an explicit threat-model paragraph naming the cross-organizational-seam attack class for format-char URL spoofing in exported JSON. Proposed text: *"**Format-char URL-spoofing accepted-risk (Layer 3 architectural-correction trade-off).** Curated format chars (bidi controls per `is_format_char`'s U+202A-202E + U+200B-200F + U+FEFF + tag-character supplementary plane) survive `bm export` as raw UTF-8 bytes in JSON output. A downstream consumer that renders the parsed-JSON `url` or `tag` fields without applying `display_safe` (canonical worked example: `bm export | jq -r '.bookmarks[].url' | xargs echo`) renders the bidi-flip / zero-width / Trojan-Source attack to the operator's terminal. Disposition: accepted-risk. The operator's mitigation handle is workflow-level — pipe through `jq --ascii-output` (which escapes non-ASCII to `\uXXXX`) when bridging JSON to terminal renderers, OR re-import to a fresh store + use `bm list` (which applies `display_safe`) instead of a JSON-aware pipe. The spec does not commit to an export-side display_safe flag at Layer 3."*

- **Path B — opt-in flag (code change):** Add a `bm export --display-safe` flag that wraps URL + tag fields with `display_safe` BEFORE serialization. Stores the escaped form in the JSON output (the operator opts-into Path A from Round 1 explicitly for the rendering scenarios). Default-off preserves the byte-preservation round-trip; opt-in serves the operator who wants pipeline-render safety. Trade-off: complexity moves from spec-amendment-only to spec-amendment + clap flag + impl + test + documentation update.

- **Path C — refuse-to-export-format-chars (code change, more conservative):** Apply the same active-mitigation pattern as imported-tag control-char rejection to URLs at import time (reject URLs containing format chars). This forecloses the import path entirely — the attack scenario requires the bidi-URL to be in the store; if `bm import` rejects it, the destination store never contains the bytes. Trade-off: breaks the spec's existing "URLs are stored as-given; rendering safety is deferred to render-time" disposition; this is a substantive architectural shift, not a Security correction.

**Recommended path (Security perspective):** Path A. Path A names the surface in the audit trail without changing the architectural correction's underlying soundness. Path B is a follow-up worth considering if cross-organizational-seam usage patterns surface in real operator workflows. Path C is over-mitigation given the threat model's other accepted-risks for similar attacker classes — the URL-rendering threat at Layer 1 is already accepted-risk (operator-supplied URLs), and the cross-organizational-seam consumer is a derivative of the same operator-pipes-stuff-they-shouldn't class.

**Classification:** Raised to SO. The amendment is documentation-level (proposed text supplied above); the operator-mitigation handle (jq `--ascii-output`) is workflow-level and operator-owned per the same ambient-authority precedent as the env-var + `--max-stdin-bytes` dispositions.

<a id="r2-f2"></a>**Finding 2 — Active control-char tag rejection predicate rejects legitimate `\n` / `\t` tags while `display_safe` passes them through; symmetry-claim comment in `import_json` is false (Dim 1, Dim 9)**

**Owner:** software-engineer
**Status:** raised
**Blocked by:** *(none)*

The post-fix `import_json` at [`src/lib.rs:583-589`](../../src/lib.rs) implements active control-char tag rejection:

```rust
for (idx, bm) in imported.iter().enumerate() {
    for tag in &bm.tags {
        if tag.chars().any(|c| c.is_control() || is_format_char(c)) {
            return Err(ImportError::TagContainsControlChars(idx, tag.clone()));
        }
    }
}
```

The in-source comment at [lines 580-582](../../src/lib.rs) makes a symmetry-claim:

> "The predicate is the same `is_control()` / `is_format_char` shape that `display_safe` uses for the escape-vs-passthrough decision."

**The claim is false.** `display_safe` at [`src/lib.rs:777-781`](../../src/lib.rs) has an explicit passthrough branch for `\n` and `\t` BEFORE the `is_control() || is_format_char(c)` check:

```rust
for c in s.chars() {
    if c == '\n' || c == '\t' {
        out.push(c);
        continue;
    }
    if c.is_control() || is_format_char(c) {
        // ... escape
    }
}
```

`char::is_control()` returns true for U+0009 (`\t`) AND U+000A (`\n`) per [the Rust stdlib documentation](https://doc.rust-lang.org/std/primitive.char.html#method.is_control). The predicates are NOT symmetric — `display_safe` treats `\n` + `\t` as legitimate whitespace; `import_json`'s rejection treats them as disallowed control chars.

**The behavioral asymmetry:**

1. A user adds a multi-line bookmark with a multi-line tag via direct `bm tag` (Layer 2). The tag stored on disk legitimately contains `\n` per the existing Layer 2 disposition at [DESIGN.md edge-case catalog](../../DESIGN.md): "Tag label containing newlines or control characters: stored as-is; rendered through the same display_safe sanitizer as URLs."
2. User runs `bm export | bm import` to round-trip the store (the canonical Layer 3 backup workflow per [DESIGN.md line 114](../../DESIGN.md)).
3. `bm export` emits the tag with `\n` as a JSON-native `\n` escape (serde_json's native encoder produces `\n` for U+000A per RFC 8259 § 7).
4. `bm import` parses the JSON, recovers the tag's `\n` byte, fires the rejection predicate at line 585, returns `ImportError::TagContainsControlChars(idx, tag)`.
5. The round-trip FAILS for tags that were legitimately created at the Layer 2 boundary AND survive the Layer 2 disposition AND are spec-permitted at the storage layer.

**Why this is a Security finding (Dim 1 input-handling + Dim 9 error-message escape):**

- **Dim 1 (Input handling — false-positive rejection at the trust boundary).** A validator that rejects spec-permitted input at the boundary breaks the symmetry between what the application accepts via one entry point (`bm tag`) and what it accepts via another (`bm import`). Per Suite [G-152](../../../../vsdd-suite/suite-development/FINDINGS-INDEX.md#g-152) (input/output strictness symmetry — the same dimension that names error-message echoing as a special-case): two write-paths for the same data type should accept the same input shapes, OR the asymmetry should be a deliberate spec choice with a named rationale. The current asymmetry is silent — neither the spec nor the implementation comments name the `\n`+`\t` exclusion as a rejection rule for the import path.
- **Dim 9 (Error-message escape — `display_safe` predicate-divergence undermines the documented escape discipline).** The `import_json` comment claims symmetry with `display_safe`'s predicate; the symmetry is the documented mental model for downstream maintainers reasoning about the validator's coverage. A future maintainer who reads the comment + then adds a new sanitizer call-site assuming the predicates match will introduce a different defect class (e.g., a tag-rendering path that rejects `\n` tags loaded from disk because they "shouldn't be possible per the import rejection" — even though Layer 2 `bm tag` happily creates them).

**Reproducer (conceptual):**

```sh
# Create a tag containing a newline via Layer 2 bm tag (currently spec-permitted):
BOOKMARK_CLI_DB=/tmp/src.json bm add https://example.com
BOOKMARK_CLI_DB=/tmp/src.json bm tag https://example.com "$(printf 'line1\nline2')"

# Round-trip via Layer 3:
BOOKMARK_CLI_DB=/tmp/src.json bm export | BOOKMARK_CLI_DB=/tmp/dst.json bm import
# Expected: success; Imported 1 bookmark.
# Observed (per code analysis at src/lib.rs:585): exit 1 with
#   "Error: imported bookmark tags contain disallowed control characters."
```

The reproducer was NOT run in-session (sandbox-restricted from binary execution); the divergence is traceable via direct code inspection.

**Proposed disposition (three paths, SO adjudicates):**

- **Path A — fix the asymmetry (recommended; recommended impl):** mirror `display_safe`'s passthrough branch in `import_json`. Change the predicate at line 585 to `if c != '\n' && c != '\t' && (c.is_control() || is_format_char(c))`. The Phase 2a regression test [`tests_import_rejects_control_char_in_tags`](../../tests/bookmarks.rs#L1815) at line 1815 uses ESC (U+001B) as the trigger byte; the test still passes after Path A (ESC is is_control AND not `\n`/`\t`). Add a NEW regression test for the `\n`-tag round-trip per the reproducer above. Update the comment at lines 580-582 to name the symmetry-after-fix accurately.
- **Path B — fix the spec to match the implementation:** Amend [DESIGN.md § Edge case catalog Layer 2 "Tag label containing newlines or control characters"](../../DESIGN.md) to name the Layer 3 import-rejection asymmetry — multi-line tags created via `bm tag` are spec-permitted to exist but CANNOT round-trip through `bm export | bm import`. Document the limitation. Operators with multi-line tags should not rely on the round-trip preserving them.
- **Path C — spec the existing behavior as deliberate (lowest-quality option):** declare the `\n`+`\t` rejection at import as deliberate — "imported tags must be single-line per the spec-cleansing-on-untrusted-input discipline." Update DESIGN.md to say so. Path C cleanest if the spec genuinely wants stricter discipline at the import boundary than at the type boundary; the trade-off is the Layer 2 / Layer 3 asymmetry becomes a spec contract.

**Recommended path (Security perspective):** Path A. The asymmetry is silent + violates the comment's stated symmetry claim + breaks the canonical round-trip workflow for a legitimately-permitted input class. Path A is a 3-character code change + a 1-test addition + a comment update.

**Classification:** Raised to SO. The fix is implementation-level (SE-owned), but the disposition between Paths A / B / C requires a spec-or-code decision that only SO can adjudicate (Path B + C are spec amendments; Path A is a behavior change requiring spec re-affirmation).

<a id="r2-f3"></a>**Finding 3 — Active control-char rejection covers tags only; imported URLs containing curated format chars (bidi, ZWJ, BOM) bypass the active mitigation and reach storage as raw bytes (Dim 1, Dim 8)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*

The post-fix `import_json` at [`src/lib.rs:583-589`](../../src/lib.rs) iterates over `bm.tags` only — the URL field is not subjected to the active control-char rejection. The Layer 3 fix-work's documented rationale at [DESIGN.md line 131](../../DESIGN.md) names URL-content as "URL contents per the Layer 1 threat-model framing on adversary-supplied URL contents — same disposition: store the bytes as-given; defer rendering safety to the `display_safe` discipline at output time." The asymmetric treatment (active mitigation for tags; accepted-risk for URLs) is a deliberate spec choice per the routing record's Path B operator decision.

**The gap (NOT a re-raising of Path B; a different attack surface the Path B rationale did not cover):**

The Layer 2 tag-injection-as-trust-signal threat that motivated active mitigation for tags was conditioned on **the trust-signal semantic** — the user querying `bm list --tag verified` expects the surfaced bookmarks to be self-authored. The active mitigation closes the control-char-injection vector for that trust-signal surface.

The URL surface has the **same trust-signal semantic** the spec did not name: a user querying `bm list https://example.com` expects the surfaced bookmark to have the URL they typed. An attacker who supplies a URL like `https://example.com[U+202E]gpj.foo` (bidi-flipped to appear as `https://example.com.foo.jpg` in renders) achieves the same trust-signal forgery — the user sees what they think is a JPG bookmark when the actual stored bytes are the malicious payload.

Per Round 1 [F2's framing](#r1-f2) for tag-injection: "Layer 3: attacker needs only the ability to publish content the user pipes in → does NOT have arbitrary-file-write leverage on the user's account → tag-injection is the PRIMARY attack primitive available to this attacker class." The identical argument applies to URL-injection: the Layer 3 stdin-attacker doesn't need write-access; URL-injection-via-format-char becomes the PRIMARY attack primitive for the URL trust-signal surface; the Layer 1 accepted-risk for URL-content was conditioned on the operator-typing-it-themselves frame (not the operator-pipes-published-content frame).

**Why Path B's routing-record framing did not cover this:**

The routing record at Phase 4 routing line 70-89 (per-domain Phase 4 appendices in `vsdd-suite/review-log/2026-05-24-<domain-slug>.md`) was scoped to **tag-injection escalation at Layer 3** — the routed finding was [Round 1 Sec F2](#r1-f2) which named tag-injection specifically. The URL-injection-via-format-char vector was implicitly subsumed under [Round 1 Sec F1](#r1-f1) (display_safe-at-export round-trip violation) which was about rendering safety, not stored-bytes-trust-signal. The two issues are different attack surfaces; the routing covered one (tag rendering) + the architectural correction covered another (rendering deferred to consumer) + this finding identifies the third (URL-injection-via-stdin reaching storage AND surviving as raw bytes through bm list rendering's display_safe protection).

**Crucial distinction from prior dispositions:**

- Layer 1 R1 F4 (Adversary-supplied URL contents): mitigated by `display_safe` at every render boundary including `bm list`. This protection STILL holds for the rendered URL — `bm list` wraps with `display_safe`.
- Round 1 R2 F1 above (cross-organizational-seam consumer-side rendering): the consumer-side rendering gap names the EXPORT-then-consumer surface. The protection at `bm list` does NOT extend to a consumer outside `bm`.
- THIS finding (R2 F3): the IMPORT surface. The active mitigation covers tags. The URL field is unmitigated at import; the stored bytes reach `bm list` which DOES apply `display_safe` (so the immediate render is safe) BUT also reach `bm export` which does NOT apply display_safe (per the architectural correction), AND the destination operator's downstream consumers per R2 F1.

The URL field bytes therefore form the **chained-vulnerability** with R2 F1: an attacker who supplies a bidi-URL via stdin import gets the URL into the destination store (this finding's surface) AND gets it out the other side via `bm export | jq -r ... | echo` (R2 F1's surface). The chained attack succeeds on a single import payload + a single common-shape jq pipeline + a single `bm export` call.

**Proposed disposition (two paths, SO adjudicates):**

- **Path A — extend active mitigation to URLs (highest-symmetry path):** mirror the tag rejection at line 585 onto URLs. New `ImportError::UrlContainsControlChars(usize, String)` variant + a sibling iteration over `bm.url` per imported record. The spec amendment at [DESIGN.md § `bm import` failure bullet](../../DESIGN.md) extends to name the URL failure mode. The chained-vulnerability with R2 F1 is closed at the import boundary; the bidi-URL never reaches storage. Trade-off: the Layer 1 R1 F4 disposition ("URLs are stored as-given") is no longer uniform across stdin-vs-direct entry — a `bm add https://example.com[U+202E]gpj.foo` still succeeds (direct-entry path), but the same URL via stdin import is rejected. The asymmetry is defensible (different attacker classes per Round 1 R1 F2's framing) but needs spec articulation.
- **Path B — extend the accepted-risk paragraph to name the URL stdin-attacker surface explicitly:** amend [DESIGN.md § Threat model](../../DESIGN.md) to add a paragraph naming URL-injection-via-stdin as accepted-risk under the same framing as Layer 1 R1 F4 (operator-supplied URLs) but with the explicit recognition that the stdin-attacker class is broader than the operator-typing class. Document the chained-vulnerability surface with R2 F1. The active-mitigation asymmetry (tags rejected; URLs accepted) is preserved as a deliberate spec choice; the rationale is **the JSON cross-store backup workflow has URLs that may legitimately contain format chars** (e.g., a user who legitimately bookmarks a Unicode-encoded URL for a Japanese/Arabic page where bidi marks are part of the URL semantic). Tags don't have this legitimate-content-class argument; URLs do.

**Recommended path (Security perspective):** Path B. Path A's active-mitigation has a real false-positive class (legitimate Unicode URLs); Path B names the asymmetry deliberately + closes the audit-trail gap. The chained-vulnerability with R2 F1 then becomes the structurally-coherent disposition (R2 F1's operator-workflow-handle mitigates both surfaces simultaneously). If SO later judges that the cross-organizational-seam attack class warrants stronger mitigation, Path A can be added without conflicting with Path B's accepted-risk audit trail.

**Classification:** Raised to SO. The disposition is a spec-amendment decision (Path A is also a code change requiring spec re-affirmation). The chained-vulnerability with R2 F1 means the two findings should be dispositioned together as a cluster — Red Team's adversarial validation should run the chained reproducer against both surfaces.

### Hallucinated

<a id="r2-f4"></a>**Finding 4 — `bookmark_set_eq` sorted-tag-comparison creates a tag-content-based timing oracle exploitable by an attacker who can supply imports and observe import-completion timing**

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*
**Validator:** sanity-check

A reviewer's first instinct on seeing the sorted-tag-comparison dedup at [`src/lib.rs:624-636`](../../src/lib.rs) might be: the predicate sorts both tag-vecs + compares them; the sort + compare is content-dependent in a way that non-constant-time-comparison primitives are; an attacker who can supply imports + observe their completion time could probe what tags exist in the destination store via differential-timing analysis.

**Specific demonstration of why the concern does not apply:**

1. **The attacker already has direct read-access to what the timing would leak.** The same attacker who can pipe imports + measure their completion times can also pipe `bm export` (no auth boundary on read; the binary runs in the operator's shell with whatever filesystem permissions the operator has) and read the destination store directly. The timing oracle would leak strictly less information than is freely available through `bm export`.
2. **The dedup-loop's O(M × N) cost dominates any tag-content-comparison sub-cost.** Per the [DESIGN.md Performance budget line 298](../../DESIGN.md) accepted-limitation for `bm import` dedup complexity, the outer loop's `Vec::contains` is the dominant cost; the inner tag-sort + compare is O(K log K) where K is tag-count-per-record (typically < 10). The signal-to-noise ratio of the inner comparison's timing variance is overwhelmed by the outer-loop variance + the filesystem-write fsync cost + the kernel-scheduling jitter. The attacker cannot reliably differentiate "tag content matched" from "tag content nearly matched" via wall-clock observation in a single-process CLI-tool deployment.
3. **The attacker model does not match the deployment context.** Timing-oracle attacks are exploitable when (a) the attacker can run many trials, (b) the timing signal is stable across trials, (c) the secret-data interest is high-value. This project's threat model is single-user local tool with confidential-class browsing-history data; the attacker who has shell access to run trials already has direct file-read access (mode 0600 protects against co-tenants who cannot ALSO observe import timings — those vectors are disjoint).

The finding does not represent a control gap because the timing-oracle attack's prerequisites (attacker can run trials + attacker cannot read the file directly) are not co-satisfiable in this project's threat model. The concern is structurally adjacent to a real oracle class (constant-time-comparison discipline in cryptographic protocols) but the specific application context — local CLI tool with mode-0600 confidentiality + no cryptographic comparison semantic — eliminates the prerequisite for the oracle to be useful.

**Classification:** Hallucinated. Validator is `sanity-check` per the Security domain prompt's validator-pair convention — there is no Red Team validation surface for a Hallucinated finding (no fix to test, no exploit to demonstrate). The finding is recorded so a future reviewer who re-discovers the surface sees the prior reasoning chain rather than re-raising the same hallucination.
