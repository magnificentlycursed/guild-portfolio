### Accepted risk

<a id="r4-f1"></a>

**Finding 1 — Unbounded tag-label length per bookmark + unbounded tag-count per bookmark — JSON `Vec<String>` storage amplifies the Layer 1 unbounded-URL DoS to a 2-D amplification surface (Dim 11)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*
**Validator:** security

[`DESIGN.md`](../../DESIGN.md) § Edge case catalog Layer 2 line 120 declares: "Very long tag label (10K+ chars): accepted. No length cap (parallel to URL rule)." The implementation matches — [`src/lib.rs:377-397`](../../src/lib.rs) (`attach_tag`) has no length check on `label`. The Layer 1 R1 F2 / R2 F8 / R3 F10 Accepted-risk on unbounded URL length now extends:

The two-dimensional amplification. Layer 1's DoS surface was a single 1M-character URL → 1M bytes on disk + 1M bytes in memory. Layer 2 adds:

1. **Unbounded label length per `bm tag` invocation.** Same 1M-char primitive applies to `label`.
2. **Unbounded label count per bookmark.** [`src/lib.rs:385-391`](../../src/lib.rs) (`attach_tag`) appends to `bm.tags` (a `Vec<String>`) if not already present. The idempotence check (`!bm.tags.iter().any(|t| t == label)`) is O(n) per call, but the spec-level cap on `bm.tags.len()` is missing. An attacker who can run `bm tag <url> tag_001`, `bm tag <url> tag_002`, … N times grows the bookmark's `tags` to length N. Each subsequent `attach_tag` invocation does O(N) idempotence-check against the existing tags PLUS O(N) `cmp` per `serde_json::to_string_pretty` line at save time.
3. **Cross-product amplification.** Attacker creates M bookmarks via `bm add <url_i>` then tags each with N distinct labels. Storage size is O(M × N × tag_length). For M = 10K bookmarks × N = 10K tags × tag_length = 10K characters → 1 TiB storage payload. Each `bm list` reads the entire file and deserializes — O(M × N × tag_length) memory.

The Layer 1 acceptance (DESIGN.md line 245 "Unbounded URL length ... DoS-via-memory is acknowledged but accepted at Layer 1") was 1-D: one URL × one length. Layer 2 is 2-D and the spec text "10K+ chars: accepted. No length cap (parallel to URL rule)" does NOT explicitly extend the acceptance to the tag-count dimension. The acceptance is implicit but not named.

Adversarial scenario. A hostile script paste — `for i in $(seq 1 1000000); do bm tag https://victim.example "$i"; done` — runs to completion (no rate-limit, no per-bookmark tag-cap), producing a bookmark with 1M tags. Subsequent `bm tag <same-url> <new>` invocations now do O(1M) idempotence checks. `bm list` deserializes 1M+ strings on every invocation. The Layer 1 budget (`< 100 ms wall-clock on a store with ≤ 1000 bookmarks` per DESIGN.md line 224) is now violated by the tag-amplification path even with only 1 bookmark.

Why Accepted risk, not Raised to SO: the Layer 1 trust delegation ("URL validation beyond non-empty — accept any string; the user is responsible" per DESIGN.md line 52) extends naturally to labels. The Red Team's job is to surface that the Layer 2 amplification IS a new attack class even if the per-axis acceptance is the same shape. A multi-user repositioning would warrant per-bookmark tag caps + per-tag length caps; at single-user Layer 2, the operator accepts the risk.

**Classification:** Accepted risk. Risk owner: solution-owner. Cross-reference: Layer 1 R1 F2 / R2 F8 / R3 F10 (unbounded URL length). (Dim 11)

**Finding 2 — `display_safe` sanitizer regression-check against the Layer 2 surface — labels stored as URLs would NOT survive sanitization the same way labels stored as labels would; the asymmetric rendering coverage holds at Layer 2 because tags are NOT rendered (Dim 7)**

**Owner:** red-team
**Status:** validated
**Blocked by:** *(none)*
**Validator:** security

The Layer 1 R3 close (`display_safe` curated Cf-coverage matcher at [`src/lib.rs:521-577`](../../src/lib.rs) — 22 ranges/singletons total) protects every user-derived value that reaches stdout/stderr. The Layer 2 surface adds two new paths where attacker-controlled values flow to terminal output:

1. **`Cmd::Tag` `NoMatch` error message** at [`src/main.rs:277-280`](../../src/main.rs): `eprintln!("Error: no bookmark found with URL {}.", display_safe(url))`. The URL is attacker-controlled (passed verbatim from argv); the `display_safe` wrap fires. **Sanitization holds.**
2. **`Cmd::List` filter empty-match message** at [`src/main.rs:230`](../../src/main.rs): `eprintln!("No bookmarks match the supplied filter.")` — the message is a static string with no user-derived interpolation. **No injection surface.**
3. **`Cmd::List` filtered output** at [`src/main.rs:234`](../../src/main.rs): `println!("{} {}", bm.timestamp().to_rfc3339(), display_safe(bm.url()))`. URL is wrapped. Tag-content NOT printed (per DESIGN.md line 70: "Per-bookmark tags are NOT printed at Layer 2"). **No tag-rendering surface; sanitization N/A for tags at Layer 2.**

Adversarial bypass attempts:

1. **Can a stored tag string with embedded ANSI bytes reach stdout via a Layer 2 path?** No — `bm list` does not print tags; `bm list --tag <label>` prints URL-only lines. The tag itself is matched against the `--tag` flag's argument (string equality at [`src/lib.rs:412`](../../src/lib.rs)) but not rendered. **Bypass fails.**
2. **Can `bm tag <url> <attacker-label>` cause the label to reach stderr or stdout?** No — `bm tag`'s success path is silent (per DESIGN.md line 78), and its error paths print error strings that do not interpolate the label. The label only reaches storage. **Bypass fails.**
3. **Can the `attach_tag` `AttachTagError::EmptyLabel` `Display` impl be exploited?** The impl at [`src/lib.rs:111`](../../src/lib.rs) returns a static string `"tag label cannot be empty"` — no interpolation. **Bypass fails.**
4. **Can the `<url>` interpolation in the `NoMatch` error message be defeated?** The `display_safe(url)` wrap escapes Cc + curated-Cf-set bytes. **Bypass fails against the named set.** The Layer 1 R3 F3 Resolved-via-curated-matcher disposition holds — the full Cf category remains uncovered but Soft Hyphen U+00AD is now in the matcher per the R3 fix; the larger set of unmatched Cf chars per R3 F3's enumeration remains a documented Accepted risk.

Forward-looking concern surfaced — recorded as Finding 3 below: the DESIGN.md line 121 acknowledges "rendered through the same `display_safe` sanitizer as URLs at the rendering boundary (Layer 2 has no tag-rendering path at the user surface — `bm list` does not print tags — but the sanitizer still applies if a future flag prints them)." A future `--show-tags` flag (out of scope for Layer 2 per DESIGN.md line 70) would activate the tag-rendering path. The current `display_safe` matcher would protect terminal-escape injection on tag content, but the **stored tags are NOT sanitized at storage time** — they are stored raw, with the assumption that sanitization happens at render time. A Layer 3 `bm export` that emits the stored JSON verbatim would expose the raw tag content downstream. See Finding 3.

**Resolution:** Layer 2's actual rendering surface is sanitized; the Layer 1 R3 close holds against the new code paths. The forward-looking concern is a separate finding (Finding 3 below).

**Classification:** Resolved (Dim 7)

<a id="r4-f5"></a>

**Finding 5 — `attach_tag` multi-match semantics amplify the duplicate-URL bookmark-cloning primitive — an attacker who can `bm add` the same URL twice can have their tag injected into 2+ bookmarks per invocation; the spec accepts this (Dim 5)**

**Owner:** red-team
**Status:** validated
**Blocked by:** *(none)*
**Validator:** security

[`DESIGN.md`](../../DESIGN.md) lines 86–87 explicitly name the semantic: "**Multi-match semantics.** If two or more bookmarks have the same URL (append-only semantics permits duplicates), `bm tag <url> <label>` tags ALL matches in one atomic save. This is the deliberate semantic — the URL is the user's identifier, and any rendering of 'tag this bookmark' against duplicate URLs is ambiguous; tagging all matches preserves invariants over `bm list --tag <label>`."

[`src/lib.rs:384-392`](../../src/lib.rs) (`attach_tag`):

```rust
let mut matched = 0_usize;
for bm in &mut self.bookmarks {
    if bm.url == url {
        matched += 1;
        if !bm.tags.iter().any(|t| t == label) {
            bm.tags.push(label.to_string());
        }
    }
}
```

The loop tags every matching bookmark. The integration test [`tests/bookmarks.rs:721-757`](../../tests/bookmarks.rs) (`tests_tag_against_duplicate_url_tags_all_matches`) exercises and asserts this.

Adversarial scenario. Attacker A persuades the user to run `bm add https://benign.example` then `bm add https://benign.example` (e.g., via a hostile script that runs the command twice). The store now has two bookmarks with the same URL. Attacker then runs `bm tag https://benign.example phishing` — the tag is applied to BOTH bookmarks in one atomic save. The amplification is 2× per duplicate; for N duplicates per URL, N× amplification.

Is this a real attack class? The amplification only matters if the attacker is amplifying SOMETHING. The label is attacker-controlled in this scenario, but attacker also has full `bm tag` invocation control — they could simply run `bm tag <url> <label>` N times against N distinct bookmarks if they wanted to. The duplicate-URL primitive amplifies one syscall to N effects, but the syscall cost is dominated by load + parse + save which doesn't scale with match count. The amplification is real but not the attacker's bottleneck. The threat-model framing per the Layer 1 R1 close is "single-user single-process scope" — an attacker who can `bm add` arbitrary URLs already has worse primitives.

Bypass attempts:

1. **Can the attacker use `bm tag` to silently tag a URL the user is not aware of?** Yes — but the URL must already be in the store (the `NoMatch` error fires otherwise per AC 6). The attacker can only tag what's already there.
2. **Does the multi-match amplify a confidentiality breach?** No — tagging is a write operation, not a read. The attacker learns nothing from tagging.
3. **Can the multi-match be exploited as a DoS amplifier?** With Finding 1's unbounded-tag-count primitive, the multi-match × N-duplicates does multiply the per-bookmark `bm.tags.iter().any(...)` cost — but the dominant cost is still `save()`-side serialization, which is O(total-bookmarks × total-tags-per-bookmark). The multi-match contributes a constant factor, not a scaling exponent. **Bypass fails as a DoS amplifier.**

**Resolution:** the multi-match semantic is spec'd, tested, and does not enable a new attack class beyond what the per-invocation primitive already grants. The Red Team contribution is to verify the threat-model framing holds; no new finding.

**Classification:** Resolved (Dim 5)

### Raised to SO

<a id="r4-f3"></a>

**Finding 3 — Stored tag content is NOT sanitized at storage time, only at render time — Layer 3 `bm export` or any future `--show-tags` flag would surface attacker-controlled bytes in the stored tags without `display_safe` coverage (Dim 7)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*
**Validator:** security

[`src/lib.rs:389`](../../src/lib.rs) (`attach_tag`): `bm.tags.push(label.to_string())` — the label is stored verbatim, no sanitization. [`src/main.rs:239-282`](../../src/main.rs) (`run_tag`) does no pre-storage sanitization either; the label flows from `argv` through `attach_tag` to disk verbatim.

[`DESIGN.md`](../../DESIGN.md) line 121 acknowledges the shape: "Tag label containing newlines or control characters: stored as-is; rendered through the same `display_safe` sanitizer as URLs at the rendering boundary (Layer 2 has no tag-rendering path at the user surface — `bm list` does not print tags — but the sanitizer still applies if a future flag prints them)."

The spec's "store raw, sanitize at render" choice is **architecturally sound** for the Layer 1 + Layer 2 surface (`display_safe` is the trust boundary the implementation enforces at every render site). The hazard is at the Layer 3 readiness layer:

1. **`bm export` (Layer 3 per DESIGN.md line 44)** — emits all bookmarks as JSON to stdout. The export is JSON-shaped; if the consumer pipes `bm export > out.json` and then `cat out.json` to the terminal, the unsanitized tag bytes hit the terminal raw. The export-then-cat workflow is the natural consumer-side composition.
2. **A future `bm list --show-tags` flag** — would render tag content. The current `display_safe` matcher would apply (at the render site, per DESIGN.md line 121). But the addition of `--show-tags` is a one-line CLI change ([`src/main.rs`](../../src/main.rs) Cmd::List would gain a flag; the per-bookmark print would interpolate `display_safe(&bm.tags().join(","))` or similar). A future maintainer adding `--show-tags` who FORGETS the `display_safe` wrap re-introduces the Layer 1 R1 F4 terminal-escape primitive against an attacker-controlled value class (tags) the spec has named as accepted.

Architectural question for SO: should attacker-controlled values that are accepted as raw input (URLs, tag labels) be sanitized at the **library boundary** (`add` / `attach_tag` reject or escape Cc/Cf bytes) rather than at the render boundary (every print site uses `display_safe`)? Pro (sanitize at library boundary): defense-in-depth; future renderers cannot forget the wrap; the storage format is then known-safe-for-rendering. Con: changes the spec's "accept any string; user is responsible" non-goal (DESIGN.md line 52); breaks round-trip fidelity (the user may legitimately want to capture a URL with a real Unicode character that the sanitizer would escape); inconsistent with Layer 1 R1 F4 / Layer 1 R3 close which deliberately chose render-time sanitization.

The Red Team recommendation: keep render-time sanitization, but DOCUMENT the Layer 3 readiness concern in DESIGN.md so a future `bm export` implementation includes the sanitization at the export boundary (which IS a render-equivalent surface).

**Proposed DESIGN.md amendment:** Add to DESIGN.md § Threat model § In-scope adversaries, after the "Adversary-supplied URL contents" entry: "Adversary-supplied tag-label contents — stored verbatim per the Layer 2 acceptance; sanitized at every render site via `display_safe`. A future Layer 3 `bm export` MUST treat its stdout-emission path as a render site and apply `display_safe` to every emitted user-derived value (URL + label) before printing — the stored JSON is NOT sanitized."

Adversarial scenarios this finding closes (forward-only):

1. **Tag-based bidi attack at Layer 3 export.** Attacker tags a bookmark with `\u{202e}attacker.example.com\u{202c}` then waits for the user to `bm export | tee backup.json` and view the file with `cat backup.json` — the bidi override executes against the terminal even though the JSON is correct.
2. **Tag-based OSC 8 hyperlink masquerade at a hypothetical `--show-tags` flag.** Same shape as Layer 1 R1 F4 against the URL field; trivially preventable if `display_safe` is applied at render.

**Classification:** Raised to SO (Dim 7)

<a id="r4-f6"></a>

**Finding 6 — Read-side mutation of stored tags by a write-access attacker creates a "tag-injection" UX confusion: `bm list --tag phishing` surfaces attacker-marked URLs as if user-curated (Dim 9)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*
**Validator:** security

The Layer 1 threat model accepts that an attacker with write access to the JSON file (e.g., out-of-scope per single-user assumption, but in-scope if `$BOOKMARK_CLI_DB` is on a shared `/tmp/` or if file mode 0o600 is bypassed) can inject arbitrary bookmarks. Layer 2 adds a NEW attacker primitive: arbitrary tag injection on existing bookmarks.

Attack scenario. Attacker has write access to the storage file. The user has bookmarked `https://benign.example`. Attacker edits the JSON to add `"tags": ["important", "verified", "trusted"]` to the bookmark — the user's own bookmark now claims to be tagged "verified" by the user themselves. When the user later runs `bm list --tag verified`, the URL surfaces as if it were a user-curated trusted source. The user's own audit trail (the tags they remember adding) is no longer authoritative.

This is a UX-confusion primitive, not a write-control primitive. The attacker cannot make `bm` execute their code; they cannot exfiltrate data; they cannot escalate privilege. But they can MISLEAD the user about which bookmarks the user themselves marked as trusted. For a user using tags as a personal-trust signal ("I tagged this `verified` after auditing it"), the attacker can violate that signal.

Cross-reference: Layer 1 R1 F5 (world-readable storage) / R2 F2 (mode 0600 fix). Layer 1's R1 F5 raised the world-readable file mode; R2 F2 closed it with `0o600`. The current threat model (DESIGN.md line 238) names mode 0600 as the defense against read-side attacker; the assumption is that write access also requires the user's UID. Layer 2's tag-injection primitive does not change the write-access prerequisite — but it adds value to the attacker who CAN gain write access (e.g., via a co-resident UID-share scenario on a poorly-isolated multi-user host).

Bypass attempts (verify the attack actually works against current implementation):

1. **Attacker edits the JSON file directly while it's mode 0600.** They need the user's UID (or root). On a single-user laptop, no exposure. On a shared dev VM where the user uses sudo for unrelated tasks, the attacker who gains root briefly gets the writeprimitive. **Works in the named scenario.**
2. **Attacker uses the symlink-follow primitive (Layer 1 R3 F2 accepted-risk TOCTOU on load).** Same precondition as L1 R3 F2 — concurrent FS-write to the parent. If the attacker wins the race, they can substitute the file. **Works in the named scenario; the tag-injection becomes a payload on top of the existing TOCTOU.**
3. **Attacker compromises the user's shell (env-var injection per Layer 1 R1 F1 accepted-risk).** Attacker sets `$BOOKMARK_CLI_DB=/<attacker-controlled>/bookmarks.json` and pre-populates the file with `[{"url":"https://benign.example","timestamp":"...","tags":["verified"]}]`. The user's subsequent `bm list --tag verified` surfaces the attacker's bookmark as if it were tagged by the user. **Works in the named scenario.**

Why this is a NEW finding, not a Layer 1 carryforward: Layer 1's R1 F1 / R2 F7 / R3 F9 named the env-var ambient-authority as accepted-risk-with-trust-delegation. Layer 2 adds a new payload class to the same attack — the attacker can inject not just bookmarks but also tags-on-bookmarks. The tag-injection-as-misleading-trust-signal is the specifically-Layer-2 attack class.

**Proposed DESIGN.md amendment:** add to § Threat model § In-scope adversaries, after the env-var entry: "Adversary-controlled storage file contents (via env-var-induced path-redirection or write-share scenarios) — at Layer 2 the storage extension is `tags: Vec<String>`, which makes tag injection a NEW primitive on top of the Layer 1 bookmark-injection. An attacker who can write the JSON can fabricate tags on user-trusted bookmarks, violating the user's tag-as-personal-trust-signal. **Mitigation:** unchanged from Layer 1 — mode 0o600 + symlink-follow rejection on load and save protect the in-scope adversary classes; the residual chained-vulnerability for the env-var-injection scenarios is accepted (per Layer 1 R3 F9). User-facing **caveat**: tags should be treated as 'what the file says,' not as 'what the user remembers tagging' — the storage file is the only authority."

**Classification:** Raised to SO (Dim 9)

### Accepted risk

<a id="r4-f4"></a>

**Finding 4 — Parent-directory `fsync(2)` between `rename(2)` and the post-rename open() is a new I/O syscall on the save path, but the implementation does NOT widen the symlink-follow attack surface (Dim 6)**

**Owner:** red-team
**Status:** validated
**Blocked by:** *(none)*
**Validator:** security

[`src/lib.rs:289-312`](../../src/lib.rs) — Layer 2 added a parent-directory `fsync` after the atomic-rename:

```rust
#[cfg(unix)]
{
    if let Some(parent) = path.parent() {
        let parent = if parent.as_os_str().is_empty() {
            Path::new(".")
        } else {
            parent
        };
        fsync_directory(parent).with_context(|| {
            format!(
                "fsyncing parent directory {} for durable rename of {}",
                parent.display(),
                path.display()
            )
        })?;
    }
}
```

[`src/lib.rs:441-445`](../../src/lib.rs) — `fsync_directory` opens the parent directory via `std::fs::File::open(path)` and calls `sync_all`. The `File::open(directory_path)` call does NOT use `O_NOFOLLOW` — it follows symlinks at the final component.

Adversarial bypass attempts:

1. **Can an attacker substitute a symlink at the parent directory between `rename(2)` and `fsync_directory`?** The Layer 1 R2 F3 / R3 F7 analysis established that `rename(2)` is atomic and does NOT follow destination symlinks. The save-side TOCTOU window between `symlink_metadata(path)` and the rest of the save is closed by `rename(2)` semantics. The fsync_directory adds a NEW open on the **parent** of `path`. If the parent is a symlink at open time, `File::open` follows it; the `sync_all` syncs the symlink's target directory, not the parent the rename actually wrote to. **Marginal hazard:** the durability-guarantee crosses to the wrong inode if the parent is a symlink. **Bypass partially succeeds — but only for the durability guarantee, not for write-redirection.**
2. **Does this widen the symlink-follow attack surface?** Negligibly. The parent directory being a symlink was already a path the symlink-rejection-on-`path` discipline did NOT cover — Layer 1 R2 F3 Adversarial probe step 3 explicitly named "Symlinked parent component" as consistent with the F1 accepted env-var trust boundary (the user owns the resolved path including its parent chain). The new fsync inherits that acceptance, but it does add an additional syscall against the user-trusted parent which could be exercised in a same-host attack scenario.
3. **What about a TOCTOU race between `rename(2)` and `File::open(parent)`?** Same race-window class as Layer 1 R3 F2 (load-side `symlink_metadata` → `read_to_string` TOCTOU, Accepted risk). The mitigation is the same: single-process foreclosure of concurrent FS-write at the parent. The save-side path is even narrower than the load-side path because the post-rename window is microseconds of one extra syscall.
4. **Is the durability guarantee voided if `fsync_directory` fails?** The implementation propagates the error via `?` ([`src/lib.rs:304-310`](../../src/lib.rs)) and the save returns Err. The on-disk state at this point is "the rename has landed; the durability fsync did not." Per the doc comment at [`src/lib.rs:225-236`](../../src/lib.rs): "(e) leaves the renamed-but-unsynced file in place (it may or may not survive a power loss; the on-disk inode is what `ls(1)` shows, and a successful retry of `save` will sync it)." **The error semantics are documented; the residual durability hazard is named.**

Architectural note: the fsync_directory should probably use `O_NOFOLLOW`-equivalent semantics. Per the Layer 1 R3 F2 disposition on the analogous load-side TOCTOU (Accepted risk; tight fix is `OpenOptions::custom_flags(O_NOFOLLOW)` deferred pending `libc` dep), the same fix would apply here. The cost-asymmetry is the same: ELOOP rejection on a symlinked parent vs. a microsecond TOCTOU window an attacker must win during a one-syscall hop.

Why Accepted risk, not Open: the implementation matches the Layer 1 R3 F2 accepted disposition. The fsync_directory is structurally consistent with the project's existing TOCTOU-acceptance baseline. The fix is the same operator-sign-off-gated `libc` dependency addition as Layer 1 R3 F2's fix. Same trigger to close.

**Classification:** Accepted risk — inherits the Layer 1 R3 F2 disposition. Cross-reference: [Red Team Review 1 Round 3 Finding 2](2026-05-20-red-team.md#r3-f2) (load-side TOCTOU Accepted risk). The Layer 2 fsync_directory does not widen the trust-boundary but it does add a new syscall that benefits from the same `libc::O_NOFOLLOW` fix when the operator chooses to add the `libc` dep. (Dim 6)

### Hallucinated

**Finding 7 — Tag-label timing oracle on the `attach_tag` URL exact-match loop reveals which URLs are in the store (Dim 8)**

The adversarial enumeration suggests that `attach_tag`'s URL-exact-match loop ([`src/lib.rs:385-392`](../../src/lib.rs)) could leak via timing — a `bm tag <known-url> x` returns NoMatch faster (one comparison per bookmark, fail-fast on no match) than `bm tag <unknown-url-with-many-chars> x` (full string comparison per bookmark). An attacker observing the timing could enumerate URLs in the store without read access.

Verified absent. The threat model (DESIGN.md line 238) names the in-scope adversary as a co-tenant on a shared Unix host with FS-read access OR a hostile script the user pastes. **Neither of these adversaries needs a timing oracle** — a co-tenant with FS-read access reads the file directly (no oracle needed); a hostile script the user pastes already executes in the user's shell context (no enumeration needed; can `cat $BOOKMARK_CLI_DB` directly if mode 0o600 permits).

The only adversary class that would NEED a timing oracle is a **remote attacker** observing process scheduling or syscall timing — but `bm` makes no network calls; there is no remote attacker in the threat model. A different adversary class (process-side-channel attacker on the same host with no FS-read) would in principle benefit from the timing oracle, but: (a) such an adversary is not in DESIGN.md's threat model; (b) `bm`'s `attach_tag` operation is dominated by file I/O (load + save), which dwarfs the per-comparison timing variance.

The defect class does not apply at the project's actual threat model. The supplement-enumerated "differential timing" attack from the Red Team domain prompt (Dim 8) is appropriate for authentication endpoints or rate-limited APIs; it is not appropriate for a local-only CLI tool.

**Classification:** Hallucinated. The dimension is enumerated for audit-trail completeness; the threat model declares single-user local tool with no network surface, and the in-scope adversaries do not need a timing oracle.

**Finding 8 — Forward-only migration of Layer-1-format files to Layer-2-format creates an attacker-controlled state — the first Layer-2 write against an attacker-pre-staged file is the attacker's vector (Dim 5)**

The adversarial enumeration suggests that the [`DESIGN.md`](../../DESIGN.md) line 114 forward-only migration ("Tag against a Layer-1-format file (no `tags` field on existing bookmarks): the missing field deserializes to an empty `Vec<String>`; `bm tag` appends; on save the file is rewritten with the field present for every bookmark") creates an attacker-controlled state if the attacker can pre-stage a Layer-1-format file.

Verified absent. The pre-stage-the-file attacker class is the env-var ambient-authority + symlink-redirection chain already named in Layer 1 R1 F1 / R3 F9. The migration shape adds NO new attacker primitive — the attacker can already pre-stage Layer-1-format files OR Layer-2-format files OR any-format files; the post-write state is determined by the implementation's serialization (always Layer 2 format on save), not by the pre-write state. There is no attacker advantage to pre-staging Layer-1-format specifically over pre-staging Layer-2-format.

The "migration is an attack surface" hypothesis fails the specificity test: what does the migration enable that arbitrary pre-write doesn't already enable? Nothing. The migration is a property of the read-path (deserializer tolerates missing field) + write-path (serializer always emits field); both behaviors are spec-compliant.

One possible adjacent concern that IS NOT this finding: a Layer-1 binary reading a Layer-2 file — see SA R2 F5 (downgrade-corruption hazard). That is a real concern but it is the SA-domain finding, not the Red Team's domain.

**Classification:** Hallucinated. The migration shape does not create a new attacker primitive beyond what the env-var + symlink-redirection chain already grants. Recorded for audit-trail completeness.
