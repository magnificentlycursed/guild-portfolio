<a id="r1-f1"></a>**Finding 1 — NUL-byte placeholders in user-facing manual test step headings (Dim 3)**

**Owner:** ux
**Status:** raised
**Blocked by:** *(none)*

The primary UX evidence file — [`manual-tests/layer-1.md`](../../manual-tests/layer-1.md) — contains literal NUL bytes (`0x00`) wrapping placeholder tokens in three step headings:

- Line 34: `## Step 1 — Happy path: \x00PROT_30\x00 captures a bookmark`
- Line 93: `## Step 3 — \x00PROT_40\x00 orders newest-first`
- Line 120: `## Step 4 — Empty-state: \x00PROT_46\x00 against an absent store`

(Byte-level confirmed via Python `repr()` of each line.) The `\x00`-wrapped tokens look like incompletely-filled section-title templates — possibly artifacts of a redaction or sanitization sweep that replaced the original titles with placeholder sigils but left them in place rather than completing them.

**Behavior consequence:** A user following the per-layer manual test plan sees the step headings render as either invisible NUL bytes (most markdown viewers + `cat` swallow the byte silently and concatenate the surrounding text into nonsense like `Happy path: PROT_30 captures a bookmark`) or as `^@` / `<00>` glyphs (less, vim, IDE markdown previews). The headings convey no real meaning either way — the placeholder tokens have not been replaced with actual descriptive heading text. The CLI supplement Dim 3 (Output scannability) extends to the manual test rendering because the manual test IS the user-facing UX evidence (per primer 3 § Manual testing-second-adversarial-surface framing in [G-132](../../../../vsdd-suite/suite-development/FINDINGS-INDEX.md#g-132)). Unrenderable step headings degrade scannability to zero for the affected steps.

Adjacent: shells, pagers, and tools that don't NUL-tolerate (some grep configurations, awk, sort) may silently truncate or behave unexpectedly on lines containing NUL — a user who pipes the manual-test file through any such tool will get inconsistent output without an obvious error.

**Classification:** Open — fix is to replace each `\x00PROT_NN\x00` token with a real descriptive heading fragment (e.g., `add` for Step 1; `list` for Step 3; `list` for Step 4) and re-save the file as clean UTF-8. **Validator pair:** [quality-engineer](../../../../vsdd-suite/domains/role/QUALITY-ENGINEER-REVIEW.md) per the [UX domain prompt](../../../../vsdd-suite/domains/role/UX-REVIEW.md) Validator-pair paragraph (behavioral UX defect — manual-test rendering is verifiable by reading the file post-fix; QE can confirm no remaining NUL bytes by file scan).

<a id="r1-f3"></a>**Finding 3 — Manual-test "expected on-disk JSON" example contradicts the actual storage format (Dim 6)**

**Owner:** ux
**Status:** raised
**Blocked by:** *(none)*

[`manual-tests/layer-1.md`](../../manual-tests/layer-1.md):59–63 documents the expected `cat "$BOOKMARK_CLI_DB"` output for Step 1 as:

```json
[{"url":"https://example.com","timestamp":"2026-05-20T22:15:42.371Z"}]
```

— a bare JSON array of bookmark objects. The implementation in [`src/lib.rs`](../../src/lib.rs):60–72 (`BookmarkStore::save`) calls `serde_json::to_string_pretty(self)` against `BookmarkStore`, which is `struct BookmarkStore { pub bookmarks: Vec<Bookmark> }` ([`src/lib.rs`](../../src/lib.rs):33–37). The serialized output is therefore a JSON **object** with a `bookmarks` key wrapping the array — confirmed by [`DESIGN.md`](../../DESIGN.md):103–110 § Storage format, which declares the canonical shape as:

```json
{
  "bookmarks": [
    {"url": "https://example.com", "timestamp": "2026-05-17T03:01:00Z"},
    ...
  ]
}
```

— and confirmed against the integration test [`tests/bookmarks.rs`](../../tests/bookmarks.rs):35–37 which parses the on-disk file as `parsed["bookmarks"].as_array()` (key-indexed against the wrapping object). The manual test's "expected" example is therefore wrong on every Layer-1 invocation: a user following Step 1 runs `cat "$BOOKMARK_CLI_DB"` and sees `{"bookmarks":[{"url":"https://example.com","timestamp":"..."}]}` (object-wrapped, pretty-printed across multiple lines via `to_string_pretty`), then compares against the documented expectation `[{"url":...,"timestamp":...}]` and concludes either (a) the manual test is wrong (the actual UX defect), or (b) the binary is broken (a false-positive failure that wastes user time).

**Behavior consequence:** The manual test is supposed to be the second adversarial surface (per [G-132](../../../../vsdd-suite/suite-development/FINDINGS-INDEX.md#g-132)) — a user-facing trip wire that catches divergence between spec/test/impl that automated tests miss. Here the trip wire is itself broken: it triggers on every clean run. A user encountering this will lose trust in the manual-test plan as a whole; the discipline of "literal expected-output blocks" is undermined when those blocks don't match reality.

**Classification:** Open — fix is to replace the bare-array expected output with the object-wrapped shape matching [`DESIGN.md`](../../DESIGN.md) § Storage format, and to make the literal example use the pretty-printed multi-line layout that `to_string_pretty` actually produces (since the manual test purports to show `cat`-output, the pretty-printed multi-line form is what the user will actually see). **Validator pair:** [quality-engineer](../../../../vsdd-suite/domains/role/QUALITY-ENGINEER-REVIEW.md) — QE owns expected-vs-observed discipline and can verify the corrected example against a fresh `cargo run -- add ...` + `cat` invocation.

<a id="r1-f4"></a>**Finding 4 — `bm --help` lacks a usage example (Dim 1)**

**Owner:** ux
**Status:** raised
**Blocked by:** *(none)*

The clap derive declaration at [`src/main.rs`](../../src/main.rs):14–16 provides:

```rust
#[command(name = "bm", version, about = "Capture URLs at the terminal; recall them later.")]
```

— `name`, `version`, and a one-line `about`. Clap's default `--help` rendering with only these attributes produces a help screen with the about line, usage summary, and the subcommand list, but **no usage example**. The [CLI supplement § UX](../../../../vsdd-suite/supplements/cli.md) Dim 1 explicitly asks: *"Does the top-level help include a usage example?"* The bookmark-cli README ([`README.md`](../../README.md):27–36) includes runnable examples (`bm add https://example.com`; `bm list`), but a user who installs the binary and runs `bm --help` (the discoverable default) does not see them.

The asymmetry matters because `bm --help` is the in-binary discovery surface — the artifact a user reaches for first when they've installed the tool but haven't read the README. A user who copies the example from `bm add --help` will see only `Usage: bm add <URL>` plus the per-argument `/// The URL to capture. Must be non-empty.` doc-comment ([`src/main.rs`](../../src/main.rs):26) — informative but no copy-pasteable example.

**Behavior consequence:** The CLI's discoverability surface skews toward the README (out-of-binary) and away from `--help` (in-binary). For a single-user tool whose installation step is `cargo install --path .` (READMEs not typically visible after install), users will rely on `--help`. The missing example forces a user to either (a) guess the URL syntax (likely OK — it's `https://example.com`-shaped), (b) read the per-argument doc-comment and infer the call shape, or (c) leave the terminal to find the README. None is catastrophic; all are friction the help text could remove.

**Classification:** Open — fix is to add a clap `long_about` or `after_help` attribute to the top-level `Cli` struct that includes a 2–3-line usage block (`bm add <url>` / `bm list` / `bm --help`). The CLI supplement Dim 1 is the operative floor; the README already supplies the content. **Validator pair:** [software-engineer](../../../../vsdd-suite/domains/role/SOFTWARE-ENGINEER-REVIEW.md) per the [UX domain prompt](../../../../vsdd-suite/domains/role/UX-REVIEW.md) Validator-pair paragraph — UI / interaction code change (clap attribute on the `Cli` struct).

<a id="r1-f5"></a>**Finding 5 — Storage error messages omit remediation hints (Dim 8)**

**Owner:** ux
**Status:** raised
**Blocked by:** *(none)*

[CLI supplement § UX](../../../../vsdd-suite/supplements/cli.md) Dim 8 names three required components for an error message: *"what failed, why it failed (if knowable), and what the user should do next."* The bookmark-cli storage errors at [`src/main.rs`](../../src/main.rs):50–52 and 56–58 emit:

```rust
eprintln!("Error: {e:#}");
return ExitCode::from(2);
```

— where `{e:#}` renders the anyhow context chain (e.g., `Error: parsing bookmark store at /Users/.../bookmarks.json: expected value at line 1 column 1`). This satisfies the *what* and *why* components: the user sees that parsing failed at a specific file with a serde-level reason. The *what to do next* component is absent — the user is told their store is corrupt but not told whether to (a) edit the file to fix the JSON, (b) delete it to start fresh, (c) restore from a backup, or (d) file a bug. Same gap applies to read-failure cases (e.g., `Error: reading bookmark store at /path: Permission denied (os error 13)` — no hint that `chmod` or `sudo` might help) and write-failure cases.

Adjacent: the empty-URL error at [`src/main.rs`](../../src/main.rs):45 (`Error: URL cannot be empty.`) is exit-1 user-error territory and is short by design — but it also misses the next-step hint. A "Usage: bm add <url>" follow-up line (or `Try 'bm add --help'`) would close the loop. The DESIGN.md error contract ([`DESIGN.md`](../../DESIGN.md):54–69) requires only `Error: URL cannot be empty.\n` for the empty-URL case — adding a remediation hint would change the literal stderr the integration test asserts ([`tests/bookmarks.rs`](../../tests/bookmarks.rs):59 `stderr("Error: URL cannot be empty.\n")`), and the spec's exit-1 stderr line is therefore SO-controlled. For the storage-error case (exit 2), [`DESIGN.md`](../../DESIGN.md):61 specifies `stderr "Error: <descriptive message>" followed by newline` — the descriptive message is not literal, so a remediation suffix can be added without spec amendment.

**Behavior consequence:** Storage errors are the highest-recovery-friction failure mode for this tool — the user has lost data or has a corrupt file, and a wrong recovery step (e.g., deleting the file when it could have been edited) costs them everything saved so far. A remediation hint is the highest-leverage user-experience improvement in the error surface.

**Classification:** Open — fix is to add a remediation suffix to the storage-error formatting in [`src/main.rs`](../../src/main.rs):50–58 and 64–67, e.g., `eprintln!("Error: {e:#}\n  hint: edit or remove the store file to recover");` (exact wording is a UX choice; the floor is that *some* next-step is named). The empty-URL case is excluded from scope here (spec-pinned). **Validator pair:** [software-engineer](../../../../vsdd-suite/domains/role/SOFTWARE-ENGINEER-REVIEW.md) — UI / interaction code change (error-formatting code in `main.rs`).

<a id="r1-f6"></a>**Finding 6 — Manual test Step 5 uses a `cd` path that fails from the post-Step-0 working directory (Dim 4)**

**Owner:** ux
**Status:** raised
**Blocked by:** *(none)*

[`manual-tests/layer-1.md`](../../manual-tests/layer-1.md):13 (Step 0) instructs the user to `cd vsdd-suite-reference-examples/bookmark-cli-manual` — placing them at the project root. The session's cwd is unchanged through Steps 1–4 (no `cd` in any of those steps; `cargo`/`bm`/`mktemp` invocations don't change the shell's cwd). [`manual-tests/layer-1.md`](../../manual-tests/layer-1.md):166 (Step 5) then issues:

```sh
cd vsdd-suite-reference-examples/bookmark-cli-manual
```

— but the user is **already in** `vsdd-suite-reference-examples/bookmark-cli-manual/`. The shell will attempt `cd vsdd-suite-reference-examples/bookmark-cli-manual/vsdd-suite-reference-examples/bookmark-cli-manual` (a non-existent path) and fail with `cd: no such file or directory`. The subsequent `cargo install --path .` then runs from the wrong directory (whichever directory the failed `cd` left the shell in — which is the same `bookmark-cli-manual/`, so the install will actually succeed, masking the divergence). The manual-test author appears to have copy-pasted the Step-0 `cd` line without recognizing the user is no longer at the parent path.

**Behavior consequence:** A user running the manual-test plan literally will see `cd: no such file or directory` printed at Step 5 — an unexpected error in a step the spec claims should produce no output. The user is then forced to decide whether the manual test is wrong or whether `cd` is misbehaving. The literal-expected-output discipline ([`manual-tests/layer-1.md`](../../manual-tests/layer-1.md) preamble) is broken — the spec promises this step has no unexpected output, but the literal commands as written generate exactly one (the failed `cd`). The downstream `cargo install` then succeeds by accident, which is the worst kind of failure: a manual test that "passes" through silent state mismatch.

**Classification:** Open — fix is to remove line 166 (the user is already in the right directory) OR replace it with a relative-up + back path that survives whatever cwd Step 4 left the user in. The simplest fix is deletion. **Validator pair:** [quality-engineer](../../../../vsdd-suite/domains/role/QUALITY-ENGINEER-REVIEW.md) — QE owns runnable-manual-test discipline (the per-step expected-vs-observed contract) and can validate the fix by following Steps 0–5 verbatim.

<a id="r1-f7"></a>**Finding 7 — Manual test Step 5 expects `which bm` to output literal "bm not found" — no real shell `which` produces that string (Dim 8)**

**Owner:** ux
**Status:** raised
**Blocked by:** *(none)*

[`manual-tests/layer-1.md`](../../manual-tests/layer-1.md):174–180 documents:

> Expected output for `which bm 2>&1` after uninstall (literal — path may differ slightly by shell):
>
> ```
> bm not found
> ```

— but no major shell's `which` produces the literal string `bm not found`:

- macOS BSD `which` (default `/usr/bin/which`): prints nothing on absent binary, exits 1.
- GNU `which` (default on most Linux): prints `which: no bm in (PATH-list)` or nothing depending on the `--show-tilde` and `--skip-alias` defaults.
- zsh / bash builtin `which` (equivalent to `whence`): prints `bm not found` only in zsh's builtin when the shell is launched without `emulate ksh`; bash builtin prefers `type` semantics and prints `bash: type: bm: not found` or `bm: command not found` via `command -v` paths.

The expected literal `bm not found` is closest to the zsh builtin output, but the manual-test plan does not declare zsh as a prerequisite. The README ([`README.md`](../../README.md):14) declares "macOS or Linux" without specifying the shell. A user on macOS with the default `/bin/bash` or `/bin/zsh` will see a different literal — either silent output (BSD `which`) or `bm not found` (zsh builtin) — and the literal-expected-output discipline breaks again.

**Behavior consequence:** Same shape as Finding 6 — a user following the literal expected-output sees a divergence that may not indicate a real defect, lowering trust in the manual-test plan as the second adversarial surface ([G-132](../../../../vsdd-suite/suite-development/FINDINGS-INDEX.md#g-132)). The CLI supplement Dim 8 ("error messages include what failed, why it failed, what to do next") doesn't directly govern third-party tools like `which`, but the manual-test author has imported `which`'s output into the literal-expected-output contract — at that point its fidelity is the manual test's responsibility.

**Classification:** Open — fix is to either (a) replace the literal expectation with a behavior assertion that survives all shell variants (`which bm` exits non-zero; stdout/stderr content is shell-dependent and not asserted) OR (b) declare a specific shell (`zsh`) as the manual-test prerequisite and use the corresponding literal. Option (a) is more portable; option (b) is more verifiable. **Validator pair:** [quality-engineer](../../../../vsdd-suite/domains/role/QUALITY-ENGINEER-REVIEW.md) — runnable-manual-test fidelity is QE territory.

<a id="r1-f8"></a>**Finding 8 — Error label uses `Error:` (Dim 8)**

The bookmark-cli error formatting at [`src/main.rs`](../../src/main.rs):45, 51, 57, 66 uses `Error:` (capital E) as the severity label, where the Rust ecosystem (cargo, rustc, clap, anyhow's own examples) uses lowercase `error:`. The capitalized form is not wrong per any portable CLI convention — many tools (curl, ssh, ssh-keygen) use mixed-case labels — but Rust users specifically may notice the mismatch and read it as non-idiomatic.

**Classification:** Dismissed — [`DESIGN.md`](../../DESIGN.md):60 explicitly pins the empty-URL stderr to `Error: URL cannot be empty.` (capital E), and the storage-error format follows the same pattern for spec-consistency. Changing the casing requires a spec amendment + an integration-test update + cascading manual-test literal-output updates. The cost is real; the user-visible benefit is small (Rust-ecosystem alignment, not a functional improvement). At Layer 1 capstone-but-reference-implementation intent, the spec-pin is binding; a Raised-to-SO classification would be defensible but the SO would almost certainly Backlog or Dismiss given the same cost/benefit calculus. Documenting the dismissal here so future UX reviewers don't re-raise it.

<a id="r1-f9"></a>**Finding 9 — `bm list` output line format breaks scannability on URLs containing spaces or newlines (Dim 3)**

The list-rendering at [`src/main.rs`](../../src/main.rs):75 uses `println!("{} {}", bm.timestamp.to_rfc3339(), bm.url)` — a single-space separator between timestamp and URL, no quoting or escaping. A URL containing spaces (rare but possible — `https://example.com/path with spaces` if pre-decoded; or whitespace-only URLs per the spec edge case) would produce ambiguous output: `awk '{print $2}'` would print only `https://example.com/path` and discard the rest. A URL containing literal newlines would render across multiple lines, breaking the "one bookmark per line" invariant ([CLI supplement § UX](../../../../vsdd-suite/supplements/cli.md) Dim 3).

**Classification:** Dismissed — [`DESIGN.md`](../../DESIGN.md):80 explicitly accepts URLs containing newlines as a deliberate edge case: *"URL containing newlines: accepted. May visually break the `bm list` output, which is acceptable for this scope."* [`DESIGN.md`](../../DESIGN.md):74 similarly defers whitespace validation to the user. The spec has made an explicit acceptance decision; raising this as a UX defect would re-litigate a closed spec choice. The dismissal is documented so the rationale persists for future rounds; the consequence (`awk`/`grep` fragility on adversarial URLs) is the spec's burden, not an impl defect.

<a id="r3-f7"></a>**Finding 7 — `emit_storage_error` load-hint message is wrong for the most common load-error case (corrupt JSON) — fixed inline (Dim 2, Dim 8)**

**Owner:** ux
**Status:** validated
**Blocked by:** *(none)*

The R2 F5 fix landed `emit_storage_error` at [`src/main.rs:81-94`](../../src/main.rs); for the `load` branch the helper emits:

```
Hint: check that the storage file at <path> exists, is a regular file (not a symlink), and is readable.
```

The implementation's `load` error sites in [`src/lib.rs::BookmarkStore::load`](../../src/lib.rs) (lines 86-115) can fail for three distinct reasons:

1. **Symlink rejection** at lines 97-104 — error message names the symlink-hardening discipline. The Hint's "is a regular file (not a symlink)" component matches this case.
2. **Read failure** (permission denied, I/O error) at line 108-109 — error wraps `read_to_string`'s underlying error with `"reading bookmark store at <path>"`. The Hint's "exists ... and is readable" components match this case.
3. **Parse failure** (invalid JSON) at line 113-114 — error wraps `serde_json::from_str`'s parse error with `"parsing bookmark store at <path>"`. **The Hint's components — "exists, is a regular file, is readable" — are all true of a parse-failing file.** The file exists, is a regular file, is readable; the JSON content is malformed. The Hint points the user at every check that is NOT the problem.

For the parse-failure case (which is the most common load-error case after first successful use — the file gets corrupted by a manual edit, a partial write from a crash, or a downstream tool that mangles JSON), the Hint actively misleads the user away from the real diagnostic action (edit or remove the file). A user troubleshooting a corrupt-JSON error reads the Hint, verifies the file exists / is regular / is readable, finds all three true, and concludes the Hint is wrong without realizing the file's *content* is the problem.

CLI supplement **Dim 8** names three required components for an error message: *"what failed, why it failed (if knowable), and what the user should do next."* The R2 fix added the "what to do next" component but mispoints it for the parse-failure subcase. The error message itself ("Error: parsing bookmark store at /path: expected value at line 1 column 1") carries the *why* (parse failure at a specific position), but the Hint contradicts the why by pointing at unrelated file-system checks. **Dim 2 (Argument and flag design)** is structurally adjacent: the helper's `kind: &str` parameter has only two valid values (`"load"` and `"save"`) — the `match` block's `_ => "is accessible to the current user."` fallback is unreachable, and the two named arms cover the load surface too coarsely (one Hint string for three distinct failure modes).

**Behavior consequence:** Storage errors are the highest-recovery-friction failure mode for this tool (per R1 F5 / R2 F5 framing). For the corrupt-JSON case specifically, a misleading Hint that points the user at non-issues costs the user time (they verify the file exists / is regular / is readable — three filesystem operations that succeed) and may push them toward the wrong recovery action (looking for permissions issues, checking symlinks) instead of the right one (open the file in an editor; verify or repair the JSON; or delete the file to start fresh). The previous R1 F5 suggestion ("Hint: edit or remove the store file to recover") would have correctly covered the parse-failure case; the R2 fix's literal Hint text instead lists filesystem checks that diagnose only the read-failure subcase.

**Recommended fix shape:**

Option (a) — Make the load Hint a disjunction that covers all three subcases:

```
Hint: if the file is corrupt JSON, edit or remove it to recover; if it cannot be read, check that <path> exists, is a regular file (not a symlink), and is readable.
```

Option (b) — Use the anyhow error chain's outermost context string to dispatch the Hint:

```rust
