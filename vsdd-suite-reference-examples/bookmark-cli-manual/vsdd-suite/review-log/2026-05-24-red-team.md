### Accepted risk

<a id="r1-f1"></a>
**Finding 1 — Dedup-on-tuple is order-sensitive on `tags: Vec<String>`; attacker re-ordering tag arrays bypasses the `import(import(X)) == import(X)` idempotence claim, enabling silent storage amplification (Dim 5, Dim 11)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*

[`src/lib.rs:558-564`](../../src/lib.rs) implements dedup as `if !self.bookmarks.contains(&new_bm) { ... }`, which calls the derived `Bookmark` `PartialEq` impl. `Bookmark`'s derive at [`src/lib.rs:50`](../../src/lib.rs) (`#[derive(... PartialEq, Eq)]`) compares all three fields including `tags: Vec<String>`. `Vec`'s `PartialEq` is order-sensitive — `vec!["a", "b"]` is NOT equal to `vec!["b", "a"]`. Spec at [`DESIGN.md`](../../DESIGN.md) line 132 states: "byte-equal records collapse to one appended record" — describing the deduplication contract in terms of byte-equality, which IS order-sensitive at the structural level. But spec at [`DESIGN.md`](../../DESIGN.md) line 223 states: "`tags` is treated as a set: duplicates are not produced by the application (idempotent `bm tag`)" — describing the LOGICAL semantic of `tags` as a set. The two statements conflict at the import boundary.

**Adversarial exploit:** an attacker who delivers a JSON payload to be imported can produce two records with the same `url`+`timestamp` but tags reordered (`["rust","cli"]` vs `["cli","rust"]`). The operator-side `bm import` reads BOTH as distinct (set-equivalent but tuple-unequal) and appends BOTH. Subsequent `bm list` (and `bm list --tag`) returns duplicate-looking rows. The attack scales:

```
payload with N entries × M permutations of K tags = N × M! amplified records
```

For a single bookmark with 5 tags, 5! = 120 permutation-records can be appended where the operator expects 1. The 10 MB stdin cap bounds the absolute count, but the attacker-vs-expectation ratio is unbounded — the operator sees N distinct records and the store contains 120N records.

**Bypass succeeds against the spec's `import(import(X)) == import(X)` claim** in the carry-forward sense: if X is the operator's intent (a set-equivalent payload), the idempotence does NOT hold. If X is the literal byte payload, it does — but the spec's prose at line 132 ("byte-equal records collapse") names the byte-equal case, while the `tags` semantic at line 223 ("treated as a set") names the set-equivalent case. The implementation matches the byte-equal frame; the operator-facing intent matches the set-equivalent frame. The gap between them is the adversary's leverage.

**Why Accepted risk rather than Raised to SO:** the spec is internally consistent if read narrowly — the dedup contract IS the byte-equal frame; the set-semantic for `tags` applies at `bm tag` time (where idempotence is enforced by `attach_tag`), not at import time (where the attacker controls the storage shape directly). Treating `tags` as a set at import would require sorting on import (which changes storage byte-shape across imports) or set-comparison on dedup (which loses ordering information). Either choice has its own surprise mode. The Red Team's job is to make the gap explicit so future review rounds + the AI-co-authored spec's `import(import(X)) == import(X)` proptest formulation use the byte-equal frame consistently. The proptest property as currently named (per [`DESIGN.md`](../../DESIGN.md) line 132 + Phase 5 strategy at [`DESIGN.md`](../../DESIGN.md) line 15) will surface this gap if the property generator is set-aware; if it's byte-aware, it will pass spuriously.

**Classification:** Accepted risk. Risk owner: solution-owner. Cross-reference: spec internal tension at [`DESIGN.md`](../../DESIGN.md) line 132 vs line 223; Phase 5 proptest formulation at [`DESIGN.md`](../../DESIGN.md) line 15 should explicitly choose a generator frame (byte-equal OR set-equivalent) and name the choice. Routes to [QUALITY-ENGINEER-REVIEW.md](2026-05-24-quality-engineer.md) for the proptest-generator-frame decision when Phase 5 proptest extension lands. Flag to [SECURITY-REVIEW.md](2026-05-24-security.md) as a coordinated finding — the asymmetric `tags`-frame is a property the Security review's threat-model audit should also reflect on.

**Finding 2 — `ImportError::InvalidJson(String)` detail string echoes the underlying `serde_json::Error`'s line/column position to stderr; provides a parse-progress oracle to an attacker fuzzing stdin (Dim 8 — Information leakage for reconnaissance)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*

[`src/lib.rs:518-519`](../../src/lib.rs) constructs `ImportError::InvalidJson(e.to_string())` from any `serde_json::from_str` failure. `serde_json::Error::Display` renders as `"<message> at line <N> column <M>"` (e.g., `"expected ident at line 1 column 5"`). [`src/main.rs:475-478`](../../src/main.rs) emits this string to stderr after the user-facing `Error: stdin is not valid JSON.` line. An attacker repeatedly piping crafted payloads can iterate: extend payload by one byte → if line/column advances, the new byte was accepted; if not, the prefix was already invalid.

**Adversarial exploit (limited scope):** an attacker who can observe stderr from `bm import` (cross-host: the operator runs `bm import` against attacker-supplied stdin and the attacker reads the operator's terminal output; same-host: a wrapper script the operator runs that pipes stdin to `bm import` and captures stderr to a file the attacker can read) gets a progress oracle for crafted JSON. The oracle does NOT leak the operator's storage contents (the parse happens on the attacker's own payload), so the practical exploit is narrow — it lets the attacker shrink a fuzzing corpus (where each fuzz iteration costs an `bm import` invocation) by an order of magnitude. Compared to running the fuzzer offline against `serde_json::from_str` directly (which gives the attacker the same oracle without needing operator cooperation), this is a marginal-cost shrink, not a new primitive.

**Why this is not a Hallucinated finding:** the oracle IS real per the named threat model — it leaks parse-state of attacker bytes back to the operator's observable channel. The Red Team supplement does not name this specific failure mode (information-leakage is Dim 8 of the prompt), and the spec at [`DESIGN.md`](../../DESIGN.md) line 122 EXPLICITLY names the diagnostic detail as intentional: "stderr `Error: stdin is not valid JSON.` followed by newline + the underlying `serde_json` parse error on the next line for diagnostic context." The spec acknowledges the diagnostic surface; the Red Team observation is that the diagnostic context IS the oracle. Spec-acknowledged → Accepted risk frame.

**Why Accepted risk rather than Raised to SO:** the spec already names the diagnostic-context decision at line 122. Removing the detail would degrade operator UX — the operator who pipes a malformed config through `bm import` benefits from knowing line:column of the parse failure. The attacker-oracle is the same channel; the trade-off is operator-discipline (don't pipe attacker-supplied stdin into `bm import` while also exposing the stderr to the attacker). The Red Team raises this as Accepted risk (not Dismissed) so the trade-off is auditable — a future production-intent fork that targets shared-pipeline deployments (where stderr might land in shared logs) should re-evaluate.

**Classification:** Accepted risk. Risk owner: solution-owner. Cross-reference: [`DESIGN.md`](../../DESIGN.md) line 122 (intentional diagnostic detail); [`src/lib.rs:518-519`](../../src/lib.rs) (`ImportError::InvalidJson(e.to_string())` capture); [`src/main.rs:475-478`](../../src/main.rs) (stderr emission of detail). Coordination: flag to [SECURITY-REVIEW.md](2026-05-24-security.md) for the cross-domain confirmation that the oracle disposition is structurally sound under the threat model.

### Raised to SO

<a id="r1-f3"></a>
**Finding 3 — DESIGN.md line 106 claims `bm export | bm import` "preserves the underlying bytes" via "JSON-valid `` sequences", but `display_safe` produces Rust-syntax `\u{001b}` (literal-string with curly braces) which is NOT a JSON-native unicode escape; the round-trip irreversibly transforms pathological URLs to their printable-text form (Dim 5 — business logic abuse — TOCTOU/spec drift; Dim 8 — information leakage; primary obligation: implementation does not match spec)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*

[`src/lib.rs:699`](../../src/lib.rs) implements `display_safe`'s escape as `write!(out, "\\u{{{:04x}}}", c as u32)` — producing the literal 8-character string `\u{001b}` for an ESC byte (backslash, lowercase u, opening curly brace, 0, 0, 1, b, closing curly brace). This is Rust source-code escape syntax, NOT JSON unicode escape syntax. JSON-native unicode escape is `` (6 characters: backslash, lowercase u, 0, 0, 1, b — no curly braces) and would be parsed back to the ESC byte by `serde_json::from_str` on re-import.

[`DESIGN.md`](../../DESIGN.md) line 106 explicitly states the byte-preservation contract:

> "terminal escape sequences serialize as JSON-valid `` sequences so the round-trip `bm export | bm import` preserves the underlying bytes."

The implementation does NOT do this. The actual round-trip:

```
source store:  url = "https://evil/<ESC>[31m"      (URL contains raw 0x1B byte)
bm export:     emits JSON "url":"https://evil/\\u{001b}[31m"
               (which JSON-decodes to the 15-char string "https://evil/\u{001b}[31m")
bm import:     parses as 15-char literal string and stores
post-import:   url = "https://evil/\u{001b}[31m"   (URL is the literal 15-char text — NO ESC byte)
```

The pathological URL has been irreversibly transformed. The round-trip is byte-different.

**Bypass attempts (which control might still hold?):**

1. **Could `serde_json::Value::String` be re-emitting the original ESC byte?** No — the `display_safe` call happens BEFORE the `Value::String` construction at [`src/lib.rs:464`](../../src/lib.rs), so the Value is constructed from the already-escaped 15-char string, and `serde_json::to_string` then JSON-escapes the backslash (producing `\\u{001b}` in the wire bytes). The ESC byte never reaches the serializer.
2. **Could the integration test `tests_export_applies_display_safe_to_pathological_url` catch this?** Partially — it asserts (a) no raw ESC in output, (b) parses as JSON, (c) URL field doesn't carry the raw ESC byte. It does NOT assert round-trip byte-equality. The other round-trip test (`tests_export_import_round_trip` at [`tests/bookmarks.rs:1601-1689`](../../tests/bookmarks.rs)) uses safe URLs `https://item-0.example` and would not exercise this codepath.
3. **Could the spec be re-interpreted to mean "preserves the printable representation"?** Not without a spec amendment — line 106's word "bytes" is the load-bearing claim. A reinterpretation that "the printable text is preserved" is a different contract.

**Why Raised to SO rather than Resolved:** the spec is silent on which side of the contract drift to land on. Either (a) DESIGN.md line 106 amends to remove the byte-preservation claim and replace it with the actual semantic ("the round-trip preserves the URL's printable representation; pathological bytes are escaped on first export and re-imported as their printable text"), OR (b) `display_safe` (or a separate `export_escape` helper) emits JSON-native `` form instead of Rust-syntax `\u{001b}` so the round-trip is byte-equal. Both directions are defensible:

- Direction (a) is consistent with the curated-Cf threat model — `display_safe` is the rendering-safety primitive; using it at export means export is also a rendering site; rendering is inherently lossy for control bytes. The spec amends to admit this.
- Direction (b) restores the byte-preservation claim — `display_safe` continues to produce Rust-syntax for `eprintln!`/`println!` paths; a NEW `export_escape` (using `` form) is the export-boundary helper; the export wraps with `export_escape` not `display_safe`. The spec stays unchanged.

The Red Team recommendation: direction (a) is the lower-cost path AND aligns with the "store-raw-sanitize-at-render" framing established at Layer 1 R1 F4 and confirmed at Layer 2 R1 F3 carry-forward. Direction (b) restores the round-trip property but requires a new helper + a test surface for the helper's correctness. SO chooses.

**Adversarial framing (why this matters beyond spec-drift):** the Phase 5 strategy at [`DESIGN.md`](../../DESIGN.md) line 15 names a proptest property `import(import(X)) == import(X)` (idempotence) AND a round-trip property `parse(serialize(X)) == X`. The current implementation FAILS the round-trip property for any X containing control bytes. A proptest generator that randomly emits control bytes in URL fields will FAIL the round-trip property — surfacing this finding via Phase 5. Catching it at Phase 3 Red Team is the cheap-route; catching it at Phase 5 proptest requires running the harness against an attacker-style generator. The cheap-route is preferred.

**Proposed DESIGN.md amendment (for SO review):** Replace line 106's sub-clause "terminal escape sequences serialize as JSON-valid `` sequences so the round-trip `bm export | bm import` preserves the underlying bytes" with: "terminal escape sequences are escaped at the export-boundary serialization step into a printable JSON-string form (e.g., the literal text `\u{001b}` for an ESC byte) — the round-trip `bm export | bm import` preserves the URL's printable representation, not the original bytes. Pathological URLs containing control bytes become their printable-text form after one round-trip; subsequent round-trips are byte-stable." This aligns the spec with the implementation AND with the broader render-safety frame, AND tightens the Phase 5 round-trip property formulation to the byte-stable post-first-round-trip semantic.

**Classification:** Raised to SO. Proposed DESIGN.md amendment above. Coordination: routes to [SOLUTION-OWNER-REVIEW.md](2026-05-24-solution-owner.md) for spec adjudication; flag to [SOFTWARE-ENGINEER-REVIEW.md](2026-05-24-software-engineer.md) if SO chooses Direction (b) (the new `export_escape` helper); flag to [QUALITY-ENGINEER-REVIEW.md](2026-05-24-quality-engineer.md) for the Phase 5 proptest formulation choice this finding gates; flag to [SECURITY-REVIEW.md](2026-05-24-security.md) per the Red-Team-to-Security flag-back convention (Security should have caught the spec-vs-impl drift on a rendering-safety contract).

**Owner:** *(N/A — Hallucinated)*

**Verification (the control's name-check applied to the Layer 3 surface):** the Layer 2 disposition at Security R1 F6 was on the storage-load path (`BookmarkStore::load`'s `serde_json::from_str`) where the attacker did not have direct write access. Layer 3 changes the threat model — `bm import` IS the attacker-write surface — so the regression-check matters. The control is the same `serde_json` parser with the same 128-limit, so the protection carries.

**Classification:** Hallucinated. The cited attack (deeply-nested JSON causing parse-stack-overflow) does not succeed against the serde_json 128-limit defense. The Layer 2 Hallucinated disposition at Security R1 F6 extends to Layer 3 without modification — same library, same limit, same defense. Documented here so a future cold-reader (or a future Phase 5 fuzz harness's grep) sees the regression-check applied at Layer 3 explicitly.

**Finding 5 — Candidate concern: billion-laughs-equivalent JSON expansion (recursive entity definitions amplifying small payload into massive in-memory representation) on `bm import` stdin (Dim 11 — Automated attack resilience; JSON supplement § Security — unbounded arrays)**

**Owner:** *(N/A — Hallucinated)*

**Bypass attempt:** Construct a JSON payload that uses entity-like structural amplification (e.g., a small payload that JSON-decodes to a much larger in-memory structure). Does the parser expand the payload to multiple-of-input-size memory consumption?

**Control held (structural impossibility):** JSON has NO entity-expansion mechanism by spec ([RFC 8259](https://datatracker.ietf.org/doc/html/rfc8259)). Unlike XML's `<!ENTITY>` declarations, JSON has no syntactic affordance for symbol-substitution-during-parse. The closest analog is repeated literal substrings (e.g., a JSON document with 1000 copies of a long string), but that consumes O(input-size) memory not O(input-size × expansion-factor). The 10 MB stdin cap bounds the worst-case memory expansion at parse time to O(10 MB) for the `Value` tree (plus the `from_value` `.clone()` at [`src/lib.rs:539`](../../src/lib.rs) doubling to ~20 MB peak).

**Adjacent concern that IS real but is captured by F1:** an attacker can amplify the EFFECTIVE record count (not the memory at parse time) by re-ordering `tags` per Finding 1. That is a logical amplification, not a billion-laughs structural amplification.

**Classification:** Hallucinated. The cited attack class is structurally impossible against JSON by spec. The adjacent logical-amplification concern is captured separately as Finding 1.

**Finding 6 — Candidate concern: `bm import` stdin cap is enforced by `take(cap+1).read_to_end(...)`; a multi-byte UTF-8 character split at the cap boundary could either (a) silently truncate accepting partial data, or (b) bypass the cap via boundary timing (Dim 5 — business logic abuse — TOCTOU; Dim 8 — information leakage)**

**Owner:** *(N/A — Hallucinated)*

**Bypass attempt 1 (silent truncation):** Construct stdin with exactly `cap` bytes of valid JSON followed by a multi-byte UTF-8 character that straddles the `cap` boundary (e.g., bytes 9_999_999..10_000_001 are the 3-byte sequence for U+1F600 EMOJI). The std-lib `FromStr` for `usize` returns `Err(ParseIntError { kind: PosOverflow })` on overflow — it does NOT wrap or saturate. clap surfaces this as a usage-error rejection at parse time (exit 64 per the spec's exit-code table at [`DESIGN.md:200-209`](../../DESIGN.md)) before `run_import` ever sees the value. The negative-value case is structurally impossible (usize is unsigned). The cap-0 case is caught by the new lower-bound check at [`src/main.rs:428-431`](../../src/main.rs).

**Classification:** Hallucinated. Both bypass attempts fail: overflow → clap exit 64; negative → type-structurally-impossible; zero → explicit lower-bound rejection. The implementation correctly enforces value-validity at every named edge.

**Control held (by-design — the trade-off is explicitly documented):** [`DESIGN.md:106`](../../DESIGN.md) (architectural correction sub-decision) + [`DESIGN.md:161`](../../DESIGN.md) (edge case catalog) BOTH explicitly name this trade-off: "curated format chars (bidi controls, ZWJ, etc.) survive as raw UTF-8 bytes in JSON output. This is the SAME store-raw-sanitize-at-render frame established at Layer 1 R1 F4 + carried at Layer 2 R1 F3. The threat-boundary shift IS documented; the consumer-applies-display_safe contract is the named trust delegation. **Verification (this finding is NOT silently dismissed):** the trust-boundary shift IS real — the architectural correction REMOVED `display_safe` from `export_json`, so the export bytes carry attacker-controllable bytes that the prior `display_safe`-wrapped export would have escaped. The pre-correction shape had `display_safe` at export which DESTROYED byte-preservation (R1 F3 root cause); the post-correction shape restores byte-preservation at the cost of the export-time render-safety. **Classification:** Hallucinated. The cited attack succeeds against the trust-boundary as documented but the trade-off is explicit in the spec; the bypass succeeds against a contract the spec deliberately delegates to the consumer. Filed with the by-design trail intact so a future Layer 4 (multi-user) or production-intent fork finds the rationale.
