#### Threat model (prerequisite record per [Security domain prompt](../../../vsdd-suite/domains/role/SECURITY-REVIEW.md) § Threat Model)

- **Plausible attackers:** (a) the local user themselves (mostly trusted; not a meaningful adversary against their own data); (b) **co-tenants on the same Unix host** if `bookmark-cli` is installed in a multi-user environment (e.g., a shared dev box, a CI runner, a multi-user VPS) — read access to `~/.bookmarks.json` is the relevant surface; (c) **supply-chain adversaries** publishing malicious crates that enter the dependency closure via `cargo install` — relevant for any Rust project that does not run `cargo audit` / `cargo deny`; (d) **upstream content that authored the bookmarked URL** — irrelevant in practice (URLs are inert strings; bookmark-cli never fetches them).
- **Crown jewel:** the user's bookmark list. The data is browsing-history-class — *confidential* by typical classification (knowing what someone is reading is sensitive). Secondary crown jewel: arbitrary code execution on the host via the binary, which is reachable through a malicious dependency in the supply-chain attacker scenario.
- **Entry points:** (1) the `url` CLI positional argument to `bm add` (untrusted string under the user's control but containing arbitrary bytes — control chars, ANSI escapes, bidi format chars); (2) the `$BOOKMARK_CLI_DB` environment variable (controls the write target path); (3) the on-disk JSON store (`bookmarks.json`) — at load time, treated as untrusted via `serde_json::from_str`; (4) the dependency closure pulled at `cargo install` / `cargo build` time. `bm list` reads no user input beyond the env var; clap parses argv before the program logic runs.
- **Relevant threat actors for this project's deployment context:** [`DESIGN.md`](../../DESIGN.md) § Constraints names "Platform: macOS, Linux" + "Deployment: `cargo install --path .` into `~/.cargo/bin/`" + "Network synchronization — local file only" + "User accounts or multi-user — single-user local tool" as non-goals. The deployment context is a single user on their own laptop. **But:** DESIGN.md does not foreclose the possibility of the user installing on a shared host. The "single-user local tool" framing in DESIGN.md describes the *application's own multi-user concurrency* (no accounts, no concurrent writes), not the *deployment host's* multi-user status. A shared dev box where bookmark-cli is installed in `~/.cargo/bin/` is consistent with DESIGN.md. The co-tenant attacker (b) above is therefore in-scope for any control whose effectiveness depends on Unix file permissions.

### Accepted risk

**Finding 1 — Error-message interpolation does not escape control / format characters before writing to stderr (Dim 9)**

<a id="r1-f1"></a>

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*
**Validator:** red-team

[`src/main.rs:51`](../../src/main.rs), [`src/main.rs:57`](../../src/main.rs), and [`src/main.rs:66`](../../src/main.rs) emit:

```rust
eprintln!("Error: {e:#}");
```

where `e` is an `anyhow::Error` whose `Display` interpolates the `with_context` strings authored at [`src/lib.rs:50`](../../src/lib.rs), [`src/lib.rs:55`](../../src/lib.rs), [`src/lib.rs:64`](../../src/lib.rs), and [`src/lib.rs:70`](../../src/lib.rs):

```rust
.with_context(|| format!("reading bookmark store at {}", path.display()))
.with_context(|| format!("parsing bookmark store at {}", path.display()))
.with_context(|| format!("creating parent dir for {}", path.display()))
.with_context(|| format!("writing bookmark store at {}", path.display()))
```

`path.display()` is a `std::path::Display` over the `PathBuf` constructed from `$BOOKMARK_CLI_DB` at [`src/main.rs:33-35`](../../src/main.rs). `Path::display()` does not sanitize control characters or format characters — it lossy-converts non-UTF-8 bytes to U+FFFD, but it does NOT escape `is_control()` (`Cc`) chars or `Cf` format chars (Trojan-Source bidi U+202E, zero-width chars). An attacker who can set `BOOKMARK_CLI_DB` to a path containing ANSI escape sequences (`\x1b[31m`), bidi format chars (`U+202E`), or terminal control bytes (`\x07` bell, `\r` carriage return) will cause those bytes to be rendered raw to the operator's terminal when bookmark-cli emits an error.

The rust supplement § Security explicitly names this dimension as a floor for Rust projects: "For every error-emit site (`panic!`, `eprintln!`, `format!` into an `Err`, `?`-propagation paths whose `Error::Display` interpolates input), confirm a sanitizer wraps every user-derived value before it reaches the error stream. The sanitizer must escape `is_control()` chars (`Cc`) AND `Cf` format chars (Trojan-Source U+202E and zero-width characters) while preserving structurally-significant whitespace." Bookmark-cli has no `display_safe` (or equivalent) sanitizer. The detector pattern from the supplement (`grep -rE 'eprintln!|format!|panic!' src/`) returns 7 sites in `src/main.rs` + `src/lib.rs`, none of which sanitize.

Reproducer (conceptual; not run in-session — reproducer test belongs to Red Team validation):

```sh
export BOOKMARK_CLI_DB=$'/tmp/\x1b[31mred\x1b[0m.json'
bm list
# Expected (sanitized): Error: reading bookmark store at /tmp/\x1b[31mred\x1b[0m.json: ...
# Observed (un-sanitized): the terminal renders the ANSI escape — "red" appears in red, the rest of the prompt may inherit the color state until a reset.
```

The attacker model is narrow (the same user who set the env var), but the rust supplement names this as a floor irrespective of attacker model — error-message escape discipline is a hygiene-tier control. Coordinated with the suite's G-125 / G-152 / G-124 framing for the dimension.

**Classification:** Accepted risk — finding raised in Round 1; Round 2 verification required per the Phase 3 primer's continue-trigger discipline.

**Coordination:** Cross-references [QE Review 2](2026-05-20-quality-engineer.md#review-2--2026-05-20-0245z) Finding 1 (Mutation Testing — `BookmarkStore::save` parent-dir creation) — the Red Gate test added there does not include a control-character-bearing path; an integration test feeding a control-character-bearing `BOOKMARK_CLI_DB` through every error path and asserting the rendered stderr is escape-free is the natural Red Team validation surface for this finding (rust supplement § Security: "Tests: include an integration test that feeds a control-character-bearing input through every error path and asserts the rendered stderr is escape-free."). Flag to QE for the test addition once the fix lands.

**Classification:** `Open`. The fix is a 3-step change: (i) add a `display_safe` helper to `src/lib.rs` (or a small new module) that escapes `Cc` + `Cf` characters while preserving `\n`; (ii) wrap every user-derived value (the `path.display()` interpolations + the `url` interpolations if any are added at future layers) before it reaches an `eprintln!` / `with_context!` / `format!`-into-`Err` site; (iii) add the integration test per the supplement. The fix is small and well-scoped; deferring it would degrade the reference-implementation's value as a worked example of the Dim 9 / rust-supplement floor. Routed to `software-engineer` for implementation; Red Team validates post-fix.

**Finding 2 — Bookmark store file is written world-readable on Unix (Dim 8)**

<a id="r1-f2"></a>

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*
**Validator:** red-team

[`src/lib.rs:69`](../../src/lib.rs) writes the bookmark store via `std::fs::write(path, json + "\n")`. On Unix, `std::fs::write` uses default file-creation permissions, which the OS combines with the process umask. A typical user umask of `0022` yields a file mode of `0644` — **world-readable**. The store contains URLs the user has captured (browsing-history-class data — "what someone is reading is sensitive" per the threat-model framing above; *confidential* tier under the [Security domain prompt](../../../vsdd-suite/domains/role/SECURITY-REVIEW.md) Dim 8 classification scheme).

On a shared Unix host (a development server, a multi-user lab machine, a CI runner with persistent home directories, a multi-user VPS), any co-tenant with read access to the user's home directory hierarchy — or to a system-writable path the user passed via `$BOOKMARK_CLI_DB` — can read the bookmark store. The DESIGN.md "single-user local tool" framing does not foreclose this deployment context (the framing is about the application's own concurrency model, not about the host's tenancy — see threat model above).

**Named failure mode (per [Security domain prompt](../../../vsdd-suite/domains/role/SECURITY-REVIEW.md) Dim 8):** "storing confidential data in localStorage or a flat file without encryption" — bookmark-cli stores confidential-class data in a flat file with no encryption and no Unix-permission restriction.

The proportionate control for confidential-class data is at minimum mode `0600` (read/write owner only) on write, set via `std::fs::OpenOptions::new().mode(0o600).write(true).truncate(true).create(true).open(path)` (Unix; behind a `#[cfg(unix)]`). Encryption at rest is the next tier up but is overkill for the spec's scope — mode `0600` is the floor.

[`DESIGN.md`](../../DESIGN.md) § Constraints names "Platform: macOS, Linux. Windows untested." Both supported platforms inherit Unix-style umask semantics; the finding applies to both supported platforms. DESIGN.md § Storage format describes the JSON document shape but is silent on file permissions — no controlled data-classification statement exists.

**Classification:** Accepted risk — finding raised in Round 1; Round 2 verification required per the Phase 3 primer's continue-trigger discipline.

**Coordination:** This finding has a **DESIGN.md change implication** (the Storage format section should declare the file permission mode and the implied data-classification tier). Per the Security domain prompt's "DESIGN.md change authority": Security flags but does not apply the DESIGN.md change. Concretely the spec amendment would add to § Storage format: *"The store file is written mode `0600` (read/write owner only) on Unix-family platforms. The data is classified `confidential` per Security Dim 8; co-tenant read on shared hosts is foreclosed by the file mode, not by encryption-at-rest (which is out of scope at Layer 1)."* If the project author rejects the spec amendment (e.g., declares the data classification `internal` and accepts world-readability), the finding's classification flips to `Accepted risk` with the spec amendment naming the risk owner.

**Classification:** `Open` pending director adjudication. The natural disposition is: (a) `Resolved` — apply the `0o600` mode at `src/lib.rs:69` + amend DESIGN.md § Storage format + add an integration test that asserts the file mode is `0600` post-write on Unix; or (b) `Accepted risk` — declare the data classification `internal`, document the co-tenant assumption, name the risk owner. Disposition (a) is the floor-compliant fix; (b) is the documented-tradeoff alternative. Routed to `software-engineer` for the code change and to `solution-owner` for the DESIGN.md amendment; Red Team validates the post-fix file mode via integration test.

**Finding 4 — `$BOOKMARK_CLI_DB` env var is unvalidated; path traversal and unbounded write target are theoretically possible (Dim 1)**

<a id="r1-f4"></a>

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*
**Validator:** red-team

[`src/main.rs:32-36`](../../src/main.rs) reads `$BOOKMARK_CLI_DB` directly into a `PathBuf` with no validation: no canonicalization, no traversal-component check, no allow-list of writable roots, no rejection of absolute paths or `..` components. The path then flows to [`BookmarkStore::save`](../../src/lib.rs) at `src/lib.rs:60-72`, which calls `std::fs::create_dir_all(parent)` followed by `std::fs::write(path, ...)` — both with the unvalidated path.

A user who sets `BOOKMARK_CLI_DB=/etc/passwd` (or, more plausibly, accidentally sets it to a path with traversal components from an automated script that joins partial paths) writes a JSON document over the target. The `create_dir_all` call escalates the surface — a path like `BOOKMARK_CLI_DB=/var/tmp/bm/sub/a.json` creates `/var/tmp/bm/sub/` even if it didn't exist, and the write happens unconditionally afterward (constrained only by the OS's permissions on the calling user).

**Classification:** `Accepted risk`. The user controls their own environment variable; an attacker who can set `BOOKMARK_CLI_DB` already has the user's shell, at which point the attacker has many cheaper paths to harm than steering bookmark-cli's writes. The OS's process-level permissions are the actual access-control boundary, and Rust's `std::fs::write` respects them — bookmark-cli cannot write where the calling user cannot. **However:** [`DESIGN.md`](../../DESIGN.md) § Edge case catalog does not name the env-var-controlled-path attack surface, and the [`README.md`](../../README.md) § Run section instructs `export BOOKMARK_CLI_DB=~/.bookmarks.json` without warning that arbitrary paths are accepted. A risk owner (the project author) accepts the surface explicitly only after this finding documents the dimension. **Risk owner:** project author (per [`DESIGN.md`](../../DESIGN.md) single-user local-tool framing).

This is the canonical "named risk owner" form of `Accepted risk` per the Phase 3 primer's classification universe — the risk is real, the rationale is explicit, the owner is named, and the surface is now in the audit trail.

**Finding 5 — TOCTOU between `path.exists()` and `read_to_string()` in `BookmarkStore::load` (Dim 1)**

<a id="r1-f5"></a>

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*
**Validator:** red-team

[`src/lib.rs:45-56`](../../src/lib.rs) implements `BookmarkStore::load` with a classic TOCTOU shape:

```
if !path.exists() {                                       // line 46 — check
    return Ok(Self::default());
}
let contents = std::fs::read_to_string(path)              // line 49 — use
    .with_context(...)?;
```

Between the `path.exists()` check at line 46 and the `read_to_string` call at line 49, a second process could replace the file (e.g., delete-then-symlink to a different target). In a multi-process attack model, the attacker could redirect the read to read content from a different file (subject to the calling user's read permissions on the symlink target).

**Classification:** `Accepted risk`. [`DESIGN.md`](../../DESIGN.md) § Edge case catalog explicitly declares: "Concurrent writes: out of scope; not a multi-process tool. Single user, single shell session." The single-process assumption is documented in the spec. The exploit requires a second process running as the same user racing the bookmark-cli read — and a process running as the same user already has read access to the same files bookmark-cli would read. The TOCTOU window does not grant the second process any capability it did not already have. The structurally-cleaner alternative (`fs::read_to_string` and handle `NotFound` directly) is a code-quality improvement, not a security control change — Software Engineer's domain. **Risk owner:** project author per DESIGN.md spec; documented here so a future maintainer who lifts the single-process assumption (e.g., for a daemon-mode Layer N) re-evaluates the dimension.

### Hallucinated

**Finding 6 — `serde_json::from_str` stack-overflow on deeply-nested attacker-supplied JSON (Dim 2)**

<a id="r1-f6"></a>

**Owner:** security
**Status:** raised
**Blocked by:** *(none)*
**Validator:** sanity-check

A reviewer's first instinct on seeing `serde_json::from_str(&contents)` at [`src/lib.rs:54`](../../src/lib.rs) over attacker-controlled file content might be: serde_json's recursive descent parser will stack-overflow on a sufficiently deeply-nested JSON document, producing a process crash (DoS). For a multi-user web service this is a real concern; serde_json indeed does not impose a default recursion-depth limit at the `Deserializer` level. The attacker-controlled bytes flow is real — an attacker who can write to `bookmarks.json` causes a process crash on next `bm list`.

**Specific demonstration of why the concern does not apply (per Phase 3 primer's hallucinated-finding discipline):** The attacker model here requires the attacker to write attacker-controlled bytes to `bookmarks.json` *before* the user runs `bm list`. The threat-model adversary (co-tenant on a shared host) reading the bookmark store via mode `0644` is a real surface (see Finding 2) — but *writing* attacker-controlled bytes to a file owned by the calling user is a privilege the threat model does not grant the attacker. A co-tenant who can read the user's `~/.bookmarks.json` does not have write access to it under any standard Unix permission scheme. A second process running *as the same user* who can write the file is not an attacker — that process is the user. A process running with elevated privileges that overwrote the file would have already escalated past bookmark-cli's threat model.

The crash-on-malformed-JSON surface produces exit code 2 (per [`src/main.rs:67`](../../src/main.rs)) — graceful failure with a `with_context`-wrapped error. The stack-overflow specifically (rather than a serde parse error) would produce a process abort, but the attacker capability to trigger it is the same capability that grants arbitrary file write — at which point the attacker has many cheaper paths to harm than overflowing serde_json's stack.

Marking `Hallucinated` per the Phase 3 primer's discipline: the surface is structurally real but the threat model does not grant the attacker the precondition to exploit it. The finding does not represent a control gap because the upstream control (file permissions, see Finding 2) is the real boundary. If a future layer adds an `bm import` command that reads JSON from stdin or an untrusted URL, this dimension re-activates and is no longer hallucinated; flag for re-evaluation at Layer 3 (per [`DESIGN.md`](../../DESIGN.md) § Scope and non-goals "`bm import` — read bookmarks from stdin" deferred to Layer 3).

**Classification:** `Hallucinated`. Validator is `sanity-check` per the Security domain prompt's validator-pair convention ("When a finding genuinely has no Red Team validation surface (e.g., a documentation-only secret-handling clarification with no exploit consequence), declare `**Validator:** sanity-check`") — there is no Red Team validation surface for a Hallucinated finding (no fix to test).
