**Finding 1 — DESIGN.md § Storage data classification names URLs as confidential but is silent on the Layer 2 `tags: Vec<String>` field; tags reveal "what someone is interested in" which is equally sensitive to URLs ("what someone is reading"); the spec-level data classification is incomplete for the Layer 2 storage extension (Dim 8 — Data classification; Dim 5 — Information exposure)**

**Owner:** security
**Status:** raised
**Blocked by:** *(none — DESIGN.md amendment required)*
**Validator:** red-team

**Domain-raised** during the cold Security pass against [`DESIGN.md:249-253`](../../DESIGN.md) (§ Storage data classification — Layer 1 declaration) + [`DESIGN.md:153-167`](../../DESIGN.md) (§ Storage format — Layer 2 `tags` field declaration) + [`DESIGN.md:234-247`](../../DESIGN.md) (§ Threat model — unchanged from Layer 1). The asymmetry is concrete:

**[`DESIGN.md:249-253`](../../DESIGN.md):**
> "The captured bookmarks are **confidential**-class data — 'what someone is reading is sensitive' per the [Security domain prompt](../../vsdd-suite/domains/role/SECURITY-REVIEW.md) Dim 8 information-leakage classification. The storage file is written with **mode 0600** (Unix; read/write owner only) using `std::fs::OpenOptions::new().mode(0o600)...` behind a `#[cfg(unix)]` gate."

The framing says "the captured bookmarks" — at Layer 1, a bookmark was `{url, timestamp}` and the classification clearly applies to the URL field (the timestamp is metadata; not adversary-interesting on its own). At Layer 2, a bookmark is `{url, timestamp, tags}`. The tags field is **not named** in the data-classification section. The Layer 2 spec change at [`DESIGN.md:153-167`](../../DESIGN.md) (§ Storage format `tags` field) introduces the field shape + serialization migration rules but does NOT amend § Storage data classification to declare the field's classification tier.

**Why this matters under Dim 8.** Per the [Security domain prompt Dim 8](../../../../vsdd-suite/domains/role/SECURITY-REVIEW.md): *"For each data type in the application: what classification does it carry? Are the applied controls — encryption, access restrictions, logging, retention limits — proportionate to the classification?"* — at Layer 2, two data types exist (URLs + tags); the spec classifies one (URLs) and is silent on the other (tags). The Dim 8 framework is unambiguous that each data type carries its own classification, even if the controls happen to be co-located (the same file, the same mode 0600).

The substantive question is whether tags warrant a different classification than URLs. The answer per the Dim 8 framework: tags are informationally adjacent to URLs in the same sensitivity class. A reader's URL list reveals *what they are reading*; their tag-set reveals *how they organize their interests* — both are personal-interest disclosures. A tag like `private`, `medical`, or `legal` on a bookmark is itself a sensitivity signal even if the URL it's attached to is innocuous (a Wikipedia article tagged `medical` reveals more than the URL alone). Tags are correctly classified at the same *confidential* tier as URLs.

**Why this is a spec-amendment finding, not a code-fix finding.** The mode 0600 file-permission control already applies uniformly to the whole storage file (URLs + tags + timestamps); the data-control surface is correctly co-located. The defect is at the *audit-trail* level — § Storage data classification does not name the new data type, so a future reader (or a future SE landing Layer 3 export/import) cannot consult the spec to determine the tag-field's classification independently of inferring it from the URL classification. This is the same Dim 8 audit-trail framing that drove the Layer 1 amendment (Security R1 F2 / R2 F2 added the data-classification section in the first place).

**Confidentiality-aware citation.** Per the [Security domain prompt § Confidentiality-aware citation reminder](../../../../vsdd-suite/domains/role/SECURITY-REVIEW.md): *"Information-exposure findings, identity-disclosure findings, and secrets-management findings are this domain's typical surface — and the worked examples that illustrate them tend to instantiate the disclosure."* — no actually-disclosed tag values are cited in this finding; the illustration uses placeholder tags (`private`, `medical`, `legal`) that are intentionally generic-categorical, not instantiated user data.

**Proposed spec amendment** (for Solution Owner authoring — Security flags but does not apply the DESIGN.md change per the DESIGN.md change authority clause):

Amend [`DESIGN.md:249-253`](../../DESIGN.md) § Storage data classification to read:

> "The captured bookmarks contain **two confidential-class data fields**: (a) the **URL** — 'what someone is reading'; and (b) the **tag set** (Layer 2) — 'how someone organizes their interests', including potentially-sensitive categorical labels (`private`, `medical`, `legal`, etc.). Both fields carry the same *confidential* classification per Security Dim 8 information-leakage framework; the proportionate Unix control is mode 0600 applied to the storage file as a whole (read/write owner only). The timestamp field is *internal*-class metadata; its co-location in the same file inherits the *confidential* file-mode automatically without requiring a separate proportionality argument."

**Why this is a Security finding** (not just SO documentation). Per [Security Dim 8](../../../../vsdd-suite/domains/role/SECURITY-REVIEW.md), the data-classification surface is a Security primary concern; the spec amendment is the Security domain's audit-trail closure of the dim against the Layer 2 extension. SO has DESIGN.md change authority, so the routing is Security → SO; the finding is owned by Security with the spec-amendment proposal routed to SO.

**Resolution path.** Raised-to-SO; Owner: security (consultative on the proposed amendment text); Validator: red-team (parallel cold-session validation in Solution-Architect/Red-Team/Platform-Engineer cluster against the spec-vs-impl alignment after the SO amendment lands). The fix is a spec-only change; no code change is required.

**Classification:** Resolved (raised; spec amendment Open per the Raised-to-SO routing).

**Coordination.** Cross-references [TW Review 5](2026-05-22-technical-writer.md) — the spec-update gap is a documentation-accuracy concern from the TW Dim 2 lens; Security owns the Dim 8 classification framing, TW owns the spec-prose-completeness framing. Both findings close together when the SO amendment lands.

### Accepted risk

<a id="r4-sec-f3"></a>
**Finding 3 — `attach_tag` byte-equal URL match (`src/lib.rs:386`) is timing-observable but the threat model declares no remote attacker entry point; Accepted risk persists per the single-user local-tool framing (Dim 1 — Input handling; Dim 5 — Information exposure)**

**Owner:** solution-owner
**Status:** raised
**Blocked by:** *(none)*
**Validator:** red-team

**Domain-raised** during the cold Security pass against the prompt's specific Layer 2 question: *"`attach_tag` does `bm.url == url` byte-comparison for URL match. Does this open any new info-leak path (e.g., timing-attack on URL existence)? Probably out-of-scope for a local single-user tool, but verify the explicit threat-model declaration."*

[`src/lib.rs:385-392`](../../src/lib.rs):

```rust
let mut matched = 0_usize;
for bm in &mut self.bookmarks {
    if bm.url == url {
        matched += 1;
        if !bm.tags.iter().any(|t| t == label) {
            bm.tags.push(label.to_string());
        }
    }
}
```

The `bm.url == url` comparison is a byte-equal `String == &str` per [`std::cmp::PartialEq`](https://doc.rust-lang.org/std/cmp/trait.PartialEq.html) — short-circuiting on the first differing byte. A side-channel observer measuring `bm tag <url> <label>` wall-clock time across multiple URL guesses could in principle distinguish a stored-URL prefix-match (longer comparison time per the average # of bookmarks scanned) from a complete miss (faster fail per bookmark).

**Why this is Accepted risk, not Open.** The threat model in [`DESIGN.md`](../../DESIGN.md) § Threat model declares the attacker surface explicitly: (a) co-tenant on a shared Unix host with read access (already foreclosed by mode 0600); (b) adversary-controlled `$BOOKMARK_CLI_DB` (env-var ambient authority Accepted risk); (c) adversary-supplied URL contents at render time (display_safe-mitigated); (d) supply-chain adversary (deny.toml-mitigated). None of the four named attacker types has a *remote* observation surface against the `bm tag` invocation — the timing channel requires the attacker to *observe* the wall-clock time of `bm` invocations, which requires either:

1. **Process-level observation as a co-tenant** — possible on a shared Unix host (`ps` shows command names + CPU time samples), but the co-tenant already has read access to nothing more than the process accounting; they cannot probe `bm tag` with arbitrary URLs because they don't have shell-level invocation rights to invoke `bm` as the target user.
2. **Remote network observation** — bookmark-cli has no network surface; the threat model declares "Network synchronization — local file only" as a non-goal at every layer.
3. **Adversary-supplied bookmark store (`$BOOKMARK_CLI_DB` ambient-authority + user invokes `bm tag` with attacker-suggested URLs)** — this collapses into the Accepted-risk env-var-ambient-authority surface (Security R1 F4 / R2 F5 / R3 F5); the timing channel does not strengthen the attacker's position beyond what env-var control already grants.

The constant-time comparison fix (e.g., `subtle::ConstantTimeEq`) would add a `subtle` dependency to defend against an attack the threat model explicitly excludes. Per the [Security domain prompt § Dim 5](../../../../vsdd-suite/domains/role/SECURITY-REVIEW.md) proportionality discipline, defenses must be proportionate to the threat — adding a crypto-grade dep for a single-user local tool's URL comparison is disproportionate.

**Why the explicit declaration matters.** The risk owner (solution-owner per the Threat model declaration) accepts the surface explicitly only after this finding documents the dimension. A future Layer 3 `bm import` (out-of-scope at Layer 2 per [`DESIGN.md`](../../DESIGN.md) § Scope and non-goals) that reads URLs from stdin or an untrusted URL could re-introduce the relevance: an attacker who can supply URLs for the user to run `bm tag` against from a script effectively has invocation rights, at which point the timing channel becomes a real distinguishability oracle for which URLs are stored. **Flagged for re-evaluation at Layer 3.**

**Resolution path.** Accepted risk per the four-class Security disposition universe. Risk owner: solution-owner (project author per DESIGN.md single-user local-tool framing). Validator: red-team (parallel Solution-Architect/Red-Team/Platform-Engineer cluster validation against the threat-model boundary).

**Classification:** Accepted risk. The rationale is preserved at the spec level (the existing § Threat model out-of-scope clauses cover this transitively); no new spec amendment required because the dimension is dominated by an Accepted-risk surface that already exists (env-var ambient authority). Recorded for audit-trail completeness so a Layer 3 cold pass picks up the re-evaluation trigger.

<a id="r4-sec-f4"></a>
**Finding 4 — New `fsync_directory` call at `src/lib.rs:304` after `rename(2)` introduces a tiny window between rename and fsync where a power-fail could lose the rename even though `save` returned success; this is a durability concern, not a security concern, but the Security domain verifies it does NOT open a new TOCTOU exploit window (Dim 1 — Input handling; verification finding)**

**Owner:** security
**Status:** validated
**Blocked by:** *(none)*
**Validator:** red-team

**Domain-raised** during the cold Security pass against the prompt's specific Layer 2 question: *"New atomic-save side effect (parent-dir fsync) — does this open a TOCTOU window between rename and fsync that an adversary could exploit?"*

[`src/lib.rs:277-311`](../../src/lib.rs):

```rust
if let Err(e) = std::fs::rename(&tmp_path, path) {
    // ... orphan cleanup ...
    return Err(e).with_context(...);
}

// Layer 2 durability — fsync the parent directory ...
#[cfg(unix)]
{
    if let Some(parent) = path.parent() {
        let parent = if parent.as_os_str().is_empty() {
            Path::new(".")
        } else {
            parent
        };
        fsync_directory(parent).with_context(...)?;
    }
}
```

**Verification: no new TOCTOU exploit window.** The rename has completed atomically by the time the fsync runs; the on-disk inode is what `ls(1)` shows from any other process at this point. The rename → fsync window is observable in the sense that an adversary with concurrent filesystem access could see the renamed file before the fsync issues, but the *only* divergent state across the window is whether the rename is durable across a power-fail — not whether the file is accessible. An adversary cannot exploit the window to redirect, swap, or otherwise tamper with the file content because:

1. The renamed-target inode is now the bookmark-cli output; an attacker swap of the file content during the window would require write access to the user's home directory, which the threat model does not grant.
2. The fsync is on the *directory* (`parent`), not on a separate file. Directory fsync's effect is to durably commit the rename's directory-entry change; it does not interact with file-content syscalls that could race.
3. The single-process foreclosure in [`DESIGN.md`](../../DESIGN.md) § Edge case catalog ("Concurrent writes: out of scope; not a multi-process tool") applies — a same-user racing process is not an adversary.

The fsync addition is a pure durability improvement; it does not introduce a security-relevant race. The Security domain's only concern would be if the fsync error path could leak information — verified at [`src/lib.rs:304-310`](../../src/lib.rs): the `with_context` formats the parent + path through anyhow's chain, which is then routed through `emit_storage_error` at [`src/main.rs:95-114`](../../src/main.rs) which wraps user-derived values through `display_safe`. Safe.

Adversarial check on the parent-directory selection at [`src/lib.rs:298-303`](../../src/lib.rs):
```rust
let parent = if parent.as_os_str().is_empty() {
    Path::new(".")
} else {
    parent
};
```
The `Path::new(".")` fallback for empty-parent paths is the current-working-directory of the bookmark-cli process. An adversary cannot exploit this because (a) the CWD is what bookmark-cli's user chose to invoke `bm` from; (b) the fsync is a stat-class operation on the CWD inode, not a write; (c) the fsync's only side effect is page-cache flush. No new attack surface.

**Resolution path.** Verified Resolved; the Layer 2 fsync side effect does NOT introduce a security-relevant TOCTOU window or information-leak path. The durability improvement is security-orthogonal. Validator: red-team (parallel Solution-Architect/Red-Team/Platform-Engineer cluster cold pass against the same code path).

**Classification:** Resolved (verification; no defect found).

**Coordination.** The fsync addition is canonical Performance Engineer domain (closes operator-queued PE fsync benchmark item); the QE Review 4 raised the WEAK-PROXY Red Gate framing question for the integration test. The Security verification here is orthogonal to both — Security's role is to confirm no new exploit window opened, not to evaluate the durability discipline itself.
