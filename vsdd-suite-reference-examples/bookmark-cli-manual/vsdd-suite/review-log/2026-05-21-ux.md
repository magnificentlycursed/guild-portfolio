**Finding 1 — "Expected stdout (literal — empty)" wording is confusing to non-author users; the empty fenced code block following it reads as an authoring-incomplete artifact rather than as an expected-empty-output assertion (Dim 6 — CLI supplement Empty state messages)**

**Owner:** ux
**Status:** validated
**Blocked by:** *(none)*
**Validator:** technical-writer

**External-feedback evidence:** Nathan Whitehead, Bluesky Post 8 (2026-05-21 19:33:14 UTC) — exact quote: *"step (1) of layer.md the expected parts look a bit weird...the \"literal -- empty\" was confusing."* (Source: [`../../../../vsdd-suite/suite-development/review-log/2026-05-21-install-verification-bluesky-thread.txt`](../../../../vsdd-suite/suite-development/review-log/2026-05-21-install-verification-bluesky-thread.txt) line 46. Note: Nathan typed the em-dash as the ASCII double-hyphen `--` per Bluesky's character-handling; the actual file uses the typographic em-dash `—`.) Nathan PASSED the install verification (PR #41 PASS row landed) despite the confusion, but his exact-quote feedback is the load-bearing signal — the wording impeded comprehension even for a verifier who completed the gate.

**Defect class.** Three locations in [`manual-tests/layer-1.md`](../../manual-tests/layer-1.md) use the formulation `Expected <stream> for <command> (literal — empty):` immediately followed by an empty fenced code block:

- **Line 42-45** (Step 1 stdout): `Expected stdout for \`bm add\` (literal — empty):` then ` ```\n``` ` (three-backtick fence with zero content lines between).
- **Line 47-50** (Step 1 stderr): same form for `bm add`'s stderr.
- **Line 140-143** (Step 4 stdout): same form for `bm list`'s stdout under the empty-state case.

**Cold-reader confusion path** (Nathan's lived experience reconstructed against the file). A first-time reader landing on Step 1 sees the runnable command block, then encounters: `Expected stdout for bm add (literal — empty):` followed by an empty fenced code block. The reader's working model needs to resolve two ambiguities at once:

1. **What does "literal — empty" mean?** Is it (a) "the expected stdout literally consists of the word 'empty'" (so the user should expect to see the word `empty` printed), (b) "the expected stdout is literally the empty string" (the parenthetical is a metadata gloss telling the reader the fenced block below intentionally contains zero bytes), or (c) "the fenced block below is a literal copy of expected stdout, and that copy is empty" (a sub-shape of (b) but with the fenced block carrying the load-bearing assertion)? The three readings have the same observable test (stdout is empty), but the wording does not communicate that — the reader has to triangulate against the empty fenced block to disambiguate.

2. **Why is the fenced block empty?** Empty fenced code blocks in markdown look like authoring stubs — places where someone meant to paste content but didn't. A reader who is unsure whether the gate is satisfied has to trust that the empty block IS the expected state, not a missing piece. Combined with the ambiguous "literal — empty" parenthetical, the reader cannot tell whether they're looking at a complete-and-correct expected-output assertion or at a half-written template.

The authoring intent (per the [CLI supplement § UX Dim 6](../../../../vsdd-suite/supplements/cli.md) — "When a command succeeds but produces no results...is there a clear message indicating the empty result rather than silent zero output?") is to communicate that `bm add` succeeds silently on stdout (the discipline is correct: `bm add` SHOULD be silent on stdout because the success signal is exit 0 + on-disk store updated). But the wording communicates the discipline poorly — the reader has to do interpretive work the wording should do for them.

**Behavior consequence.** Nathan's "confusing" quote is the direct signal. The asymmetry matters because [`manual-tests/layer-1.md`](../../manual-tests/layer-1.md) is the install-verification gate's load-bearing artifact — every non-author operator runs through this file step-by-step ([G-155](../../../../vsdd-suite/suite-development/FINDINGS-INDEX.md#g-155) Platform Engineer Dim 38). Confusing wording at Step 1 sets a bad tone for the remaining 5 steps; a verifier who has to second-guess the wording is in a worse position to catch real behavioral defects (which is the whole point of manual testing being "a second adversarial surface to IAR" per [G-132](../../../../vsdd-suite/suite-development/FINDINGS-INDEX.md#g-132)).

**Proposed change.** Replace the three `(literal — empty):` parentheticals with explicit prose that names the expected behavior:

- Line 42: `Expected stdout for \`bm add\` (literal — empty):` → `Expected stdout for \`bm add\` — none (the command is silent on success; the fenced block below is intentionally empty):`
- Line 47: `Expected stderr for \`bm add\` (literal — empty):` → `Expected stderr for \`bm add\` — none (the command emits nothing to stderr on success; the fenced block below is intentionally empty):`
- Line 140: `Expected stdout for \`bm list\` (literal — empty):` → `Expected stdout for \`bm list\` — none (the empty-state message routes to stderr; stdout is intentionally empty so pipe-consumers don't see placeholder text; the fenced block below is intentionally empty):`

Alternative shape — replace the empty fenced block entirely with a single italic line: `*Expected stdout — none (the command is silent on success).*`. This eliminates the empty-code-block-looks-like-authoring-stub ambiguity but loses the structural symmetry with the other expected-output blocks in the same step (which DO use fenced blocks). The recommended fix is the first form (descriptive parenthetical + retain the empty fenced block) — it preserves the structural symmetry while replacing the ambiguous "literal — empty" wording with explicit prose.

**Resolution.** Fixed inline during this Round 4 cluster pass. [`manual-tests/layer-1.md:42`](../../manual-tests/layer-1.md) + line 47 + line 140 now read with the explicit-prose parenthetical: each block names *why* the output is empty (silent-on-success / routes-to-stderr) and explicitly tells the reader the empty fenced block is intentional. The fenced blocks remain (preserving structural symmetry with the non-empty expected-output blocks in the same step); only the wording above each block changed.

**Cross-domain pair.** [Finding 1 (QE)](2026-05-21-quality-engineer.md#r3-f1) — the QE companion finding raises the same wording defect from the test-discipline angle (an ambiguous expected-output block is a test-discipline defect because the verifier cannot confidently distinguish pass-from-fail when the assertion is unclear). The two findings are non-duplicative: UX owns the user-facing prose change; QE owns the test-plan-as-falsifiable-assertion stance.

**Classification:** Resolved — inline fix applied at [`manual-tests/layer-1.md:42`](../../manual-tests/layer-1.md), line 47, line 140. (Dim 6 — CLI supplement § Empty state messages)

**Finding 3 — `bm add` silent-on-success has no first-time affordance signal; a new user cannot tell whether the command succeeded or did nothing (Dim 6 — CLI supplement § Empty state messages; Dim 8 — CLI supplement § Error message quality)**

**Owner:** ux
**Status:** raised
**Blocked by:** Spec authority — [`DESIGN.md`](../../DESIGN.md) § Acceptance criteria AC 1 explicitly mandates `stdout silent` on successful add.
**Validator:** solution-owner

**Domain-raised** during the cold UX pass against [`src/main.rs`](../../src/main.rs) + [`manual-tests/layer-1.md`](../../manual-tests/layer-1.md) Step 1 + DESIGN.md AC 1. After re-reading Finding 1's "literal — empty" formulation, the underlying behavior (`bm add` silent on success) reads as itself an affordance defect for first-time users, distinct from how the manual-test plan describes that behavior.

**The behavior.** `bm add https://example.com` succeeds → exit 0; stdout silent; stderr silent; the on-disk store is updated. From the user's terminal, the visible outcome is: the cursor returns to the prompt with no message. There is no confirmation that the bookmark was captured.

**Cold-reader experience.** A first-time user runs `bm add https://example.com`, sees nothing, and has to choose between:

1. **Trust the silent-success convention** ([Unix tradition: "Rule of Silence"](https://en.wikipedia.org/wiki/Unix_philosophy)) — silent exit means success. Experienced CLI users default to this and verify by running `bm list`.
2. **Worry the command did nothing** — newer CLI users or users coming from GUIs expect a confirmation. They re-run the command (creating a duplicate bookmark — the impl doesn't dedupe; see [`src/lib.rs`](../../src/lib.rs) `add` method), or they try `--help` to figure out what went wrong, or they ask for help.
3. **Reach for `bm list`** — the canonical verification path. The user has to know about `bm list` to take this step.

The [CLI supplement § UX Dim 6](../../../../vsdd-suite/supplements/cli.md) names the empty-state question explicitly: "is there a clear message indicating the empty result rather than silent zero output?" — the dim was authored for empty-result-on-list cases (which `bm list` handles correctly via the stderr "No bookmarks yet." message). The silent-success-on-add case is the parallel concern: the success result has no message.

The asymmetry against the empty-list case is particularly notable: `bm list` against an empty store emits `No bookmarks yet.` to stderr (Step 4); `bm add https://example.com` emits nothing. The two surfaces are not symmetric in their affordance richness — list-empty has a message; add-success doesn't.

**Spec authority.** [`DESIGN.md`](../../DESIGN.md) § Acceptance criteria AC 1 explicitly mandates `stdout silent` on successful add. The silent-success behavior is therefore SO-controlled — changing it requires a DESIGN.md amendment. Per the [UX domain prompt](../../../../vsdd-suite/domains/role/UX-REVIEW.md) § DESIGN.md change authority clause, this finding routes to the [Solution Owner](../../../../vsdd-suite/domains/role/SOLUTION-OWNER-REVIEW.md) as a Raised-to-SO candidate.

**Proposed change (to DESIGN.md AC 1, pending SO ratification).** Two alternatives, both within the [CLI supplement § UX Dim 4 stdout/stderr discipline](../../../../vsdd-suite/supplements/cli.md):

- **Alt A — opt-in confirmation:** Add a `--quiet` / `-q` flag (CLI supplement § UX Dim 11 — Verbose / quiet modes). Default behavior emits `Saved: <url>` to **stderr** (so pipe-consumers don't see it on stdout); `--quiet` suppresses for scripting. This adds the affordance while preserving the pipe-clean stdout discipline.
- **Alt B — info-line on stderr by default:** Emit `Saved bookmark: <url>` (or `Added: <url> at <RFC3339-timestamp>`) to stderr on every successful add. No flag needed. Pipe-clean stdout discipline preserved. The user sees a confirmation message; scripting use is unaffected (stderr is not captured by default pipes).

Alt B is the simpler fix; Alt A is the more orthodox CLI-design fix (default-quiet is the Unix tradition; opt-in verbose is the affordance for users who want it). The recommendation depends on whether the SO prioritizes Unix orthodoxy (Alt A) or first-time-user affordance (Alt B). The current behavior optimizes for orthodoxy; the finding raises whether the project's target user (a single-user portfolio CLI for terminal bookmark capture per [`README.md`](../../README.md) § What this is) is the orthodox CLI user or the first-time CLI user.

**This finding does NOT route to inline-fix in this PR #42.** Per the [UX domain prompt](../../../../vsdd-suite/domains/role/UX-REVIEW.md) DESIGN.md-change-authority clause, the SO is the sole domain authorized to modify DESIGN.md. The finding is filed as **Raised to SO** for the next SO round to ratify either Alt A, Alt B, or to dismiss with a documented rationale (a defensible dismissal would be: "the project's intent is portfolio-demonstration of the VSDD methodology; the silent-success behavior is the spec'd shape; first-time-user affordance is out of scope for a worked-example reference implementation"). Either outcome is acceptable; the methodology requires the routing be visible in the audit trail, not that the change be applied.

**Classification:** Resolved — finding raised to SO per the DESIGN.md change authority clause. The audit-trail-visibility goal of routing the finding is satisfied by filing this entry; the inline-fix question routes to [Solution Owner](../../../../vsdd-suite/domains/role/SOLUTION-OWNER-REVIEW.md). (Dim 6 + Dim 8 — CLI supplement § Empty state messages + § Error message quality)

Cross-references SE Review 4 Finding 2 (the `usize` return value of `attach_tag` becomes load-bearing).

Recommend Alt A — the simplest fix, the lowest user friction, and the only one of the three that closes the affordance gap without requiring the user to type a flag. The spec amendment is one sentence in [`DESIGN.md`](../../DESIGN.md) § `bm tag` § Success output.
