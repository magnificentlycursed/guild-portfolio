### Stumbling point 4 — 80 Round-1 findings is a spec/test under-investment signal disguised as IAR thoroughness

**AI-authored scaffold:** PR #38's [Round 1 cold-session IAR](../../vsdd-suite/suite-development/review-log/2026-05-20-suite-review.md#review-82--2026-05-20-2000z) Finding 2) produced **80 findings across 10 domains**. The signal is double-coded: it demonstrates IAR's adversarial cold-session discipline works (real defects surfaced); it ALSO demonstrates Phase 1a+1b spec authoring + Phase 2a Red Gate test authoring + Phase 2b implementation had substantive gaps that IAR Round 1 was effectively the first comprehensive review for. A capstone-intent project at MVR-pre-IAR would surface ~10-20 findings at Round 1 (per the AI Engineer R1 capstone-intent expected band of 100k-300k tokens/finding); 80 findings is over-investment-in-cold-session-IAR relative to under-investment-in-pre-IAR-phases. The methodology fix is to harden the Phase 1a+1b self-adversary check + the Phase 2a Red Gate explicit-failing-test commit discipline + the Phase 2b in-author cross-source consistency check (per Stumbling point 1 above). **Review-log evidence:** [Review 82 Finding 2](../../vsdd-suite/suite-development/review-log/2026-05-20-suite-review.md#review-82--2026-05-20-2000z); 80 findings tallied across [10 per-session review-log files](vsdd-suite/review-log/).

**Three-audience lens:**

- **Suite developers:** the 80-finding count is the calibration signal that the suite's pre-IAR primers (1a+1b, 2a, 2b) have under-specified the in-author discipline that should reduce Round-1 IAR scope. Hardening opportunity: each primer's "Completion criteria" section should add a checklist of pre-IAR self-checks the author should run BEFORE the cold-session adversaries get their hands on the artifact. The AI Engineer Dim 8 (Phase 4 routing as Round-2+ scope-reducer) names this at the IAR-round level; the equivalent discipline at the pre-IAR-phase level would reduce the Round-1 surface that IAR needs to cover.
- **Suite users:** if your Round 1 IAR surfaces 50+ findings, treat it as a signal that the pre-IAR phases need hardening, not as a signal that IAR is working well. The IAR cycle's job is to catch the adversarial defects in-author review missed; if it's catching the in-author defects that pre-IAR self-check should have caught, the methodology investment is mis-targeted.
- **AI agents:** the failure mode is "Round 1 as first comprehensive review" — treating IAR Round 1 as the de-facto first-comprehensive-pass over the artifact instead of as the cold-session-adversarial-validation of an already-self-reviewed artifact. The discipline is to run an in-author self-check BEFORE inviting cold-session adversaries; the pre-cycle methodology check (per [primer 3 § Pre-cycle methodology check](../../vsdd-suite/primers/3-review-session.md)) names this at the cycle level; the in-author equivalent is a pre-handoff grep + cross-source consistency check.

### Stumbling point 5 — Operator-directive correction cost (3 mid-cycle slips in PR #38)

**AI-authored scaffold:** PR #38's [Round 3 cycle surfaced 3 mid-cycle slips](../../vsdd-suite/suite-development/review-log/2026-05-20-suite-review.md#review-82--2026-05-20-2000z) that the operator caught + corrected: (1) Round 2 agents initially produced `2026-05-20-{domain}-round-2.md` filenames violating the per-session-file convention (consolidated post-execution); (2) initial Round 3 cluster spawn co-located adversarial pairs (Security+Red Team in one agent; TW+Doc Reviewer in another) — operator caught + corrected to adversarial-pair-separated clusters; (3) initial Round 3 cluster files used letter-coded names ("Cluster A/B/C/D") — operator caught + corrected to descriptive-by-constituent-domains names. Each slip required rework: the wrong-shape artifact was created, the operator caught it, the discipline was re-applied, the correct-shape artifact was created. The rework cost is real (tokens + cycle time + audit-trail complexity); the methodology fix is the [AI Engineer R1 F4](vsdd-suite/review-log/2026-05-21-ai-engineer.md) discipline of codifying operator-directive corrections back into the methodology so future cycles don't repeat them. **Review-log evidence:** all 3 slips named in the [feedback memory on avoiding lettering and abbreviation standards](https://github.com/magnificentlycursed/guild-portfolio) + the [AI Engineer R1 F4](vsdd-suite/review-log/2026-05-21-ai-engineer.md) Round-3-cycle audit; the AI Engineer Round 1 mining of PR #38 codified the rework cost as Dim 12.

**Three-audience lens:**

- **Suite developers:** mid-cycle operator-directive corrections are a signal that the methodology hasn't fully codified the discipline the operator is enforcing. Hardening opportunity: every operator-directive correction landed mid-cycle becomes a candidate codification — either as a primer convention, a hook check, a domain prompt dimension, or a memory entry. The 3 slips in PR #38 became: per-session-file convention + adversarial-pair-separation rule + descriptive-cluster-naming rule.
- **Suite users:** if you find yourself correcting the AI's outputs for the same defect-class twice in a project, that defect-class is a methodology gap, not an AI-mistake-to-tolerate. File a methodology-fix proposal (Phase 4 routing to Suite-development per [primer 4](../../vsdd-suite/primers/4-feedback-integration.md)) so the next project doesn't repeat the same correction.
- **AI agents:** the failure mode is "operator catches mistake; AI corrects; cycle continues" — treating the operator-correction as the discipline rather than treating the methodology authoring as the discipline. The methodology fix is "operator catches mistake; AI corrects + codifies the discipline-gap as a methodology-authoring task" so the operator's catch is the LAST time that specific discipline-gap surfaces. The cost of codification is small; the cost of repeated operator-corrections across projects is large.

### Stumbling point 6 — Site-specific fix declared closure (Doc Reviewer R3 pattern)

**AI-authored scaffold:** PR #38's [Documentation Reviewer R3 cycle surfaced 5 Deferred carryforwards](vsdd-suite/review-log/2026-05-20-documentation-reviewer.md) where the fix-cycle had visited the cited sites for each finding but had NOT swept the project for adjacent sites with the same defect class. The recurring pattern across R1 → R2 → R3: a Resolved finding for "stale `1ab-spec-development.md` link in DESIGN.md:3" closed the cited site but missed the same defect at SA-REVIEW.md:21 + QE-REVIEW.md:21; a Resolved finding for "duplicate-name sweep artifact in DESIGN.md:17" closed the cited site but missed the same defect at PROCESS.md:23 + SOLUTION-ARCHITECT-REVIEW.md:21; etc. The root cause: AI-author defaults to "fix the cited site; declare closure" when the methodology required "fix the cited site + grep for the defect class + declare closure when grep returns clean." The methodology fix landed in PR #40 as the [`grep -rn before claiming closure` anti-pattern](../../vsdd-suite/primers/4-feedback-integration.md) in primer 4. **Review-log evidence:** [Doc Reviewer R1 + R2 + R3 carryforwards](vsdd-suite/review-log/2026-05-20-documentation-reviewer.md); [Review 84 Finding 1](../../vsdd-suite/suite-development/review-log/2026-05-21-suite-review.md#review-84--2026-05-21-1100z) (methodology fix); [Review 84 Finding 3](../../vsdd-suite/suite-development/review-log/2026-05-21-suite-review.md#review-84--2026-05-21-1100z) (Doc Reviewer Round 4 closure).

**Three-audience lens:**

- **Suite developers:** the Doc Reviewer carryforward pattern across 3 rounds is the calibration signal that the methodology's Phase 4 routing discipline had a missing piece: closure required defect-class evidence, not just site-fix evidence. Hardening opportunity: the `grep -rn before claiming closure` anti-pattern in primer 4 codifies the discipline; pair it with a hook that scans Resolved findings for "defect class" markers (specific keywords like "stale path reference", "duplicate-name artifact", "retired terminology") + verifies the Resolution paragraph cites a grep-clean evidence command.
- **Suite users:** when you author a fix for a Resolved finding involving any rename / reword / retire / restructure operation across files, run a project-wide `grep -rn` for the defect class BEFORE marking the finding Resolved. The discipline is the same whether the project uses VSDD or not — site-specific fixes for project-wide defect classes always leak.
- **AI agents:** the failure mode is "site-specific fix declared closure" — the most efficient fix shape from the AI's local perspective is also the failure mode the cold-session adversarial review catches reliably. The methodology fix is to make the grep-clean evidence part of the Resolution paragraph, not an optional verification step. The cost of the grep is seconds; the cost of the recurring carryforward across rounds is hours of cycle time.
